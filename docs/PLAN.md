## 1. 목표와 원칙

### 1.1 무엇을 만드는가 (기술 관점)
- 단일 월드(한 서버군, EVE식 통합 경제)를 쓰는 사이보그·미니언 전략 게임.
- 은하 → 항성계 → 행성. 행성은 3D 1차맵(전략 지도, 5단계 확대)과 2차맵(주 활동 공간: 유닛·건물·채집·전투)으로 본다.
- 유닛은 자동으로 행동·전투하고, 유저는 목적지·타겟·스킬로 개입한다.
- 거래창은 HTS(주식 트레이딩)처럼 빠르고 정확해야 한다.
- 개발자용 행성 생성·편집기와 운영·개발 관리자 기능이 핵심 기술이다.

### 1.2 플랫폼
- 모바일 웹 1순위, 데스크톱 웹 2순위. PWA(홈 화면 설치). 게임엔진 대신 웹 기술.
- 지원 브라우저 하한(ADR 28): iOS 16.4+, Chrome·Edge 111+, 삼성 인터넷 22+, Firefox 115+. 더 새 기능은 기능 확인 뒤에만 쓴다.
- 언어: 한국어 기본, 영어 필수 (8장).

### 1.3 우선순위
1. 개발·유지보수 효율 (사람과 AI 에이전트 모두 이해하기 쉬운 구조, 타입 안정성)
2. 운영 안정성·비용
3. 런타임 성능 — 단, 맵과 거래창은 성능 테스트 기준을 둔다 (11장)
4. 대규모 확장성

### 1.4 규모 목표
| 구분 | 목표 |
|---|---|
| 구조가 감당해야 할 목표 | 동시접속 1만 명 + 자율 유닛 10만 개 이상(유저 + NPC 세력 합계, ADR 27). 지역 단위로 상태를 나눠 나중에 서버를 늘린다 |
| 첫 배포 | Synology NAS 1대 (기존 테스트 환경·테스트 DB(5440) 자리를 비우고 사용). 운영 환경(기존 버전)은 당분간 그대로 |

### 1.5 설계 원칙
1. **서버 권위**: 결과에 영향을 주는 판정은 모두 서버가 한다.
2. **규칙·수치는 데이터로**: 게임 규칙과 밸런스는 콘텐츠 팩(7장)에 둔다. 기획이 바뀌어도 코드는 덜 바뀐다.
3. **시스템별 모듈 경계**: 한 시스템을 갈아엎어도 다른 시스템이 영향받지 않게 하고, 도구로 강제한다 (10.4).
4. **기획 무관 플랫폼부터**: 계정, 시간·이벤트 엔진, 원장, 맵 격자·스트리밍, 편집기 기반, 배포를 먼저 만든다.
5. **되돌릴 수 없는 결정은 ADR로 먼저**: 격자·스케일, 상태 저장, 시간 기준, 프로세스 구조, 데이터 버전.
6. **측정 후 결정**: 성능·구조 선택은 실제 휴대폰과 NAS에서 측정한 뒤 확정한다.

## 4. 시스템 구조

### 4.1 저장소 구조
```
apps/
  game/            # 플레이어 앱 + 관리자 화면(지연 로딩) — Vite + React. 다국어 메시지 원본(messages/ko·en)
  server/          # Fastify: API, WebSocket, 정적 파일, 시뮬레이션, 워커 풀
packages/
  protocol/        # 실시간 메시지 타입, 버전, 코덱
  shared/          # 공용 타입, 유틸, 결정적 수학·난수, 경로 보간(기기·서버 공용)
  sim/             # 서버 전용 판정, 테스트 대상: 경로탐색·이동·이벤트 예약·건물 배치·S1 임시 지형(구현), 전투·채집·정산(예정). 이동 보간·정수 수학은 기기도 쓰므로 shared로 옮긴다
  planet/          # 격자·ID·투영, 행성 생성기(서버 굽기 + 편집기 미리보기 공용)
  engine/          # Three.js 렌더러(행성 LOD, 2차맵, 유닛 표현) — React 비의존
  content/         # 콘텐츠 팩 스키마(Zod), 검증기
content/           # 버전 붙은 콘텐츠 팩(JSON)
docs/              # 계획서, ADR, 작업 기록, 보호 목록, design/(기획서 — 다른 세션이 관리)
ops/               # compose, deploy.sh, 실행기(runner) 설정, 백업 스크립트, NAS 설치 안내
scripts/           # 검사 스크립트(모듈 경계·파일 크기·다국어·비밀값·문서 규칙), 작업 기록 목차 생성
```
의존 방향(도구로 강제: `scripts/check-boundaries.mjs`): `apps/* → packages/*`, `engine`은 `server`·`sim`을 import 금지, `sim`은 `engine`·DOM 금지, **`apps/game`은 `sim` import 금지**(판정 코드를 기기로 보내지 않음), `protocol`·`shared`는 아무것도 import하지 않는 최하층. 예외 하나: `apps/game`은 tRPC 라우터 타입 때문에 `apps/server`를 **타입으로만**(`import type`) 가져온다(ADR 23).

관리자 화면 코드도 정적 파일이라 누구나 내려받을 수 있다. 비밀값·시드·숨김 데이터는 코드에 넣지 않고 서버가 권한 확인 후에만 보낸다.

### 4.2 런타임 토폴로지
- **v1 = 서버 프로세스 1개 + DB 1개** (게임 스택 컨테이너 2개 + 운영용 self-hosted runner 1개).
  - 메인 스레드: HTTP(API, 정적 파일), WebSocket 게이트웨이, 월드 상태, 이벤트 스케줄러, 시장별 매칭 엔진.
  - 워커 스레드 풀(Piscina): 경로탐색, NPC 판단, 2차맵 생성·집계, 전투 빨리감기 판정 — 입력을 받아 결과를 돌려주는 상태 없는 계산만. 단, 경로탐색은 S1부터 `node:worker_threads` 자체 풀이다: 워커마다 배치 격자 사본(캐시)을 들고 편집을 같은 순서로 따라 한다(원본은 메인 스레드, ADR 33 "구현하며 정한 것 (서버 연결)"). 1차맵 행성 굽기(생성 → 타일 → gzip)도 풀 없이 `node:worker_threads` 워커를 굽기마다 하나 띄우고 끝낸다(ADR 36 "구현하며 정한 것 (타일·서버)").
  - 전투 워커 스레드: 진행 중인 교전의 상태를 들고 틱을 돌리는 전용 스레드(교전 여러 건을 묶어 실행). 개입 명령은 메인 스레드를 거쳐 전달.
- **기능 플래그**: 시스템 단위 켜기·끄기를 런타임 설정으로(기획이 자주 바뀌므로).
- **버스 인터페이스**: 모듈 간 통신은 in-process 버스로 하되, 전달 규칙(순서·중복·재시도)을 문서화하고 DB 아웃박스(이벤트를 DB에 먼저 기록 후 발행)를 쓴다.
- **분리 대비**: 모든 월드 상태는 `regionId` 키로 나눠 보관한다. 지역별 프로세스 분리가 필요해지면 버스 구현만 NATS 등으로 교체한다(그때 ADR).
- WebSocket 게이트웨이는 연결 상태를 가진다("무상태 api"가 아님). 확장 시 지역별 게이트웨이 라우팅이 필요하다.

### 4.3 연산 분담
| 기기 | 서버 |
|---|---|
| 렌더링, 이동 보간, 연출·이펙트, 경로 제안(서버는 검증만), 내 명령의 즉시 반영(예측 — 거절 시 되돌림), 판정과 무관한 장식용 생명체·군중·날씨 | 자원 획득량, 전투 승패·피해, 거래·잔고, 아이템 생성, 조우, 소유권 — 결과에 영향을 주는 모든 판정 |

- 접속 중에는 유닛이 풍부하게 행동하고, 로그아웃 후에는 **24시간까지만**(기획 D-061) 단순 행동(작업 단위)을 이어가고, 그 뒤 대기한다. 하루 1회 접속을 유도한다(웹 푸시, 9.5). 24시간을 언제부터 세는지와 단순 행동 목록은 기획 질문(14장)이다.
- 게임 상태를 바꾸는 명령은 **WebSocket 한 채널로만** 보낸다(순서 보장). tRPC는 조회와 비실시간 기능에 쓴다.

### 4.4 시뮬레이션 모델
- **이벤트 예약**: 유닛은 "경로 + 출발 시각 + 속도"를 저장하고, 위치는 필요할 때 계산한다. 도착·채집 완료·AI 판단 같은 일은 그 시각에만 처리한다.
- **시뮬레이션 상세도 4단계**: ① 접속 유저 주변(세밀) ② 누군가 관측 중(보통) ③ 무관측(예약 이벤트만) ④ 오프라인 작업(정산만).
- **해결 함수는 메커니즘당 1개**: 상세도와 무관하게 같은 함수(또는 같은 기대값을 내는 축약 공식)를 쓴다. 단계 간 기대값 일치는 통계 테스트로 검사한다(로그아웃으로 유리한 결과를 얻는 악용 방지).
- **정산 시점**: 소유자 로그인뿐 아니라 다른 유저가 관측·상호작용할 때, 그리고 주기적 정산 시각.
- **조우**: 경로가 각 칸에 들어가는 시각을 미리 계산하고, 조우 판정은 `(유닛, 칸, 틱)` 키로 결정한다. 경로가 바뀌면 다시 계산한다.
- **경로탐색**: 장거리는 1차맵 격자에서 거칠게(A*), 2차맵 안에서는 배치 격자 기준으로 정밀하게(계층 경로탐색). 경로 제안은 기기, 검증은 서버.
- **전투**: 교전마다 별도 전투맵 인스턴스를 만든다(기획 D-172, ADR 35 제안). 지형은 조우 지점 둘레 2차맵 배치 격자를 복사한다(일반 64×64칸, 공성 128×128칸 — 출발값). 전투 워커 스레드에서 약 200ms 틱으로 계산하고, 바뀐 것만 **참가자와 같은 세력 구성원에게** 받는 사람마다(편마다 시야, D-208·D-236·D-6036) 걸러 보낸다. 기기는 보간·연출만 한다. 명령은 유닛마다 대기 명령 1칸이고 실행 틱은 서버가 정한다(D-177·D-180). 보는 사람(전투 화면에 들어간 참가자, 같은 세력 구성원)이 없는 전투는 같은 판정을 빨리감기로 끝낸다(D-6023).
- **결정적 판정 규칙** (재현·테스트용): 정수·고정소수점, 시드 기반 자체 난수(PCG32 등), 판정 코드에서 `Math.sin/cos/exp/pow` 등 초월함수 금지(엔진마다 결과가 다를 수 있음 [V: 명세]) — 필요하면 자체 구현·표 사용, 반복 순서 고정. 전투 기록은 `(시드, 입력 목록, simVersion, contentVersion)`으로 저장해 재생·디버깅한다.

### 4.5 상태 저장·복구
- **DB가 원본**: 경로·출발 시각, 예약 이벤트, 전투 시드·입력, 주문, 잔고는 DB가 원본이고 메모리는 캐시다.
- 경제 변동은 즉시 커밋한다. 유도 가능한 값(현재 위치 등)은 저장하지 않거나 묶어서 늦게 저장한다.
- 주기적 스냅샷 + 명령 로그. 종료 신호(SIGTERM) 시 새 명령을 막고 진행 중 작업을 정리한 뒤 종료한다.
- 부팅 시: DB에서 상태를 읽고 예약 이벤트를 다시 걸며, 시장은 미체결 주문으로 호가창을 복원한다.
- CI 통합 테스트: 부하 중 `kill -9` → 재시작 → 불변 조건(원장 합계, 중복 아이템 없음, 예약 누락 없음) 검사.

### 4.6 시간 기준과 세션 프로토콜
- **시간 기준은 서버**(UTC 밀리초). 기기는 접속·복귀 때마다 시계 차이를 측정(여러 번 왕복 후 중앙값)해 보간에 쓴다.
- **접속 핸드셰이크**: `protocolVersion`, `simVersion`, `contentVersion`, `clientBuild` 교환. 서버는 현재와 직전 프로토콜 버전을 지원하고, 최소 버전 미만이면 새로고침을 강제한다(PWA가 옛 코드를 들고 있는 문제 대응).
- **명령**: `id` + 응답 확인(ack) + 중복 방지 키.
- **스트림**: 모든 실시간 스트림에 순번. 끊기면 버퍼에서 이어 받고, 안 되면 스냅샷.
- **안전 장치**: 하트비트 약 25초, 메시지 크기 상한 약 64KB(ws 기본값 100MiB는 과다), 계정별 속도 제한, 느린 기기의 전송 버퍼 상한과 오래된 갱신 병합.
- **시야 기준 전송**: 관심 영역은 화면 범위가 아니라 **시야 판정**(전장의 안개)으로 거른다. 남의 경로는 보이는 구간만 보낸다(전체 경로 = 목적지 노출).

### 4.7 경제·거래소
- 금액은 최소 단위 정수: DB `int8`, JS `BigInt`, 전송 시 문자열. 실수 계산 금지.
- 복식부기 원장: 모든 잔고 변동은 원장 항목(차변·대변)으로만.
- 주문 접수 시 자금·물품을 묶어둔다(에스크로).
- 시장별 단일 작성자(매칭 엔진)가 체결 묶음을 한 트랜잭션으로 커밋한 뒤 아웃박스로 발행한다.
- 시세 전송: 순번 + 변경분, 누락 시 스냅샷 재요청.
- 주문 응답 목표(서버 내부 p95 ≤ 50ms)는 M0에서 NAS 디스크 동기화 지연을 측정한 뒤 확정한다. 측정 결과(2026-10-28): fdatasync 약 77ms/회(HDD) [V: `ops/nas-facts.md`] → 건별 동기 커밋으로는 불가. 묶음 커밋·`synchronous_commit`·SSD 중 선택은 거래소 설계 ADR에서 정한다.

### 4.8 인증·권한·감사
- Better Auth 세션(쿠키). 역할: `player`, `gm`, `dev`, `admin`(조합 가능).
- 관리자 화면은 같은 앱 안의 메뉴로 통합(권한자에게만 표시), 관리자 코드는 지연 로딩.
- **서버가 모든 관리자 요청의 권한을 검증**하고, 테스트는 "기본 거부"를 확인한다.
- 모든 관리자 행동은 삭제할 수 없는 감사 기록(누가·언제·무엇을·이전 값)으로 남긴다.
- 구현(2026-10-28, ADR 29): 로그인 아이디(영문·숫자·_ 3~20자, 남에게 안 보임)로 들어가기, 없는 아이디는 확인 화면 뒤 만들기, 복구 이메일 일치로 비밀번호 찾기, Better Auth HTTP는 세션 조회·로그아웃만, 관리자 기능은 tRPC(기본 거부), 감사 기록은 DB 트리거로 추가만, 관리 명령은 GitHub Actions `account-admin`. 화면(작업 기록 28-2150): 로그인·새 아이디 확인·비밀번호 찾기·계정 줄(앱 뼈대에서 사이드 메뉴의 아이디·설정·로그아웃으로 바꾼다, ADR 37), 관리자 화면(지연 로딩, 사용자 찾기·역할 바꾸기).
- 콘텐츠 보안 정책(CSP)과 출력 이스케이프로 XSS를 막는다(관리자 화면이 같은 주소에 있으므로 특히 중요).

## 5. 맵·행성

### 5.1 계층
- 은하 → 항성계 → 행성. 첫 구현은 우리은하 + 태양계(데이터로 정의).
- 항성계 화면은 행성과 분리된 가벼운 화면. 오브젝트는 데이터로 정의하는 타입 시스템(항성, 행성 프리셋, 위성, 소행성대, 정거장, 영토 구조물, 스타게이트, 이상 현상, 웜홀 등 — EVE 참고, 규칙은 기획 세션). 기후 연결 없음.

### 5.2 격자·스케일·ID 계약
| 항목 | 결정 |
|---|---|
| 격자 | 정육면체를 구에 투영한 사각 격자(cube-sphere). 자체 구현(S2 방식 계층), **탄젠트 투영**(같은 단계 칸 면적 차이 최대 약 1.4배 [V: S2 라이브러리 문서, 구현에서 잰 값 레벨 9 1.41배]; 기본 이차 투영은 약 2.1배) |
| 행성 크기 | "면 레벨"로 정한다. 지구 기본값 = 레벨 9(면당 512×512칸), 축척 약 1:12, 반지름 약 531km [A: 계산]. 생성기 1판·콘텐츠 팩 행성은 면 레벨 4~9만 받는다: 레벨 10은 생성 하나에 약 55초·최대 RSS 약 770MiB [V: 개발 컨테이너, ADR 36]라 NAS 앱 컨테이너(1GiB) 안에서 굽게 9로 둔다. 격자 계약 4~14는 그대로 |
| 1차맵 | 5단계 확대(면당 32 → 64 → 128 → 256 → 512칸). 최소 칸 평균 약 1.5km |
| 2차맵 지형 | 1차맵 최소 칸 1개 = **128×128** 지형 칸(평균 약 11.7m, 위치에 따라 약 ±10% [V: 구현에서 잰 값 평균의 0.91~1.09배]) |
| 2차맵 배치 | 건물 배치·충돌·경로탐색용 **256×256 세부 격자**(평균 약 5.9m). 점유된 칸만 저장 |
| 유닛 위치 | 격자에 묶이지 않는 연속 좌표(2차맵 로컬 좌표) |
| 게임 규칙 단위 | 이동 속도·사거리·건물 크기는 **칸 수**로 정의. 미터는 표시용 |
| 고도 축척 | 수평과 같은 1:12(저장 값은 게임 m, 에베레스트 약 737m). 기후 식은 실제 고도로 바꿔 계산, 1차맵 화면만 과장해 그린다. 기획 확정(D-215, ADR 36) |
| 꼭짓점 8곳 | 2차맵이 3장만 만나는 특이점. 행성을 회전시켜 꼭짓점을 바다에 두고, 생성기는 꼭짓점 주변을 바다·통행 불가로 처리. 지구는 꼭짓점이 모두 바다에 오는 회전을 찾고(가능 여부 [A]), 안 되면 그 지점만 개별 진입 |
| 면 경계 | 인접 면으로 넘어갈 때의 좌표 변환표를 두고 전수 테스트 |
| ID | 행성 ID + 셀 키(면 3비트 + 레벨 5비트 + 힐베르트 순서) — JS 안전 정수(53비트) 안에 들어감. 같은 지역은 가까운 번호 → DB 범위 조회·지역 분할에 유리. 비트 배치(ADR 34): `[면 3][힐베르트 위치 44][레벨 5]` 52비트, 최대 레벨 22(면 레벨 4~14). 한 칸의 모든 하위 칸이 키 구간 하나에 들어간다. 행성 ID는 키 밖(쌍). 구현은 `packages/planet`(정수 `.` + 투영 `./projection`) |

### 5.3 생성 파이프라인
순서는 ADR 31(`2026-10-28-planet-generation-order.md`)이 정한다. 강의 물 양은 비에 달려 있어서, 물 흐름 양·침식·강은 기후 뒤에 둔다.
1. 판 구조(구면 보로노이로 지각판 → 충돌·분리로 산맥·해구) + 지형 틀(대륙 안쪽 고원·분지·구릉, 해안선 흔들기, 경계를 따라 바뀌는 산맥, 열점 사슬) → 기본 고도
2. 해수면(행성 설정값, 기획 D-141)으로 땅과 바다를 나눈다
3. 웅덩이 채우기·흐름 방향(Priority-Flood, 고도만 씀)
4. 기후(흔든 기후 위도, 고도에 따른 기온 감소, 바람(위도 띠 + 굽이)·비그늘, 바다까지 거리, 기온·강수의 여러 크기 변이, 행성 설정값) → 기온·강수. 바이옴 판정은 저장 값만 보므로, 자연스러운 경계·군집은 기후 필드와 지형의 여러 크기 변이로 만든다(ADR `2026-10-29-generator-variety.md`)
5. 물 흐름 누적(강수로 가중) → 침식(큰 강이 드는 마른 분지는 뚫는다) → 강·호수 경로 데이터(빙상 기후 웅덩이는 얼음 평지)
6. 수심 등급(심해·대륙붕·연안)
7. 습도(강수 + 강·호수 주변)
8. 바이옴(기온 × 습도) → 기본 밀도(숲 밀도, 광물 풍부도 등) = 고정 환경 값의 함수
9. 지구: ETOPO 2022 고도를 1차맵 해상도로 미리 변환해 1단계 대신 쓰고 2~8단계를 같은 방식으로 적용한다. 실측 고도에 침식을 적용할지는 S2에서 정한다. 2차맵 디테일은 절차 생성. 지구도 프리셋으로 불러와 다른 행성처럼 고칠 수 있다(기획 D-155). 고친 뒤에는 국가 프리셋 위치를 다시 맞추고 꼭짓점 검사(5.2)를 다시 돌린다.

모든 노이즈는 3D 구면 좌표에서 계산해 이음매와 극지 찌그러짐을 없앤다. 생성 코드는 `packages/planet` 하나를 서버와 편집기가 공유한다.

### 5.4 위에서 생성, 아래에서 변화
- **생성(위 → 아래)**: 1차맵 칸의 기본 값(숲 밀도 등)에 맞춰 2차맵을 생성한다. 처음부터 두 맵이 일치한다.
- **변화(아래 → 위)**: 2차맵 활동(벌목·건설·채굴)이 그 칸의 집계 값을 바꾸고, 데이터로 정의한 변환 규칙이 1차맵 표시를 바꾼다(예: 숲 → 개간지, 건물 수 → 마을·도시). 상위 단계는 하위 4칸을 다시 집계한다.
- 기온·습도 같은 기본 환경 값은 바꾸지 않는다(표시·분류만 변경).

### 5.5 세계 데이터 버전
- 모든 생성 결과에 `generatorVersion`, `contentVersion`을 기록한다.
- CI에서 고정 시드의 결과 해시를 비교한다(생성기 코드가 바뀌면 즉시 감지 — 과거 생성기 불일치 재발 방지).
- **플레이어가 처음 손댄 2차맵은 저장본으로 고정**한다. 이후 생성기가 바뀌어도 그 맵은 변하지 않는다.
- 편집기의 "공개"는 새 행성 버전을 만든다(기존 버전은 불변).
- 데이터는 "불변 기본본(버전 붙은 주소) + 작은 변경 오버레이"로 나눠 저장·전송한다.

### 5.6 전송·캐시
- 1차맵: 단계별 타일을 서버가 미리 구워 버전 붙은 불변 주소로 제공. 첫 진입 로딩 화면에서 넓은 단계를 한 번에 받는다.
- 2차맵: 처음 요청될 때 워커가 생성해 압축 저장, 이후 캐시. 1차맵 최대 확대 시 주변 2차맵을 미리 받는다.
- 기기 저장: 서비스워커 Cache Storage + HTTP 캐시. 지워져도 다시 받으면 되는 데이터만 저장한다(iOS는 오래 안 쓰면 지울 수 있음 [V: WebKit 정책]).
- **숨김 정보**(자원 위치·크리쳐)는 기기로 보내는 지형 데이터에 넣지 않는다. 시야·탐사 규칙에 따라 서버가 따로 보낸다.
- **안개**(기획 D-103·D-107, ADR 26): 1차맵 지형 타일은 모두에게 같은 공개 파일이고, 안개(검정·지형만)는 기기가 그린다. 2차맵 상세(지형 포함)와 건물·유닛·자원은 서버가 그 플레이어의 탐사·시야를 확인한 뒤에만 보낸다. 탐사 기록은 서버가 원본이다.

### 5.7 렌더링
- **행성 LOD**: 면별 쿼드트리, 화면 오차 기준으로 세분화, 부모 타일을 먼저 보여주고 교체, 화면당 타일 수 상한, 틈 메우기(skirt), 카메라 기준 좌표(반지름 531km에서 32비트 실수는 6.25cm 단위라 떨림 발생 [V: 계산]).
- **지표 레이어**(영역·물류·군사·도시·자원): 셰이더 데이터 텍스처 + 인스턴싱 선·아이콘.
- **2차맵**: 지형 메싱은 Web Worker에서, 같은 오브젝트는 인스턴싱. 가까이서는 셰이더 디테일로 지형을 촘촘하게 보이게 한다(데이터 격자와 화면 해상도 분리).
- **2차맵 시점**: 쿼터뷰(기울기 약 35~55°, 자유 회전, 사용자 결정 2026-10-28, ADR 33).
- **유닛 표현 단계**(유닛 크기 0.5~3m, 보스·전설·신수 최대 약 12m — 기획 D-095. 과장 없음 — 기획 D-068, ADR 25):
  | 확대 | 표현 |
  |---|---|
  | 근접(화면 가로 약 40m) | 실제 크기 3D 모델 — 키 1.8m ≈ 18 CSS px (393px 폭 기준 [A: 계산]) |
  | 중간 | 실제 크기 + 외곽선·선택 링 |
  | 원거리 | 아이콘·부대 묶음 표시. 실제 크기로 알아보기 어려운 거리부터 바꾼다(전환 거리는 S1에서 잰다) |
- 유닛 애니메이션은 텍스처로 구워 인스턴싱으로 재생, 원거리 식생·유닛은 판자 이미지(임포스터).
- **WebGL2 기본**. WebGPU(Three.js WebGPURenderer + TSL)는 S2 1주차에 측정해 셰이더 언어를 확정한다.
- **모바일 예산**: 기기 등급별 텍스처·지오메트리 메모리, 드로우콜, 인스턴스 수 상한. 압축 텍스처(KTX2), 픽셀 비율 상한 1.5~2, 렌더러 1개 재사용, 화면 변화 없으면 렌더 중지, WebGL 컨텍스트 손실 복구 경로(iOS 앱 전환 시 발생 [V: three.js·Apple 포럼]). iOS는 메모리 초과 시 경고 없이 탭을 종료한다 [V: WebKit 버그 300782, 독립 검토 확인].
- 고빈도 상태(유닛 위치 등)는 엔진 내부 타입 배열에 두고 React에는 요약만 전달한다.

## 6. 편집기·관리자

### 6.1 환경 필드와 배치 엔진
- 모든 칸이 환경 값(고도, 수심, 경사, 기온, 습도, 바이옴, 강·해안까지 거리 등)을 가진다.
- 배치 규칙은 데이터다. 예: `철광석: 경사 ≥ 15°, 고도 300~2000m, 산악 바이옴, 군집형`. 크리쳐 서식 규칙도 같은 형식.
- 같은 배치 엔진을 생성기와 운영 도구가 함께 쓴다.

### 6.2 행성 편집기 단계
| 단계 | 기능 |
|---|---|
| 1단계 (S2) | 세계 설정 프리셋(해수면 군도·보통·대륙, 기온, 강수, 산악도, 판 개수, 화산 등, 기획 D-154)으로 시작, 파라미터 슬라이더(해수면, 대륙, 극지·적도 비중, 기온(절대 °C)·습도, 수심, 강 밀도, 호수), 지구본 실시간 미리보기(저해상도, 기기 워커), 2차맵 미리보기, 시드·버전 저장. 공개한 행성의 설정값은 잠근다(D-156) |
| 2단계 (이후) | 영역 선택(브러시·올가미·조건), 지형 조각(올리기·내리기·평탄화·부드럽게·강/호수 추가), 기후 보정, 자원·크리쳐 편집(6.3), 서버 최종 굽기 + 미리보기와의 차이 경고 |
| 3단계 (이후) | 항성계 편집기(오브젝트 배치, 행성 프리셋을 궤도 슬롯에) |

### 6.3 자원·크리쳐 편집 UX
- 자원: 배치 가능 영역 히트맵 → 자동 분포 미리보기 [다시 돌리기 / 시드 고정 / 확정] → 수동 배치·배치 금지 구역.
- 크리쳐(이동 중 조우): 서식 적합도로 칸별 조우 테이블(확률, 무리 구성, 레벨 범위) 자동 생성, 2차맵·지역 단위 덮어쓰기, 희귀 크리쳐 수동 배치(출현 지점·조건).
- 선택 영역 통계: 드래그·올가미로 고른 영역의 평균 환경 값, 자원 분포, 조우 구성 표시.
- 행성 전체 비율(%) 표와 이상치 경고(예: 배치 가능 칸 0개, 확률 합 100% 초과, 특정 크리쳐가 전체의 50% 이상).
- 공통 편의: 되돌리기·다시하기, 명령 팔레트, 인스펙터(값 + 그 값을 만든 규칙), 비교(시드 A/B, 공개본 vs 초안), 보기 북마크, 변경 이력, CSV·JSON 내보내기·가져오기.

### 6.4 대량 작업 (스크립트 콘솔 대체)
- 임의 코드 실행 기능은 두지 않는다.
- 정해진 종류의 대량 작업(예: "선택 영역의 자원 X 밀도 −20%")을 미리보기 → 차이 확인 → 실행 → 감사 기록 → 되돌리기 순서로 실행한다.
- CSV·JSON 가져오기는 **초안에만** 적용하고 엄격한 스키마로 검증한다.

### 6.5 편집 반영 규칙
- 편집은 항상 초안에서 한다. 공개 시 플레이어 건물·소유지가 없는 지역은 자동 반영, 걸리면 영향 목록을 보여주고 운영자가 승인한다.

## 7. 콘텐츠 팩과 검증 파이프라인
- 원본: 관리자 편집기(스테이징)에서 작업 → **버전 붙은 콘텐츠 팩(JSON)**으로 내보내 git에 커밋 → 운영 서버는 팩을 가져온다. 롤백 = 이전 팩.
- 커밋 주체: v1은 스테이징에서 내보낸 파일을 개발자·에이전트가 커밋한다. 이후 버튼 한 번으로 자동 커밋하는 기능을 붙인다.
- 행성 데이터: 정의(시드·파라미터·편집 작업 목록)는 콘텐츠 팩(git)에, 구운 타일과 큰 편집 래스터는 NAS 저장소에 둔다(해시로 참조, 정의 + 생성기 버전으로 다시 만들 수 있음).
- 언어: 콘텐츠의 이름·설명에 `en`이 없으면 1단계 검사에서 실패한다.
- 검증 단계 (CI `content-check`):
  | # | 검사 | 시작 시점 |
  |---|---|---|
  | 1 | 스키마 검증(타입, 필수 값, 범위) | M0 |
  | 2 | 참조 무결성(없는 ID 참조, 중복 ID, 고아 데이터) | M0 |
  | 3 | 규칙 검사(배치 가능 칸 0개, 확률 합, 순환 제작으로 무한 이익 등) | 규칙 정의 시 |
  | 4 | **이전 버전과의 호환성 검사**: 삭제·이름 변경된 ID를 운영 데이터(인벤토리·건물 등)가 쓰고 있으면, 이전 매핑(이름 변경표·보상 규칙)이 없을 때 실패 | M0(기본) → 운영 데이터 생긴 뒤 강화 |
  | 5 | 헤드리스 시뮬레이션 회귀: 테스트 행성에서 봇으로 N일 진행 → 불변 조건(원장 합계, 음수 재고, NaN), 인플레이션 등 지표를 이전 팩과 비교한 보고서 | 경제 규칙 정의 시 |
  | 6 | 기록된 전투·시나리오 재생 비교 | 전투 규칙 정의 시 |
  | 7 | 스테이징 배포 + 자동 점검 → 운영 반영 | M0 |
- 구현(2026-10-28, ADR 24): 1·2·4·7단계.
  - 팩은 `content/<팩 ID>/`에 `manifest.json`·`id-changes.json`·`<분류>.json`. ID는 영어 snake_case, 한 번 쓴 ID는 다시 쓰지 않는다. 지우거나 바꾼 ID는 `id-changes.json`에 뒤에 추가만 한다. 이름·설명은 ko·en **둘 다** 필수(사용자 확인 2026-10-28: 유지).
  - 검증기는 `packages/content`, 검사는 `pnpm check:content`(`scripts/check-content.mjs`). `pnpm check`가 1·2·4a단계(팩 하나만), 푸시 전·CI가 4b단계(기준 커밋의 팩과 비교)까지 본다.
  - 팩은 서버 이미지에 넣는다(`CONTENT_DIR`) → 코드와 팩이 함께 배포·되돌림된다(롤백 = 이전 이미지 = 이전 팩). 서버는 시작할 때 1·2·4a단계를 검사하고, 틀리면 뜨지 않는다.
  - 7단계: `/health`의 `contentVersion`(`core@1` 형식)·`contentHash`와 WebSocket 접속 인사를 `ops/smoke.mjs`로 점검한다(CI 이미지 작업, NAS 배포). 배포는 healthy + 점검 통과여야 끝나고, 아니면 직전 버전으로 되돌린다.
  - 스테이징: 따로 두지 않는다. 지금 NAS 새 스택(실유저 없음)이 스테이징이고 "운영 반영" 대상은 아직 없다. 실유저 전에 운영 스택 + promote 워크플로를 더할지, 기존 운영을 먼저 내릴지 사용자가 정한다.
  - M0 팩 `content/core`는 형식 확인용 임시 데이터(`placeholder: true`)다. 운영 데이터 사용 여부(`LiveUsage`) 검사는 운영 데이터가 생기면 배포 단계에 더한다.

## 8. 다국어
- UI 문자열은 전부 메시지 키(Paraglide). 한국어 기본, **영어 누락 시 빌드·CI 실패**.

## 9. 운영

### 9.1 NAS 배포
- 이미지: GitHub Actions에서 amd64 이미지 빌드(기존과 같은 방식) → GHCR에 커밋 해시·버전 태그로 푸시. 기본 이미지는 Debian slim(glibc), Alpine 미사용.
- 배포: NAS의 GitHub self-hosted runner가 `ops/deploy.sh <태그>` 실행 → 이미지 받기 → DB 백업 → 마이그레이션 1회 → 기동 → 헬스체크 → 실패 시 자동 롤백. 외부 포트를 열 필요 없음.
- 새 스택 이름: 컨테이너 `tic-app`·`tic-db`·`tic-runner`, 네트워크 `tic-net`(기존 `terra-*`와 겹치지 않게). 앱은 NAS 안 `127.0.0.1:4100`에만 열고 외부 접속은 역방향 프록시가 맡는다. 설치 순서는 `ops/nas-setup.md`.
- watchtower(개발 중단 [V])는 쓰지 않는다. 기존 watchtower가 새 스택을 건드리지 않도록 새 컨테이너에 제외 라벨을 붙인다. 기존 운영 환경은 건드리지 않는다.
- ⚠️ 기존 watchtower는 필터 없이 NAS의 **모든 컨테이너**를 60초마다 확인·갱신한다(`--interval 60 --cleanup`) [V: 기존 compose]. 2026-10-28 13:15경 DB 컨테이너 4개가 한꺼번에 다시 만들어진 것도 이 동작으로 보인다 [A: 사용자 제공 화면의 생성 시각]. `postgres:latest`를 쓰는 DB(다른 프로젝트 DB 포함)는 PostgreSQL 19가 `latest`가 되면 새 메이저로 바뀌어 기동에 실패할 수 있다 [A] → 사용자 결정(2026-10-28): 기존 watchtower는 그대로 둔다. 새 스택만 제외 라벨과 이미지 버전 고정으로 보호한다. 다른 프로젝트 DB의 위험은 사용자에게 알렸다.
- GHCR 비공개 이미지는 "현재 무료"(1개월 전 고지 후 변경 가능 [V]) → 이미지에 에셋을 넣지 않아 크기를 줄이고 오래된 태그는 정리한다.

### 9.2 NAS 사양 자동 수집 (M0 첫 작업)
- 확인된 사실(2026-10-28 사용자 제공 화면) [V]: Synology Container Manager 사용. 같은 NAS에 다른 프로젝트 컨테이너(DB 2개, 문서 뷰어, 랜딩 페이지)도 있다 → 새 스택은 고유한 컨테이너 이름·네트워크·포트를 쓰고 다른 컨테이너를 건드리지 않는다.
self-hosted runner로 `uname -r`, CPU, 코어 수, 메모리, 디스크 종류·여유, Docker·Compose 버전, `pg_test_fsync`(디스크 동기화 지연)를 수집해 `ops/nas-facts.md`에 기록한다(`nas-facts` 워크플로 수동 실행 → Actions 요약 화면 → 파일로 옮김). 커널이 Node 공식 지원 최소 버전(glibc 기준 4.18)보다 낮으면 대응을 ADR로 정한다 → 측정 결과 4.4.302+ [V], ADR 18로 그대로 운영하기로 함(첫 배포에서 Node 24·PostgreSQL 18 동작 확인 [V]).

### 9.3 네트워크
- 외부에는 HTTPS 하나만 연다(DSM 역방향 프록시, Let's Encrypt). 새 스택은 기존 운영 주소와 겹치지 않게 별도 포트 또는 별도 호스트 이름으로 연결한다 → 2026-10-28 설정: `https://riversun7.synology.me:4443` → `localhost:4100`(기존 인증서 사용).
- 프록시에서 WebSocket 헤더 옵션 사용, 서버는 하트비트로 연결 유지, Fastify `trustProxy` 설정.
- **DB 포트는 외부에 공개하지 않는다**(내부 네트워크만). 기존 테스트 서버는 공개 주소에서 평문 HTTP 3001·3002로 응답 중이었다 [V: 2026-10-26 보고서].

### 9.4 DB
- 기존 테스트 DB 컨테이너 `terra_testDB`: PostgreSQL 18.6(`postgres:latest` 이미지), 포트 5440, 데이터는 `/volume1/docker/terra-testDB/data`(바인드 마운트, PGDATA 직접 지정) [V: 사용자 제공 화면]. 버전이 이미 18이라 교체는 필요 없다.
- 사용자 허가에 따라 이 자리를 비우고 새 스택 전용으로 쓴다. 새 DB는 `tic-db`(`postgres:18.6-trixie` 고정), **호스트 포트 없음**(내부 네트워크만, 관리는 `docker exec`), 데이터는 `/volume1/docker/terra-in-cognita/pgdata`. 기존 `terra_testDB`와 `terra-test-server`는 사용자 결정(2026-10-28)으로 삭제한다(기존 버전은 운영 서버만 남김, 순서는 `ops/nas-setup.md` 7단계).
- 스키마 변경: Drizzle 마이그레이션(`apps/server/drizzle/`)을 배포 5단계에서 새 이미지로 한 번 적용한다(배포 전 백업 다음, 앱 교체 전). 되돌림은 DB를 되돌리지 않으므로 마이그레이션은 직전 버전 앱과 호환되게 만든다(ADR 22).
- 기존 테스트 서버(`terra-test-server`)는 이 DB를 쓰므로 함께 삭제한다.

### 9.5 백업·관측·알림
- 백업: 매일 `pg_dump` → NAS 백업 폴더 → NAS 밖 보관(예: Hyper Backup). 주 1회 임시 컨테이너에 자동 복구 + 원장 합계 검사. 마이그레이션 전 자동 백업. 실유저 단계 전에 WAL 아카이브(시점 복구)를 추가한다. 구현(2026-10-28): `nas-backup` 워크플로(매일 03:17 백업, 매주 월 03:43 복구 훈련, `ops/backup.sh`·`ops/restore-check.sh`), 되돌림 훈련은 `rollback-drill` 워크플로. 원장 합계 검사는 원장이 생기면 복구 훈련에 더한다. NAS 밖 보관은 Hyper Backup(사용자 설정).
- 관측: 구조화 로그(Fastify 기본 pino, 용량 회전), 서버 지표(틱 시간, 이벤트 루프 지연, GC, 접속 수, 큐 길이)를 관리자 대시보드로, 기기 성능 오버레이(fps, 프레임 시간, 메모리)와 텔레메트리, 기기 오류 수집(서버 로그 테이블), 외부 가동 확인(선택). 구현(2026-10-28): 기기 오류(`client_errors`)·성능 요약(`client_perf_samples`, 1분마다·화면 숨길 때)을 `POST /api/telemetry/*`로 받는다(화면을 닫을 때도 보내려고 sendBeacon을 쓰므로 tRPC가 아닌 일반 HTTP, 주소별·전체 속도 제한). 성능 오버레이는 fps·프레임 시간 p95·메모리. 서버 지표(이벤트 루프 지연 p50·p99·최대, 메모리, 접속 수)는 1분마다 로그 한 줄. 관리자 대시보드와 오래된 기록 정리는 아직 없다.
- 웹 푸시(하루 1회 접속 유도): iOS는 홈 화면에 설치한 웹앱에서만, 사용자가 버튼을 눌렀을 때만 권한 요청 가능 [V].

### 9.6 비밀값
- 비밀값은 NAS에만 둔다(첫 배포 때 무작위 생성해 NAS의 `.env`에 저장). git에는 절대 넣지 않는다(gitleaks로 커밋·CI 검사).
- 기존 프로젝트의 DB 비밀번호·JWT 기본값은 git 이력에 남아 있다. 교체는 사용자 결정대로 정식 서비스 직전에 한다.
- M0 네트워크 설정 때 기존 DB 포트(5439·5440)가 공유기에서 외부로 포워딩되어 있는지 확인한다. 열려 있으면 닫을지 사용자와 정한다(닫으면 교체 전 위험이 크게 줄지만, 기존 개발 스크립트처럼 외부에서 DB에 직접 접속하는 방식은 막힌다). 이 세션에서는 외부 노출 여부를 직접 확인하지 못했다 [U]. 다만 2026-10-28 공유기 포워딩 없이 새 포트 4443이 외부에서 열렸다 → NAS 포트가 직접 노출된 구조로 보이고, DB 포트도 열려 있을 가능성이 높다 [A].

### 9.7 리소스
- 컨테이너마다 메모리 상한 + CPU 상대 우선순위(`cpu_shares`). CPU 상한(`cpus`)은 NAS 커널(4.4)이 지원하지 않는다 [V: 첫 배포 오류] → ADR 18. 부하 테스트 봇은 NAS 밖(CI 러너·개발 PC)에서 실행. 무거운 테스트는 기존 운영 영향이 적은 시간대에.

### 9.8 에셋
- 이미지·모델 원본은 git에 넣지 않는다(기존 `.git` 487MiB의 원인). NAS 에셋 저장소에 해시 파일명으로 두고, git에는 목록(매니페스트)만 둔다.
  - 예외: 앱 아이콘·파비콘(`apps/game/public/`, 파일마다 수십 KB 이하). 앱 주소에서 바로 내려줘야 한다(ADR 28).
- 변환 파이프라인: 텍스처는 KTX2, 모델은 glTF + meshopt(glTF Transform). 앱 이미지에는 에셋을 넣지 않는다.

## 10. 개발 방식

### 10.1 작업 흐름 (브랜치 보호 없음 — 무료 플랜)
- **트렁크 기반**: 기본은 `main`에서 바로 작업한다.
- 여러 에이전트가 동시에 큰 작업을 할 때만 짧은 브랜치·worktree를 쓰고 빨리 합친다. 같은 브랜치 동시 작업 금지.
- 푸시 전 `git pull --rebase`. **main이 CI 실패 상태면 다른 작업보다 먼저 고친다.**
- 클라우드 세션이 작업 브랜치를 배정받는 경우 그 브랜치에서 작업하고, 검사 통과 후 main에 합친다.

### 10.2 훅과 CI
| 시점 | 검사 |
|---|---|
| commit-msg | Conventional Commits 형식(commitlint) |
| pre-commit | 포맷(Biome), 비밀값(자체 스크립트, 흔한 형태만) — 빠르게 |
| pre-push | 린트(oxlint), 타입 검사, 단위 테스트, 모듈 경계, 파일 크기, 다국어, 콘텐츠 검증, 문서 갱신 검사 (`pnpm check` + 문서 검사 + 콘텐츠 호환 검사) |
| main 푸시 CI | 위 전체 + DB 통합 테스트(PostgreSQL 18.6 서비스 컨테이너)·표 정의와 마이그레이션 일치 + 비밀값 전체 이력(gitleaks) + 콘텐츠 검증 + 이미지 빌드 + 스테이징 배포. 문서·스킬만 바뀐 푸시는 이미지·배포 생략 |
| 정기(NAS) | 매일 DB 백업, 주 1회 복구 훈련(`nas-backup`). 되돌림 훈련은 수동(`rollback-drill`) |
| 정기(GitHub) | 매주 월요일 Dependabot PR(npm·Actions). 버전 올림만 있는 PR은 작업 기록 검사에서 빠진다(ADR 21) |
| 야간 CI | 생성기 해시, 복구 테스트, 성능 스모크 |
| 화면을 고칠 때(손으로) | 화면 시험(Playwright, 저장소 `e2e/`). 화면을 고친 에이전트가 돌리고 결과(통과·실패, 잰 값)를 작업 기록에 남긴다. CI에서는 자동으로 돌리지 않는다. 필요해지면 손으로 실행하는 워크플로부터 만든다(ADR 37, 사용자 결정 2026-10-29) |

### 10.3 기록 체계
- `docs/WORKLOG.md`: 자동 생성 목차. 실제 항목은 작업마다 파일 1개 — `docs/worklog/YYYY/MM/DD-HHMM-<영문슬러그>.md` (일시 KST, 작업 도구, 내용, 변경 파일·이유, 함께 바꿔야 하는 파일, 건드리지 말 것, 미검증·TODO, 관련 ADR). 여러 에이전트가 동시에 써도 충돌하지 않는다.
- `docs/adr/YYYY-MM-DD-<영문슬러그>.md`: 결정마다 1개(배경, 선택지, 결정, 이유, 결과). 확정된 ADR은 고치지 않고 새 ADR로 대체한다.
- `docs/PROTECTED.md`: 승인 없이 바꾸면 안 되는 파일·시스템과 이유.
- `docs/DECISION_LOG.md`: 이 계획을 만든 질문·답변 기록(사용자 답변 원문 포함). 수정하지 않고 보존한다.
- `CHANGELOG.md`: 버전 태그 때 git-cliff로 생성. 게임 전체를 하나의 SemVer로 관리(클라·서버가 프로토콜로 묶여 함께 배포).
- 새 **런타임 의존성 추가**는 ADR 필수(버전 올림·개발 도구는 제외).
- 작업 도구 이름은 항상 기록한다. Claude 세션은 운영 규칙상 AI 모델 식별자를 기록하지 않는다(다른 도구는 원하면 기록 가능).
- 파일명은 영문 ASCII(한글 파일명은 도구 간 경로 깨짐 사례 있음 [V]).

### 10.4 코드 규칙
- 주석은 한국어, 이름(변수·함수·파일)은 영어.
- 모듈 경계는 `scripts/check-boundaries.mjs`(package.json 내부 의존 허용 목록 + 타입 전용 의존의 `import type` 검사 + 판정 코드 금지 API) + pnpm 엄격 의존성 + 패키지 `exports`로 강제(4.1 의존 방향, ADR 17·23). 게임 앱 코드의 Node 전역·내장 모듈은 oxlint로 막는다(ADR 23).
- 파일 크기: 600줄 초과 경고, 1,000줄 초과 CI 실패(자동 생성 파일 제외). 기존 프로젝트는 최대 4,765줄이었다 [V].
- 복사해 쓴 코드·데이터의 출처와 라이선스는 `THIRD_PARTY_NOTICES.md`에 적는다(FastNoiseLite 등).
- 보호 경로(`packages/protocol`, 원장, `packages/planet` 생성기, `packages/sim`)는 ADR 링크 없이 의미를 바꾸지 않는다.
- AI 지침: `AGENTS.md`가 원본, `CLAUDE.md`는 `@AGENTS.md`로 불러온다 [V: Claude Code 문서]. Antigravity는 `AGENTS.md`를 읽는 것으로 알려져 있다 [A: 3차 출처, IDE 버전 확인 필요]. 스킬은 `.claude/skills/`에 두고 Antigravity는 같은 폴더를 `.agent/skills`(링크)로 읽는다. 구성·사용 순서는 ADR 19와 AGENTS.md 8장.

## 11. 로드맵

| 단계 | 기간 상한 | 내용 | 통과 기준 | 실패 시 |
|---|---|---|---|---|
| **M0 기반** | 2~3주 | 모노레포·CI·훅, 이미지·`deploy.sh`·롤백, HTTPS·WebSocket, NAS 사양 수집, 백업 + 복구 훈련, 성능 오버레이·텔레메트리, 접속 핸드셰이크(버전·시계·재접속), 콘텐츠 검증 1·2·4·7단계, 다국어 골격, **ADR**: 격자·스케일·ID / 상태 저장·복구 / 시간 기준·세션 / 프로세스 구조 / 세계 데이터 버전 | 배포·롤백 시연, 복구 훈련 통과, 휴대폰이 HTTPS로 앱을 열고 백그라운드 복귀 후 연결 유지 | — |
| **S1 2차맵** | 2~3주 | 임시 지형으로 2차맵 스트리밍 + 서버 경로를 따르는 유닛 1,000개 + 건물 배치 + 유닛 표현 단계 | 기준 기기 20분 연속: 프레임 시간 p95 ≤ 33ms, 메모리 예산 이내, 재진입 ≤ 1초·첫 진입 ≤ 3초(4G) | 2차맵 개별 진입 방식, 밀도·주변 범위 축소 |
| **S2 행성 LOD** | 2~3주 | 자체 LOD 렌더러 + 최소 생성기(노이즈 + Priority-Flood + 단순 기후) 행성 1개 + 지표 레이어 2종 + 편집기 1단계. 셰이더 언어 결정. 지구 ETOPO는 통과 후 | 첫 표시 ≤ 3초, 화면당 타일 상한 준수, 틈 없음, p95 ≤ 33ms | 단계 수 축소, 미리 구운 텍스처 |
| **앱 뼈대** | 2주 | 화면 주소(자체 라우터)·뒤로 규칙, 화면 틀(위 띠·하단 탭 A·C·사이드 메뉴, 폭 3단계), 홈 대시보드(템플릿 6개 시안, 기본 DT-HYBRID), 처리할 일·복귀 요약 자리, 계정 설정 넓히기(`nav`·`home`), 화면 시험(`e2e/`)·첫 화면 크기 검사. 0단계 계약 → W1~W5(ADR 37) | W1(틀)·W4(홈) 통과 기준 + NAS 배포 뒤 사용자 휴대폰에서 홈·탭·뒤로·서랍 확인 | 템플릿은 조합·격자를 먼저 하고 나머지 넷과 끌어 옮기기를 뒤로 미룬다 |
| **S3 서버 규모** | 2주 | 유닛 10만 개(유저 + NPC 세력 합계, NPC는 단순 행동 규칙, ADR 27) 이벤트 예약 + 시야 전송 + NAS 밖 봇 1~2천 + 임시 전투 공식 + 오프라인 정산 + `kill -9` 복구 | 이벤트 루프 지연 p99 < 50ms, 복구 < 60초 + 불변 조건 유지 [A: 기준값] | 유닛 수 축소, 워커 분리 앞당김 |
| **M2 연결** | 2주 | 벌목 → 집계 → 다른 기기의 1차맵 갱신 | 정해진 시간 안에 다른 기기에 반영, 기본 데이터 재생성 없음 | — |
| **N1 NPC 세력** | 2~3주 | 공통 의사결정 틀, 유저와 같은 규칙(기획 D-013), 유저 0명으로 며칠 헤드리스 실행(기획 P0 D-044, ADR 27) | 단계를 시작할 때 ADR로 정한다 | — |
| 이후 | — | 지구 ETOPO 반영, 편집기 2·3단계, 거래소(경제 기획 확정 후 1~2주), 전투 규칙, 항성계 화면 | 단계별 ADR | — |

공통 규칙:
- 단계마다 가설·측정 수치·결론을 ADR로 남긴다.
- 기간 상한에 도달하면 "거의 됐다"도 멈추고 보고·결정한다.
- 검증 단계 동안 기획 변경은 백로그로(기준이 흔들리지 않게).
- 기준 기기: 사용자 휴대폰 + 출시 3년 이내 중가 안드로이드폰(+ 가능하면 아이폰 1대). iOS 저전력 모드는 30fps로 제한되므로 [V: WebKit 버그 215745, 독립 검토 확인] 측정에서 제외하고 따로 기록.
- 예상 총 기간 약 13~18주 [A: 대략치, N1 포함. 앱 뼈대 2주를 더하기 전 값].
