# 인증과 계정: Better Auth, 아이디로 들어가기, 관리자 권한, 감사 기록

- 상태: 제안
- 날짜: 2026-10-28
- 관련: docs/PLAN.md 3장(인증)·4.8, 조사 `docs/research/2026-10-28-better-auth-integration.md`·`docs/research/2026-10-28-username-login.md`, `2026-10-28-db-access-and-migrations.md`(ADR 22), `2026-10-28-trpc-type-sharing.md`(ADR 23), 작업 기록 `2026/10/28-1935-proxy-trust-static-404.md`(접속 주소)

## 배경
- PLAN 4.8: Better Auth 세션(쿠키), 역할 `player`·`gm`·`dev`·`admin`(조합 가능), 서버가 모든 관리자 요청을 검증, 지울 수 없는 감사 기록.
- 사용자 결정(2026-10-28, 원문)
  - "로그인시 없는 아이디면 입력한 그대로 아이디 생성. 관리자는 관리자페이지에서 권한 부여 설정 가능."
  - "확인 거치고 이메일 주소 입력을 하면 비밀번호 찾기 가능기능. 현재 확인메일 보내기구현안할거라, 비번찾기에서 이메일 일치만 하면 비밀번호 변경 가능하게만."
  - "로그인 아이디와 사이보그 캐릭터 생성시 캐릭터 이름과는 다른것이다."
  - 첫 관리자: 사용자가 정한 계정 2개를 지금 만든다.
- Better Auth 1.7.14에는 "로그인하다 없는 아이디면 만들기"가 없다. 그리고 모든 사용자에게 이메일이 필요하다(Verified: 조사).

## 선택지
자동 가입을 어디서 할지:
1. Better Auth 플러그인 엔드포인트를 만든다. 내부 API로 자격 확인을 다시 짜고, `@better-auth/core`를 직접 의존한다.
2. Fastify 경로 하나가 Better Auth의 공개 `auth.api`만 부른다.

이메일:
1. 사용자가 넣은 이메일을 Better Auth `email` 열에 넣는다.
2. `email` 열에는 서버가 만든 가짜 주소를 넣고, 복구 이메일은 따로 저장한다.

로그인 아이디 글자: 한글·영문·숫자·_ / 영문·숫자·_.

## 결정
- 의존성(모두 MIT, 설치 스크립트 없음, Verified: 조사·npm 2026-10-28)
  - 서버 `better-auth` 1.7.14, `@better-auth/drizzle-adapter` 1.7.14.
  - 게임 앱은 Better Auth 클라이언트를 쓰지 않는다. 들어가기·비밀번호 찾기는 일반 POST, 내 정보·관리자 기능은 tRPC다.
- 설정
  - `better-auth/minimal`. Drizzle 어댑터는 relations-v2(`@better-auth/drizzle-adapter/relations-v2`), `usePlural`, `transaction: true`.
  - 표: `users`, `sessions`, `accounts`, `verifications`. 기본 키는 UUID.
  - `telemetry: { enabled: false }`. 쿠키 이름 앞머리 `tic`.
  - 비밀값 `BETTER_AUTH_SECRET`(NAS에서 무작위 생성), 주소 `BETTER_AUTH_URL`.
  - DB가 없으면 인증을 켜지 않는다(CI 이미지 확인은 DB 없이 돈다).
- Better Auth의 HTTP 경로(`/api/auth/*`)는 허용 목록에 있는 것만 연다. 처음에는 세션 조회와 로그아웃뿐이다. 나머지(이메일·아이디 가입과 로그인, 비밀번호 재설정, 정보·이메일 변경, 계정 삭제, 관리자 경로 전부)는 404다.
- 로그인 아이디
  - 영문·숫자·_ 3~20자. 앞뒤 공백을 지우고 NFKC로 바꾼 뒤 검사한다.
  - 대소문자는 하나로 본다. 소문자로 저장하고, 입력한 모양은 `name`에 둔다.
  - 바꿀 수 없다.
  - 다른 플레이어에게 보이지 않는다. 게임 안 이름은 사이보그 캐릭터 이름이다(사용자 결정). 그래서 사칭 방지 예약어는 로그인 아이디에 두지 않는다.
- 들어가기 `POST /api/account/enter`
  - 있는 아이디: 비밀번호를 확인하고 로그인한다.
  - 없는 아이디: "새 아이디" 확인 화면을 띄운다. 비밀번호를 한 번 더 넣고, 이메일은 넣어도 되고 안 넣어도 된다. 그 뒤 계정을 만들고 로그인한다.
  - 새 비밀번호: 8~128자, 아이디와 같으면 안 된다, 흔한 비밀번호 목록에 있으면 안 된다.
  - 같은 출처(`Origin`)의 JSON 요청만 받는다.
  - 시도 제한: 접속 주소별, 아이디별, 전체. 계정 생성 상한: 접속 주소별 시간당 3개, 전체 시간당 30개. 숫자는 처음 값이고 쓰면서 고친다(Assumed).
  - 가입 닫기 스위치: 환경 변수 `AUTH_OPEN_SIGNUP`.
- 비밀번호 찾기 `POST /api/account/reset-password`
  - 아이디와 이메일이 저장된 복구 이메일과 같으면 새 비밀번호로 바꾼다. 확인 메일은 없다(사용자 결정).
  - 바꾸면 그 계정의 세션을 모두 끊는다.
  - 시도 제한은 들어가기보다 엄격하다. 아이디가 틀렸는지 이메일이 틀렸는지 구분해 알려 주지 않는다.
  - 이메일이 없는 계정은 관리자가 바꿔 준다.
- 이메일 저장
  - Better Auth `email` 열에는 항상 서버가 만든 `<UUID>@id.placeholder.invalid`를 넣는다.
  - 복구 이메일은 별도 표 `account_recovery`에 둔다(소문자, 여러 계정이 같은 이메일을 써도 된다).
- 역할
  - `player`(기본)·`gm`·`dev`·`admin`. 여러 개를 함께 가질 수 있다.
  - 역할 바꾸기는 `admin`만 한다. 마지막 `admin`의 admin 역할은 뺄 수 없다.
- 관리자 기능
  - tRPC 프로시저로만 연다. 매 요청 서버가 세션과 역할을 확인한다(기본 거부). 그 안에서 `auth.api`를 관리자 세션 머리글과 함께 부르므로 Better Auth도 한 번 더 확인한다.
  - 관리자 화면은 게임 앱 안의 메뉴다. 지연 로딩하고, admin에게만 보인다. 사용자 찾기(아이디)와 역할 바꾸기를 둔다.
- 감사 기록 표 `audit_log`
  - 누가(`actor_kind`: user·admin·cli·system, `actor_id`), 언제, 무엇을(`action`, `target_id`), 이전 값·이후 값(jsonb, 비밀번호 제외), 접속 주소를 남긴다.
  - DB 트리거로 UPDATE·DELETE·TRUNCATE를 막는다.
  - 대상: 계정 생성, 비밀번호 찾기로 바꿈, 역할 바꾸기, 관리 명령.
- 관리 명령(CLI, `dist/cli.js`)
  - 계정 만들기, 역할 바꾸기, 비밀번호 바꾸기.
  - 비밀번호는 명령줄 인자가 아니라 환경 변수로 받는다.
  - GitHub Actions 수동 실행 작업(NAS 실행기)으로 부른다. 감사 기록은 `actor_kind: cli`다.
  - 첫 관리자 계정은 사용자가 정한 아이디·비밀번호로 이 작업을 써서 만든다. 관리 명령만 길이 규칙을 건너뛸 수 있다(경고를 남긴다).
- 접속 주소는 Fastify가 믿는 프록시를 거친 값(`request.ip`)을 Better Auth에 넘긴다.

## 이유
- Fastify 경로 + 공개 `auth.api`
  - 비밀번호 확인·세션·쿠키는 Better Auth가 그대로 맡는다. 플러그인으로 만들면 내부 API로 자격 확인을 다시 짜야 한다(Verified: 조사).
  - 대신 시도 제한과 출처 확인은 우리가 한다. 서버에서 `auth.api`를 부르면 Better Auth의 HTTP 보호(속도 제한, 출처 확인, `disabledPaths`)가 돌지 않기 때문이다(Verified: `better-auth/dist/api/index.mjs`).
- HTTP 경로 허용 목록: 쓰지 않는 경로를 하나씩 끄는 방식은 새 버전이 경로를 추가하면 그대로 열린다. 허용 목록은 기본이 닫힘이다.
- 가짜 이메일
  - `email` 열은 필수이고 고유하다. Better Auth도 익명·SIWE 사용자에게 같은 형식을 쓴다(Verified: 조사).
  - `.invalid`는 메일이 갈 수 없는 이름이다(RFC 2606).
- 복구 이메일을 따로 두는 이유
  - 확인하지 않은 주소가 `email` 열에 있으면, 나중에 소셜 로그인이나 메일 기능을 켤 때 확인된 주소처럼 다뤄질 위험이 있다(Assumed: 계정 연결 규칙).
  - 고유 제약이 있으면 "이미 쓰는 이메일"이라는 사실이 드러난다.
  - Better Auth가 모르는 표라서 세션 응답에 섞여 나가지 않는다.
- 영문·숫자·_
  - 로그인 아이디는 남에게 보이지 않으니 한글이 꼭 필요하지 않다. 한국 서비스에서 흔한 규칙이다.
  - 나중에 한글을 허용하기는 쉽다. 거꾸로 막으려면 있는 아이디를 옮겨야 한다.
- UUID: 앞으로 많은 게임 표가 사용자를 참조한다. 기본 32자 문자열보다 작다. 나중에 바꾸기 어렵다(조사 추천).
- 비밀번호 8자: Better Auth 기본값이다. 서버가 인터넷에 열려 있다.

## 결과
- 감수할 점
  - 아이디와 복구 이메일을 아는 사람은 비밀번호를 바꿀 수 있다(확인 메일이 없어서). 막는 장치: 아이디는 남에게 보이지 않는다, 시도를 엄격히 제한한다, 바꾸면 모든 세션을 끊는다, 감사 기록을 남긴다. 메일 발송을 붙이면 확인 메일 방식으로 바꾼다(그때 새 ADR).
  - 들어가기는 아이디가 있는지를 알려 준다(자동 가입의 성질). 대신 확인 한 번이 로그인 시도 한 번과 같은 제한을 받는다.
  - 시도 제한은 메모리에 있다. 서버를 다시 시작하면 초기화되고, 프로세스 하나만 막는다.
  - Drizzle RC와 relations-v2 어댑터가 아직 자주 바뀐다. DB 시험이 안전장치다.
  - 첫 관리자 비밀번호는 사용자가 정한 값이라 일반 규칙보다 약할 수 있다. 정식 서비스 전 보안 점검 때 바꾼다.
  - 관리 명령의 비밀번호는 GitHub Actions 입력값으로 지나간다(비공개 저장소, 소유자만 봄). 로그에는 가린다.
- 나중에 할 일: WebSocket 접속에 세션 연결, 콘텐츠 보안 정책(CSP), 로그인한 뒤 복구 이메일 넣기·바꾸기.
- 다시 볼 조건: 메일 발송, 소셜 로그인, 서버 프로세스 여러 개(시도 제한 저장소), 정식 서비스 전 보안 점검.
