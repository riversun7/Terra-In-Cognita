# 콘텐츠 팩과 검증 파이프라인

- 상태: 확정
- 날짜: 2026-10-28
- 관련: PLAN 7장, DECISION_LOG Round 9

## 배경
기획이 자주 바뀌므로 규칙·수치는 데이터로 둔다. 사용자는 업데이트 때 오류와 기존 버전과의 충돌을 미리 확인할 수 있는지 물었다(Round 9).

## 결정
- 원본: 스테이징의 관리자 편집기 → 버전 붙은 콘텐츠 팩(JSON) → git 커밋 → 운영 서버가 가져옴. 롤백 = 이전 팩.
- v1은 내보낸 파일을 개발자·에이전트가 커밋한다. 나중에 버튼 한 번 자동 커밋을 붙인다.
- 행성 정의(시드·파라미터·편집 작업 목록)는 팩(git)에, 구운 타일과 큰 편집 래스터는 NAS에(해시 참조).
- CI 검증 7단계: ① 스키마 ② 참조 무결성 ③ 규칙 검사 ④ **이전 버전 호환성**(운영 데이터가 쓰는 ID가 지워지거나 바뀌었는데 변환표가 없으면 실패) ⑤ 헤드리스 시뮬레이션 회귀 ⑥ 전투 재생 비교 ⑦ 스테이징 점검 후 운영 반영.
- ①②④⑦은 M0부터, ③⑤⑥은 규칙이 생기는 시점부터.

## 이유
- 데이터 변경도 코드 변경처럼 검사·비교·되돌리기가 가능해야 기획 변경을 안전하게 반영할 수 있다.
- 큰 이진 데이터를 git에 넣으면 기존 저장소처럼 커진다.

## 결과
- 콘텐츠 스키마(`packages/content`)가 기획 데이터의 형식 계약이 된다.
