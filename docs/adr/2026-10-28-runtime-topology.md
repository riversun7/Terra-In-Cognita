# 런타임 토폴로지: 단일 프로세스 + 워커, 버스·아웃박스, 지역 키

- 상태: 확정
- 날짜: 2026-10-28
- 관련: PLAN 4.2, 독립 검토 C1

## 배경
처음 계획은 api·월드 시뮬레이션·전투 인스턴스·NPC AI·백그라운드를 별도 프로세스로 두면서 Redis 없이 PostgreSQL만 쓰는 것이었다. 그러면 프로세스끼리 통신할 수단이 없다(Postgres NOTIFY는 메시지 8,000바이트 미만, 커밋 시 잠금 — 독립 검토 확인). 기존 프로젝트는 pm2 cluster 모드로 게임 루프가 중복 실행될 위험도 있었다.

## 선택지
1. 역할별 프로세스 + 메시지 브로커(NATS, Valkey 등)
2. **프로세스 1개 + 워커 스레드, 버스 인터페이스로 나중에 분리 가능하게**
3. 프로세스 1개, 단일 스레드

## 결정
- v1은 서버 프로세스 1개(+ DB). 메인 스레드: HTTP, WebSocket, 월드 상태, 이벤트 스케줄러, 시장별 매칭 엔진.
- Piscina 워커 풀: 상태 없는 계산(경로탐색, NPC 판단, 2차맵 생성·집계, 전투 빨리감기 판정).
- 전투 워커 스레드: 진행 중 교전의 상태를 들고 틱을 돈다.
- 모듈 간 통신은 in-process 버스 인터페이스 + DB 아웃박스. 월드 상태는 `regionId` 키로 나눈다.

## 이유
- 우선순위 1(개발·유지보수)과 2(운영 안정성)에 맞는 가장 단순한 형태다. 컨테이너 2개로 운영할 수 있다.
- 워커 스레드로 NAS의 여러 코어를 쓰면서도 메시지 브로커를 들이지 않는다.
- 버스 인터페이스와 지역 키가 있으면 지역별 프로세스 분리가 "버스 구현 교체"로 끝난다.

## 결과
- 프로세스가 하나라 메모리 초과 등으로 죽으면 전부 멈춘다 → 상태 저장·복구 규칙으로 대응(상태 저장 ADR).
- 동시접속 1만 명 단계에서는 지역별 분리와 게이트웨이 라우팅이 필요하다 → 그때 새 ADR.
