# S1 2차맵: 쿼터뷰 카메라, 서버 경로 이동, 건물 배치, 측정 계획

- 상태: 제안 (S1 측정 뒤 확정)
- 날짜: 2026-10-28
- 관련: docs/PLAN.md 5.2·5.7·11장(S1), `2026-10-28-planet-grid-contract.md`(격자·ID), `2026-10-28-map-delivery-and-rendering.md`(전송·렌더링), `2026-10-28-unit-display-real-size.md`(유닛 표현), `2026-10-28-simulation-model.md`(이벤트 예약), `2026-10-28-server-authority.md`, `2026-10-28-time-and-session-protocol.md`, `2026-10-28-fog-and-map-visibility.md`, `2026-10-28-stack-baseline.md`(Three.js), 기획 D-064·D-102·D-108·D-120·D-133·D-135·D-139

## 배경
- S1의 목표(PLAN 11장): 임시 지형으로 2차맵 스트리밍, 서버 경로를 따르는 유닛 1,000개, 건물 배치, 유닛 표현 단계.
- 통과 기준: 기준 기기 20분 연속, 프레임 시간 p95 ≤ 33ms, 메모리 예산 이내, 재진입 ≤ 1초, 첫 진입 ≤ 3초(4G).
- 2차맵을 보는 시점은 기획서·계획서 어디에도 정해져 있지 않았다.
- 사용자 결정(2026-10-28): "쿼터뷰 + 회전".

## 선택지 (시점)
1. 쿼터뷰(약 45°) + 회전.
2. 거의 위에서(60~75°) + 회전.
3. 자유 카메라(기울기를 수평 가까이까지).

## 결정
### 카메라와 조작
- 쿼터뷰다. 기울기는 약 35~55°(기본 45°)로 묶어 지평선이 보이지 않게 한다. 회전은 자유다. 확대는 근접(화면 가로 약 40m)부터 2차맵 전체가 보이는 거리까지다.
- 휴대폰: 한 손가락으로 끌면 이동, 두 손가락으로 확대·회전, 누르면 고르기·명령. 데스크톱: 끌기 이동, 휠 확대, 오른쪽 끌기 회전.
- 2차맵 밖은 그리지 않고 경계를 표시한다. 경계를 넘어가면 짧게 전환한다(D-139).

### 2차맵 데이터 (임시 지형)
- 2차맵 하나 = 1차맵 최소 칸 하나(격자 ADR). 지형은 128×128칸(높이는 꼭짓점 129×129), 배치는 256×256칸이다.
- S1은 임시 지형을 쓴다. 칸 키에서 시드를 만들어 노이즈 고도와 임시 지표 종류(물·풀·흙 등)를 만든다. 행성 생성기(S2)가 생기면 바꾼다.
- 서버가 처음 요청 때 만들고 저장·캐시한다(맵 ADR). 이진 형식에 `generatorVersion`을 붙인다.
- 숨김 정보(자원·크리쳐)는 넣지 않는다. 탐사·시야 확인 뒤에만 준다(ADR 26). S1은 확인하는 자리만 두고 모두 통과시킨다.

### 유닛 이동 (서버 판정)
- 위치는 2차맵 로컬 연속 좌표다. 값은 정수 고정소수점이고, 단위는 배치 칸의 1/1024다.
- 시각은 서버 시계의 ms, 속도는 단위/초 정수다. 출발값은 기획 D-120(걷기 약 0.42칸/초 이상, 차 약 4.7칸/초)이다.
- 경로탐색: 배치 칸 격자에서 8방향 A*. 대각선으로 모서리를 뚫고 지나가지 않는다.
  - 크기 등급은 2~3개다(통과 폭 1·2칸, 필요하면 3칸, D-135). 등급마다 통과 가능 지도를 따로 둔다.
  - 도로는 종류별 이동 비용이 있다(D-102). S1의 비용 수치는 임시값이다.
- 저장은 경로(꺾이는 점 목록), 출발 시각, 속도다. 위치는 필요할 때 계산한다. 도착만 이벤트로 예약한다(시뮬레이션 ADR).
- 판정 코드는 새 패키지 `packages/sim`에 둔다. 정수 계산만 쓰고 초월함수는 쓰지 않는다.

### 전송
- 2차맵에 들어가면 그 2차맵을 구독하고, 나오면 해제한다.
- 서버는 처음에 유닛 목록(위치 + 경로)을 준다. 그 뒤에는 경로가 바뀔 때만 보낸다. 기기는 경로를 따라 위치를 계산해 그린다. 위치를 계속 보내지 않는다.
- 이동·배치 명령은 WebSocket 프로토콜(`packages/protocol`)로 보낸다(AGENTS 4장).

### 렌더링
- 새 패키지 `packages/engine`에 Three.js 엔진을 둔다. React와 나눈다(stack ADR).
- 의존성(Verified: npm 2026-10-28, 둘 다 MIT)
  - `three` 0.186.1(2026-09-24 공개): 기기로 가는 코드.
  - `@types/three` 0.186.0(2026-09-11 공개): 개발 의존성.
- 지형 메시는 Web Worker에서 만든다. 유닛·건물은 인스턴싱으로 그린다.
- S1 그림은 임시 도형(캡슐·상자)이다. 원거리는 아이콘·묶음으로 바꾼다(ADR 25). 바꾸는 거리는 S1에서 잰다.
- 렌더러는 하나를 재사용한다. 화면 변화가 없으면 그리기를 멈춘다. 컨텍스트 손실 뒤 복구한다. 픽셀 비율에 상한을 둔다(PLAN 5.7).

### 건물 배치
- 칸 조합 모양이다(S1은 직사각형). 90° 회전, 2차맵 하나 안이다(D-133).
- 겹침·지형·도로 검사는 서버가 한다. 기기는 미리 보기만 한다.

### 측정
- 성능 오버레이와 텔레메트리(M0에서 만듦)로 프레임 시간 p95, 메모리, 진입 시간을 잰다.
- 기준 기기는 사용자 휴대폰과 출시 3년 안의 중가 안드로이드폰이다(PLAN 11장).
- 유닛 1,000개는 서버의 시험용 봇이 움직인다.

## 이유
- 쿼터뷰
  - 사용자 결정이다.
  - 기획 톤(D-064, 라그나로크·메이플 느낌)과 맞는다.
  - 기울기를 묶으면 보이는 범위가 정해진다. 그래서 메모리·그리기 예산을 지키기 쉽다(Assumed).
- 경로가 바뀔 때만 보내기
  - 유닛 1,000개가 움직여도 보낼 것이 적다.
  - 틱마다 위치를 보내면 휴대폰과 NAS 둘 다 부담이 크다(Assumed: S1에서 잰다).
- 정수 고정소수점: 판정 결과가 서버·버전마다 같아야 한다(시뮬레이션 ADR).
- 크기 등급별 통과 지도: 큰 유닛이 좁은 길로 가지 않는다(D-135).

## 결과
- 새 패키지 2개(`packages/sim`, `packages/engine`)와 런타임 의존성 `three`가 생긴다.
- S1이 끝나면 측정 수치와 결론을 이 ADR에 더하고 확정한다(PLAN 11장 공통 규칙).
- 통과하지 못하면 대안(PLAN 11장)을 쓴다. 2차맵마다 따로 들어가는 방식이나 밀도·주변 범위 축소다.
