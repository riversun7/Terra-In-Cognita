- 상태: 제안 (휴대폰에서 열기·미리보기·초안 저장을 확인한 뒤 확정)
- 날짜: 2026-10-29
- 관련: docs/PLAN.md 4.1·4.8·5.5·6.2·6.3·7장·11장, ADR `2026-10-29-s2-planet-lod.md`(36) "시험 화면과 편집기 1단계", `2026-10-29-app-shell.md`(37, 주소 표·사이드 메뉴), `2026-10-28-planet-generation-and-versioning.md`(10), `2026-10-28-editor-and-placement.md`(12), `2026-10-28-content-pack-format.md`(24), `2026-10-28-auth-and-accounts.md`(29), `2026-10-28-db-access-and-migrations.md`(22), `2026-10-28-design-system.md`(30), `2026-10-28-pwa-and-browser-baseline.md`(28), 기획 질문 `docs/questions/2026-10-29-special-terrain.md`, 기획 D-141·D-154·D-155·D-156·D-214·D-215·D-258·D-259·D-5020·D-6002·D-6003, 작업 기록 `docs/worklog/2026/10/29-1920-planet-editor-decisions.md`

## 배경
- S2 1차맵이 NAS에 올라갔다. 사용자 휴대폰에서 114~120fps, 첫 표시 225ms다(Verified: ADR 36 "휴대폰에서 잰 값").
- 사용자 의견은 "좋다 안끊긴다", "지형모델은 조금 마음에 안들지만 행성편집생성기가 나오면 다시 체크"다. 편집기 1단계의 첫 목적은 생성 지형을 바꿔 보고 휴대폰·데스크톱에서 빨리 다시 보는 것이다.
- 편집기 질문에 사용자가 지형에 대해 따로 적은 답(2026-10-29, 원문):
  "1. 지형이 단조롭게 너무 큼 전부 갈색 전부 사막 등 랜덤성이 조금 떨어짐 어느정도 겹치는 구간 군집구간, 반듯한 선이아닌 자연스러운 노이즈 경계
  2. 2차맵이 너무 저해상도에 뿌옇다.
  3. 구름 같은 요소도 추가되면 좋을듯
  4. 항성의 위치를 기반으로 낮과 밤의 표현.
  5. 달도 있으면 좋겠다"
  - 1은 세부 수치로 고칠 수 없는 생성기 구조 문제다(위도 띠·바람길 줄무늬·매끈한 해안, 특수 지형 제안서 4.1·4.3). 생성기 다양성 고침(작업 가지 `work/generator-variety`, 새 ADR 예정)이 맡는다.
  - 2는 2차맵 화면 선명도 조사(작업 가지 `work/second-map-sharpness`), 3~5는 1차맵 하늘 설계(구름·항성 기준 낮밤·달, 새 ADR 예정)가 맡는다. 이 ADR의 범위가 아니다.
- ADR 36이 정한 1단계: 프리셋 + 세부 수치 슬라이더, 기기 워커의 낮은 해상도 지구본 미리보기, 바이옴 면적표, 정의 JSON 내보내기. 서버 초안 저장은 2단계였다(Verified).
- PLAN 6.2의 1단계 목록은 더 길다: 2차맵 미리보기, 시드·버전 저장, 공개 행성 설정 잠금(D-156)(Verified).
- 사용자는 D-154에서 "프리셋 + 고도 강 호수 등의 편집."이라고 했다. PLAN 6.2는 직접 편집을 2단계에 둔다(Verified).
- ADR 10(확정)과 PLAN 5.5는 "편집기 공개 = 새 행성 버전(기존 버전은 불변)"이라고 정했다(Verified).
- 기획은 행성 편집기, 개발자 정보 메뉴(D-214), 개발자 페이지(D-5020)를 한 줄기로 보자고 했다. 특수 지형 양은 행성마다의 조건값이고, 편집기의 종류별 조절은 고르지 않았다(D-259)(Verified).
- 지금 코드(Verified: main `25b7ebc`)
  - 생성기 출력 판 2(`GENERATOR_VERSION` 2), 면 레벨 4~9(`PLANET_GENERATOR_FACE_LEVELS`). 프리셋 수치표는 `@terra/shared`에 있다.
  - 엔진 메모리 상한 이름은 `memoryBytes`다. 목록 정보에 가장 높은 땅(`maxElevationM`)이 있다.
  - 셰이더 측정판은 관리자 화면 안에 있다(`apps/game/src/admin/GpuBenchPanel.tsx`, `admin/gpuBench/`). 그 조각은 서비스 워커 미리 캐시에서 빠진다(`globIgnores`, 검사 `ADMIN_ONLY_CHUNK`).
  - 앱 뼈대(ADR 37, 제안)의 주소 표(`packages/shared/src/routes.ts`)·사이드 메뉴·화면 시험(`e2e/`)은 아직 코드가 없다.
- 설계 때 잰 것(Verified: 개발 컨테이너 4코어 공유, 헤드리스 Chromium 153)
  - 판 2 생성기를 브라우저 모듈 워커에서 돌려도 결과 해시가 Node와 같다(F5~F9). F9는 약 15초다. Safari·Firefox는 돌려 보지 않았다(Unknown).
  - 워커 안에는 `performance.memory`가 없다. 워커가 잡은 메모리는 화면 쪽 값에도 잡히지 않는다.
  - 엔진을 다시 만든 뒤 첫 표시까지 0.1~0.75초다(소프트웨어 그리기). 휴대폰 시간·메모리는 모른다(Unknown).

## 선택지
### 개발자 도구를 두는 곳
1. 관리자 화면 안(지금 셰이더 측정판처럼).
2. 개발자 영역 한곳: 주소 `/dev`, 폴더 `apps/game/src/editor/`.

### 누가 쓰나
1. admin만.
2. dev·admin.

### 초안을 두는 곳
1. 기기 저장소 + JSON 내보내기·가져오기.
2. 서버 DB 표 + tRPC 쓰기 + 감사 기록(ADR 36의 2단계 일을 당김).

### 미리보기를 만드는 곳
1. 기기 워커(빠른 F5 + 기본 F7, F6·F8·F9는 고를 때).
2. 기기 워커 + 서버 F9 확인 굽기.
3. 서버만.

### 새 결과를 화면에 올리는 법
1. 결과마다 엔진을 버리고 다시 만든다(엔진 변경 없음).
2. 엔진에 타일 원천 바꾸기 기능을 더한다.

### 행성 정의를 기기로 가져오는 법
1. 권한을 보는 tRPC 조회.
2. 사람이 JSON을 붙여 넣는다.

## 결정
도구 자리·사용자는 2번, 초안은 2번(사용자 결정), 나머지는 1번이다. 사용자가 고른 곳은 [사용자 Dn]으로 적는다("결과" 끝 표에 원문).

### 1. 개발자 도구 한곳 [사용자 D7·D8]
- 사용자 원문: "당연히 편집기 아닌가? 관리자 페이지도 매우 방대하므로 개발자기능은 한곳으로 모아라".
- 폴더 `apps/game/src/editor/`가 개발자 도구 전부의 자리다.
  - `editor/DevHome.tsx`: 개발자 홈(도구 목록).
  - `editor/planet/`: 행성 편집기.
  - `editor/gpuBench/`, `editor/GpuBenchPage.tsx`: 셰이더 측정판. 관리자 화면에서 옮긴다.
  - 나중 도구도 여기에 더한다: 지형 정보(D-214), 출현 분포(D-5018·D-5020), 크리쳐 생성 에디터(D-5024).
- 관리자 화면(`/admin`)에는 계정·운영 기능만 남긴다.
- 화면 주소(ADR 37 주소 표에 더한다)

| 주소 ID | 경로 | 화면 | 틀 | 부모 | 누가 |
|---|---|---|---|---|---|
| `dev` | `/dev` | 개발자 홈 | 있음 | `home` | dev·admin |
| `dev_planet_editor` | `/dev/planet-editor` | 행성 편집기 | 숨김 | `dev` | dev·admin |
| `dev_gpu_bench` | `/dev/gpu-bench` | 셰이더 측정 | 있음 | `dev` | dev·admin |

  - 예약: `/dev/:tool`(위 나중 도구). ADR 37 6-5 후보의 `/admin/:section` 예약은 이것으로 바꾼다.
- 사이드 메뉴 시스템 묶음: 설정 · 개발자(dev·admin) · 관리자(admin) · 로그아웃. 하단 탭과 메뉴 편집 목록에는 넣지 않는다.
- 권한: 사용자 원문 "dev·admin". 서버 권한 문장 `planetEditor: ["read", "write"]`를 dev와 admin에게 준다(기본 거부). 셰이더 측정판은 서버 자료를 쓰지 않아 기기에서만 가린다. 화면 가림은 편의이고, 서버가 매 요청 권한을 본다.
- 붙이는 때: 앱 뼈대 0단계가 주소 줄·권한 줄을 먼저 넣는다. 화면은 W1(라우터·틀) 뒤에 붙인다. W1이 편집기 화면보다 늦으면 지금 `App.tsx`의 열린 화면 종류에 `dev`를 더하고 계정 줄 [개발자]로 연다. 그때는 W1이 주소로 옮긴다.
- 미리 캐시: 개발자 조각(`gpuBench*`, `planetEditor*`)은 서비스 워커 미리 캐시에서 뺀다. 검사 이름은 `ADMIN_ONLY_CHUNK` → `DEV_ONLY_CHUNK`(`/^assets\/(gpuBench|planetEditor)[^/]*\.(js|css)$/`), `globIgnores`도 같게 고친다. 조각 이름은 진입 파일 이름을 따르므로 진입 파일 이름 앞머리를 지킨다.

### 2. 범위
- 넣는 것
  - 프리셋 6축 × 3단계, 세부 수치, 시드. 단계마다 정하는 값을 함께 보인다. 슬라이더 범위는 생성기 입력 검사와 같은 표에서 읽는다(한 곳). 생성기 다양성 고침이 수치를 더하면 표에 줄만 더한다.
  - 기기 워커 미리보기: 빠른 F5, 기본 F7, 고를 때 F6·F8·F9 [사용자 D4].
  - 칸 정보창, 바이옴 면적표.
  - 평면 미니맵, 공개본 ↔ 초안 번갈아 보기, 면적 차이 열 [사용자 D1].
  - 서버 초안: 사람마다·행성마다 하나, 자동 저장, 판 기록(최근 50개), 판 되돌리기. JSON 내보내기·가져오기 [사용자 D3].
  - 열 때 기기 결과와 서버 결과가 같은지 확인.
  - 편집 전용 행성 `s2_editor_planet` [사용자 D2].
- 빼는 것
  - 2차맵 미리보기(D6a). 행성 값으로 2차맵을 만드는 일(특수 지형 제안서 4.3 5단계)이 먼저다.
  - D-156 잠금 장치(D6b). 아래 "공개와 잠금" 규칙으로 대신한다.
  - 고도·강·호수 직접 편집 [사용자 D6c]. 2단계다.
  - 특수 지형 종류별 조절. 사용자가 D-259에서 고르지 않았다.
  - 초안 여러 개 목록, 다른 사람 초안 보기. 요청하지 않았다.
- 행성 크기(면 레벨)와 바이옴 표는 읽기만 한다.

### 3. 미리보기 (기기 워커) [사용자 D1·D4]
- 입력은 `planetInputFromDefinition(행성 항목, 바이옴 항목들, 미리보기 면 레벨)`이다. 화면 스레드가 `validatePlanetInput`으로 먼저 본다.
- 워커는 생성기 진입점(`@terra/planet/generator`)과 타일 모으기만 가져온다. 콘텐츠 패키지·엔진은 가져오지 않는다.
- 워커는 둘이다. 빠른 워커(F5)는 열 때와 슬라이더를 끄는 동안 쓴다(미니맵이 결과마다 다시 그린다). 본 워커(기본 F7)는 슬라이더를 놓았을 때와 프리셋·시드를 바꿨을 때 쓴다.
- 상한은 정의의 면 레벨과 `PLANET_GENERATOR_FACE_LEVELS`의 위쪽 값 중 작은 쪽이다. 값을 코드에 적지 않는다.
- 생성은 중간에 멈출 수 없다. 그래서 본 워커는 이렇게 한다.
  - 새 일이 왔는데 도는 일이 기후 단계 전이면 워커를 끝내고 다시 띄운다. 다시 띄우는 값은 F7에서 약 0.3~0.4초다(Verified: 헤드리스).
  - 기후 단계를 지났으면 끝까지 두고 결과만 기억한다. 남은 일은 전체의 약 12~17%다(Verified: 판 2).
- 열 때 순서: 공개본 F5(확인과 첫 지구본) → 초안 F7 → 공개본 F7(차이 열·번갈아 보기).
- 모으기(맵 레벨 F−4~F)와 꼭짓점 높이도 워커가 하고 배열을 넘긴다. 화면 스레드는 타일만 자른다.
- 결과는 입력(키를 정렬한 JSON) + 면 레벨로 기억한다. 바이트 상한(처음 32MiB)을 두고 오래된 것부터 버린다. 공개본 결과는 남긴다.
- 워커를 못 쓰면 미리보기를 만들지 않고 안내한다.

### 4. 메모리와 F8·F9 [사용자 D4]
- 브라우저 워커는 자기 메모리를 읽을 수 없다(Verified). 그래서 이렇게 본다.
  - 결과마다 넘긴 배열 바이트(정확한 값)와 레벨별 최대 추정치(Node에서 잰 표, "추정"이라고 적음)를 상태 칩에 보인다.
  - F9는 확인 창을 띄운다(데스크톱 약 15초, 휴대폰 모름, 데스크톱을 권함).
  - F8·F9를 시작하기 전에 기기 저장소에 표시를 남기고 끝나면 지운다. 다음에 열 때 표시가 남아 있으면 탭이 꺼진 것으로 보고 그 기기의 상한을 한 단계 낮춘다. [다시 허용]으로 되돌린다. 이 표시는 기기 설정일 뿐 초안이 아니다.
  - 사용자 휴대폰에서 F7·F8·F9를 한 번 손으로 잰다. 원격 개발자 도구를 쓸 수 없으면 탭이 꺼지는지만 본다.
- 굽기가 끝난 행성은 목록 정보에 결과 해시(`fieldsHash`, 선택 칸)를 싣는다. 기기 F9가 그 값과 같으면 "굽기와 같음"이다. 프로토콜 판은 올리지 않는다(앞선 예: `maxElevationM`).

### 5. 지구본 갱신
- 새 결과를 보일 때 엔진을 버리고 다시 만든다. 위도·경도·거리는 넘긴다. 방위는 북쪽으로 돌아간다(엔진 보기 값에 방위가 없다, Verified).
- 새 결과가 올 때까지 지금 지구본을 둔다. 그래서 바꿀 때마다 빈 화면은 한 번이다(헤드리스 0.1~0.75초, 휴대폰 모름).
- 행성 설명: 면 레벨은 미리보기 레벨, 반지름은 정의 면 레벨의 반지름, 가장 높은 땅은 결과의 최댓값이다. 메모리 상한은 넘기지 않는다(엔진 기본값).

### 6. 결정성과 판 확인
- 서버가 켤 때(요청을 받기 전) 팩 행성마다 F5 결과 해시를 만든다. 정의 조회가 그 값을 준다.
- 기기는 열 때 공개본을 F5로 만들어 비교한다. 다르면 "이 기기의 미리보기는 서버와 다릅니다"를 띄우고 내보내기를 막는다.
- 생성기 판이 기기와 서버에서 다르면 "앱을 새로 고치세요"를 띄우고 내보내기를 막는다. 초안은 서버에 남는다.
- 내보낸 JSON에 기기 해시(면 레벨별)를 넣는다. 반영할 때 Node에서 다시 비교한다.
- 편집기 코드와 시험에는 해시 값을 적지 않는다(생성기 판이 바뀌어도 깨지지 않게).

### 7. 칸 정보창 (D-214 정보창의 1단계)
- 누른 점의 위도·경도로 미리보기 면 레벨의 칸을 찾는다. 타일 값이 아니라 생성 결과 값을 읽는다.
- 보이는 것: 셀 키·면·i·j·위도·경도, 고도(게임 m, 실제 m = × 12), 물(수심 등급·호수·강 등급·해안), 기온, 강수, 습도, 숲, 바이옴.
- 수심 등급은 물 비트에서 읽는다. 등급은 반올림 전 깊이로 정해서, 보이는 고도(12m 단위)와 경계에서 어긋날 수 있다고 적는다(Verified: `surface.ts`).
- 바이옴 설명: 표 순서대로 조건마다 값·범위·통과 여부, 처음 맞은 규칙, 마지막 육지 바이옴으로 떨어졌는지, 저장 바이옴과 다시 판정한 것이 같은지.
- 근접 실패 눈금은 특수 지형 제안서와 같다: 기온 2°C, 습도 10, 고도 실제 100m. 표는 생성기 쪽 한 곳에 둔다.
- 출처: 팩 버전, 생성기 판, 바이옴 ID. 정의 해시는 공개본만 보인다. 초안은 "초안(굽지 않음)"이라고 적는다.
- 창 부품은 칸 값과 설명 묶음 목록만 받는다. 특수 지형 설명은 묶음을 더해 붙인다.

### 8. 바이옴 면적표
- 면적 가중이다(생성기의 칸 면적 표). 행성 `biomes` 순서다. 열은 행성 대비 %, 육지 대비 %, 공개본 대비 차이다.
- 아래 줄: 육지·호수·강 칸·바다 등급 비율, 면적 평균 기온, 해수면(실제 m), 가장 높은 땅.
- 머리에 "미리보기 F7 기준, 굽기 F9와 다를 수 있음"을 적는다.

### 9. 서버 초안 [사용자 D3]
- 사용자 답: "서버 DB 저장". 추천(기기 + JSON)과 다르다.
- 표 2개, 마이그레이션 하나(더하기만. 직전 버전 앱은 이 표를 모른 채 그대로 돈다)
  - `planet_drafts`: `id`(uuid), `owner_id`(→ `users`, 계정을 지우면 함께 지움), `planet_id`(콘텐츠 ID 규칙), `revision`(1부터), `base`(jsonb: 팩 버전·정의 해시·생성기 판. 없을 수 있음), `entry`(jsonb: `planets.json` 항목), `created_at`, `updated_at`. (`owner_id`, `planet_id`)는 하나뿐이다.
  - `planet_draft_revisions`: `id`, `draft_id`(→ `planet_drafts`, 지우면 함께), `revision`, `entry`, `base`, `saved_at`. (`draft_id`, `revision`)은 하나뿐이다. 초안마다 최근 50개만 남긴다(저장할 때 오래된 것을 지운다).
- 초안은 사람마다·행성마다 하나다. 팩에 있는 행성만 초안을 둔다. 그래서 한 사람의 초안 수는 팩 행성 수를 넘지 않는다.
- tRPC 묶음 `planetEditor`

| 이름 | 종류 | 권한 | 하는 일 |
|---|---|---|---|
| `definitions` | 조회 | `read` | 팩 버전·임시 여부·서버 생성기 판, 행성마다 원본 항목·정의 해시·F5 확인 해시, 바이옴 항목 |
| `drafts.get` | 조회 | `read` | 내 초안(항목·기준·판·시각) 또는 없음 |
| `drafts.revisions` | 조회 | `read` | 내 초안의 판 목록(판·시각·크기) |
| `drafts.save` | 쓰기 | `write` | 항목·기준·기대 판을 받아 저장하고 새 판을 돌려준다. 기대 판이 지금 판과 다르면 `CONFLICT` |
| `drafts.restore` | 쓰기 | `write` | 판 하나를 초안으로 되돌린다(새 판이 된다) |
| `drafts.remove` | 쓰기 | `write` | 초안과 판 기록을 지운다 |

- 서버 검사: 항목은 `planetEntrySchema`(콘텐츠 형식) → 바이옴 참조가 팩에 있음 → 행성 ID가 팩에 있음 → 생성기 입력 확인(`validatePlanetInput`). 직렬화한 항목은 8KiB 이하다. 틀리면 `BAD_REQUEST`와 코드만 준다. 화면은 코드를 메시지 키로 바꾼다(스키마 오류 문구는 쓰지 않는다).
- 두 기기에서 같은 초안을 고치면 늦게 저장한 쪽이 `CONFLICT`를 받는다. 화면은 "다른 기기에서 바뀌었습니다"와 [그쪽 불러오기] [이걸로 덮기]를 보인다.
- 자동 저장: 바꾼 뒤 2초, 보내는 중인 저장은 하나만. 실패하면 "저장 안 됨"을 띄우고 다시 시도한다. 저장하지 않은 변경이 있으면 화면을 떠날 때 묻는다. 기기 저장소에는 초안을 두지 않는다.
- 감사 기록(PLAN 4.8): 정의 조회(`planet_editor.read_definitions`, 열 때 한 번), 초안 만들기(`planet_draft.create`)·되돌리기(`planet_draft.restore`)·지우기(`planet_draft.remove`). 감사 기록을 못 쓰면 그 요청을 실패로 돌린다.
  - 자동 저장마다는 감사 기록을 쓰지 않는다. 감사 기록은 지울 수 없는 표라 저장마다 쓰면 끝없이 는다. 저장의 누가·언제는 판 기록에 남는다. 저장은 게임 상태와 다른 계정을 바꾸지 않는다.
- 시드는 조회 응답, 초안 표, 내보낸 JSON에만 있다. 코드에는 넣지 않는다(PLAN 4.1). tRPC 응답에 `cache-control: no-store`를 붙인다.
- tRPC 쓰기(POST)에 계정 경로와 같은 출처 확인(`Sec-Fetch-Site`·`Origin`, `src/auth/requestGuard.ts`와 같은 규칙)을 붙인다. 새 쓰기 경로를 다른 사이트가 부르지 못하게 하려는 것이다. 지금 관리자 쓰기에도 함께 적용된다.
- 내보내기·가져오기는 남긴다. 반영(에이전트에게 주기)과 백업에 쓴다. 가져오기는 확인 뒤 그 행성 초안을 바꾼다(새 판).
  - 내보내기 모양: `{ format: "terra-planet-draft", formatVersion: 1, exportedAt, generatorVersion, base, checks, planet }`. `planet`은 `planets.json` 항목 그대로다.
  - 가져오기: 64KiB 상한 → JSON 읽기 → 바깥 모양 확인 → 서버 `drafts.save`와 같은 검사. 복사를 못 쓰는 곳에서는 글 상자를 보이고 직접 복사하게 한다. 파일로도 받는다.

### 10. 공개와 잠금 (ADR 10, D-156) [사용자 D2]
- ADR 10은 바꾸지 않는다. "편집기 공개 = 새 행성 버전"은 플레이어에게 행성을 처음 공개할 때부터 쓴다.
- 지금은 플레이어에게 공개한 행성이 없다. 그래서 팩 행성은 "git에 둔 초안"이다. 편집 결과를 같은 ID에 반영해도 된다(기획 질문 3에서 확인한다).
- 잠금은 팩 전체의 임시 표시(`placeholder`)가 아니라 행성마다의 공개 표시로 건다. 공개 표시는 처음 공개할 때 새 ADR로 콘텐츠 형식에 더한다(D6b).
  - 바이옴 때문에 팩의 임시 표시를 떼도(D-214) 초안 행성은 계속 고칠 수 있게 하려는 것이다.
- 편집기는 공개본을 바꾸지 않는다. 늘 초안을 고친다.
- 반영은 PLAN 7의 v1 흐름이다. 사용자가 내보낸 JSON을 에이전트에게 준다. 에이전트가 `content/core/planets.json`을 고치고 팩 버전을 올린다. 검사·해시 비교 뒤 작업 기록을 쓰고 커밋한다.
- 편집 전용 행성 `s2_editor_planet`을 팩에 더한다. 처음 값은 `s2_test_planet`과 같고 시드만 다르다. `s2_test_planet`은 시험·벤치 기준으로 그대로 둔다. 1차맵은 처음 반영 때 편집 전용 행성으로 바꾼다.
  - NAS는 빈 캐시에서 두 행성을 차례로 굽는다(판 2 기준 약 37초, Assumed: 행성 하나 18.7초 × 2).
- 사용자가 고른 수치도 임시값이다. 기획이 확인하기 전에는 게임 수치가 아니다(AGENTS 4장).
  - → D-5032 뒤(기술 해석): 기획은 세부 수치를 확정하지 않는다(모두 개발자 패널 설정값). 그래서 편집기에서 고른 값은 "기획 확인을 기다리는 값"이 아니라 언제든 다시 고치는 설정값으로 읽는다. 아래 "기획에 물을 것" 6.

### 11. 서버: 정의 조회
- 서버가 켤 때(요청을 받기 전) 한 번 만든다: 팩 버전, 임시 여부, 서버 생성기 판, 행성마다 원본 항목(JSON 그대로)·정의 해시·F5 확인 해시, 바이옴 항목 전체. F5는 행성마다 약 0.2~0.4초다(Assumed: Node 판 2 F5 239ms, 부하 있음). 걸린 시간을 기록에 남긴다.
- 권한은 두 겹으로 본다: 우리 권한 표, 그리고 Better Auth `userHasPermission`. 다른 관리자 기능과 같다.
- 감사 기록을 쓴 뒤에만 보낸다. 시드가 든 자료라서다.

### 12. 생성기 (출력 변경 없음)
- 새 순수 함수 두 개를 `@terra/planet/generator`에 더한다: `explainBiome`(판정 설명), `summarizePlanet`(면적 가중 요약). 칸 면적 표(`faceAreaTable`)를 내보낸다.
- 둘 다 저장 필드(물·기온·습도·고도)와 바이옴 표만 읽는다. 생성기 다양성 고침도 "바이옴은 저장 필드만의 함수"를 지킨다. 그래서 생성기 판이 바뀌어도 깨지지 않는다.
- 이 일은 생성기 다양성 고침을 합친 뒤에 한다(같은 파일 `generator/index.ts`, 바이옴 판정을 맞춰 보려고).
- 시험: `explainBiome`의 결과가 모든 칸의 저장 바이옴과 같다.

### 13. 화면
- 휴대폰 세로: 지구본 + 아래 판(설정·면적·칸·초안 탭). 가로·넓은 화면: 옆 판(D-6002·D-6003). 폭 경계는 앱 뼈대와 같다(37.5em·64em).
- 화면은 `{ onClose, monitor }`만 받는다(앱 뼈대의 주소 → 화면 표와 같다).
- 문구는 메시지 키(ko·en)다. 키로 고르는 이름표는 편집기 조각 안 표(`editorMessages.ts`)에 둔다.
- 디자인 토큰만 쓴다. 빽빽한 판은 `data-density="compact"`다.
- 화면 시험은 앱 뼈대의 `e2e/`가 생기면 거기에 둔다(`e2e/planet-editor.spec.ts`). 그 전에는 저장소 밖 스크립트로 돌리고 결과를 작업 기록에 남긴다.
- 큰 새 화면이라 `web-design-guidelines`·`impeccable`(audit·polish)·`review-animations`·`break-ui`로 마무리 검토한다(AGENTS 8장).
- 첫 화면 JS는 지연 로딩 껍데기 말고는 늘지 않는다.

### 16. 나중 도구에 넘길 것 (기획 답, 원본 f0e0e71. 1단계 범위 밖)
1절의 "나중 도구"(지형 정보, 출현 분포, 크리쳐 생성 에디터)에 기획이 정한 것이다. 1단계에서 만들지 않는다. 그 도구를 설계할 때 읽는다.
- 지형 정보창(D-214 → D-264): 개발자 창(칸 값, 맞은 규칙, 아깝게 떨어진 조건)과 플레이어 짧은 창("이 땅의 특징": 이름·설명·효과)으로 나눈다. 개발자 창은 이 편집기의 칸 정보창(7절)을 넓혀 쓴다. 특수 지형 설명(지형·생태·지점 층에서 이긴 것, 순위로 진 것, 조항별 판정)은 7절의 "설명 묶음"으로 더한다(ADR 36 "그 뒤 온 기획 답: 특수 지형 층"). 플레이어 짧은 창은 지도 화면(기획 6-3)에 둔다고 읽었다(기술 해석, D-264는 자리를 정하지 않았다). 그래서 이 편집기 범위가 아니다.
- 크리쳐 생성 에디터(D-5024·D-5026)
  - 개발자가 특성(크기·성향·주력 스탯·속성 등)을 고르고 고르지 않은 부분은 자동으로 만든다. 고른 특성마다 스탯 분포 보정 규칙(설정값)을 쓴다(D-5024). 자동 생성 결과는 에디터에서 고칠 수 있다(D-5024 해석).
  - 생성기 안에서 필요한 태그를 그 자리에서 새로 만들어 붙인다(D-5026). 태그를 새로 만드는 권한은 개발자에게 있다(D-5026 해석). 이 도구는 dev·admin만 쓰므로(1절) 따로 막을 것이 없다.
  - 세트 단위로 주력 스탯이 6스탯에 고르게 퍼졌는지 검사한다(D-5024 영향, 기획자 제안).
  - 첫 입력 자료는 `docs/design/51_Creature_Presets.md`다(D-5048, 모두 후보·Assumed). 시트에는 이름(ko·en)·등급·속성 제안만 있어, 넣을 때 코드·태그·크기·기본 속성·허용 아종을 채운다(기술 해석).
  - 기술 제안: 새 태그도 콘텐츠 팩 쓰기다. 그래서 이 편집기처럼 서버 초안 → 내보내기 → 반영(9·10절) 흐름을 쓴다. 태그 코드는 콘텐츠 ID 규칙(영어 snake_case, 한 번 쓴 ID는 다시 쓰지 않음)을 따른다. 자동 생성은 시드로 다시 나오게 하고, 팩에는 결과 값을 저장한다(PLAN 14장 편집기 행).
- 건물 에디터(D-5044): 건물 데이터 = 기능 대분류 + 칸 모양 + 레벨별 {성능, 직무, 수용 인원, 내구도} + 태그. 첫 자료는 옛 BLD-2 목록이다. 같은 `/dev` 아래 도구로 더한다(주소는 1절의 나중 도구 규칙을 따른다, 기술 제안).
- 세력 배치(D-076·D-154, 나중 단계): 세력마다 시작 도시 2~4곳을 표시한다(D-6041 기술 전달 "세력마다 '시작 도시' 표시(편집기 설정)"). 도시별 붐빔 지표와 세력별 지원금 표시는 서버가 세는 값이라 편집기 설정이 아니다(기술 해석, PLAN 14장 "캐릭터 생성" 행).
- 개발자 페이지 공통 틀(D-6048): 왼쪽 표(걸러 보기·정렬) · 가운데 1차맵 겹치기 · 오른쪽 편집 패널, 모든 변경 기록·되돌리기, "한 번만"·"직접 켬"을 고르면 P0 경고. 기획 해석은 같은 틀을 행성 편집기(D-154)와 지형 조건 정보창(D-214)에도 쓰고, 데스크톱용(Assumed)이라 했다.
  - 이 편집기와 맞는 곳: 가운데 지도는 지구본과 평면 미니맵이다. 넓은 화면의 옆 판이 오른쪽 편집 패널에 해당한다.
  - 다른 곳: 이 편집기는 휴대폰 세로(지구본 + 아래 판)도 둔다(13절, 사용자가 휴대폰과 데스크톱 모두에서 다시 본다). 왼쪽 표는 행성 하나를 고치는 이 편집기에 해당하는 목록이 없어 두지 않는다. 세 칸 틀은 출현 분포 도구부터 쓴다(기술 해석). 기록·되돌리기는 초안 판 기록(9절)이 하지만 초안마다 최근 50개만 남기고, 자동 저장마다 감사 기록을 쓰지 않는다. D-6048 "모든 변경은 기록하고 되돌릴 수 있다"보다 좁다. 이 다른 점은 기획에 알린다.
- 세부 수치는 모두 설정값이다(D-5032). 이 도구들이 고치는 값은 콘텐츠 팩 값이고, 반영은 10절 흐름(내보내기 → 에이전트 커밋 → 팩 판 올림 → 배포)이다(기술 해석, PLAN 14장 "설정값" 행). 한 번 반영에 약 5분이 걸려(아래 "결과"의 감수할 점) 실행 중에 바로 바뀌지는 않는다. D-5032 사용자 원문 "언제든지 밸런싱 작업으로 수정가능하다"를 이렇게 읽은 것도 기획에 알린다.
- 관리자 경제 감시(D-6047: 원장 대조·화폐 흐름·경보·NPC 세계 건강도)는 개발자 도구가 아니라 관리자 영역(`/admin`, 운영)이다. 1절의 "관리자 화면(`/admin`)에는 계정·운영 기능만 남긴다"와 같다.

## 이유
- 개발자 도구 한곳: 사용자 결정이다. 관리자 화면은 계정·운영으로 이미 크고, 개발자 도구(편집기, 측정판, 나중의 정보창·분포·크리쳐 편집)는 계속 는다. 주소 하나 아래 모으면 권한·미리 캐시·메뉴 규칙도 한 번만 정한다.
- dev·admin: 사용자 결정이다. 개발자(dev) 계정이 계정 관리 권한 없이 도구만 쓴다. 시드는 dev에게도 보이지만 dev는 팀 계정이다(Assumed).
- 서버 초안: 사용자 결정이다. 휴대폰과 데스크톱이 같은 초안을 본다. 시드가 기기에 남지 않는다. 판 기록으로 되돌릴 수 있다. 대가는 표 2개·마이그레이션·쓰기 경로·충돌 처리다.
- 기기 미리보기: 같은 코드·같은 정의면 기기 F9 결과가 서버 굽기와 같다(Verified: 판 2, Chromium 153). 서버 확인 굽기는 같은 답을 내려고 굽기 한 번에 CPU 약 18~20초와 굽기 워커 메모리 약 190MB를 쓴다(Verified: 판 2 굽기, NAS 18.7초·194MB).
- 엔진을 다시 만드는 쪽이 가장 작다. 엔진을 고치지 않는다.
- 빠른 F5 + 기본 F7: F7은 F9와 땅·바다가 면적의 99.0%, 바이옴이 93.9%에서 같다(Verified: 출력 판 1 조사. 판 2·판 3은 다시 재지 않았다).
- 자동 저장마다 감사 기록을 쓰지 않는 이유: 감사 표는 추가만 된다(DB 트리거). 판 기록이 같은 정보를 지울 수 있는 표에 남긴다.
- 같은 출처 확인: 쓰기 경로가 생기므로 계정 경로와 같은 규칙을 tRPC에도 건다. 하나의 규칙이 모든 쓰기를 덮는 것이 쓰기마다 따로 거는 것보다 빠뜨리기 어렵다.
- 잠금을 행성마다 거는 이유: 팩의 임시 표시는 팩에 하나뿐이다(Verified: `content/core/manifest.json`). 바이옴 때문에 떼면 모든 행성이 한꺼번에 잠긴다.
- 미리 캐시에서 빼는 이유: 개발자만 쓰는 코드를 모든 플레이어가 설치 때 받지 않게 한다.
- 생성기 출력을 이 일에서 바꾸지 않는 이유: 구조 문제(사용자 지형 의견 1)는 생성기 다양성 고침이 맡는다. 같은 파일을 두 줄기가 고치지 않는다.

## 결과
- 좋은 점
  - 편집기가 휴대폰·데스크톱에서 같은 초안을 보고, 판을 되돌릴 수 있다.
  - 엔진·생성기 내부를 고치지 않는다.
  - 개발자 도구가 한 주소·한 폴더·한 권한 규칙 아래 모인다.
  - 칸 정보창과 기기 F9가 D-214 개발자 메뉴의 바탕이 된다.
- 감수할 점
  - 서버 일이 늘어난다: 표 2개, 마이그레이션, tRPC 6개(쓰기 3개), 충돌 처리, 판 기록 지우기.
  - 결과가 바뀔 때마다 화면이 잠깐 비고 방위가 북쪽으로 돌아간다.
  - 미리보기(F7)의 강·바이옴 비율은 F9와 다르다.
  - 반영은 에이전트를 거친다. 한 번에 약 5분이다(Verified: 앞 조사, CI·배포 약 4분 40초 + NAS 굽기).
  - 휴대폰 메모리는 간접으로만 본다.
  - tRPC 같은 출처 확인이 지금 관리자 쓰기에도 걸린다. 같은 출처 화면에서만 부르므로 바뀌는 것은 없을 것으로 본다(Assumed: 화면 시험으로 확인).
- 다시 볼 조건
  - 휴대폰에서 빈 화면이 0.2초를 넘거나 F7이 3초를 넘으면 엔진 원천 바꾸기나 단계 캐시를 본다.
  - 여러 사람이 같은 초안을 고쳐야 하거나 래스터 편집(2단계)이 오면 초안을 나눠 쓰는 규칙을 정한다.
  - 플레이어에게 처음 공개할 때 행성마다 공개 표시와 잠금 규칙을 새 ADR로 정한다.
  - 다른 브라우저 엔진에서 확인 해시가 다르면 그 엔진의 미리보기를 막고 원인을 찾는다.
  - CSP(PLAN 4.8)를 넣을 때 편집기 워커(`worker-src 'self'`)를 허용한다.

### 기획에 물을 것 (기획 세션에 보낸다)
1. 프리셋 단계별 수치는 지금 기술 임시값이다(예: 해수면 군도·보통·대륙 = 육지 15·30·45%, 판 개수 7·13·24개, 강수 55·100·160%). 기획 값으로 바꿀까, 편집기로 조정한 값을 보고 정할까?
2. PLAN 6.2·D-154의 세부 수치 뜻: 「대륙」은 크기·개수·쪼개짐 중 무엇인가? 「극지·적도 비중」은 위도에 따른 기온 곡선 모양인가? 「습도」는 강수와 따로 정하는가? 「수심」은 바다 깊이 등급 경계(지금 실제 60m·200m)인가, 바다 밑 모양인가? 바람은 꼭 설정이어야 하나? 「평균 기온」(D-141)은 설정인가, 적도·극 기온에서 계산해 보여 주는 값인가? 「해수면」은 높이인가, 지금처럼 육지 비율인가?
3. D-156 「공개한 행성의 설정값은 잠근다」와 ADR 10 「편집기 공개 = 새 행성 버전」의 「공개」를 플레이어에게 처음 내보내는 때로 봐도 되나? 잠그는 값은 세부 수치·시드·바이옴 표·색 중 무엇인가? 생성기 판이 바뀌어 공개 행성의 지형이 바뀌는 것은 허용하나(지금 규칙은 플레이어가 손댄 2차맵만 고정, ADR 10)?
4. D-154의 순서(프리셋 → 고도·강·호수 직접 편집 → 세부 수치)는 화면 흐름 순서인가, 직접 편집이 1단계에 꼭 있어야 하나? (사용자는 직접 편집을 2단계로 골랐다)
5. 편집기의 2차맵 미리보기로 무엇을 확인하려 하나(지형 모양, 엄폐물, 자원)? 행성 값으로 2차맵을 만드는 일 뒤로 미뤄도 되나?
6. 편집기에서 사용자가 고른 수치는 기획 확인 전까지 임시값으로 둔다. 이 방식이 맞나, 사용자가 고른 값을 바로 기획 값으로 받을까? → D-5032 뒤 기술 해석: 세부 수치는 확정하지 않는 개발자 패널 설정값이라, 편집기에서 고른 값이 곧 그 설정값이고 언제든 다시 고친다. 이 해석이 맞는지만 확인받는다(10절).
7. 칸 정보창(D-214, 개발자 페이지 D-5020과 같은 줄기)에 1단계부터 꼭 보여야 할 값이 더 있나? 「거의 맞음」 눈금(기온 2°C, 습도 10, 고도 실제 100m)은 기술 제안값이다. 1차맵 개발자 메뉴에도 같은 창을 두는 것이 맞나? → 마지막 물음은 답함: D-264 "개발자·관리자: 행성 생성기와 개발자 메뉴에서 칸 값, 맞은 규칙, 아깝게 떨어진 조건까지 본다". 앞의 두 물음(더 보일 값, 눈금)은 남는다.
