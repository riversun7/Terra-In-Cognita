## 선택지
### 시간과 항성 위치
1. 기기 시계로 계산한다. 기기마다 하늘이 다를 수 있다.
2. 서버가 항성 위치를 메시지로 보낸다. 프로토콜이 바뀌고 계산은 같다.
3. 공용 행성 달력(정수, 결정적) + 서버 시각(기기 시계 + 시계 차이)으로 엔진이 계산한다. 보내는 것이 없다.

### 낮밤 음영
1. 카메라 빛을 항성 방향으로 바꾼다(과장한 지형 법선 그대로). 산이 낮밤 경계를 들쭉날쭉하게 만들고, 밤 쪽 기복이 사라진다.
2. 낮밤은 매끈한 구 법선으로, 기복은 카메라 빛의 경사만 쓴다.
3. 대기 산란까지 계산한다(O'Neil, GPU Gems 2 16장, 2005). 무겁고 요청 밖이다.

### 구름 방식
1. 껍질 구 + 화소마다 노이즈를 매 프레임 계산한다. 코드는 짧지만 화소마다 수백~수천 연산이고, 움직이려면 늘 그려야 한다.
2. 워커에서 JS로 큐브 텍스처를 만든다. 만들기가 느리고(6 × 512² 1.32초, Node 24) JS 사본 1.5MiB가 남는다.
3. GPU에서 가끔 굽는 큐브 렌더 타깃(화면 대신 그리는 텍스처) + 껍질 구 하나. 그리기는 화소당 큐브 읽기 2번(덮임, 해 쪽 두께)이다.
4. 부피 광선 행진, 낱개 구름 판, 지구 구름 사진. 휴대폰에 무겁거나(부피), 유닛 표지와 헷갈리거나(판), 행성마다 쓸 수 없다(사진).

### 구름 노이즈의 원천
1. 셰이더 안 실수 해시(Hoskins "Hash without Sine" `hash13`) 값 노이즈. 시제품이 썼다. 원본 라이선스를 확인하지 못했다(사본들은 MIT 고지, Assumed: 검색 요약). 해시는 GPU 실수 차이에 민감하다.
2. 3D 노이즈 텍스처(64³ R8, 256KiB)를 저장소 `createRng`(`@terra/shared`)로 한 번 만들고, 셰이더는 칸 안 위치만 부드럽게 바꿔 읽는다. 새 라이선스가 없고, 격자값이 모든 기기에서 같다.

### 구름의 시간 흐름
1. 날씨 창마다 바뀌는 정지 구름. 창 안에서는 그대로이고, 창이 바뀔 때 1초 옅어졌다가 새로 굽고 1초에 걸쳐 나타난다.
2. 창 안에서 위도 띠 바람으로 흘리고, 반 창 어긋난 두 위상을 섞는다(흐름 맵 2위상). 텍셀마다 구름을 두 번 계산해 굽기가 2배다. 두 노이즈를 그냥 섞으면 분산이 줄어 구름 양이 출렁인다(아래 이유). 그려 보지 않았다(Unknown).
3. 화소마다 매 프레임 시각을 넣어 계산한다. 늘 그려야 한다(PLAN 5.7과 어긋남).

### 가까이 갈 때 구름
1. 투명해지며 사라진다.
2. 덮임 문턱을 올려 구름이 걷히며 사라진다.
3. 화면 가운데에 구멍을 낸다.

### 달 그리기
1. 화면에 고정한 장식 그림. 돌리면 위상이 따라 돌고 시차가 틀린다.
2. 깊이 시험하는 3D 구 + 먼 자르기 면 늘리기. "지도를 가리지 않음"이 가드(달이 카메라와 행성 사이에 오지 않게 하는 거리 조건)에만 기댄다.
3. 배경 구: 가장 먼저, 깊이 끔, 자르기 z = 0.5·w(두 그래픽 API 모두 자르기 범위 안). 행성이 늘 그 위에 그린다.

### 달의 보이는 축척
1. 실제 비(거리 60.3R, 반지름 0.273R): 사용자 휴대폰 지구본에서 약 10 CSS px로 점이다.
2. 거리 12R, 반지름 0.27R: 약 35~37px.
3. 거리 8R: 약 47px. 아주 좁은 창에서는 가드에 걸려 숨는다.

  - `PLANET_CALENDAR_EPOCH_MS = 1_790_812_800_000`(2026-10-01 00:00 UTC, Verified: 계산). 지난 날짜라 지금 연도·일 수가 음수가 아니다. 정시라 경도 0의 자정이 매 정시 UTC(= 매 정시 KST)다.
  - 출시 전에 기획 답(질문 1)으로 한 번 정하고, 출시 뒤에는 바꾸지 않는다. 바꾸면 연도·나이(D-021)·계절(D-118)이 모두 밀린다(PROTECTED).
- `planetCalendarAt(utcMs)` → `{ msSinceEpoch, dayIndex, msIntoDay, yearIndex, msIntoYear, dayOfYear, season, dayOfSeason }`
  - 나머지 = `((x % D) + D) % D`, 몫 = `(x − 나머지) / D`(늘 정확히 나눠진다). 기원 앞도 맞다.
  - 판정 쪽 입구다. 입력이 받는 시각(안전 정수이고 기원에서 잰 ms도 안전 정수)이 아니면 `RangeError`를 던진다. 판정 쪽 실수를 잡기 위해서다.
  - 2300년까지 정확하다(안전 정수 안, Verified: 조사 계산 15개 통과, Node 24.22.1. 구현 시험은 아래).
  - 계절 번호 0~3 = 북반구 봄·여름·가을·겨울. 남반구 계절 = (계절 + 2) mod 4(D-142, `southernSeason`).
  - 모듈 주석에 적는다: "지역 시각(낮밤)은 판정에 쓰지 않는다(D-142). 판정은 계절만 쓴다(D-118)."
- 화면 쪽 입구 `planetCalendarForDisplay(utcMs)`: 내림(`Math.floor`)한 뒤 `planetCalendarAt`에 넘긴다. 내린 값이 받는 시각이 아니면(NaN·무한대·범위 밖) null이다. 던지지 않는다. 엔진은 이것만 부른다(`sky.ts` `skyAt`).
- 달 위상은 여기에 두지 않는다. 화면만 쓰므로 엔진 `sky.ts`가 `msSinceEpoch`의 정수 ms 나머지로 계산한다. 판정이 쓰게 되면 그때 이 모듈로 옮긴다.
- 서버의 계절 보정(D-118, S2·S3)과 기기 하늘이 이 모듈 하나를 쓴다. 그래서 보이는 계절이 판정 계절과 같다.
- 기기 시각
  - 화면이 `serverNow: () => number | null`을 넘긴다. null은 "시계를 아직 못 쟀다"다.
  - `ServerLink`에 `clockMeasured(): boolean`을 더한다. 지금 `clockOffsetMs()`는 못 쟀을 때 0이라 구분할 수 없다(Verified). 2차맵 보간도 쓸 수 있다.
  - 시계 차이가 x.5ms면 기기 시각이 정수가 아니다. 그대로 `planetCalendarAt`에 넘기면 `RangeError`가 나고, 예약기가 예외를 잡지 않아 지도가 멈춘다(Verified: 코드 읽기. 세션의 약 절반, Assumed: 홀짝 확률). 그래서 화면 쪽 입구가 내린다(위).
  - 하늘 갱신은 `try`로 감싼다. 오류가 나면 하늘만 끄고(off와 같은 모습) 기기 오류 보고를 한 번 남긴다. 지도는 계속 그린다.
  - 못 쟀으면(null) 낮으로 그린다(밤 0, 달·구름은 시작하지 않는다). 재면 0.5초에 걸쳐 켠다. 1차맵을 연 뒤 5초 안에 못 재면 기기 시계로 켜고 통계에 `clock: "device"`로 알린다. WebSocket이 막힌 세션은 끝까지 기기 시계다.
  - 나중에 잰 값이 쓰던 시각과 1분 넘게 다르면 0.5초에 걸쳐 맞춘다. 날씨 창이 바뀌었으면 구름도 다시 굽는다.
  - 시계 차이 오차는 수십 ms로 항성 0.01° 아래다(Assumed).

### 3. 항성 방향 (`packages/engine/src/planet/sky.ts`, 화면용 실수 계산)
- 엔진은 판정 코드가 아니라 `Math` 함수를 쓴다(ADR 36과 같다). 순수 함수이고 단위 시험을 둔다.
- 식(행성 좌표: 북극 +z, 경도 0 = +x, 동쪽 +y. `globeCamera.ts`와 같다)
  - dayFrac = msIntoDay ÷ PLANET_DAY_MS, yearFrac = msIntoYear ÷ PLANET_YEAR_MS
  - 항성의 황도 경도(공전 궤도 위의 각) L = 2π(yearFrac − φ0), 적위(항성이 적도에서 남북으로 떨어진 각) δ = asin(sin ε · sin L)
  - 항성 바로 아래 경도 λs = π − 2π·dayFrac(−π~π로 감음)
  - 항성 방향 s = (cos δ cos λs, cos δ sin λs, sin δ). 그곳 항성 고도의 sin = dot(위쪽, s)
  - 지역 시각(시) = 24·dayFrac + 경도 ÷ 15°(mod 24)
- 임시 행성 값: 자전축 기울기 ε = 23.44°, φ0 = 1/8(계절 가운데가 춘분·하지·추분·동지, 여름 한가운데에 항성이 가장 높다).
- 균시차는 없다. D-091은 지역 시각을 경도로만 정하고, 길이가 같은 계절은 원 궤도로 본다(Assumed).
- 확인(Verified: 조사 계산, 검토가 다시 계산, 구현 시험): 기원에 λs = 180°, +30분 0°, +15분 +90°. 계절 가운데 δ = 0, +ε, 0, −ε. 하지 정오의 항성 고도는 40°N 73.44°, 40°S 26.56°. 고도 식 = 내적(2,000개 무작위, 오차 1e-12 아래).
- 빠르기(Verified: 계산): 항성은 1초에 0.1° 돈다. 낮밤 경계는 적도에서 초속 927m다. 지구본에서는 약 0.3 CSS px/s다(Assumed). 한겨울 극야는 70°에서 실제 약 4.8시간, 80°에서 약 10시간, 극에서 14시간이다.
- 처음 보기(위도 20°·경도 30°)의 지역 시각은 24·dayFrac + 2시라, 여는 시각에 따라 약 절반은 밤이다(Assumed: 계산).

### 4. 낮밤 음영 (선택지 2)
- 낮밤 = 매끈한 구 법선 · 항성 방향(sunCos)이다. 과장한 지형 법선을 쓰지 않는다.
- 기복은 지금 카메라 빛의 경사만 쓴다: relief = dot(n, L) − dot(위쪽, L)(평지 0). 공 모양 가짜 어둡기가 없어지고 밤 쪽에도 기복이 보인다. 항성이 머리 위일 때 기복은 지금과 같다(Verified: 시제품 사진).
- 출발값(시제품 3판, 휴대폰에서 다듬는다)
  - 낮밤 띠: smoothstep(−0.14, 0.06, sunCos) = 항성 고도 −8.0° ~ +3.4°(엔진 `DAY_NIGHT_BAND`, 셰이더와 하늘 시계가 같은 값을 쓴다)
  - 밤 빛 곱: 0.70 × 라벤더 (0.72, 0.76, 1.0). 흰 땅의 휘도는 낮의 약 32%, 눈으로 느끼는 밝기(L*)는 약 63%다(Verified: 계산, 색 관리를 끈 렌더러라 sRGB 값에 곱한다). 2판(0.62)은 휘도 약 25%(L* 약 57%)였다. 처음 적은 "밝기 약 62%"는 파랑 채널 곱일 뿐이었다.
  - 어두운 색 들어 올림 (0.02, 0.02, 0.05), 깊은 밤에만 채도 6% 빼기
  - 박명(해 뜨기 전·진 뒤의 어스름): 좁은 따뜻한 파스텔 띠, 색 곱 (1.0, 0.90, 0.86), 띠 가운데에서 0.5
  - 낮 쪽: 0.94 × (1 − 0.18 × (1 − √max(sunCos, 0)))
  - 물 반짝임은 항성 방향이고 낮 쪽에만 있다
- 밤 바닥(단위 시험으로 지킨다. JS판 식이 셰이더와 같은 값을 낸다)
  - 인접 바이옴 12쌍의 대비가 밤 세기 1에서 낮 대비의 80% 이상이다.
  - 2판은 두 쌍에서 못 지켰다: 초지/온대림 0.77, 열대우림/심해 0.76. 3판(0.70)은 모두 0.81 이상이다(Verified: 계산). 헤드리스 사진에서 3판은 2판보다 조금 밝고 밤 느낌은 남았다(Verified: 사진. 휴대폰 미확인).
  - 원래 낮 대비가 낮은 쌍(초지/사바나 1.06, 타이가/열대우림 1.07)은 밤과 상관없이 낮다. 색표 문제이고 이 ADR 밖이다.
  - 밤 쪽 가장자리: 어두운 바이옴과 우주색(`#1e2a4a`)의 대비는 밤에 1.07~1.7로 떨어진다(Verified: 계산). 지금 대기 띠가 밤 쪽에도 그대로 있어 행성 실루엣이 남는다(Verified: 시제품 사진). 대기 띠를 바꾸는 선택 제안 1을 하게 되면 밤 쪽 띠 세기에 바닥을 둔다.
- 시제품 1판(밤 55%, 채도 18% 빼기)은 가까이서 회색, 박명에서 탁한 갈색이 되어 버렸다(Verified: 시제품 사진).
- 기후 레이어(자료 색·범례)는 낮밤 세기 0.35다. 1.0이면 밤 쪽 범례 색이 탁해진다(Verified: 시제품 사진).
- 가까이에서의 밤 세기(사용자 결정 U1 (나) "가까이선 옅은 밤")
  - 가장 가까이(F9 약 12km)에서 0.6, 거리(목표점에서 카메라까지) 0.5R(F9 약 265km)부터 1이다. 사이는 로그 거리를 따라 smoothstep으로 늘어난다(기울기와 같은 모양, 엔진 `nightStrength`·`CLOSE_NIGHT_RULE`).
  - 그래서 일하는 거리(12~300km)에도 라벤더 밤 기운이 옅게 남는다. 시제품의 18km 사진에서 0.6은 "회색빛 초록"으로 읽혔다(Verified: 사진 `v2-close-night-near06`, 휴대폰 미확인).
  - 2차맵(고정 빛)으로 들어갈 때 밤이면 조명이 조금 바뀐다(0.6 → 0). 밤 세기 1인 (가)보다 작다. 2차맵 낮밤(질문 22)이 정해지면 맞춘다.
  - 0.5R가 가장 가까운 거리보다 가까운 작은 행성(F4, 0.5R 약 8.3km)은 모든 거리에서 1이다.
  - 고르지 않은 것: (가) 모든 거리 1, (다) CesiumJS 기본(카메라와 행성 중심 거리 π/2·R 안 밤 0, π·R 밖 1. Verified: `GlobeFS.glsl` 364~385행, `Globe.js` 기본값, 2026-10-29). 사용자 답은 끝의 "사용자 결정".
- 합성 순서(타일 조각 셰이더)

| 차례 | 무엇 | 밤의 영향 |
|---|---|---|
| 1 | 지형색(바이옴·물·기복) | – |
| 2 | 낮밤 빛 | 곱한다 |
| 3 | 안개(ADR `2026-10-28-fog-and-map-visibility.md`, 아직 없음) | 빛 뒤에 얹는다. 안개는 색을 지우는 쪽(검정·지형만), 밤은 색을 남기는 쪽이다. "밤 + 시야 안"과 "낮 + 시야 밖"이 헷갈리지 않는지 안개 작업 때 사진으로 본다 |
| 4 | 지표 레이어(영역·물류·군사·아이콘)·고른 칸 | 빛 뒤(밤에도 밝다). 지금 고른 칸은 빛 앞에 섞여 밤에 어두워진다(Verified: 코드 순서) → 옮긴다. 빛 뒤 테두리 대비는 밤 4.2~5.1이다(Verified: 계산) |

- 바탕 구(타일이 아직 없는 곳)도 같은 낮밤을 쓴다. 대기 띠는 그대로 둔다(선택 제안 1).
- 하늘을 끄면(off) 지금 식 그대로 그린다. 끔 모드 사진은 지금 사진과 같아야 한다(시험).
- GLSL 조각 `dayNightLight(sunCos)` 하나를 타일·바탕 구·구름이 같이 쓴다. 공용 uniform(`uSunDir` 행성 좌표, `uSunDirView` 보기 좌표, 밤 값)은 지금처럼 타일이 나눠 쓰는 객체에 넣고 프레임마다 한 번 고친다.

### 5. 달
- 임시 달 하나. 화면 연출만이다(조수·사건·밤 밝기 없음).
- 궤도: 같은 달력에서 계산한다(엔진 `sky.ts` `moonAt`).
  - 위상 f = floorMod(t − 기원 − 삭 오프셋, 삭망월(위상 한 바퀴)) ÷ 삭망월(정수 ms라 정확하다).
  - 방향: 황도 경도 L + 2πf, 궤도 기울기 i, 승교점(궤도가 황도를 남에서 북으로 지나는 곳) Ω를 황도 좌표에서 돌린 뒤, 자전축으로 돌려 행성 좌표로 옮긴다. 이 식의 항성은 낮밤 식의 항성과 같다(Verified: 조사 시각 3,000개에서 차이 0, 구현 시험은 기울기 0 삭에서 달 = 항성).
  - 조석 고정: 앞면이 늘 행성 쪽이다.
- 임시 값: 삭망월 7일(실제 7시간, 계절에 한 번, 1년에 4번), 삭 = 계절 첫날(그래서 보름 = 계절 가운데), i = 5°(지구 달 5.145°, NASA NSSDC 자료, Assumed: 검색 요약), Ω = 0 고정, 모습 시드 고정.
- 보이는 축척(화면 표현 값이고 항성계 규모가 아니다): 거리 12R, 반지름 0.27R(선택지 2). 사용자 휴대폰 지구본에서 약 35~37 CSS px다.
  - 가드: 거리 − 2 × 반지름(11.46R) > 카메라의 행성 중심 거리 상한(세로 6.94R, 가로 3.36R). 그러면 달이 카메라와 행성 사이에 오지 않는다(Verified: 저장소 카메라 함수로 2만 번 모의, 검토가 `globeLimits` 식으로 다시 계산, 구현 시험).
- 그리기
  - `SphereGeometry` 32×16(삼각형 960), 텍스처 없음. 파스텔 바다 3개·크레이터 15개를 물체 공간 원판(uniform 배열)으로 그린다(D-064).
  - 빛은 공용 `uSunDirView`라 위상이 저절로 맞다. 어두운 쪽은 라벤더 행성빛 + 가장자리 빛으로 삭에도 실루엣이 남는다.
  - `depthTest: false`, `depthWrite: false`, `renderOrder = −10`, `frustumCulled = false`, 꼭짓점 셰이더 끝에서 `gl_Position.z = 0.5 * gl_Position.w`. WebGL 자르기 범위는 [−w, w], WebGPU는 [0, w]라 0은 WebGPU의 앞 자르기 면 경계다. 0.5·w는 둘 다 안쪽이다.
  - 그래서 타일·바탕 구가 늘 그 위에 그린다. 달은 하늘과 행성 가장자리 뒤에서만 보이고 지도를 가리지 못한다. 엔진의 near·far는 그대로다. CesiumJS 달과 같은 방법이다.
  - 첫 표시 뒤 숨긴 채(`visible = false`) 만들고 `renderer.compileAsync`로 미리 컴파일한다. three 0.186.1의 `compile`은 숨긴 메시의 재질도 모은다(Verified: `three.module.js` `compile`이 재질을 `scene.traverse`로 모은다).
- 보일 때만 그린다(아니면 `visible = false`, 비용 0)
  - 하늘 모드가 clock·fixed이고, 시계를 쟀거나 기기 시계로 켰고, 틈 찾기가 아니고, 첫 표시 뒤다.
  - 화면 네 모서리 광선 중 하나라도 행성(반지름 R)을 비킨다. 행성의 화면 모양이 볼록이라 정확하다(`skyOnScreen`).
  - 달 구가 화면 옆 네 평면 안에 들고, 가드를 지키고, 행성 원판 뒤에 다 가리지 않는다(`moonOnScreen`. 마지막 조건은 구현하며 더했다).
  - 거리 문턱은 쓰지 않는다. 가로 화면에서는 0.47R(252km)까지 달이 보일 수 있다(Verified: 모의, 구현 시험은 0.47R에서 하늘이 보임).
- 세로 휴대폰 지구본에서 달이 화면에 있는 시간은 약 3%다(가로·데스크톱 6~10%, Verified: 모의). 사용자는 그대로 두기로 했다(사용자 결정 U3: 달 찾기 단추·위상 줄 없음).
- 일식·월식은 그리지 않는다. 이 축척과 임시 값에서는 너무 잦다: 보름 4번이 모두 월식(춘·추분 보름 2번은 개기, 하·동지 보름 2번은 부분)이고, 삭 4번도 모두 일식이다(달 그림자 축이 행성 중심에서 0.74R)(Assumed: 계산, Ω = 0·삭망월 = 계절이라 해마다 같다). 일식 그림자(폭 약 230km)는 지도를 가린다. 드문 사건으로 쓸지는 기획 질문 12다. 달빛도 없다.
- 누르기는 그대로다. 달 화소는 행성 밖이라 누르면 null(행성 밖)이다.
- 여럿이 되면 깊이 없이 먼 것부터 그린다(4개 이하).

### 6. 구름 (선택지 3)
- 노이즈: 3D 노이즈 텍스처(노이즈 원천 선택지 2)
  - 64³ R8(256KiB), 되풀이(REPEAT), 삼선형. 격자값은 행성 시드로 `createRng`(mulberry32, `@terra/shared`)가 만든다. 처음 굽기 전에 한 번 만든다.
  - 셰이더는 칸 안 위치를 smoothstep으로 바꾼 자리를 읽는다(값 노이즈 한 번 = 텍스처 읽기 한 번). 격자 자국은 헤드리스 경위도 그림에서 보이지 않았다(Verified: 사진).
  - 실수 해시(`hash13`)는 쓰지 않는다. 다시 쓰게 되면 원본 라이선스를 열어 확인하고 `THIRD_PARTY_NOTICES.md`에 행을 더한다.
- 굽기
  - `WebGLCubeRenderTarget(512, { format: RedFormat, type: UnsignedByteType, generateMipmaps: true, minFilter: LinearMipmapLinearFilter, depthBuffer: false })` 하나(GPU 2.0MiB, JS 사본 없음, 이중 버퍼 없음).
  - 전체 화면 삼각형 하나로 면을 그린다. 면 방향은 OpenGL ES 3.0 표 3.21을 거꾸로 푼 식이다(셰이더·JS가 같은 식, 시험).
  - 셰이더: fbm(여러 크기 노이즈의 합) 6옥타브(크기 단계). 휘기(뭉게 모양)는 낮은 옥타브만: 3옥타브 fbm 3개로 자리를 휘고 6옥타브 fbm을 읽는다(텍셀당 노이즈 15번). 여기에 기후 치우침을 곱하고 문턱을 뺀다.
  - 쉬는 프레임마다 면 하나를 굽는다. 굽는 동안 껍질은 숨긴다. 밉맵(줄인 텍스처 단계)은 여섯째 면 뒤에 한 번 만든다.
  - R8 렌더 타깃을 쓸 수 없으면 구름을 끄고 기기 오류 보고에 한 번 남긴다. R8은 WebGL2에서 늘 색 렌더·필터가 되므로(Assumed: ES 3.0 표, 검색 요약) RGBA8 대체 경로는 두지 않는다.
  - 굽기·껍질 프로그램은 첫 표시 뒤 `renderer.compileAsync`로 미리 컴파일한다.
- 기후 치우침
  - 바다: 위도 띠. 적도 수렴대·중위도 폭풍대는 흐리고 아열대는 맑다. 생성기 `zonalPrecipitation`과 같은 모양이다.
  - 땅: 습도. 마른 땅은 맑고 습한 땅은 흐리다.
  - 땅·습도는 첫 단계 타일(맵 레벨 F−4)로 만든 RG8 기후 큐브에서 읽는다. 면당 2^(F−4)칸(64칸 상한), F9는 약 12KB다.
  - 첫 단계 타일은 시야 밖 면을 받지 않으므로 늘 있지 않다. 그래서 첫 표시 뒤 첫 단계 타일 모두를 낮은 우선의 "늘 원함"으로 받는다(`tilePipeline`에 취소하지 않는 작은 기능, 시험). F ≤ 9는 6개(하나 약 8.3KB, 압축 전), F10은 24개다. 첫 단계는 이미 `evict`가 버리지 않는다.
  - 처음 굽기는 첫 단계 타일이 다 오거나 10초가 지난 뒤다. 그때 없는 타일은 바다로 본다(위도 띠만).
  - F11(96개, 약 800KB)은 다 받지 않는다. 받은 타일만 쓰고 날씨 창이 바뀔 때마다 큐브를 다시 만든다. 그 행성에서 "같은 구름"은 근사다.
  - 밉맵 한 단계 위로 읽고 노이즈로 찾는 자리를 흔든다. 해안선 모양이 구름에 찍히지 않게 하려는 것이다.
  - 타일 형식·서버·목록 정보는 그대로다. 1차맵 지형은 공개 자료라 습도를 따라도 숨김 정보가 새지 않는다(ADR `2026-10-28-fog-and-map-visibility.md`). 안개가 들어오면 가 보지 않은 곳(검정) 위 구름이 대륙 모양을 비출 수 있다. 정보 문제가 아니라 보기 문제라 안개 작업 때 정한다(그곳은 위도 띠만 쓰는 것이 후보).
  - 계절에 따라 적도 수렴대를 옮기는 일(±6~8°)은 기획 답(질문 20) 뒤에 켠다.
- 시간과 흐름(구름 시간 흐름 선택지 1)
  - 날씨 창(임시 3시간, 실제 시간) 안에서는 구름이 그대로다. 창 번호는 서버 시각에서 JS(64비트)로 계산하고(달력의 `msSinceEpoch`), 창 번호 → `createRng` → 노이즈를 읽는 자리 오프셋으로 넘긴다. 서버 ms를 32비트 uniform으로 넘기면 1.79e12에서 간격이 131,072ms라 쓸 수 없다(Verified: 계산).
  - 창이 바뀌면 껍질을 1초에 걸쳐 숨기고, 쉬는 프레임마다 면 하나씩 다시 구운 뒤, 1초에 걸쳐 보인다. 손가락 동작 중이거나 끝난 지 300ms가 안 됐으면 옛 구름을 둔 채 미룬다.
  - 창 안에서 흘리지 않는 이유: 지구본에서 바람 흐름(약 시속 72km)은 약 90초에 1화소라 보이지 않는다. 흐름 맵 2위상은 굽기를 2배로 하고 그려 보지도 않았다(Unknown). 다시 열면 날씨가 바뀌어 있는 것은 창 바꾸기로 충분하다(Assumed).
  - 다시 굽는 때: 처음, 창이 바뀔 때, 컨텍스트 복구 뒤(렌더 타깃 내용은 복구되지 않는다), 시계를 늦게 재서 창 번호가 바뀌었을 때. 90초마다 다시 굽기는 하지 않는다.
  - 행성 시드 = 목록 정보 `definitionHash` 앞 8자리. 정의(바이옴 규칙 등)를 고치면 지형도 바뀌므로 구름이 다시 섞여도 된다(의도). 목록 정보에 행성 시드 필드가 생기면 그것으로 바꾼다.
- 껍질
  - `SphereGeometry(1, 128, 64)`를 꼭짓점 셰이더에서 R + 높이로 키운다. 높이 = 600 게임 m × 고도 과장(기본 ×6 = 3.6km)이고, 대기 띠 두께(0.018R)의 0.9배 아래로 묶는다. 과장을 바꿔도 산과 구름의 관계가 같고, 아주 높은 봉우리만 구름을 뚫는다.
  - 위치 = 행성 중심 − 카메라(64비트 뺄셈). 큐브는 물체 공간 방향으로 화소당 2번 읽는다(덮임, 해 쪽으로 조금 옮긴 자리 = 두께 음영).
  - `transparent`, `depthWrite: false`, 깊이 시험 켬, `FrontSide`, 대기 띠 다음에 그린다. 먼 자르기 면을 정하는 바깥 반지름에 구름 반지름을 넣는다.
  - 색: 흰색, 두꺼운 곳만 조금 어둡게. 밤 쪽은 같은 낮밤 조각으로 라벤더로 어둡게 하고 불투명도 × 0.55(땅이 보이게). 가장자리(시선과 거의 직각)는 옅게 해 대기 띠와 하얀 고리가 겹치지 않게 한다.
  - 고른 칸 둘레는 비운다: 고른 칸 방향·각 반지름 uniform 하나로 그 둘레의 불투명도를 0으로 한다(비용 거의 0).
  - 최대 불투명도 0.8, 덮임 문턱 0.44~0.64(시제품 값, 휴대폰에서 다듬는다).
- 가까이 갈 때(가까이 갈 때 구름 선택지 2, 걷히기, 엔진 `cloudFade`)
  - u = smoothstep(1.2R, 2.5R, 거리). 덮임 문턱을 +0.24 × (1 − u) 올리고 불투명도는 × √u다.
  - u = 0이면(F9: 637km 안쪽) 껍질 `visible = false`다. 일하는 거리(12~637km)에는 구름이 없다.
  - 투명해지며 사라지는 방식은 900km에서 지도 전체가 뿌연 안개가 됐다. 걷히는 방식은 남은 구름이 또렷하고 지도가 더 많이 보였다(Verified: 합친 시제품 사진 비교).
- 끄는 곳: 기후 레이어, 틈 찾기, 하늘 off. 앞으로 올 지표 레이어(영역·물류 등)에서 끌지는 기획 답(질문 18)으로 정한다.
- 구름 그림자(땅에 지는 그림자)는 넣지 않는다(사용자 결정 U2). 타일 셰이더는 구름 큐브를 읽지 않는다.

### 7. 쉬는 동안 다시 그리기
- 하늘 시계 하나를 둔다. 보이는 하늘이 바뀔 때만 돈다(엔진 `skyClockIntervalMs`).
  - 밤 세기가 0보다 크고 낮밤 띠가 화면에 있으면 1.7초 ÷ 밤 세기마다 한 번 그린다. 1.7초는 지구본(F9 세로 휴대폰)에서 경계가 0.5 CSS px 움직이는 시간이다(경계 초당 약 0.3px). 한 화소의 밝기는 그 땅의 항성 고도로만 바뀌어 거리와 상관이 없다. 그래서 가까이서도 같은 밝기 걸음을 밤 세기로 나눠 쓴다: 밤 세기 1(지구본, 거리 0.5R 밖)은 1.7초, 가장 가까이(0.6)는 약 2.8초다. 한 걸음의 밝기 변화는 낮의 약 0.5%(띠 가운데)~1.3%(항성이 지평선에 걸린 곳)다(Assumed: 3판 식으로 계산, 휴대폰 미확인).
  - 띠 없이 낮 쪽만 보이면 4초(가장 느린 간격)마다. 낮 쪽 밝기도 항성 높이를 따라 천천히 바뀐다(한 걸음 0.3% 이하, Assumed: 계산). 오래 쉰 뒤 첫 손가락 동작에서 밝기가 튀지 않게 하려는 것이다.
  - 밤 쪽만 보이면 바뀌는 것이 없어 멈춘다.
  - 달이 화면에 있으면 한 걸음 0.5 CSS px다. 달은 초당 1.0~1.5px라 0.33~0.5초다(Verified: 모의).
  - 간격은 위 가운데 가장 짧은 것이고, 0.25~4초로 묶는다.
  - 띠가 화면에 있는지는 화면 표본 5×5의 항성 고도 범위로 본다. 행성을 비킨 시선은 그 쪽 가장자리 점을 본다(`sunCosRangeOnScreen`).
- 가까운 거리에서는 화면 전체가 낮이거나 밤인 때가 많다: 밤이면 멈추고, 낮이면 4초, 띠가 지나가는 동안(적도에서 약 2분)만 약 2.8초에 한 번 그린다. U1 (나)라 일하는 거리에서도 시계가 돈다.
- 구름이 옅어지거나 나타나는 2초(날씨 창이 바뀔 때, 3시간에 한 번)와 시계를 잰 뒤 밤이 켜지는 0.5초는 움직임이라 프레임마다 그린다.
- 멈추는 때: 숨긴 탭, 컨텍스트 잃음, 화면 닫음, 하늘 off, fixed 모드(시각이 멈춰 있다. 구름도 한 번만 굽는다), 시계를 재기 전(낮으로 그린다), 밤 쪽만 보이고 달이 없을 때. 손가락 동작 중의 프레임은 늘 지금 하늘을 쓴다.
- 기기의 "동작 줄이기"(`prefers-reduced-motion: reduce`)가 켜져 있으면 화면이 `fixed`(1차맵을 연 시각)를 넘긴다. 하늘이 움직이지 않는다. 설정이 바뀌면 `setSky`로 바꾼다.
- WCAG 2.2 성공 기준 2.2.2(멈춤·정지·숨김): D-142로 밤은 연출이라 "꼭 필요한 움직임" 예외가 아니다. 저절로 바뀌는 하늘에는 화면 안에서 멈추거나 숨기는 수단이 있어야 한다(Assumed: W3C 해설 검색 요약, 원문을 열지 못함).
  - 설정 스위치는 `user_settings` 열·마이그레이션·tRPC·문구 ko·en이 드는 일이라 이 ADR 범위 밖이다.
  - 출시 전 설정 화면 작업에서 "하늘 연출 줄이기"를 넣는다(PLAN 14장 할 일). 그때까지 이 기준은 미충족이다(Assumed 판단). 엔진은 `setSky`로 바로 받을 수 있다.

### 8. 엔진 바깥 모양 (모두 선택)
```ts
/** 하늘 보기(화면이 정한다). 없으면 off = 지금 모습(카메라 빛, 밤·달·구름 없음) */
export type PlanetSkyMode =
  | { readonly kind: "off" }
  | {
      readonly kind: "clock";
      /** 서버 시각(ms). null이면 시계를 아직 못 쟀다(낮으로 그린다). 소수여도 된다(엔진이 내림한다) */
      readonly serverNow: () => number | null;
      readonly features?: PlanetSkyFeatures;
    }
  | { readonly kind: "fixed"; readonly utcMs: number; readonly features?: PlanetSkyFeatures };

/** 켤 요소. 기본은 모두 켬. 휴대폰 켬·끔 비교와 대체 경로에 쓴다. 구름 그림자는 없다(사용자 결정 U2) */
export interface PlanetSkyFeatures {
  readonly dayNight?: boolean;
  readonly moon?: boolean;
  readonly clouds?: boolean;
}
```
- `PlanetEngineOptions.sky?: PlanetSkyMode`
- `PlanetEngine.setSky(mode: PlanetSkyMode): void`: 실행 중에 모드·요소를 바꾼다. 세기 uniform을 바꾸고 달·구름 자원을 만들거나 버린다. 타일 프로그램은 다시 컴파일하지 않는다(시험: 바꾸기 전후 `renderer.info.programs.length`). 동작 줄이기·앞으로의 설정·편집기 계절 미리보기가 엔진을 다시 만들지 않게 하려는 것이다. 엔진을 다시 만들면 타일 파이프라인·GPU 자원·셰이더를 모두 새로 한다(three는 쓰는 재질이 0이 되면 GL 프로그램을 지운다, Verified: 검토).
- `PlanetDescription.sky?: PlanetSkyDescription`: 자전축 기울기, 계절 위상 φ0, 달 목록(삭망월·삭 오프셋·궤도 기울기·승교점·보이는 거리·반지름·모습 시드). 없으면 엔진의 `PLACEHOLDER_PLANET_SKY`(임시 값, `[임시]` 주석)다. 나중에 목록 정보의 선택 필드 `sky`에서 온다.
- `PlanetDescription.skySeed?: number`: 구름 시드(u32). 화면이 목록 정보 `definitionHash` 앞 8자리로 만든다(이미 있는 값). 없으면 0.
- `PlanetStats.sky`: 모드, 시계 상태(`waiting`·`server`·`device`·`fixed`·`off`), 하늘 시각, 항성 바로 아래 위도·경도, 낮밤 세기, 그린 달 수, 구름 불투명도, 굽기 횟수·면 하나 굽기 최대 시간, 하늘 GPU 메모리 추정(타일 상한 64MB와 따로 센다).
- 파일 나누기
  - `sky.ts`: 순수 계산과 타입(항성·달 위상·달·낮밤 세기·구름 걷힘·보임 판정·하늘 시계 간격, `PlanetSkyMode` 등). 타입은 WP3에서 `planetTypes.ts`·`index.ts`가 다시 내보낸다.
  - `skyController.ts`: 프레임마다 uniform·달·구름을 놓고 하늘 시계를 돌린다. 오류 가두기(2절)도 여기다.
  - `moon.ts`, `clouds.ts`: 메시·재질·굽기. `cloudNoise.ts`: 3D 노이즈 격자값(순수 함수, 시험)
  - 셰이더 조각은 `planetMaterials.ts`(325줄)에 두고, 550줄을 넘으면 `skyShaders.ts`로 뺀다.
  - `planetEngine.ts`에는 몇 줄만 더한다(600줄 경고 아래. sharpness 가지가 5줄을 더한다).
- 화면을 닫을 때 렌더 타깃·노이즈 텍스처·기후 큐브·껍질·달을 모두 버린다. 렌더러는 2차맵이 이어 쓰므로 버리지 않으면 GPU 메모리가 샌다.
- TSL로 옮길 길을 막지 않는다
  - 새 재질은 `onBeforeCompile` 없이 `ShaderMaterial` 하나씩이다. 조각은 uniform과 기하 법선만 쓰는 순수 함수다.
  - 달의 z = 0.5·w는 TSL `vertexNode`로, 굽기는 WebGPU `CubeRenderTarget` + `setRenderTarget(rt, face)`로, 껍질은 `cubeTexture`로, 노이즈는 `texture3D`로 옮긴다(Verified: three 0.186.1 꾸러미 코드). WebGPU `unclippedDepth`(선택 기능)에는 기대지 않는다.

### 9. 1차맵 화면이 넘기는 것
- `sky: { kind: "clock", serverNow }`. `serverNow`는 새 순수 모듈 `apps/game/src/map/planetSky.ts`(시험)가 만든다: 시계를 쟀으면 `Date.now() + clockOffsetMs()`, 못 쟀으면 null, 연 뒤 5초가 지나면 기기 시계.
- 동작 줄이기면 `{ kind: "fixed", utcMs: 연 시각 }`(7절).
- 주소 매개변수(시험·측정용, 화면 문구 없음). 읽기는 `planetSky.ts`에 둔다. 모두 `packages/shared/src/routes.ts` `map_planet.search` 표와 `routes.test.ts`에 더한다(표에 없는 검색어는 주소를 다시 만들 때 빠진다, Verified). sharpness 가지의 `pixel-ratio`도 표에 없으면 같이 넣는다.
  - `?planet-time=<ISO 시각 또는 정수 ms>` → `{ kind: "fixed" }`. 정수로 내림한다. 틀린 값은 무시한다(사진·시험이 시각에 따라 바뀌지 않게).
  - `?planet-sky=off` → 하늘 끔
  - `?planet-sky-skip=night,moon,clouds` → 고른 요소만 끔(휴대폰 켬·끔 비교)
  - `?planet-sky-bench=<1|2|4>` → 재기 모드(10절): 프레임마다 장면을 k번 그리고, 그리기·굽기 뒤 `gl.readPixels` 1화소로 GPU 끝을 기다린 시간을 잰다. three `readRenderTargetPixels`는 R8 타깃을 읽지 못하므로 직접 부른다(Verified: `textureFormatReadable`).
  - `?planet-debug=cracks`는 하늘을 끈다(자홍색 틈 찾기가 그대로 보이게).
- 성능 보고 화면 이름: 하늘을 끈 비교는 `planet-map:sky-off`, 재기 모드는 `planet-map:sky-bench`로 따로 보낸다(`nas-metrics`가 나눠 본다. 화면 이름은 자유 문자열이라 프로토콜 변경 없음, Verified: 검토).
- HUD 성능 판: 하늘 줄은 재기 모드에서만 보인다(sharpness 가지의 픽셀 비율 줄까지 더하면 390px 판이 8줄이 된다). 메시지 키 `planet_perf_sky`, 값은 숫자만 넣는다(방위 글자를 넣으려면 메시지 키로 한다).
  - ko "하늘 {lat}°, {lon}° · 굽기 {bake}ms · 달 {moons} · {mb}MB", en "Sky {lat}°, {lon}° · bake {bake} ms · moons {moons} · {mb} MB"
- `data-*`(Playwright): `data-sky`, `data-sky-clock`, `data-sun`(위도·경도), `data-night`, `data-moons`, `data-cloud-opacity`, `data-cloud-bakes`, `data-cloud-bake-ms`.
- 편집기(ADR `2026-10-29-planet-editor-stage1.md`)는 아무것도 넘기지 않는다 → 지금 모습. 편집기 코드는 엔진 설명을 직접 만들고 하늘을 넘기지 않는다(Verified: 검토). 계절 미리보기가 필요하면 나중에 `fixed` + `setSky`를 쓴다.
- `planetDescriptionOf(manifest)`가 `skySeed`(정의 해시 앞 8자리)를 더한다. 목록 정보에 `sky`가 생기면 그것도 넘긴다(지금은 없다).

### 10. 성능 상한과 재는 법
- 하늘을 넣기 전에 sharpness 가지(상한 2)를 합치고, 하늘 없는 1차맵을 사용자 휴대폰에서 다시 잰다. 그 값이 기준선이다. 하늘 측정은 상한 2(기본)와 `?pixel-ratio=1.5` 둘에서 한다.
- 120Hz 화면에서 rAF 간격은 GPU 일이 8.3ms 안이면 그대로 8.3ms이고 넘으면 16.7ms로 뛴다(Assumed: 수직 동기 일반 동작). 앱 프레임 측정기(rAF 간격)와 엔진 몫(화면 스레드 CPU 시간)은 GPU 시간을 재지 않는다(Verified: `frameMonitor.ts`, `renderStats.ts`). GPU 시간 확장(`EXT_disjoint_timer_query_webgl2`)은 안드로이드에서 거의 없다(Assumed: web3dsurvey·caniuse 검색 요약). 그래서 GPU 몫은 재기 모드로 잰다.

## 이유
- 외부 자료는 모두 2026-10-29에 읽었다. "검색 요약"은 원문을 열지 못하고 검색 결과 요약으로만 본 것이라 Assumed로 적는다(이 세션 네트워크 설정에서 en.wikipedia.org·arxiv.org·cesium.com·w3.org 등이 막혔다). 시제품 수치는 헤드리스 Chromium + SwiftShader(소프트웨어 그리기, 4 vCPU 공유)라 휴대폰 값이 아니다.
- 공용 정수 달력(선택지 3): 판정 계절(D-118)과 보이는 계절이 같은 함수에서 나온다. 결정적이고(정수, 결정성 검사), 프로토콜이 바뀌지 않는다. D-5030의 "모든 시간은 실제 시간"과도 맞는다(행성 하루 = 실제 1시간).
- 입구를 둘로 나누고 하늘 오류를 가두기: 판정용 달력은 실수를 잡으려고 던져야 하지만, 화면 시각은 원래 소수가 섞인다. 화면 쪽 입구 한 곳에서 정수로 만들고, 하늘 오류가 지도 전체를 멈추지 않게 한다. 사진 시험은 모두 정수 `?planet-time=`이라 이 길을 타지 않았다. 그래서 소수 시계 차이 단위 시험을 따로 둔다.
- 시계를 맞추기 전에는 낮: 0으로 쓴 차이와 잰 차이를 가를 수 없으면, 기기 시계가 몇 분 틀린 기기에서 하늘이 한 번 튄다(1분에 항성 6°, 30분이면 낮밤이 뒤집힌다, Assumed). 낮으로 시작해 0.5초에 걸쳐 켜면 튐이 보이지 않는다.
- 낮밤을 매끈한 구 법선으로: 과장한 산이 경계를 흔들지 않고, 밤 쪽 기복이 남는다. CesiumJS(`GlobeFS.glsl`: 측지 법선으로 낮밤, Verified: main 가지 원문, 2026-10-29)와 three.js `webgpu_tsl_earth` 예제(`normalWorldGeometry · sun`, Verified: dev 가지, 2026-10-29)가 같은 방법이다. 지도 음영의 관례도 왼쪽 위 빛이다(Esri 기본 방위 315°·고도 45°, Assumed: 검색 요약).
- 밤 0.70·라벤더·대비 바닥: D-063·D-070 ①은 밤을 어둡게 하되 화풍은 그대로 두라고 한다. G12·D-5019는 검정 대신 라벤더다. D-064는 실루엣과 색이 뚜렷하라고 한다. 1차맵은 지표 레이어 화면이라(D-055) 읽을 수 있어야 한다. 그래서 밤의 바닥을 숫자로 정하고 시험으로 지킨다.
- 가까이선 옅은 밤(U1 (나)): 사용자가 골랐다. 1차맵을 가장 자주 보는 가까운 거리(D-6017·D-6018)에도 밤 분위기가 옅게 남아 거리마다 하늘이 이어진다. 밤 세기 0.6이면 밤 1보다 이웃 바이옴 대비가 높다(검토 계산의 2판 값: 초지/온대림 밤 1 1.52, 0.6 1.74). 2차맵 전환의 조명 차는 (가)보다 작다. 기술 권고였던 (다)는 전환 튐이 없지만 일하는 거리가 늘 낮이었다.
- 구운 구름 큐브(선택지 3)
  - 그리기 비용이 화소당 큐브 읽기 2번이다. 헤드리스에서 화소마다 fbm 6옥타브의 약 1/3, 휘기의 약 1/8이었다(Verified, 1번 읽기 기준). 실제 GPU는 텍스처가 더 싸서 차이가 더 크다고 본다(Assumed: 10~20배).
  - 쉬는 동안 비용이 0이다. 늘 그리는 방식은 120Hz에서 사용자 휴대폰 GPU 시간의 약 16~31%를 쓴다(Assumed: 계산).
  - JS 워커보다 굽기가 약 10배 빠르고(Verified: 헤드리스 137ms 대 Node 1.32초) JS 사본이 없다.
  - three 0.186.1에서 R8 큐브 렌더 타깃 면별 그리기·밉맵, `samplerCube` bias 읽기, 데이터 큐브 텍스처 올리기, R8 3D 텍스처 삼선형 읽기가 오류 없이 돌았다(Verified: 헤드리스 시제품 3개). 면 방향 식은 선형 함수를 구워 읽은 오차 0.022로 확인했다(면이 뒤집히면 0.1 넘음). WebGL2 큐브 필터는 늘 이음매가 없다(Assumed: 검색 요약 — Mesa 커밋, KhronosGroup/WebGL 이슈 #1528, ES 3.0 부록 F.2).
  - 기후를 따라 행성마다 그럴듯하다. 합친 시제품에서 큰 사막은 맑고 바다 띠는 흐렸다(Verified: 사진). 다만 그 가짜 행성은 사막이 아열대 맑음 띠와 겹쳐 땅 습도의 몫을 따로 보기 어려웠다(Unknown: S2 시험 행성에서 다시 본다).
  - 부피 구름(Horizon Zero Dawn, Schneider SIGGRAPH 2015·Nubis 2022)은 콘솔에서 약 2ms인 방식이다(Assumed: 검색 요약). 우주에서 보는 지도에는 이득이 작고 휴대폰 WebGL에 무겁다(Assumed).
- 3D 노이즈 텍스처: 라이선스를 새로 확인할 것이 없고(저장소 `createRng`), 격자값이 기기와 무관하게 같아 "같은 구름"에 보탬이 되고, 실제 GPU에서 굽기 연산이 크게 준다(Assumed). 모양은 실수 해시판과 비슷했다(Verified: 헤드리스 경위도 그림 3장 비교).
- 면 나누기 굽기: 채택한 휘기판의 굽기는 휘기 없는 값의 약 2배다(Verified: 헤드리스). 중급 휴대폰에서 6면을 한 번에 구우면 수십 ms짜리 GPU 일 하나다. 모바일 GPU는 대개 중간에 끊어 넘기지 못해 브라우저 화면 합성까지 멈춘다(Assumed). 면 하나씩이면 쉬는 프레임 하나에 든다.
- 창 안 정지 구름: 흐름 맵 2위상(Vlachos "Water Flow in Portal 2", SIGGRAPH 2010, Assumed: 검색 요약)은 굽기를 2배로 한다. 서로 무관한 두 노이즈 A·B를 w : 1 − w로 섞으면 분산이 w² + (1 − w)²배라 w = 0.5에서 표준편차가 약 29% 준다. 평균보다 높은 문턱(0.44~0.64)에서는 구름 양이 반 창마다 줄었다 는다(Assumed: 계산). 나중에 쓰게 되면 분산을 지키며 섞는다: (wA(A − m) + wB(B − m)) ÷ √(wA² + wB²) + m.
- 걷히는 사라지기: 900km 사진에서 투명 방식은 안개처럼 보였고 걷히는 방식이 지도를 더 많이 보여 줬다(Verified: 합친 시제품).
- 637km 안쪽 구름 없음: 그 거리는 맵 레벨 9가 화면을 덮는 일하는 거리다(ADR 36). D-6020의 지표 층을 가리지 않는다.
- 구름 그림자 없음(U2): 사용자가 골랐다. 위에서 내려다보면 그림자 대부분이 구름 바로 밑이라 구름에 가려 차이가 작고(조사), 타일 셰이더·시험이 단순하다.
- 배경 달: 깊이를 끄고 먼저 그리므로 기하가 틀려도 지도를 가릴 수 없다. near·far를 바꾸지 않아 지형 깊이 정밀도도 그대로다. CesiumJS가 같은 방법이다(`Moon.js`: `depthTestEnabled: false`, `Scene.js`: 지구 그리기 전 환경 단계, Verified: main 가지 원문, 2026-10-29).
- 달 12R: 실제 비는 점(약 10px)이고 8R은 좁은 창에서 숨는다. 12R은 크기(약 35px)와 가드를 함께 지킨다. 화면 고정 장식 달은 버렸다: 돌리면 위상이 돌고 시차가 틀린다.
- 달 그대로(U3): 사용자가 골랐다. 달은 지도를 가리지 않는 배경으로만 남고, 문구·화면 일이 없다.
- 일식·월식 없음: 축척을 줄여서 너무 잦다(Assumed: 계산). 기획 결정도 없다.
- 하늘 시계: 지구본에서 경계는 초당 약 0.3px, 달은 1.0~1.5px다. 그 빠르기면 0.5px 걸음이 눈에 띄지 않는다(Assumed). 한 화소의 밝기 변화는 거리와 상관이 없어(그 땅의 항성 고도로만 바뀐다) 가까이서도 같은 밝기 걸음을 쓴다. 사용자 휴대폰 엔진 2.4ms 기준으로 2초에 한 번은 1% 아래다(Assumed).
- 기본 off: 편집기는 지형을 보는 도구라 반쪽이 어두우면 안 된다. 지금 시험·사진도 그대로 둔다.
- TSL: 같은 방법이 TSL에도 있다(`webgpu_tsl_earth`, three 0.186.1의 `vertexNode`·`cubeTexture`·`texture3D`·`CubeRenderTarget`). 셰이더 언어 결정을 막지 않는다.

## 결과
### 좋은 점
- 사용자 요청 셋이 들어간다. 판정·서버·프로토콜·타일 형식·첫 화면 JS는 그대로다.
- 판정이 쓸 계절 달력이 미리 한 곳에 생긴다(D-118). 서버와 기기가 같은 값을 낸다.
- 하늘을 끄면 지금 모습이라 편집기·시험·대체 경로가 쉽다. 요소마다 끌 수 있고 실행 중에 바꿀 수 있어, 휴대폰이 힘들면 하나씩 내린다.
- 일하는 거리에서도 옅은 밤 기운이 남아 1차맵 분위기가 거리마다 이어진다(U1 (나)).
- 구름 그림자가 없어 타일 셰이더가 구름을 읽지 않는다(U2).
- 새 런타임 의존성이 없다.

### 감수할 점
- 지구본 거리에서 1차맵 반쪽이 늘 밤이다. 읽기 쉬움은 휴대폰에서 파스텔·다크 테마로 확인해야 한다.
- 일하는 거리에서도 밤이면 화면이 옅게 어둡다(밤 세기 0.6~1). 밤에 1차맵에서 2차맵(고정 빛)으로 들어가면 조명이 조금 바뀐다. 2차맵 낮밤(질문 22)이 정해질 때까지 그대로다.
- 지구본 거리에서 구름이 지도 일부를 가린다(시제품 기본값 약 30% 안팎, Assumed: 눈대중).
- 쉬는 동안에도 그린다(지금은 0): 지구본에서 1.7초에 한 번, 가까운 거리에서는 낮이면 4초, 띠가 지나가는 동안 약 2.8초에 한 번. 배터리 부담은 작다고 본다(Assumed).
- GPU 메모리 약 2.7MiB, 셰이더 프로그램 3개(껍질·굽기·달), 1차맵 조각 약 20~25KB(gzip 8~10KB)가 는다(Assumed).
- 날씨 창이 바뀔 때(3시간마다) 구름이 2초쯤 옅어졌다 다시 생긴다. 창 안에서는 구름이 움직이지 않는다.
- 시계를 맞추기 전 1초 남짓은 낮으로 보이다가 밤이 켜질 수 있다.
- 세로 화면에서는 달을 보기 어렵다(약 3%). 사용자가 그대로 두기로 했다(U3).
- WCAG 2.2.2의 화면 안 멈춤 수단은 설정 화면 작업 전까지 없다(동작 줄이기만 따른다).
- 화면 사진·시험이 시각에 따라 바뀐다. 시험은 늘 `?planet-time=`으로 시각을 멈춘다. 사용자에게 보내는 첫 확인 사진도 시각을 정해 낮·경계·밤을 한 장씩 찍는다.
- 임시 값(기원·기울기·달)은 바뀐다. 기원은 출시 전에 꼭 정해야 한다.
- 극지방 영토는 겨울에 실제 몇 시간씩 밤이다(70°에서 약 4.8시간).
- 셰이더 언어를 TSL로 정하면 셋 다 옮겨야 한다(작은 일, Assumed).

### 다시 볼 조건
- 휴대폰이 10절 상한을 넘으면: 구름 256² → 구름 끔. 면 하나 굽기가 상한을 넘으면 반 면(scissor)으로 나눈다.
- 2차맵 낮밤(질문 22)이 정해지면: U1을 다시 본다(2차맵에도 밤이 오면 가까운 거리의 밤을 2차맵과 같게).
- 가까운 거리의 밤이 일하기에 어둡다는 의견이 나오면: `CLOSE_NIGHT_RULE`의 0.6을 낮추거나 (다)로 바꾼다(값 하나).
- "구름이 안 움직인다"는 의견이 나오면: 창 길이를 줄이거나, 창 안 흐름(2위상, 분산 보존 섞기, 굽기 2배)을 시험하고 휴대폰 비용을 잰다.
- 구름 그림자를 다시 원하면: 타일 조각 셰이더가 구름 큐브를 해 쪽으로 옮긴 방향으로 한 번 더 읽는 설계(조사 문서, 그리기 호출 0)를 쓴다.
- 달이 거의 안 보인다는 의견이 나오면: 달 찾기 단추(조사 문서, 약 0.4일)를 다시 묻는다.
- 기획이 날씨·달을 판정에 넣으면: 서버 권위 날씨 상태·프로토콜, 달 위상은 공용 달력으로 옮겨 서버가 계산한다.
- 기획 답(기원·기울기·달·구름 양)이 오면: 콘텐츠 팩 `planets[].sky` + 목록 정보 선택 필드로 옮긴다.
- 안개(ADR `2026-10-28-fog-and-map-visibility.md`)를 그리게 되면: 합성 순서 표대로 넣고, 밤과 안개가 헷갈리지 않는지, 가 보지 않은 곳 위 구름을 어떻게 할지 정한다.
- 셰이더 언어를 WebGPU + TSL로 정하면: 8절 길로 옮긴다.
- 지구(ETOPO)가 들어오면: 지리와 격자 사이 회전이 있으면 항성·달에도 같은 회전을 준다(Unknown). 설정이 "실제 달"이면 사진 텍스처와 자산 ADR(출처·라이선스).
- 면 레벨 11 행성을 쓰게 되면: 기후 큐브 원천(첫 단계 타일 96개)을 다시 본다.
- 화면 시험 폴더(`e2e/`, ADR `2026-10-29-app-shell.md`)가 생기면: 일회용 하네스의 사진 시험을 옮긴다.

## 선택 제안 (요청 밖이라 결정에 넣지 않음)
1. 대기 띠가 항성을 따르게: 항성 쪽 밝은 초승달 모양 띠, 밤 쪽은 옅은 라벤더, 해 질 녘은 따뜻하게. 지금 그리기 안에서 바꾸므로 비용이 거의 0이다(시제품에서 확인). 밤 쪽 띠 세기에 바닥을 둔다(시제품의 × 0.28은 밤 쪽 실루엣을 거의 지웠다, Verified: 검토 계산).
2. 항성 그림(빛 원판 하나, 그리기 1회): 하늘이 화면에 드물어 거의 안 보인다. 대기 띠의 초승달이 방향을 알려 준다.
3. 밤 쪽 도시 불빛: 도시 지표 자료가 생긴 뒤.
4. 칸 정보에 지역 시각·계절(반구 반영) 한 줄.
5. 달빛: 보름일수록 밤 쪽을 조금 밝게(uniform 하나).
6. 2차맵 낮밤: 같은 항성 함수로 2차맵 빛 방향·밝기.

## 구현하며 정한 것 (공용 달력·하늘 계산, 2026-10-29)

### 공용 달력 (`@terra/shared/planetCalendar`)
- 내보내는 것: 상수(`PLANET_DAY_MS`·`PLANET_DAYS_PER_SEASON`·`PLANET_SEASONS_PER_YEAR`·`PLANET_DAYS_PER_YEAR`·`PLANET_SEASON_MS`·`PLANET_YEAR_MS`·`[임시]` `PLANET_CALENDAR_EPOCH_MS`), `PlanetCalendar`·`PlanetSeason`(0~3) 타입, `planetCalendarAt`(판정 쪽, 던짐), `planetCalendarForDisplay`(화면 쪽, 내림·null), `isPlanetCalendarTime`, `southernSeason`.
- `PlanetCalendar.msSinceEpoch`를 더했다: 기원에서 잰 정수 ms다. 달 위상과 구름 날씨 창 번호가 이것의 정수 나머지·몫을 쓴다.
- 받는 시각 = 안전 정수이고, 기원에서 잰 ms도 안전 정수다. 그래서 `Number.MIN_SAFE_INTEGER`처럼 기원을 빼면 안전 정수를 벗어나는 값도 던진다(조사 메모는 입력만 봤다).
- 결정성 검사가 이 파일을 본다(Verified: `Math.sin`·`**`를 넣은 사본에서 `check-boundaries`가 실패, 2026-10-29).
- 시험 14개(Verified: Vitest 5.0.5): 기획 값, 기원·기원 1ms 전·하루·계절·한 해 경계, 2300년, BigInt로 따로 센 값과 2,005개 시각(±2^53 근처 포함) 비교, 소수·NaN·무한대·범위 밖 던지기, 남반구 계절, 화면 쪽 입구의 x.5ms 500개·null. 바꾼 코드 4가지(나머지 식, 남반구 +1, 내림 → 반올림, 기원 +1ms)에서 시험이 실패했다(Verified).

### 하늘 계산 (`packages/engine/src/planet/sky.ts`)
- 타입(`PlanetSkyMode`·`PlanetSkyFeatures`·`PlanetSkyDescription`·`PlanetMoonDescription`·`SunState`·`MoonState`·`PlanetSkyState`)은 `planetTypes.ts`가 아니라 `sky.ts`에 두었다. sharpness 가지가 `planetTypes.ts`를 고치고 있어서다. WP3에서 `planetTypes.ts`·`index.ts`가 다시 내보낸다.
- `skyAt(utcMs, sky)`가 엔진의 입구다: 화면 쪽 달력 입구로 내리고, 항성(`sunAt`)·달(`moonAt`)을 함께 낸다. 시각이 수가 아니면 null이다(낮으로 그린다).
- `moonAt`은 달 방향·궤도 극·위상·밝은 비율을 낸다. `moonPhaseMs`는 `msSinceEpoch`의 정수 나머지다.
- 화면 쪽 계산: `nightStrength`(U1 (나)), `cloudFade`(6절 걷히기), `skyOnScreen`·`moonOnScreen`(5절), `sunCosRangeOnScreen`·`skyClockIntervalMs`(7절). 값은 `DAY_NIGHT_BAND`·`CLOSE_NIGHT_RULE`·`CLIMATE_NIGHT_FACTOR`·`CLOUD_FADE`·`SKY_CLOCK` 상수 한곳에 있다.
- 달 보임에 "행성 원판 뒤에 다 가리면 그리지 않는다"를 더했다. 가린 달을 그리면 비용만 들고, 하늘 시계가 달 걸음(0.33~0.5초)으로 돌기 때문이다. 가장자리에 반쯤 걸친 달은 그린다.

- 시험 51개(Verified: Vitest 5.0.5): 알려진 시각의 항성(기원 경도 180°·적위 −16.34°, +15·30·45분, 계절 가운데 적위), 고도 식 = 내적(2,000곳), 항성 빠르기 0.1°/s, 지역 정오, 경계 이어짐, 반구별 계절 부호·정오 고도·극야·백야, 기울기 0, 달 위상·2300년·삭·보름 이각·순행(상현 +90°)·밝은 비율·기울기 0 삭에서 달 = 항성·적위 상한·궤도 극 29바퀴, 낮밤 세기(0.6·1·로그 가운데 0.8·기후 0.35·F4), 구름 걷힘, 하늘·달 보임(세로·가로 휴대폰, 가드 6.94R·3.36R), 항성 고도 범위, 하늘 시계 간격. 바꾼 코드 11가지(항성 경도·계절 위상·θ의 부호, 회전, 달이 도는 쪽, 0.5R, 원판 뒤 가림, 띠 조건, 가장자리 점, 지역 시각, 구름 문턱)에서 모두 실패했다. 처음에 살아남은 둘(달이 도는 쪽, 반쯤 걸친 달)은 시험을 더해 잡았다(Verified).
