# S2 행성 LOD: 결정적 생성기, 쿼드트리 타일, 서버 굽기, 렌더러, 편집기 1단계, 측정 계획

- 상태: 제안 (S2 측정 뒤 확정)
- 날짜: 2026-10-29
- 관련: docs/PLAN.md 5.2~5.7·6.2·11장(S2), `2026-10-28-planet-grid-contract.md`(ADR 9), `2026-10-28-planet-generation-and-versioning.md`(ADR 10), `2026-10-28-map-delivery-and-rendering.md`(ADR 11), `2026-10-28-editor-and-placement.md`(ADR 12), `2026-10-28-fog-and-map-visibility.md`(ADR 26), `2026-10-28-planet-generation-order.md`(ADR 31), `2026-10-29-cell-key-layout.md`(ADR 34), `2026-10-28-s1-second-map.md`(ADR 33), 기획 D-055·D-104·D-107·D-141·D-154~D-156

## 배경
- S2 목표(PLAN 11장): 자체 LOD 렌더러, 최소 생성기(노이즈 + Priority-Flood + 단순 기후)로 행성 1개, 지표 레이어 2종(고도·해수면, 기온·바이옴, D-141), 편집기 1단계, 셰이더 언어 결정. 지구 ETOPO는 통과 뒤.
- 통과 기준: 첫 표시 3초 이하, 화면당 타일 상한 준수, 틈 없음, 프레임 p95 33ms 이하. 실패하면 단계 수를 줄이거나 미리 구운 텍스처를 쓴다.
- ADR 34가 남긴 문제: 생성기가 엔진마다 결과가 다를 수 있는 `Math.tan` 같은 함수에 기대면, 고정 시드 결과 해시(PLAN 5.5)를 지킬 수 없다.
- 기획에 바이옴 목록과 고도 축척이 없다. 수평 축척은 1:12(D-055)이고 건물·유닛은 실제 크기다.

## 선택지
### 생성기 결정성
1. 실수 + `Math` 초월함수 그대로: 엔진·버전이 바뀌면 결과가 바뀔 수 있다.
2. 실수 기본 연산 + 명세가 정확히 정한 함수만 + 초월함수는 자체 근사.
3. 모두 정수·고정소수점: 노이즈·기후 코드가 크게 어려워진다.

### 타일
1. 단계마다 면 전체 이미지 하나.
2. 면별 쿼드트리 타일(32×32칸).
3. 면별 쿼드트리 타일(64×64칸).

### 고도 축척
1. 수평과 같은 1:12(고도도 줄임).
2. 실제 고도 그대로(1:1).
3. 그 사이(예: 1:4).

## 결정
### 생성기 결정성 (선택지 2)
- 생성 코드는 실수의 사칙연산과 명세가 결과를 정확히 정한 함수만 쓴다.
  - 쓸 수 있는 함수: `Math.sqrt`·`floor`·`ceil`·`round`·`trunc`·`abs`·`min`·`max`·`sign`·`fround`·`imul`.
  - 초월함수(`sin`·`cos`·`tan`·`atan`·`exp`·`log`·`pow` 등)는 `packages/shared`의 자체 근사(사칙연산만 쓰는 다항식)를 쓴다.
- 투영(`@terra/planet/projection`)도 자체 근사로 바꾼다. 그러면 생성기와 화면이 같은 위치를 쓰고, 경계 검사에서 투영 파일 예외를 없앤다.
- 시드 난수는 `@terra/shared` `createRng`다. 반복 순서는 고정한다(면 0~5, 행, 열).

### 행성 정의 (콘텐츠 팩)
- 콘텐츠 팩에 분류 `planets`를 더한다. 항목: ID(snake_case), 이름 ko·en, 면 레벨(4~14), 시드(u32), 프리셋, 세부 수치 덮어쓰기.
- 프리셋 축(D-154): 해수면(군도·보통·대륙), 기온(추움·보통·더움), 강수(건조·보통·습윤), 산악도(젊음·보통·늙음), 판 개수, 화산(적음·보통·많음). 축마다 정할 세부 수치와 그 값은 S2 임시값이다(`placeholder: true`).
- 기온 경계는 절대 °C다(D-154).
- S2 시험 행성은 하나다. 면 레벨 9(지구 크기, 칸 157만 개)로 LOD를 실제 규모로 시험한다.
- 행성 ID = 콘텐츠 ID 문자열이다. DB에서 칸은 (행성 ID, 셀 키) 쌍으로 가리킨다(ADR 34). DB 표는 행성 상태를 처음 저장할 때 만든다.

### 생성기 1판 (`packages/planet`, 서버 굽기와 편집기 미리보기가 함께 씀)
- 순서는 ADR 31을 따른다.
  1. 판 구조: 구면 보로노이 → 판 경계 충돌·분리로 산맥·해구 + 3D fBm 노이즈 → 기본 고도
  2. 해수면: 육지 비율(프리셋)의 백분위로 정한다
  3. 웅덩이 채우기·흐름 방향: Priority-Flood, 8이웃
  4. 기후: 위도(구 위 점의 z = sin 위도라 역삼각함수가 필요 없다), 고도에 따른 기온 감소, 위도 띠 바람과 비그늘, 바다까지 거리 → 연평균 기온·강수
  5. 물 흐름 누적(강수 가중) → 단순 침식(몇 번) → 강(누적 문턱)·호수(채운 웅덩이)
  6. 수심 등급(연안·대륙붕·심해)
  7. 습도
  8. 바이옴(기온 × 습도 표) → 숲 밀도
- 출력 `PlanetFields`: 면 레벨 F 칸마다(n = 2^F, 순서는 면 × n² + j × n + i, `@terra/planet`의 면·i·j와 같다)
  - `elevationM` Int16(해수면 0 기준, 게임 m)
  - `biome` Uint8(바이옴 표 번호)
  - `temperatureC` Int8(연평균)
  - `precipitationMm` Uint16(연)
  - `humidity` Uint8(0~255)
  - `water` Uint8(비트: 바다·호수·강·해안, 수심 등급 2비트)
  - `river` Uint8(하천 등급, 0 없음)
  - `forest` Uint8(0~255)
  - 메타: generatorVersion, 시드, F, 풀어 쓴 설정값, 결과 해시(FNV-1a)
- 바이옴 표 1판은 임시다(빙상·툰드라·타이가·온대림·초지·사막·사바나·열대우림·습지·고산 + 바다 수심 3·호수). ID·이름 ko·en·색을 콘텐츠 팩에 둔다(`placeholder: true`). 목록은 기획 세션에 요청한다.
- `GENERATOR_VERSION`을 두고, 출력이 바뀌면 올린다. 고정 시드 골든 해시를 CI 시험으로 비교한다(PLAN 5.5).

### 고도 축척 (선택지 1, 기획 D-215 확정)
- 고도도 수평과 같이 1:12로 줄인다. 저장 값은 게임 m다(예: 에베레스트 실제 8,849m → 약 737m).
- 기후 식(기온 감소율 등)은 실제 고도로 바꿔(× 12) 계산한다.
- 1차맵 화면은 보기 쉽게 고도를 과장해 그린다(배율은 화면 설정, 판정과 무관).
- 기획 D-215로 확정됐다(처음에는 출발값으로 정하고 기획에 확인을 요청했다). 바뀌면 `GENERATOR_VERSION`을 올린다.

### 타일 (선택지 2)
- 1차맵 5단계(맵 레벨 F−4 ~ F)마다 면을 쿼드트리로 나눈다. 타일 하나 = 그 맵 레벨의 32×32칸이다(면이 32칸보다 작으면 면 전체).
- 지구 크기(F = 9): 맵 레벨 5~9 = 쿼드트리 깊이 0~4. 면당 341개, 모두 2,046개다.
- 타일 ID = 쿼드트리 칸(레벨 = 맵 레벨 − 5)의 셀 키(ADR 34)다.
- 내용(이진, 형식은 `packages/protocol`)
  - 머리: 형식 버전, F, 맵 레벨, 면, 첫 칸 i·j, 한 변 칸 수
  - 꼭짓점 높이 33×33(Int16, 게임 m)
  - 칸마다 바이옴·물 비트·기온·습도·숲·하천 등급(각 1바이트)
  - 크기: 약 8.3KB(압축 전). 행성 전체 약 17MB(압축 전).
  - 처음 화면용 맵 레벨 5~6(30개)은 약 250KB(압축 전)다.
- 꼭짓점 높이 = 그 꼭짓점을 나누는 칸들의 평균이다(면 경계 너머 칸 포함, 큐브 꼭짓점은 3칸). 그래서 같은 레벨 이웃 타일은 경계 높이가 같다(틈 없음). 레벨이 다른 이웃 사이는 렌더러가 치마(skirt)로 막는다.
- 윗 레벨 값 = 아래 2×2칸에서 모은다. 고도·기온·습도·숲은 평균, 바이옴은 가장 많은 것(동점은 작은 번호), 물·하천은 규칙(바다가 2칸 이상이면 바다, 하천은 가장 큰 등급)으로 정한다. 모으기도 결정적이다.
- 숨김 정보(자원·크리쳐)는 넣지 않는다(ADR 26). 1차맵 지형은 모두에게 같은 파일이다.

### 서버 굽기·전송
- 서버는 콘텐츠 팩의 행성마다 (정의 해시, generatorVersion)로 굽는다. 디스크 캐시(`PLANET_CACHE_DIR`, NAS는 볼륨)에 있으면 읽고, 없으면 워커 스레드에서 생성 → 타일 → 압축 → 저장한다. 굽는 동안 서버는 다른 요청을 계속 받는다.
- 전송
  - `GET /api/planets/<ID>`: 목록 정보 JSON(F, 반지름, generatorVersion, 정의 해시, 상태 준비 중·완료, 타일 주소 틀, 바이옴 범례)
  - `GET /api/planets/<ID>/tiles/<타일 ID>?v=<버전>`: 이진. 압축한 것을 그대로 보낸다. 버전이 붙은 주소라 `immutable`
- 로그인한 사용자만 받는다(S1 지형 파일과 같음). 속도 제한이 있다.

### 렌더러 (`packages/engine`)
- 면별 쿼드트리 LOD. 화면 오차(칸 크기 → 화면 픽셀)로 나눈다. 부모를 먼저 그리고 자식이 오면 바꾼다. 화면에서 안 보이는 타일(시야 밖·지평선 뒤)은 그리지 않는다.
- 상한(출발값): 보이는 타일 160개, 동시 받기 6개, 한 프레임에 올리기 4개, 타일 메모리 추정 64MB(GPU 추정 + JS에 남는 사본, 아래 "렌더러 검토 반영").
- 카메라 기준 좌표: 타일마다 원점(실수 64비트)을 두고 정점은 원점 기준 32비트로 둔다. 모델뷰는 CPU에서 64비트로 만든다(PLAN 5.7).
- 레이어 2개: 지형(고도·해수면·바이옴 색), 기후(기온·습도 색). 바다는 해수면 높이의 구다.
- 타일 해석은 Web Worker에서 한다. 화면 변화가 없으면 그리지 않는다. 렌더러는 앱에 하나다(S1과 같이 씀).
- 셰이더 언어: 지금은 WebGL2 + GLSL(three `ShaderMaterial`·`onBeforeCompile`)로 짧게 쓴다(PLAN 5.7 "WebGL2 기본"). WebGPU(WebGPURenderer + TSL)는 같은 일을 하는 시험 화면으로 따로 재고, 그 결과로 정한다. 둘이 비슷하면 사용자에게 묻는다.

### 시험 화면과 편집기 1단계
- 시험 화면: S1처럼 계정 줄에 임시 [1차맵] 버튼. 화면 흐름(기획 Step 6)이 정해지면 옮긴다.
- 편집기 1단계(관리자 화면, 지연 로딩, PLAN 6.2)는 생성기·타일·렌더러가 합쳐진 뒤 만든다.
  - 프리셋 + 세부 수치 슬라이더
  - 기기 워커에서 낮은 해상도(F = 6~7)로 생성해 지구본 미리보기
  - 바이옴 면적표(D-154)
  - 정의 JSON 내보내기(콘텐츠 팩에 커밋)
  - 서버 쪽 초안 저장은 2단계다.
- 2차맵을 행성 값에서 만들기(위에서 생성, PLAN 5.4)는 생성기가 합쳐진 뒤 S2 안에서 따로 한다. 그때 ADR 33의 임시 지형을 바꾼다.

### 측정
- 첫 표시(목록 정보 + 맵 레벨 5~6 타일 + 첫 프레임) 3초 이하(4G), 화면당 타일 상한, 틈 없음(같은 레벨 경계 높이 같음은 시험으로, 치마는 화면으로), 돌리기·확대 중 프레임 p95 33ms 이하. 기준 기기는 PLAN 11장.
- 서버: 생성 시간·최대 메모리(NAS), 타일 전체 크기, 캐시 읽기 시간.

## 이유
- 결정성: ECMA-262는 `Math.sqrt`를 정확히 반올림한 값으로 정한다. `sin`·`cos`·`tan`·`atan`·`exp`·`log`·`pow` 등은 "정밀하게 정하지 않음" 목록에 있다(Verified: tc39/ecma262 `spec.html` main, 2026-10-29). 사칙연산은 IEEE 754 배정밀도 반올림으로 정해져 있다. 그래서 선택지 2는 엔진·버전이 바뀌어도 같은 결과를 낸다. 정수만 쓰는 선택지 3보다 노이즈·기후 코드가 훨씬 쉽다.
- 32×32 타일: 쿼드트리 깊이 0~4가 1차맵 5단계와 꼭 맞는다. 64×64면 깊이가 4단계라 단계 하나가 남는다. 타일이 작아 처음 화면이 빨리 온다(약 250KB, 압축 전).
- 고도 1:12: 수평만 줄이면 경사가 실제의 12배가 된다. 산악 2차맵이 절벽이 되어 길찾기·건설이 안 된다(Assumed: 계산). 같이 줄이면 지구와 같은 경사가 된다. 대신 1차맵에서는 높낮이가 잘 안 보이므로 화면에서만 과장한다.
- 꼭짓점 평균 높이: 이웃 타일이 같은 값을 쓰므로 같은 레벨 틈이 생기지 않는다. 쿼드트리 LOD의 일반 방법(치마)과 함께 쓴다.

## 구현하며 정한 것 (생성기)
2026-10-29 생성기 구현(작업 기록 `docs/worklog/2026/10/29-1020-s2-generator.md`)과 리뷰 뒤 고침(`docs/worklog/2026/10/29-1415-s2-generator-review-fixes.md`). 상태는 제안 그대로다. 잰 값 전체는 작업 기록에 있다.

### 결정적 수학 (`@terra/shared` `detMath.ts`)
- 함수 7개: `detSin`·`detCos`·`detTan`·`detAtan`·`detAtan2`·`detAsin`·`detExp`. 로그·거듭제곱은 아직 쓸 곳이 없어 만들지 않았다.
- 방법: Cody–Waite 인수 줄이기(π/2는 세 조각, ln 2는 두 조각) + 테일러 다항식. atan은 m/8(m = 0~8) 값 표 + 급수다. 상수는 Python decimal 90자리로 계산했다.
- 잰 최대 오차(4배 정밀도 C quadmath 기준, Verified): sin·cos 1ulp(|x| ≤ 100), atan·exp 1ulp, asin·atan2 2ulp, tan 2ulp(|x| ≤ π/4)·3ulp(|x| ≤ 20). 인수 줄이기는 |x| ≤ 약 1e6까지 정확하다. 그보다 크면 값은 결정적이지만 정확하지 않다.
- 거듭제곱 연산자 `**`도 명세가 "구현이 근사한 값"으로 둔다(Number::exponentiate, Verified: tc39/ecma262 `spec.html` main, 2026-10-29). 그래서 경계 검사가 `**`도 막는다. `Math.PI`·`Math.LOG2E`는 함수가 아니라 명세가 정한 상수라 써도 된다.
- 경계 검사(`scripts/determinism-scan.mjs`)가 보는 곳: `packages/sim/src`, `packages/planet/src` 전체(투영·생성기), 그리고 `@terra/shared`의 결정적 모듈(`detMath`·`rng`·`planetDefinition`·`planetPresets`). 시험 파일(`*.test.ts`)과 시험 도우미(`test`로 시작하는 파일, 예: `testOracle.ts`)만 뺀다.
  - 주석·문자열·템플릿 글자는 지운 뒤 본다(템플릿 `${…}`는 코드다). 그래서 설명에 `Math.atan2`를 적어도 되고, 문자열 안 `**`로 잘못 실패하지 않는다.
  - `Math`를 통째로 꺼내거나 계산된 이름으로 읽는 것(`Math["sin"]`, `= Math`)과 `performance.now`·`crypto` 난수도 막는다.
- 시험이 잡는 것(Verified: 일곱 함수의 본문을 하나씩 엔진 `Math` 함수로 바꿔 돌림)
  - `detMath.test.ts` 골든 비트는 적어 둔 점의 비트만 본다. 함수마다 Node 24.22.1(V8) `Math`와 마지막 비트가 다른 점을 두 개씩 넣었다. 그래서 det 함수를 엔진 `Math`로 바꾸면 일곱 함수 모두 실패한다. 적어 둔 점 밖에서만 값이 바뀌는 변경은 잡지 못한다.
  - 생성기 정수 골든 해시는 어느 바꿈에도 그대로였다. 실수의 마지막 비트 차이가 Float32 저장과 정수 반올림에 묻힌다.
  - 그래서 `generate.test.ts` "실수 지문"이 격자(칸 중심·면적)와 해수면의 64비트 값을 고정한다. detTan·detAtan 바꿈을 잡는다. 판 구조 고도·기온·강수의 Float32 지문은 알고리즘 변경은 잡지만 1ulp 차이는 잡지 못했다.
  - 엔진 `Math`를 쓰는 것 자체는 경계 검사가 막는다.
- det 함수 값이 바뀌면 생성기 결과가 바뀔 수 있다. 그러면 `GENERATOR_VERSION`을 올리고 골든 비트·골든 해시·실수 지문을 같은 커밋에서 고친다.

### 행성 정의 (콘텐츠 팩 `planets`·`biomes`)
- 이름·범위는 `@terra/shared` `planetDefinition.ts` 한 곳에 둔다. 콘텐츠 스키마(`@terra/content`)와 생성기(`@terra/planet`)는 서로를 가져올 수 없어서다(경계 규칙).
- `planets` 항목: `id`, `name`(ko·en), `description`(선택), `faceLevel`, `seed`(u32), `presets`(6축 모두 필수), `overrides`(선택, 세부 수치 13개 중 일부), `biomes`(바이옴 ID 참조 목록, 1~255개, 같은 것 두 번 금지).
  - 면 레벨은 4~9다(위 결정은 4~14, 격자 계약은 그대로). 메모리 때문이다.
    - 레벨 10은 생성 하나만으로 최대 RSS 771MiB, 약 55초다(Verified: 이 컨테이너). NAS 앱 컨테이너 상한은 1GiB다(`ops/compose.yml`). 서버가 이미 쓰는 메모리를 더하면 상한에 닿거나 넘을 수 있다(Assumed).
    - NAS에서 굽기를 잰 뒤 다시 본다. 콘텐츠 스키마·생성기 입력 검사·서버 시작 검사가 같은 상수(`PLANET_GENERATOR_FACE_LEVELS`)를 쓴다.
  - 판 개수 축의 단계 이름은 적음·보통·많음(few·normal·many)이다. 정확한 개수는 `overrides.plateCount`로 준다.
  - 세부 수치 13개: 육지·대륙붕 비율, 판 개수, 산맥 세기·기복·침식, 열점 수·화산 높이, 적도·극 기온(°C, 극 ≤ 적도), 강수 배율, 강 밀도, 호수 보존. 모두 정수다. 프리셋 단계 → 수치 표(`PLANET_PRESET_VALUES`)와 풀기(`resolvePlanetSettings`)는 `@terra/shared` `planetPresets.ts`다. 콘텐츠 검증과 생성기가 같은 표로 풀게 하려는 것이다. 생성기 진입점도 같은 이름을 다시 내보낸다.
  - 콘텐츠 검증은 생성기가 받지 않는 정의를 먼저 막는다.
    - 1단계(스키마): 극 기온 ≤ 적도 기온을 풀어 쓴 값으로 본다. 한쪽만 덮어쓰면 다른 쪽은 기온 프리셋 값이다.
    - 2단계 뒤(`validate/planets.ts`): 참조한 바이옴에 바다·호수·육지 규칙이 하나씩 있는지 본다.
    - 생성기 시험은 팩의 모든 행성을 면 레벨 4로 생성해 본다(검증이 놓친 조건을 서버 굽기 전에 찾는다).
- `biomes` 항목: `id`, `name`, `description`(선택), `color`(`#rrggbb`), `forestDensity`(0~255), `rule`.
  - 규칙 종류: 바다(수심 등급 연안·대륙붕·심해 중 하나), 호수, 육지(기온 °C·습도 0~255·실제 환산 고도 m의 범위 [min, max), 없는 쪽은 끝이 없다).
  - 바이옴 번호(`biome` 값) = 행성 `biomes` 배열의 위치다. 그래서 범례는 행성 정의의 `biomes` 순서이고 색은 바이옴 항목에 있다. 메타에는 바이옴 ID를 넣지 않았다.
  - 판정: 표 순서대로 처음 맞는 규칙. 육지 규칙이 하나도 맞지 않으면 표의 마지막 육지 바이옴이다. 저장한 값(기온·습도·고도 × 12)으로 판정하므로 출력만 보고 다시 판정해도 같다(시험).
- 바이옴 표 1판(14개, 이 순서): 심해·대륙붕·연안 바다, 호수, 빙상, 고산, 습지, 툰드라, 타이가, 온대림, 초지, 사막, 사바나, 열대우림. 범위는 지구의 기온 × 습도 분류를 대략 흉내 낸 임시값이다(`placeholder: true`, 기획 확인 전). 팩 버전 1 → 2.

### 생성기 1판 (`@terra/planet/generator`)
- 진입점: `generatePlanet(입력) → PlanetFields`. 도구용 `runPlanetGenerator(입력, { onStage })`는 흐름 방향(`receiver`), 웅덩이 처리(`basinKind`), 호수 수면 높이(`lakeSurfaceM`), 해수면도 돌려준다. 정의 읽기는 `planetInputFromDefinition(행성, 바이옴 항목들, 면 레벨?)`, 프리셋 풀기는 `resolvePlanetSettings(프리셋, 덮어쓰기)`다.
- `PlanetFields` 모양은 위 결정 그대로다. 정한 세부:
  - `water`: 1 바다, 2 호수, 4 강(하천 등급 > 0인 땅), 8 해안(8이웃에 바다가 있는, 바다가 아닌 칸). 4~5비트 수심 등급은 바다에만 있다: 1 연안(실제 환산 깊이 60m 미만), 2 대륙붕(200m 미만), 3 심해.
  - `elevationM`: 바다·호수는 바닥 높이다. 작은 웅덩이를 메운 평지와 마른 분지는 채운 높이(평평)다.
  - 호수 수면은 `GeneratorDetails.lakeSurfaceM`(게임 m, Int16)이다. 호수 칸만 값이 있고(그 밖은 0), 한 호수는 모두 같은 값이며 넘치는 곳(호수 밖 첫 칸)의 저장 고도와 같다(시험).
  - 강은 유량 문턱(실제 환산 12km³/년 × 100 ÷ 강 밀도 %) 이상인 땅 칸이다. 바다·호수·마른 분지에서 끝난다. 하천 등급은 Strahler 차수다.
  - 습도 = 255 × AI ÷ (AI + 0.75) + 강가·호숫가 가산. AI = 강수 ÷ 증발 가능량(max(80, 45 × (기온 + 6)) mm). 바다·호수는 255다.
  - 강가·호숫가 가산(`riparian.ts`): 물가에서 실제 환산 12km 띠 안의 땅이 받는다. 강은 강 칸 가운데를 지나는 선에서, 호수는 호숫가에서 잰다. 강은 19~44(하천 등급), 호수는 24다.
    - 칸이 띠보다 크면 칸 폭 중 띠가 차지하는 몫만 더한다. 강 머리 칸은 칸 안에서 강이 차지하는 길이 몫((유량 − 문턱) ÷ 그 칸 자신의 유출)도 곱한다.
    - 그래서 가산을 받는 땅의 면적이 면 레벨과 무관하다(강을 가로지르는 칸 줄의 몫 × 칸 폭의 합 = 띠 폭, 시험).
  - 숲 밀도 = 바이옴 기본값 × 습도 비율(0.6~1) × 노이즈(0.85~1.15).
  - 해시: FNV-1a 32비트, 16진수 소문자 8자리. 면 레벨 1바이트 뒤에 필드마다 배열 전체를 칸 번호 순서로 잇는다: `elevationM`(칸마다 2바이트 little-endian), `biome`, `temperatureC`, `precipitationMm`(2바이트 LE), `humidity`, `water`, `river`, `forest`. 시드·설정은 해시에 넣지 않는다(메타에 따로 있다).
- 정육면체 꼭짓점(ADR 34가 남긴 Unknown): 판·대륙·노이즈를 돌린 좌표(무늬 공간)에서 계산한다. 무작위 회전 128개(0번은 회전 없음) 중 꼭짓점 8곳 대륙성의 최댓값이 가장 낮은 것을 고르고, 꼭짓점 가까이(0.035라디안)는 대륙성을 조금 누른다. 마지막으로 꼭짓점 둘레 약 100km(칸이 더 크면 칸 1.2개)를 해수면보다 적어도 400m(실제 환산) 아래로 누른다. 시드 여러 개에서 꼭짓점 칸 24개가 모두 바다다(시험). 기후는 돌리지 않은 좌표(z = 자전축)로 계산한다.
- 해수면: 면적 가중 백분위다. 해수면 아래지만 바다와 이어지지 않은 작은 낮은 땅(구 면적 0.2% 미만, 실제 환산 약 100만 km²)은 바다가 아니라 웅덩이로 둔다. 웅덩이는 최대 깊이 35m 미만이거나 면적 3,000km² 미만이면 메운 평지(물은 지나간다)가 되고, 그 밖은 물 수지로 호수(들어온 물 ≥ 수면 증발, 남는 물만 넘친다)나 마른 분지(물이 나가지 않는다)가 된다.
- 기후는 침식 전 고도로 한 번 계산한다(ADR 31 순서). 침식 뒤 기온을 다시 계산하지 않는다.
- 침식: Braun·Willett(2013) 암시적 하천 침식 3번. 매번 흐름 방향을 다시 구한다.
- 해상도 무관: 판 흔들기·경계 폭·노이즈 주파수·기후 거리·강가 띠를 모두 구 위 각도(실제 환산 km)로 정했다. 그래서 편집기 미리보기(F = 6~7)가 굽기(F = 9)와 거의 같은 대륙·산맥·바이옴 면적이다.
  - 시험: F5와 F6 육지 일치 90% 이상. F6과 F8의 육지 바이옴 면적 차이가 바이옴마다 2.5%p 안, 평균 습도 3%·숲 밀도 6% 안(S2 시험 행성).
  - 잰 값(Verified, S2 시험 행성): F6과 F8의 육지 바이옴 면적 차이는 가장 큰 것이 사바나 1.93%p다. 습도는 1.2%, 숲은 3.5% 다르다.
  - 남은 사바나 차이는 강가 가산을 꺼도 1.9%p라 기후 쪽에서 온다. 습기 흐림을 km로 맞춰도 2.0%p라 흐림 때문은 아니다(원인 Unknown).
  - 처음 1판은 강가 가산이 강 칸과 그 8이웃 전체에 붙어 칸 크기를 따라갔다. 그때는 사바나 6.1%p, 열대우림 5.4%p, 숲 20%가 달랐다(리뷰 뒤 고침).
  - 해상도를 따라 다른 것: 해안선의 잔 모양(노이즈 옥타브가 해상도를 따라 는다), 강 칸 비율(강은 칸 하나 폭: 육지 중 F6 29%, F9 1.9%), 해안 비트(바다와 맞닿은 칸).
- 난수는 `@terra/shared` `createRng`(단계마다 시드를 가른다)와 정수 해시(lowbias32, 노이즈 격자점)다.

### 버전·시험
- `GENERATOR_VERSION` 2. 이 값은 출력 판 번호다(설계는 생성기 1판 그대로). 출력이 한 칸이라도 바뀌면 올리고 골든 해시를 같은 커밋에서 고친다(PROTECTED).
  - 1은 첫 출력(main `523f373`), 2는 리뷰 뒤 강가 가산을 면 레벨과 무관하게 고친 것이다.
  - 검토는 1판을 내보내기 전이니 1로 두자고 했다. 그런데 작업 중 1판이 origin/main에 올라갔다. 서버 캐시 키와 타일 주소 판이 이 값을 쓰므로, 1로 두면 이미 구운 캐시와 기기 타일 캐시가 옛 출력을 낸다. 그래서 2로 올렸다.
- 골든 해시 3개: F5 시드 1 극단 프리셋 `005378e0`, F5·F6 S2 시험 행성 설정 `5c984c77`·`215d9b32`. 실수 지문: 격자·해수면(64비트), 판 구조·기후(Float32).
- 출력 판 3(생성기 다양성 고침: 노이즈 2판, 굽이치는 바람, 기후 위도·기온·강수 변이, 지형 틀(안쪽 고원·분지·구릉, 해안선 흔들기, 산맥 단면·세기, 열점 사슬), 반복 검사)은 ADR `2026-10-29-planet-generator-variety.md`가 정한다. 이 절의 판 2 값은 그 ADR 이전 기록이다.
- 성질 시험: 결정성, 해수면 비율, 강 내리막, 하천 등급, 바이옴 재판정, 물 비트, 호수 수면, 꼭짓점 바다, 기온 띠, 프리셋 방향, 해상도 일치(육지·바이옴 면적), 팩의 모든 행성 생성, 입력 검사.
- 다른 엔진(브라우저)에서 같은 해시가 나오는지는 아직 돌려 보지 않았다(Assumed: 명세상 같다).

### 아직 정하지 않은 것
- 흐름 방향은 `PlanetFields`에 없다. 타일·렌더러가 강을 선으로 그리려면 모양을 바꿔야 한다(타일 쪽과 함께 정한다).
- 호수 수면 높이도 `PlanetFields`에 없다(`GeneratorDetails.lakeSurfaceM`에만 있다). 호수를 평평한 수면으로 그리려면 타일에 수면을 싣거나, 굽기에서 호수 칸 높이를 수면으로 바꿔야 한다. 어느 쪽인지 타일·렌더러 쪽과 함께 정한다.
- 기획에 물을 것: 바이옴 기온·습도 범위(Step 5), 프리셋 단계별 수치. 바이옴 목록(D-214)과 고도 1:12(D-215)는 답을 받았다.

## 구현하며 정한 것 (타일·서버)
2026-10-29 타일·서버 구현(작업 기록 `2026/10/29-0950-s2-tiles-server.md`). 상태는 제안 그대로다. 생성기·렌더러가 합쳐진 뒤 S2 측정과 함께 다시 본다.

### 타일 (`packages/planet/src/tiles/`)
- 생성기 출력 모양 `PlanetFields`를 이 폴더에 적었다. 생성기가 합쳐질 때 하나로 맞춘다. 타일 코드가 메타에서 읽는 값은 면 레벨뿐이다.
- 면이 32칸보다 작은 맵 레벨(L < 5, 면 레벨 8 이하 행성에만 있다)은 면 전체가 타일 하나다. 이 타일의 ID는 그 맵 레벨의 (0, 0) 칸 키다.
  - L ≥ 5 타일이 쓰는 키 레벨은 0 ~ F−5이고, L < 5 타일은 F−4 ~ 4라서 한 행성 안에서 겹치지 않는다. F ≥ 9는 위 결정 그대로다.
  - 타일 수: F = 4는 30개, 6은 48개, 9는 2,046개, 10은 8,184개.
- 타일 순서(굽기·캐시): 맵 레벨 오름차순, 그 안에서 키 오름차순(면 → 힐베르트). 처음 화면용 거친 단계가 앞에 온다.
- 모으기(아래 2×2 → 위 1칸)
  - 평균(고도·기온·습도·숲)은 가장 가까운 정수, .5는 +∞ 쪽(`Math.round`)이다. 단계마다 반올림하므로 네 단계 위는 아래 값 평균과 최대 약 2 차이가 난다(Assumed: 계산).
  - 바이옴은 가장 많은 것, 동점이면 작은 번호.
  - 물 비트: 바다가 2칸 이상이면 바다다. 수심 등급은 바다 칸들의 등급 중 가장 많은 것이고, 동점이면 얕은 쪽이다. 바다가 아니고 호수가 2칸 이상이면 호수다. 강·해안 비트는 한 칸이라도 있으면 켠다. 남은 비트(6~7)는 0이다.
  - 하천 등급은 가장 큰 등급.
  - 주의(다듬기 통합에서 바로잡음): 바이옴은 물 비트와 따로 모은다. 팩 바이옴 표는 바다 바이옴이 0~2번, 호수가 3번이라 동점이면 물 바이옴이 이긴다.
    - 바다 2칸 + 땅 2칸은 물 비트도 바이옴도 바다라 맞는다.
    - 바다(또는 호수) 1칸 + 서로 다른 땅 바이옴 3칸이면 물 비트는 땅인데 바이옴은 바다(호수)다. 렌더러는 그 칸을 바다 바이옴 색으로 칠하고, 칸 정보는 그 이름을 쓴다(물 비트를 먼저 보는 것은 반대 경우만 막는다).
    - 통합 검토 측정(F9 팩 행성): 맵 레벨 5~8에서 레벨마다 땅 칸 5~13개(+ 호수 바이옴 1~2개), 맵 레벨 9는 0개.
    - 고침(같은 물 종류 칸에서만 최빈값)은 타일 값 규칙이 바뀌어 `PLANET_TILE_FORMAT_VERSION`을 올려야 한다. 특수 지형을 더하는 타일 형식 2판과 함께 한다(아래 "구현하며 정한 것 (다듬기 통합)").
- 꼭짓점 높이는 맵 레벨마다 행성 전체를 한 번 계산한다(면마다 (n+1)²). 면 경계는 `wrapFaceIJ`로 이웃 면 칸까지 4칸, 큐브 꼭짓점은 3칸이다.
- 시험: 같은 레벨 이음매를 구현과 따로 쓴 기준(3D 정수 격자점, `testOracle.ts`)으로 전수 확인한다(F 5·6의 모든 단계, 면 모서리 12개·큐브 꼭짓점 8곳 포함). 고정 입력의 골든 해시도 둔다.

### 이진 형식 "TCPT" 1판 (`packages/protocol/src/planetTile.ts`)
- 머리 56바이트(작은 끝): 마법 값, 형식 버전, 머리 길이, F, L, 면, i0, j0, 한 변 칸 수, 생성기 버전(u32), 정의 해시(SHA-256 32바이트).
- 본문: 꼭짓점 높이 i16 × (size+1)², 그다음 칸 값 6가지(바이옴·물 비트·기온 i8·습도·숲·하천 등급)를 필드마다 size²바이트씩 이어 붙인다. 같은 필드가 모여 있어 gzip이 잘 줄인다. 32×32 타일은 8,378바이트다.
- 형식 버전(`PLANET_TILE_FORMAT_VERSION`)은 바이트 배치뿐 아니라 타일 값 규칙(모으기·꼭짓점)이 바뀌어도 올린다. 같은 주소로 다른 내용이 나가지 않게 하려는 것이다.
- 정의 해시 = 타일 내용을 정하는 입력(이름 제외)의 정규 JSON(키 정렬)의 SHA-256, 16진수 64자다.
- 타일 주소: `/api/planets/<ID>/tiles/<타일 ID>?v=<형식 버전>.<생성기 버전>.<정의 해시 앞 16자>`. 목록 정보의 `tileUrlTemplate`에 `{tileKey}` 자리가 있다.
- WebSocket 메시지가 바뀌지 않아 `PROTOCOL_VERSION`은 2 그대로다.

### 목록 정보 (`packages/protocol/src/planetManifest.ts`)
- 필드: `id`, `name`(ko·en), `faceLevel`, `radiusM`(표시용), `generatorVersion`, `definitionHash`, `status`(generating·ready), `tileFormatVersion`, `tileUrlTemplate`, `biomes`(index·id·colour·name), `maxElevationM`(선택, 준비된 뒤에만, 다듬기 통합). 모르는 필드는 버린다(새 서버 + 옛 기기).

### 진입점과 입력
- 1차맵 엔진은 새 진입점 `@terra/engine/planet`의 `createPlanetEngine(container, options)`다. React와 상관없다. 2차맵 진입점(`@terra/engine`)과 나눠서 2차맵 조각에는 1차맵 코드가 없다. three·공용 렌더러·프레임 예약은 두 지도가 같이 쓰는 조각 하나로 묶인다(Verified: 빌드 소스 맵).
- 타일 원천은 `TileSource = (request, signal: AbortSignal) => Promise<DecodedTile>`다.
  - 요청은 `{face, mapLevel, i0, j0, size}`(그 맵 레벨의 칸 좌표)다. size는 32이고, 면이 32칸보다 작은 단계는 면 전체다.
  - 엔진은 동시에 6개까지 부른다. 원하지 않게 된 요청은 signal로 멈춘다.
- `DecodedTile`은 `{faceLevel, mapLevel, face, i0, j0, size, heightsM, biome, water, temperatureC, humidity, forest, river}`다.
  - `heightsM`은 Int16 (size + 1)²개, `temperatureC`는 Int8 size²개, 나머지는 Uint8 size²개다. 배열은 행 우선(j, 그다음 i)이다.
  - 물 비트는 1 바다·2 호수·4 강·8 해안이다. 4~5비트는 수심 등급(1 연안·2 대륙붕·3 심해, 0 모름)이다.
  - 엔진은 받은 타일이 요청·면 레벨·배열 길이와 맞는지 본다. 틀리면 실패로 세고, 그 자리는 부모가 그린다.
- 행성 설명은 `{faceLevel, radiusM, biomeColors, maxElevationM?}`다.
  - 바이옴 색은 번호별 0xRRGGBB다. 없는 번호는 회색으로 그린다.
  - `maxElevationM`은 고르기 경계구·지평선·누르기·먼 자르기 면에 쓴다. 목록 정보의 값(서버가 구울 때 센 가장 높은 칸, 다듬기 통합)을 쓰고, 없으면(옛 서버) 기본 1,000을 쓴다. 받은 타일이 더 높으면 엔진이 그 높이로 늘린다(검토 반영).
- 렌더러는 면 레벨 4~11만 그린다(`MAX_RENDER_FACE_LEVEL`). 그 밖의 행성 설명은 던지지 않고 오류 상태로 알린다(검토 반영).
- 이진 타일은 메시 워커에서 푼다. 원천이 받은 이진을 `{kind: "encoded", bytes}`로 넘기고, 워커가 `decodePlanetTile`로 푼 뒤 엔진이 모양·요청을 확인한다. 통합에서 이었다(아래 "구현하며 정한 것 (통합)" 기기 절). 렌더러 작업 때는 자리만 있었다.
- [임시] 가짜 행성은 `@terra/engine/mock`의 `createMockPlanet()`이다(엔진 단위 시험용, 화면은 서버 타일).
  - 칸 값은 시드 노이즈의 면 레벨 F 칸이다(대륙·산맥·기후 띠·호수·강·해안).
  - 타일은 서버 굽기와 같은 코드(`@terra/planet` 모으기·꼭짓점 평균·타일 만들기)로 만든다. 렌더러 작업 때는 꼭짓점이 그 방향의 점 값이라 레벨 사이 높이 차가 없었다(검토 반영).

### 고르기와 받기
- 화면 오차(CSS px) = 칸 평균 변 × (화면 높이 ÷ (2 tan 20°)) ÷ 타일 경계구까지 거리다.
  - 문턱은 4px다(옵션 `maxScreenErrorPx`). 휴대폰이 힘들면 이 값부터 올린다.
  - 오차가 큰 마디부터 나눈다. 나누면 그릴 타일이 160개를 넘는 마디는 나누지 않는다.
  - 자료 없는 마디(면 레벨 10·11의 맵 레벨 5 ~ F−5)는 상한과 상관없이 늘 나눈다. 가장 거친 단계가 행성에 96개(F = 11) 이하라 상한 안이다. 고른 수가 상한을 넘으면 상한 도달로 센다(검토 반영).
- 부모 먼저: 나눈 마디는 보이는 자식이 모두 올라왔을 때만 자식으로 바꾼다. 아니면 그 마디를 그리고, 그것도 없으면 가장 가까운 윗 마디를 그린다. 그래서 그린 타일은 서로 겹치지 않는다. 가장 거친 1차맵 단계(맵 레벨 F−4) 타일이 없는 곳만 바탕 구가 보인다.
  - 자료 없는 마디는 대신 그릴 수 없으므로 그릴 수 있는 자식을 모두 넘긴다. 첫 단계 타일 하나가 없다고 면 전체를 버리지 않는다(검토 반영).
- 받는 차례는 거친 레벨 먼저, 같은 레벨은 화면 오차가 큰 것 먼저다.
  - 원하지 않게 된 받기는 0.5초 뒤 취소한다. 고르기가 잠깐 흔들려도 다시 받지 않게 하려는 것이다.
  - 실패하면 1초부터 두 배씩 30초까지 기다린 뒤 다시 받는다.
  - 받기 하나가 15초 안에 답하지 않으면 멈추고(abort) 실패로 센다. 브라우저 fetch는 기본 시간 제한이 없어서다. 시간은 원천을 부른 때부터다(원천 안의 기다림 포함, 검토 반영).
- 올리기는 한 프레임에 4개이고, 지금 원하는 것을 먼저 올린다. 남으면 다음 프레임을 예약한다.
- 메모리 추정 = GPU 추정 + JS에 남는 것이다(검토 반영).
  - GPU 추정은 정점 배열과 칸 텍스처의 합이다(타일 하나 50,100바이트, 같이 쓰는 인덱스는 뺀다).
  - JS에 남는 것: three가 올린 뒤에도 들고 있는 같은 배열(50,100바이트)과, 누르기용으로 풀어 둔 타일(8,322바이트)이다. 올린 타일 하나가 약 108KB다.
  - 64MB(`budgets.memoryBytes`, 약 620개)를 넘으면 이번 프레임에 안 쓴 타일을 오래된 것부터 버린다.
  - 맨 위 레벨은 버리지 않는다(늘 부모가 있게).
- 시야 밖 타일은 절두체 평면 6개로 버린다(실수 64비트로 계산).
- 지평선 뒤 타일도 버린다. 기준은 두 각의 합이다: 카메라에서 행성 몸(가장 거친 메시의 활꼴 깊이만큼 작은 구)에 그은 접선 각, 그리고 가장 높은 땅까지의 각.

### 메시·바다·치마
- 정점은 칸 꼭짓점 33×33개 + 치마(네 변 × 33개)다.
  - 면 전체 타일(32칸 미만)은 32마디로 나누고, 높이는 이중선형으로 채운다.
  - 삼각형 인덱스는 모든 타일이 하나를 같이 쓴다.
- 바다: 따로 겹친 바다 구를 두지 않는다.
  - 타일 셰이더가 높이를 max(높이, 0) × 과장만큼 올린다. 그래서 해수면 아래는 해수면 구 위에 그려지고, 칸의 물 비트·수심 등급 색으로 바다가 된다. 본문의 "바다는 해수면 높이의 구"와 모습은 같다.
  - 이유: 구를 따로 두면 타일과 나눔이 달라 해안에서 두 면이 겹쳐 깜박이거나 틈이 생긴다.
  - 바다 밑 지형은 그리지 않는다.
- 법선: 정점마다 높이 기울기(m/m)를 넣고, 셰이더가 정규화(위 − 과장 × 기울기)로 법선을 만든다.
  - 과장을 바꿔도 메시를 다시 만들지 않는다.
  - 타일에 테두리 칸이 없어 가장자리 기울기는 한쪽 차분이다(알려진 문제: 타일 경계에서 음영 선이 살짝 보인다).
- 치마는 모든 타일이 같은 바닥까지 내려간다(검토 반영). 바닥 = 해수면 − (가장 거친 1차맵 단계 마디의 활꼴 깊이 + 30m)다. 지구 크기(F = 9)는 420.9m다.
  - 보이는 높이는 0 아래로 내려가지 않는다. 그래서 어느 레벨의 이웃 변도 이 바닥보다 낮지 않고, 두 변 사이 높이 차를 늘 막는다.
  - 과장과 상관없다. uniform 하나를 모든 타일이 같이 쓴다.
  - 렌더러 작업 때는 치마 깊이 = 활꼴 깊이 + 과장 × 그 타일 높이 범위 + 30m였다. 고운 타일 변이 거친 이웃 변보다 높으면 못 막았다(아래 "렌더러 검토 반영").
- 칸 색: 칸 자료를 텍스처 2장(RGBA = 바이옴·물 비트·기온 + 128·습도, RG = 숲·하천)으로 올린다.
  - 셰이더가 칸마다 그대로 읽는다(texelFetch). 그래서 칸 경계가 또렷하다.
  - 지형 레이어 = 바이옴 색 + 물(수심 등급·호수·강·해안)이다. 기후 레이어 = 기온 색 띠 + 습도다.
- 바탕 구(해수면 1,500m 아래)가 타일이 아직 없는 곳을 채운다. 대기 띠(반지름 × 1.018)는 멀리서만 보인다.
- 시험 전용 틈 찾기(`?planet-debug=cracks`)는 바탕 구·하늘을 자홍색으로 칠한다.
- 셰이더는 three `ShaderMaterial`(WebGL2, GLSL)이다. 타일 재질은 uniform 객체(과장·레이어·빛·바이옴 색표·고른 칸)를 같이 쓴다.

### 카메라 기준 좌표
- three 카메라는 원점에 두고 회전만 준다.
- 타일마다 원점(타일 가운데 방향 × 반지름, 실수 64비트)을 둔다. `mesh.position` = 원점 − 카메라 위치이고, 실수 64비트로 뺀다. 정점은 원점 기준 32비트다. three는 모델뷰를 실수 64비트로 곱한 뒤 32비트로 올린다.
- 시험(Verified: `cameraRelative.test.ts`): 가장 가까운 거리(12km, 기울기 40°)의 맵 레벨 9 타일에서 잰다.
  - 이 방식은 꼭짓점 오차 5mm 아래, 화면 0.01px 아래다.
  - 세계 좌표를 32비트로 보내는 방식은 cm 단위로 틀린다(이 방식의 10배 넘게).

### 카메라와 조작
- 세로 시야각은 40°다. 거리(지구 크기 F = 9 기준):
  - 가장 가까이 = 맵 레벨 F 칸 8개가 화면 짧은 변에 드는 거리(12.0km)
  - 가장 멀리 = 행성 지름 × 1.15가 화면 짧은 변에 드는 거리(3,150km)
  - 처음 = 가장 멀리 × 0.9, 위도 20°·경도 30°
- 기울기: 가장 가까운 거리 × 60(720km)보다 멀면 0°(바로 내려다봄)다. 가까워질수록 로그 거리를 따라 부드럽게 늘어, 가장 가까이에서 40°가 된다.
- 조작
  - 한 손가락 끌기 = 행성 돌리기(잡은 땅이 손가락을 따라온다)
  - 두 손가락 = 확대·방위 돌리기·옮기기(두 손가락 가운데 기준)
  - 휠 = 커서 아래 땅 기준 확대
  - 오른쪽·가운데 끌기 = 방위 돌리기
  - 두 번 누르기 = 그곳으로 2.5배 가까이(0.3초, 기기의 "동작 줄이기"가 켜져 있으면 바로)
- 카메라는 아래 땅(과장한 높이) + 가장 가까운 거리 × 0.3보다 낮아지지 않는다.
- 누르기 = 칸 고르기
  - 화면 광선을 보이는 높이(과장 반영)와 맞대 찾는다(행진 + 이분법).
  - 그곳을 덮은 가장 고운 받은 타일의 칸을 돌려준다: 면·i·j·맵 레벨·셀 키·위경도·높이·바이옴·물·기후.
  - 고른 칸은 노란 테두리로 보인다.
- 렌더러·프레임 예약·컨텍스트 손실 처리·픽셀 비율 상한(휴대폰 1.5)은 2차맵과 같다. 화면이 멈추면 그리지 않는다.

## 구현하며 정한 것 (통합)
2026-10-29 생성기·타일·서버·렌더러를 한 가지에 합치고 끝까지 이었다(작업 기록 `2026/10/29-1250-s2-integration.md`). 상태는 제안 그대로다. NAS·휴대폰에서 잰 뒤 확정한다.

### 이음매를 하나로
- 생성기 출력 모양(`PlanetFields`·`PlanetFieldsMeta`)과 물 비트·수심 등급 상수는 `@terra/planet` 정수 진입점의 `src/tiles/fields.ts` 하나에 둔다.
  - 생성기(`generator/types.ts`)의 사본은 지웠다. 생성기 진입점(`@terra/planet/generator`)은 같은 정의를 다시 내보낸다.
  - 이름은 `WATER_DEPTH_SHIFT`·`WATER_DEPTH_MASK`로 맞췄다(생성기의 `DEPTH_CLASS_SHIFT`·`DEPTH_CLASS_MASK` 대신). 수심 등급 값은 `DEPTH_NONE`~`DEPTH_DEEP`(0~3)이다.
  - 메타 `settings`는 `PlanetSettings`(@terra/shared)다. 값·알고리즘은 바꾸지 않아 골든 해시가 같다.
- 렌더러(`packages/engine`)는 경계 표상 `@terra/planet`·`@terra/protocol`을 가져와도 된다. 그래서 사본을 두지 않고 가져온다. 경계 표는 바꾸지 않았다.
  - `WATER_BITS`는 `@terra/planet` 상수에 이름을 붙인 것이다. 셰이더 문자열의 물 비트·수심 등급 숫자도 그 상수를 넣어 만든다.
  - `DecodedTile = Readonly<Omit<PlanetTileData, "generatorVersion" | "definitionHash">>`다. 해석기(`decodePlanetTile`) 결과를 바꾸지 않고 그대로 받는다.

### 서버: 실제 생성기
- 원본 종류는 `generator` 하나다. 서버가 시작할 때 콘텐츠 팩 `planets`마다 설명을 만든다(`planetSpecsFromPack`).
  - 생성기 입력 = `planetInputFromDefinition(행성 항목, biomes 항목들)`.
  - 범례 = 행성 `biomes` 순서의 `{index, id, colour, name{ko, en}}`. 색·이름은 바이옴 항목에서 온다.
- 생성기가 받지 않는 정의면 서버가 시작하지 않는다(생성기에 `validatePlanetInput`을 내보냈다: 면 레벨 4~9(생성기 검토 반영으로 10 → 9), 세부 수치 범위, 바다·호수·육지 규칙). 팩이 틀린 것과 같게 본다. 굽기를 거듭 실패하는 것보다 낫다.
- 설명(spec)에 순수 JSON 생성기 입력을 넣는다. 굽기 워커는 그것으로 원본을 다시 만들고 생성기 버전·정의 해시가 메인 스레드와 같은지 본다(타일·서버 절 그대로).
- 정의 해시 = `{kind: "generator", faceLevel, seed, settings, biomes: [{id, forestDensity, rule}]}`(바이옴은 행성 순서)의 키 정렬 JSON SHA-256이다.
  - `settings`는 프리셋과 덮어쓰기를 푼 값이다. 원문 대신 푼 값을 넣어서 같은 수치가 되면 다시 굽지 않는다.
  - 이름·설명·색은 넣지 않는다. 캐시 키(생성기 버전 + 정의 해시 + 타일 형식 버전)는 그대로다.
- 굽기 워커는 생성기 단계(9개)가 끝날 때마다 메모리를 잰다(`onStage`). 단계 안의 순간 최대는 잴 수 없다(워커가 계산 중이라 타이머가 돌지 않는다).
- [임시] 합성 원본(`TEMP_S2_PLANET`, `synthetic.ts`)과 그 시험을 지웠다.
  - 서버 시험 원본(`smallSource`)은 팩 S2 시험 행성 정의를 작은 면 레벨(기본 5)로 실제 생성기에 돌린다(약 0.1초).
  - 팩 행성을 면 레벨 5로 만든 결과 해시가 생성기 골든 값과 같은지 서버 시험도 본다(출력 판 2 `5c984c77`, 판 1은 `3321d859`).

### 기기: 서버 타일
- [임시] 시험 화면이 여는 행성 ID는 상수 하나다(`PLANET_ID = "s2_test_planet"`).
- 목록 정보: `GET planetManifestPath(ID)` → `planetManifestSchema`로 읽는다. 같은 행성인지, 읽을 수 있는 타일 형식인지, 주소 틀이 같은 출처인지 본다.
  - 굽는 중이면 Retry-After(없으면 5초)마다 다시 묻고 "만드는 중, N초 뒤 다시 확인" 안내를 띄운다. 429도 Retry-After 뒤 다시 묻는다.
- 타일: `planetTilePath(주소 틀, planetTileKey(맵 레벨, 면, i0, j0))`을 엔진이 준 AbortSignal과 함께 같은 출처 쿠키로 받는다.
  - 받은 이진은 그대로 엔진에 넘긴다(`{kind: "encoded", bytes}`). 메시 워커가 `decodePlanetTile`로 풀고 모양·요청 칸 범위를 확인한다. 워커가 없으면 화면 스레드에서 같은 함수를 쓴다.
  - 이진은 복사해서 워커에 보낸다(약 8KB). 워커가 죽으면 같은 입력으로 화면 스레드에서 다시 만들기 위해서다.
- 메시 워커는 진입점 `@terra/protocol/planetTile`에서 해석기를 가져온다.
  - 묶음 전체(`@terra/protocol`)를 가져오면 zod 메시지 스키마까지 워커에 들어간다(빌드로 확인: 메시 워커 6.4kB → 103kB. 진입점으로 8.1kB).
  - 그래서 `ProtocolError`를 `errors.ts`로 옮겼다. 메시지 의미는 그대로라 `PROTOCOL_VERSION`은 2다.
- 실패
  - 429·409는 Retry-After까지 새 타일 요청을 미룬다. 엔진은 실패한 타일을 1~30초 뒤 다시 받는다.
  - 타일 401은 로그인 상태를 다시 확인하고 안내한다. 타일 404(판이 바뀜)는 [다시 시도]를 띄운다.
  - 목록 정보 실패(401·404·네트워크·서버·읽지 못함)는 이유 문구와 [다시 시도]를 띄운다. 다시 시도는 화면 안쪽을 새로 만든다(목록 정보부터).
- 엔진은 목록 정보를 받은 뒤에 만든다. 그 전에 고른 레이어·고도 과장도 엔진에 넘긴다(Playwright로 확인).
- 바이옴 이름은 목록 정보 범례(ko·en)에서 온다. 가짜 행성(`@terra/engine/mock` `createMockPlanet`)은 엔진 단위 시험에만 남는다.

### 정한 것
- 치마 바닥 = 해수면 − (가장 거친 1차맵 단계 마디의 활꼴 깊이 + 30m)(`skirtDepthM`). 모든 타일이 uniform 하나(`uSkirtDepth`)를 같이 쓴다.
  - 면 레벨 4·6·9·10·11에서 42.2·78.9·420.9·225.5·127.7m다. 면 레벨 10·11은 가장 거친 단계가 맵 레벨 6·7이라 더 얕다.
  - 막는 이유: 보이는 높이는 max(높이, 0) × 과장이라 0 아래로 가지 않는다. 그래서 어느 타일 변도 해수면 − 가장 거친 활꼴 깊이보다 낮지 않다. 높은 쪽 타일의 치마는 바닥까지 내려가므로 낮은 쪽 변을 늘 지나친다.
  - 맞닿은 두 변과 치마는 같은 대원 평면 위에 있다(면 변은 대원이고, 치마는 반지름 방향으로 내린다). 그래서 그 평면에서 두 선을 견주면 된다(`skirt.test.ts`).
  - 과장과 상관없다. 과장을 바꿀 때 타일마다 치마를 고치던 일(`updateSkirt`)을 지웠다.
  - 치마가 깊어진 만큼 그리는 조각(fragment)이 늘 수 있다. 휴대폰에서는 재지 않았다(Unknown).
- 메모리 상한 `budgets.memoryBytes`(이름을 `gpuMemoryBytes`에서 바꿈) = GPU 추정 + JS 사본(`GpuTile.retainedBytes`) + 풀어 둔 타일(`decodedTileBytes`).
  - 올린 타일 하나는 108,522바이트다(GPU 50,100 + JS 사본 50,100 + 풀어 둔 타일 8,322). 64MB면 약 618개다. 예전 셈으로는 약 1,340개였다.
  - 올린 뒤 JS 배열을 버리는 길(three `onUpload`)은 택하지 않았다. 컨텍스트 복구 때 three가 다시 올릴 배열이 없어져 타일을 다시 받아야 한다(iOS 앱 전환마다).
- 가장 높은 땅 = max(행성 설명 값(없으면 1,000m), 지금까지 만든 타일의 가장 높은 꼭짓점)이다. 낮추지 않는다.
  - 모으기(2×2 평균)는 봉우리를 낮춘다. 그래서 아직 받지 않은 고운 타일의 봉우리는 모른다. 목록 정보 값이 정답이다.
- 렌더러 면 레벨 상한은 11이다(`MAX_RENDER_FACE_LEVEL`). 생성기는 면 레벨 4~9만 받는다(생성기 검토 반영).
  - F = 11은 가장 거친 단계(맵 레벨 7)가 행성에 96개라 상한 160 안이다. F = 12는 384개라 먼 거리에서 160개를 넘는다(검토 실험: 가장 먼 거리 198개).
  - 그릴 수 없는 설명(면 레벨·반지름·가장 높은 땅)은 던지지 않고 오류 상태(`{kind: "error"}`)로 알린다. 화면은 오류 안내를 띄운다.
- 받기 시간 제한은 15초다(`FETCH_TIMEOUT_MS`). 원천을 부른 때부터 잰다.
  - 서버 타일 원천은 429·409 뒤 Retry-After까지 원천 안에서 기다린다. 지금 서버는 1초(429)·5초(409)라 15초 안이다.
  - Retry-After가 15초를 넘으면 기다리던 받기가 시간 제한에 걸려 실패로 세지고, 1~30초 뒤 다시 기다린다(요청은 보내지 않는다).
  - 화면이 멈춰 있어도 시간 제한 때 한 번 깨워 그린다.
- 통계에 단계별 그린 타일 수(`tilesDrawnByLevel`), 타일 메모리(`memoryBytes`), 가장 높은 땅(`maxElevationM`)을 더했다. 시험 화면은 `data-levels`·`data-memory-bytes`·`data-max-elevation`을 달고, HUD 성능 줄에 "타일 메모리"를 보인다.
- [임시] 가짜 행성은 면 레벨 F 칸 값을 만들고(`generateMockFields`, 생성기 출력 `PlanetFields` 모양), 타일은 `@terra/planet`의 `aggregatePlanetLevels`·`planetCornerHeights`·`buildPlanetTile`로 만든다(`createMockTileMaker`). 엔진 단위 시험과 화면 스레드 대체 경로가 같은 규칙을 쓴다.

## 구현하며 정한 것 (셰이더 측정)
2026-10-29 셰이더 측정판(작업 기록 `2026/10/29-1210-s2-webgpu-bench.md`, 리뷰 반영 `2026/10/29-1505-s2-webgpu-bench-review.md`, 조사 `docs/research/2026-10-29-webgpu-vs-webgl2.md`). 상태는 제안 그대로다. 셰이더 언어는 휴대폰 값을 본 뒤 사용자가 정한다.

### 측정판
- 관리자 화면 아래 "셰이더 측정 (S2)". [측정 시작]을 누를 때만 측정 코드(`three`·`three/webgpu`·`three/tsl`)를 받는다(지연 조각). 측정 조각은 서비스 워커 미리 캐시에서 뺐고(`assets/gpuBench*.js`), `check-pwa`가 막는다. 결과는 표와 복사할 요약 글이다. 서버로 보내지 않는다.
- 방식 3개: WebGL2 + GLSL(`WebGLRenderer` + `ShaderMaterial`), WebGPU + TSL(`WebGPURenderer`), WebGL2 + TSL(`forceWebGL`). WebGPU가 없으면 three가 WebGL2로 바꾼다. 판은 "WebGL2로 바뀜"으로 적고 뒤의 WebGPU 측정은 건너뛴다.
- 일감: 33×33 정점 타일(치마 포함 정점 1,221개·삼각형 2,304개, 인덱스 공유, 정점 색, 셰이더 빛) 40·160·320개 + 바다 구. 타일 원점은 메시 위치(카메라 기준 좌표). 카메라는 12초에 한 바퀴, 반지름 1.75~4.25배를 오간다. 몸풀기 1초 + 재기 6초. 픽셀 비율 상한은 엔진과 같다.
- 같은 일을 재게 한 것(리뷰 반영)
  - TSL 두 방식은 `renderer.highPrecision = true`로 모델뷰를 CPU에서 64비트로 곱한다(이 ADR의 카메라 기준 좌표 규칙). three 기본은 셰이더에서 32비트로 곱한다.
  - 컴파일은 재질마다 물체 하나(첫 타일 + 바다)로 한다. WebGL은 링크 확인까지 컴파일 단계에서 끝낸다(`getUniforms()`). 나머지 타일은 그 뒤 넣는다. 비교는 "컴파일 + 첫 그리기"로 한다(버퍼 올리기 단계가 렌더러마다 달라서).
  - 방식 순서는 타일 수마다 한 칸씩 돌린다. 그 API를 처음 켠 줄에 `first_use`, WebGPU 호환 모드라 MSAA가 꺼진 줄에 `no_msaa`를 붙인다. 첫 어댑터 요청 시간을 따로 적는다.
  - GPU 완료 지연은 두 API 모두 프레임 시작에서 확인한다(프레임 단위로 올린 값). API끼리는 GPU 완료/초로 비교한다.
  - 어댑터 확인·초기화·컴파일·첫 프레임 기다림은 시간 상한과 [멈춤]으로 그만두고, 늦게 생긴 렌더러는 버린다.
- 잰 값: 받기·초기화·장면·컴파일·첫 그리기·첫 프레임, 프레임 간격 p50·p95, `render()` CPU 시간, GPU 완료 지연과 GPU 완료/초, 그리기 수, JS 힙, 받은 JS 크기(전송/원본). 준비 합계 = 초기화 + 장면 + 컴파일 + 첫 프레임(받기 뺌). GPU 완료 알림이 하나도 안 오면 "실패"다(헤드리스 WebGPU가 그렇다).
- `apps/game`이 `three` 0.186.1과 `@types/three` 0.186.0을 직접 적는다. 엔진과 같은 판이라 새 꾸러미는 없다(잠금 파일은 링크만 바뀜). 엔진과 판을 함께 올린다.

### 헤드리스 결과와 권고 (휴대폰 값이 아니다)
- 화면 있는 Chromium 153 + SwiftShader(두 API 모두), 390×844 → 그리기 585×1266, MSAA 4, 6번 실행(고친 측정판).
- 셰이더 준비는 비슷하다: 컴파일 + 첫 그리기 중앙값 65~169ms, 순위가 타일 수마다 바뀐다. 앞 판의 "TSL 컴파일 5~8배"는 측정 방법 탓이었다(GLSL의 링크 확인·버퍼 올리기가 첫 그리기에 있었다).
- `render()` CPU 시간은 TSL이 약 2.5~3배다(160타일 1.2ms 대 2.9~3.1ms, 320타일 2.2ms 대 6.3~6.6ms, 둘 다 카메라 기준 좌표를 지킨 조건).
- GPU 쪽은 세 방식이 오차 안에서 같다(GPU 완료/초 ≈ fps, 소프트웨어 GPU가 병목). 초기화 비교는 순서·데움에 따라 달라 근거로 쓰지 않는다.
- 묶음: 같은 일을 하는 코드가 gzip 130.5KB 대 241.1KB(+110.6KB, brotli +85.3KB).
- 권고: 지금은 WebGL2 + GLSL 유지(이 ADR의 렌더러 계획 그대로). 헤드리스로는 이쪽이 더 분명해졌지만 GPU 쪽은 휴대폰에서만 알 수 있어, 휴대폰 값이 나오기 전까지 가까운 판단으로 두고 사용자가 정한다. 휴대폰에서 잴 것과 다시 볼 조건은 조사 문서 6·7장.

### WebGPU를 고르면 (렌더러 하나라 S1 엔진도 옮긴다)
- `render/sharedRenderer.ts`(비동기 `init()`, 장치 잃음), `secondMapEngine.ts`(`webglcontextlost` 대신 `onDeviceLost`, three가 되살리지 않음), `units/unitMaterials.ts`(GLSL `ShaderMaterial` 2개 → TSL), `units/unitView.ts`(WebGPU는 1px 점만 → 아이콘을 `Sprite` + 인스턴싱으로).
- 카메라 기준 좌표: 전역 `renderer.highPrecision`은 three 설명에 `InstancedMesh`·`SkinnedMesh`와 함께 못 쓴다고 되어 있고, S1 엔진의 유닛(`units/unitView.ts`)·건물(`buildings/buildingView.ts`)이 `InstancedMesh`를 쓴다. 그래서 행성 타일·바다 재질마다 `material.contextNode = context({ modelViewMatrix: highpModelViewMatrix, modelNormalViewMatrix: highpModelNormalViewMatrix })`로 켠다(셰이더 글로 확인함, `InstancedMesh`와 함께 그려 보지는 않음).
- `compileAsync`는 재질마다 대표 물체 하나로 부른다(three가 물체마다 쉬어 가고, 사파리에는 `scheduler.yield`가 없어 한 프레임씩 기다린다).
- 이 ADR 렌더러의 `ShaderMaterial`·`onBeforeCompile`도 TSL로 바꾼다. troika-three-text(지도 라벨)는 `onBeforeCompile`을 써서 `WebGPURenderer`에서 못 쓴다.
