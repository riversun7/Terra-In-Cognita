## 배경
- 기획 Step 8이 출시 범위를 정했다(Verified: 미러 결정 로그 D-389~D-399).
  - D-389: 출시 3단계 = 내부 플레이판 → 무결제 공개 테스트 → 한국 정식.
  - D-390: 지휘 루프(강하 → 채집 → 생산 → 거래소 판매 → 고용·직무 → 오프라인 정산 → 웨이브 방어)와 원정 루프(탐험 → 조우 전투 → 포획 → 교배)를 같은 깊이로. 둘의 모든 단계가 출시 필수다.
  - D-391: 출시 시점 = NPC 자동 시뮬레이션 시험 통과 뒤. 조건은 독점 없음, 통합·분열 되풀이, 기술 발전과 후퇴. 지표는 세력별 점유율 최대값과 지속 기간, 세력 생성·소멸 수, 세력별 기술 단계 오르내림. 문턱은 설정값.
  - D-393: 출시 경제 = 원장 + 물자 거래소 + NPC 화폐(고정 단계) + 환전. 은행·증권·유저 화폐 발행은 출시 뒤.
  - D-395: 휴먼 수명·사망·상속·환생·신격화까지 출시(시험에서 세대가 돌아야 해서).
  - D-396: 연구 시설·도시를 잃으면 기술 단계가 내려간다. 설계도는 남는다.
  - D-397: 유저도 NPC처럼 자유롭다. `46_Faction_Society.md`의 세력 기능 전체가 출시 범위다(화폐 발행·증권만 잠금).
  - D-398: 콘텐츠 양은 개발자 페이지에서 정한다. 모든 콘텐츠를 거기서 더하고 놓고 켜고 끌 수 있어야 한다. D-399: 아트 = 몸 틀 + 부위 칸 + 색 팔레트, 아이템은 아이콘.
- 기획 세션 의견(자료, 기획 쪽 표기 Assumed): N1이 출시의 길목이 되고, NPC가 유저와 같은 규칙이라(D-013) N1 전에 원장·생산·거래소·조우 전투의 최소판이 필요해 보인다. 기획이 기술 순서를 물었다.

## 1. N1이 돌려야 하는 것 (D-013: NPC도 유저와 같은 규칙)
원칙
- 시뮬레이터는 규칙을 따로 만들지 않는다. 판정·정책 함수는 `packages/sim`에 한 벌 두고 서버와 시뮬레이터가 같은 함수를 부른다(ADR 5 "해결 함수는 메커니즘당 1개").
- 유저가 없으므로 모두 상세도 ③④(예약 이벤트·정산, PLAN 4.4)로 돈다. 전투는 무관측 빨리감기(D-189, 같은 판정)다. NPC에게는 안개가 없다(D-143).

- 합계(Assumed, 대략): N1까지 규칙 줄기 약 20~23 AD(조정 제외). 지도 줄기 6~7 AD, 개발자 페이지 8~10 AD는 함께 간다. 출시까지 모두 약 65~85 AD(조정 제외).
- 함께 갈 수 있는 것
  - R2 ∥ R3: 모듈이 다르다(원장·거래소 / 전투 판정). 겹치는 곳은 `apps/server/src/db/schema.ts`와 마이그레이션이다. 갈래가 생기면 다시 만들지 않고 그대로 합친다(AGENTS.md 6장 Drizzle).
  - 지도 줄기 ∥ 규칙 줄기: 겹치는 곳은 2차맵 배치 칸의 엄폐 값·숲이다. 이 자료를 R3 시선 판정이 쓰므로 V2 설계 ADR에서 칸 형식을 먼저 정한다.
  - D1 ∥ R2~R5. L1의 일부 화면(생산·거래창은 R2 뒤, 전투 화면은 R3 뒤)은 당길 수 있지만, 토큰을 아끼려고 기본은 N1 뒤에 묶는다.
  - 동시 에이전트는 둘이 기본이다(규칙 + 지도·편집기). 셋 이상이면 같은 파일(`schema.ts`, `apps/game/messages/*.json`, 콘텐츠 팩)이 자주 겹친다.
- 토큰 절약
  - 단계를 9개 줄기로 묶었다. 작업 묶음은 단계 안에서 나눈다.
  - 새 ADR은 되돌리기 어려운 결정이 있는 곳만 쓴다: R1(시뮬레이터 구조), R2(통화 원장·거래소 커밋 방식), R3(ADR 35 확정), V2(2차맵 생성), D1(설정 칸 형식), L2(본서버). 나머지는 이 ADR과 작업 기록으로 간다.
- NAS·본서버
  - 판정이 결정적이라 시험 결과는 기계와 상관없고 걸리는 시간만 다르다.
  - 실시간 부하(R5·L2)는 NAS 값을 하한으로 적는다(1천 유닛당 비용, PLAN 9.9).
  - 공개 테스트는 본서버를 정한 뒤가 맞다고 본다(Assumed: NAS 메모리 약 4GB에 운영 DB와 다른 프로젝트 컨테이너가 함께 있다, `ops/nas-facts.md`).

## 3. 선택지
| 안 | 좋은 점 | 나쁜 점·위험 |
|---|---|---|
| A. 규칙 먼저(헤드리스 시뮬) + 관전판 (추천) | 길목(N1)에 가장 빨리 닿는다. 가장 모르는 일(조정)을 일찍 시작한다. 화면을 규칙이 선 뒤 한 번에 만들어 다시 만들 일이 적다(토큰 절약). 시뮬레이터가 콘텐츠 검증 5단계(헤드리스 회귀, PLAN 7장)를 겸한다 | 사용자가 손으로 해 보는 것이 늦다(R1~N1 동안 관전판·그래프만). 화면을 만들며 규칙 빈틈이 나오면 R단계로 돌아간다. 시뮬과 서버 코드가 갈라질 수 있다 → 규칙 함수는 `packages/sim` 한 벌, 서버는 부르기만, R5부터 NAS 실시간 NPC와 시뮬 지표를 견준다 |
| B. 수직 조각(단계마다 화면까지) | 단계마다 휴대폰에서 해 본다. 느낌 문제를 일찍 찾는다 | N1이 늦다(화면 몫 약 10~15 AD가 앞에 온다, Assumed). 뒤 단계(세력·전쟁)가 앞 화면(생산·거래)을 바꿔 다시 만든다. 토큰이 더 든다 |
| C. 지도·화면 먼저, 규칙은 뒤 | 보이는 결과가 빠르다 | 출시 시점을 정하는 시험(D-391)이 가장 늦다. 규칙이 서기 전 화면은 임시 자료로 만든다 |

- 경제 먼저 / 전투 먼저(A 안에서, 에이전트 하나일 때): 경제 먼저를 추천한다. 유지비 → 만족도 → 반란이 분열의 주된 길이고, NPC 정책과 군대 비용이 경제 신호를 읽는다. 전투는 ADR 35로 설계가 거의 끝나 뒤에 와도 빨리 붙는다. 에이전트가 둘이면 함께 간다.
- 뺀 안: ADR 27 원안(NAS에서 실시간으로 며칠). 수명이 실제 2~3개월이라 세대 교체를 보지 못한다. 실시간 실행은 R5의 보조 확인으로만 남긴다.
- 추천: A + 지도 줄기 동시 + (에이전트 둘이면) R2·R3 동시.

## 4. D-391 측정 계획
- 시뮬레이터
  - 가상 시계: 예약 큐(`packages/sim/src/events`, (시각, 순번) 순서)를 시각 순서대로 비운다. 실제 시간을 기다리지 않는다. 서버는 같은 큐를 실제 타이머로 돈다(`apps/server/src/world/scheduler.ts`가 `now`를 주입받는다, Verified).
  - 상세도: 모두 ③④. 2차맵 안 걷기는 하지 않고, 이동은 경로 길이로 낸 도착 예약이다. 전투는 빨리감기(같은 판정).
  - 결정성: 세계 시드 하나에서 갈라 쓰는 `createRng` 흐름(국가 배치·판단·출생·조우), 같은 시각의 순서 키(S3 예약 큐), 정수 판정(AGENTS.md 4장). 같은 시드 = 같은 결과(R1 통과 기준). 보고서에 판정 판·콘텐츠 판·시드를 적는다(전투 기록과 같은 원칙, PLAN 4.4).
  - 영속: 시험 동안 DB를 쓰지 않는다(메모리). 불변 조건(원장 I1, 음수 잔고, 중복 아이템)은 정한 간격과 끝에 검사한다.
- 지표(사건 기록 → 하루 단위 표)
  - 독점: 하루마다 세력별 도시 몫(정원사 제외), 인구 몫, 영토 칸 몫. 그날 가장 큰 도시 몫 = share_max. 독점 구간 = share_max가 문턱 이상인 연속 날들. 가장 긴 구간의 길이와 세력.
  - 통합·분열: 세력 생김(원인: 반란·독립·새 도시·유목·계정의 NPC 전환)과 사라짐·합쳐짐(멸망·파산·편입·종속) 사건 수, 세력 수 시계열, 30일 구간마다 둘 다 있었는지.
  - 기술: 세력별 기술 단계 시계열, 오름·내림 수, 내림 원인(시설 파괴·도시 잃음), 시작·끝 평균.
  - 조정용으로 함께 적는 것: 국고, 도시별 생필품 가격, 만족도 평균, 인구, 웨이브·전쟁 수, 굶어 멈춘 국가 수, 불변 조건 위반.
- 판정: 질문 119의 문턱(새 설정 칸). 답이 오기 전에는 기술 기본안(가)으로 본다.
- 실행 묶음: 시드 5개 × 실제 180일 분량(기본안). 빠른 확인은 시드 1개 × 30일 분량.
- 어디서 도나
  - 개발 컨테이너: 만들면서 짧게(30일 분량).
  - 출시 시험: NAS 자체 실행기에서 도는 수동 GitHub Actions 작업. 운영 밖 시험 컨테이너, `cpu_shares` 낮게, 밤 시간. S3 `s3-ramp`와 같은 틀이다.
  - 본서버(맥미니 등)가 생기면 거기로 옮긴다. 판정은 같고 빨라질 뿐이다.
  - GitHub 호스트 러너는 쓰지 않는다(Assumed: 비공개 저장소 무료 분 한도와 작업 6시간 상한, 이번에 문서를 열지 않음).
- 배속: Unknown. R1에서 잰다(빈 세계, 국가 16). 목표(Assumed): 180일 분량이 NAS에서 하룻밤(약 8시간) 안, 곧 약 540배 이상. 모자라면 차례로 ① 판단·정산 주기를 늘리고 ② 시드마다 프로세스를 나눠 4스레드에 돌리고 ③ 그래도 모자라면 시험 세계의 국가·도시 수를 줄인다(규칙은 같고 규모만 다름, 보고서에 적음).
- 보고: JSON + 그래프(새 런타임 의존성 없이 스크립트로 그림) → 작업 기록과 이 ADR. 개발자 페이지 관전판과 관리자 NPC 세계 건강도(D-6047)가 같은 지표 형식을 읽는다.
- 서버와 어긋남 확인: R5부터 NAS 운영 컨테이너의 NPC 세력(실시간)이 같은 지표를 낸다. 같은 기간의 시뮬 지표와 견줘 규칙이 같게 도는지 본다(시드·시각이 달라 값이 같을 필요는 없다).

- RU3 가: M2는 V2 다음, 지도 줄기에서 한다(N1 조건 아님).
- RU5 가(추천대로, 따로 묻지 않음): 만들 땐 개발 컨테이너, 출시 시험은 NAS 밤 시간, 본서버가 생기면 거기.
- RU6 나: 무결제 공개 테스트는 **NAS로 먼저** 연다(추천과 다름). 그래서 L2의 "본서버" 조건을 빼고, L2 점검표에 NAS 상한을 넣는다: 동시 접속 상한(설정값), NAS 메모리 약 4GB(사용 가능 약 2GB)에서 운영 DB·다른 프로젝트 컨테이너와 함께 도는 것, 접속이 많아 느려지면 본서버로 옮길 문턱. 본서버로 옮기는 절차(9.9, arm64 이미지)는 L2 전에 문서로 둔다.

## 6. 기획 세션에 보낼 기술 순서 요약
1. 길목은 N1 NPC 시뮬레이션 시험(D-391)이다. 원장·생산·거래소·조우 전투가 먼저 필요하다는 기획 의견에 동의한다.
2. 여기에 세력·도시·점령, 인구·수명·출생, 연구·기술 단계, NPC 정책 틀, 정원사 웨이브가 더 든다.
3. 순서: ① 규칙 틀·시뮬레이터 → ② 경제 코어 ∥ ③ 전투 코어 → ④ 세력·도시·인구·기술 → ⑤ NPC 두뇌·정원사 → ⑥ N1 시험·조정.
4. 그다음 ⑦ 내부 플레이판(두 루프 화면, 개발자 페이지 편집기, 몸 틀 아트) → ⑧ 무결제 공개 테스트 → ⑨ 한국 정식.
5. 지도 줄기(2차맵 낮밤 → 행성 값으로 2차맵 → 벌목이 1차맵에 반영)는 ①~⑥과 함께 간다. N1 조건이 아니다.
6. 시뮬레이터는 따로 된 규칙을 만들지 않는다. 서버와 같은 판정 함수를 빠른 가상 시계로 돌린다(D-013).
7. 판정이 결정적이라 같은 시드는 늘 같은 결과다. 실패한 세계를 다시 열어 원인을 본다.
8. 시험 기본안: 실제 180일 분량 × 시드 5개, 도시 수 점유율(질문 119).
9. N1을 막는 기획 빈 곳은 셋이다: 시험 문턱(119), 휴먼 출생(120), 기술 단계가 여는 것(121).
10. 122(물자 체결 방식)는 경제 코어, 123(공개 테스트 세계)은 공개 테스트 환경에 걸린다.
11. Step 5 수치는 막지 않는다. 출발값 없는 칸은 기술이 시험값을 넣고 조정한다(49 "개발자 패널에서 채운다").
12. 화면은 규칙이 선 뒤 묶어 만든다. 그 사이 진행은 개발자 페이지의 관전판(세력 몫 그래프·영토 지도)으로 본다.
13. 순서·동시 진행 수는 사용자 결정 전이다(이 ADR 5절).

## 이유
- 출시 시점이 N1 결과로 정해지고(D-391), 조정이 가장 모르는 일이다(Unknown). 그래서 규칙 줄기를 길목으로 두고 먼저 닿게 한다.
- 같은 규칙(D-013)을 지키는 가장 싼 길은 판정 함수 한 벌 + 가상 시계다. 시뮬용 규칙을 따로 두면 서버와 어긋나는 것을 늘 확인해야 한다.
- 지도 줄기는 N1 조건이 아니면서 출시에는 필요하다(원정 루프의 탐험, 사용자 요구 PLAN 5.4). 다른 모듈이라 동시에 가도 덜 부딪친다.
- M2는 2차맵 변경 오버레이 위에 선다. 오버레이는 "2차맵을 행성 값에서 만들기"(PLAN 5.4) 위에 선다. 그래서 그 뒤가 자연스럽다(Assumed: V2 설계 ADR에서 다시 본다).
- 화면을 뒤로 묶는 것은 D-390 두 루프가 서로 엮여(생산 → 거래소 → 고용 → 웨이브) 규칙이 다 서야 화면 흐름이 굳기 때문이다(Assumed).

## 결과
- 확정하면
  - 통합 담당이 PLAN 11장의 M2·N1·이후 줄을 2절 표로 바꾸고, 11장 "예상 총 기간"을 AD로 다시 적는다.
  - ADR 27 상태를 "확정 (일부 대체됨: `2026-10-31-roadmap-to-launch.md` — N1의 자리(M2 다음 → 규칙 줄기 끝)와 내용(며칠 실시간 → 빠르게 도는 시험, 통과 기준 D-391))"으로 바꾼다. 본문은 고치지 않는다.
  - PLAN 7장 5단계(헤드리스 시뮬레이션 회귀)는 R1 시뮬레이터로 시작한다.
- 좋은 점: 출시 조건을 재는 도구가 가장 먼저 생긴다. 콘텐츠를 바꿀 때마다 같은 시험을 다시 돌려 세계 건강을 본다.
- 감수할 점
  - 사용자가 손으로 해 보는 시점이 L1이다(그 전에는 관전판과 지금 만든 화면).
  - 시뮬 조정이 길어지면 출시가 그만큼 밀린다(D-391이 출시 조건이라).
  - 규칙 함수를 `packages/sim`으로 모으면서 서버의 일부 코드(정산 등)를 옮기는 일이 생긴다.
- 다시 볼 조건
  - 질문 119~123의 답.
  - R1 배속 측정값(목표에 크게 못 미치면 4절 대책 차례를 다시 정함).
  - N1 조정이 4 AD를 넘을 때: 규칙 문제인지 수치 문제인지 보고하고 사용자와 정한다.
  - 본서버 결정(L2 앞), 기획 Step 8의 나머지 묶음(출시 판 시스템 등급 등).
