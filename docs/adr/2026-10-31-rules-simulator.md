# 규칙 시뮬레이터(R1): 서버와 같은 판정 함수를 가상 시계로 돌린다

- 상태: 제안
- 날짜: 2026-10-31
- 관련: ADR `2026-10-31-roadmap-to-launch.md`(R1 행, 4절), `2026-10-31-n1-real-time-gate.md`(조정 시뮬과 출시 관문을 나눔), `2026-10-31-s3-server-stage.md`(예약 차례 키·원장·정산·불변 조건), `2026-10-28-simulation-model.md`(5), `2026-10-28-economy-ledger.md`(8), `2026-10-28-npc-scale-and-stage.md`(27), 기획 D-013·D-098·D-324·D-391·D-410·D-412, 질문 119(D-412로 기본안 받음), 작업 기록 `docs/worklog/2026/10/31-1800-rules-simulator-r1.md`

## 배경
- 규칙 줄기의 첫 단계 R1이다. 규칙(R2~R5)을 화면 없이 시뮬로 확인한다(사용자 결정 RU1).
- NPC도 유저와 같은 규칙을 따른다(D-013). 그래서 시뮬레이터가 따로 된 규칙을 가지면 안 된다. 서버가 쓰는 `packages/sim` 판정 함수를 그대로 불러야 한다.
- 시뮬레이터의 쓰임은 개발 중 규칙·설정 조정이다. 출시 관문(N1)은 실제 시간으로 몇 달 돌린다(D-410·D-412, ADR `2026-10-31-n1-real-time-gate.md`). 그래서 속도 목표는 "조정이 하루에 여러 번 돌 만큼"이다. 지표는 관문과 같은 모양이어야 한다.
- 지금 있는 것(Verified: main `c4c5457` 파일 읽기)
  - 예약 큐 `packages/sim/src/events/eventQueue.ts`는 (시각, 예약 번호) 차례다. 서버는 다시 켤 때만 (시각, 종류, 유닛 ID)로 정렬해 다시 걸었다(`secondMap.ts` restore).
  - 원장의 판단(복식부기 거절·잔고)은 서버 `apps/server/src/economy/ledger.ts` 안에 쓰기 대기열과 섞여 있었다.
  - 소유 주체 정산(유지비 거래·산출 거래 묶기)은 서버 `world/settlement.ts` 안에 있었다. S3 ADR이 "R1에서 `packages/sim`으로 옮길 후보"라고 적었다.
- 이 결정이 되돌리기 어려운 까닭: R2~R5의 규칙 코드와 N1 지표가 모두 이 틀(루프·장부·기록기·출력 형식) 위에 선다.

## 결정
### 1. 구조
```
packages/sim/src/
  events/eventKey.ts      같은 시각 차례 (종류, 대상) — 서버 2차맵 예약과 시뮬이 같이 쓴다
  ledger/ledgerBook.ts    원장 장부(복식부기·잔고). 서버 원장 = 이 장부 + DB 쓰기 고리
  ledger/audit.ts         메모리 불변 조건 I1·I2·I6(문구는 서버 SQL 검사와 같은 상수)
  settle/owner.ts         소유 주체 정산(시험 직무·유지비 → 장부 거래). 서버 settlement.ts가 부른다
  simulator/loop.ts       가상 시계 실행 루프
  simulator/scenario.ts   시나리오 형식·검사
  simulator/world.ts      세력·도시·유닛·장부, 정산·도시 옮기기·불변 조건(I4·I5·I6)
  simulator/stubRules.ts  [임시] 대리 규칙(게임 규칙 아님)
  simulator/metrics.ts    D-391 지표 기록기(시계를 모른다 → 실제 시간 관문도 같은 것)
  simulator/run.ts        차리기 → 하루마다 비우기·정산·기록·검사 → 요약
packages/sim/cli/         sim.ts(실행), speed.ts(속도), common.ts(시나리오·팩 읽기). Node API는 여기만
packages/sim/scenarios/   stub16.json(빈 세계, 국가 16), synthetic.json(속도용 이동 부하)
```
- 경계(AGENTS.md 4장): `src/`는 Node·DOM·엔진을 쓰지 않고 결정성 검사를 받는다. `cli/`는 `src/` 밖이라 걸린 시간을 재고 파일을 쓴다. 팩 읽기(`@terra/content/node`)는 `cli/`만 한다(`@terra/sim` → `@terra/content`는 원래 허용된 방향).

### 2. 실행 루프와 차례 키
- 가상 시계: `runUntil(t)`는 시각 < t인 예약을 차례로 꺼내 처리하고, 처리 중 시계는 그 예약의 시각이다. 끝나면 시계는 t다. 타이머·실제 시각이 없다. 지난 시각에 예약하면 거절하고, 처리 함수가 던지면 멈춘다(숨기지 않는다).
- 차례 키 = (시각, 종류, 대상, 예약 번호). 종류는 문자 코드 순서로 비교한다(`localeCompare`는 실행 환경 지역 설정을 탄다). 큐가 이 키로 차례를 정하므로 넣은 차례(실행 이력)와 상관없이 상태만으로 차례가 정해진다.
- 서버도 같은 키를 쓴다: 2차맵 스케줄러에 같은 비교 함수를 넘겼다. 실행 중 차례 = 다시 켤 때 차례가 됐고, restore의 따로 된 정렬을 지웠다. 서버 시험(DB 시험 포함)은 그대로 통과했다(Verified).
- `SIM_VERSION`은 올리지 않았다: 큐의 기본 동작(차례 함수 없음)은 그대로이고, `packages/sim` 판정 함수의 같은 입력 결과는 바뀌지 않았다. 서버 봇의 같은 시각 처리 차례만 바뀌었다(봇 판단 난수는 (시드, 유닛, 횟수)라 차례와 무관하고, 워커 경로 결과가 오는 시각은 원래 매번 달랐다).

### 3. 원장과 정산을 한 벌로
- 장부가 판단한다: 자산마다 합 0, 주체 계정 0 아래 금지, 모르는 계정·빈 거래 거절, 틀리면 아무것도 바꾸지 않음. 고리 `accountCreated`·`posted`로 바깥에 알린다. 서버는 고리에서 거래·항목·잔고를 쓰기 대기열에 넣는다(쓰는 행은 전과 같다).
- 시뮬은 DB가 없어서 감사(`createLedgerAudit`)가 고리로 항목을 따로 더해 두고(장부의 잔고 계산과 다른 길) 하루마다 견준다: I1(자산 합·거래별 합), I2(잔고 = 항목 합, 주체 잔고 ≥ 0), I6(중복 방지 키 하나). 메모리는 계정당 BigInt 하나 + 키 집합이다.
- 소유 주체 정산(`settleOwnerPeriod`)을 서버에서 옮겼다. 서버와 시뮬이 같은 함수로 유지비·산출 거래를 낸다. 시험 자산 코드(`s3_test_*`)도 sim 상수가 원본이다(서버는 다시 내보내기만).

### 4. 세계 차리기
- 시나리오(JSON, `packages/sim/scenarios/`): 세력 무리(코드·수·고정 여부·도시 수·일꾼 수·처음 시험 화폐·기술 단계), [임시] 대리 규칙 손잡이, 선택으로 유닛 이동 부하.
- 콘텐츠 팩은 실행 도구가 읽어 판·해시를 머리 줄·요약에 적고, 시나리오가 가리키는 행성 ID가 팩에 있는지 본다.
- 팩 분류(국가 프리셋·아이템·레시피·시설)는 R1에서 만들지 않는다(기술 순서 ADR R1 행과 다름). 그 모양은 규칙을 만드는 단계(R2 경제, R4 세력·도시)에서 나온다. 지금 정하면 ID를 다시 쓸 수 없는 팩에 곧 바뀔 모양을 남긴다. 그 분류가 생기면 시나리오는 팩 ID와 개수만 가리킨다.
- 소유 주체 = 세력(시뮬에는 유저가 없다). NPC는 늘 접속 중이다(서버와 같다). 도시를 옮기기 전에 두 세력을 지금까지 정산한다(상호작용 전 정산, S3 ADR 4절).

### 5. 결정성
- 세계 시드 하나에서 (흐름, 대상, 차례)로 갈라 쓰는 `createRng`(차림·판단·이동 흐름). 한 대상의 판단 수가 다른 대상의 난수를 바꾸지 않는다.
- 정수만 쓴다(금액 BigInt, 몫은 만분율 정수, 평균은 천분율 정수). 출력 객체의 칸 차례가 고정이다(이름 차례로 놓는 칸은 정렬).
- 걸린 시간은 줄·요약에 넣지 않는다(표준 오류로만). 그래서 같은 (시나리오, 시드, 날 수, 콘텐츠 판)이면 줄 파일과 요약이 바이트까지 같다. 요약의 `linesHash`(FNV-1a)가 지표 해시다.

### 6. 지표 기록기와 출력 형식(관전 그래프용)
- 기록기는 시계를 모른다. 사건(`born`·`died`·`tech`)은 시각을 받고, 하루 몫(`day`)은 부르는 쪽이 하루가 끝날 때 넘긴다. 그래서 실제 시간 관문의 서버도 같은 기록기를 부르면 같은 줄이 나온다(관리자 NPC 건강도 D-6047, 개발자 관전판).
- 날은 실제 24시간(D-391)이다. "N일째"는 1부터 센다.
- JSON 줄 종류(형식 판 `SIM_OUTPUT_FORMAT` = 1)
  - `header`: 형식 판, 판정 판, 시나리오, 시드, 날 수, 시작 시각, 콘텐츠 판·해시.
  - `start`: 처음 세력(고정 여부, 기술).
  - `born`·`died`·`tech`: 시각, 날, 세력, 원인(+ 부모·흡수한 세력·전후 단계).
  - `day`: 날, 도시 합, 도시 몫 최대(만분율)와 그 세력, 세력마다 {도시, 인구(유닛 수), 기술, 국고}. 조정용 칸은 R2~R5에서 더한다(읽는 쪽은 모르는 칸을 무시한다).
  - `summary`: 아래 요약.
- 요약: 세 조건(질문 119 기본안, D-412: 도시 몫 40% 이상이 한 번에 30일을 넘지 않음 / 30일 구간의 5/6 이상에서 생김·사라짐 / 내려간 적 있는 세력 30% 이상 + 끝 평균 > 시작 평균)의 값과 통과 여부, 날마다 계열(세력 수·몫 최대·기술 평균), 원인별 수, 예약 수, 장부 거래 수, 불변 조건 검사·위반, 줄 수·해시. 문턱은 기록기 매개변수다(설정 칸 49 S38이 생기면 거기서 읽는다).
- 관전판 자리(R1은 만들지 않음): 개발자 페이지 아래 새 화면(`/dev` 밑, dev·admin 권한, 예: `/dev/sim-watch`). 서버가 실행 결과 파일이나 실시간 기록기의 줄을 tRPC 조회로 넘기고, 화면은 `day` 줄로 세력 몫 쌓은 그래프·기술 선, `born`·`died`로 사건 표시를 그린다.

### 7. 대리 규칙 [임시]
- 게임 규칙이 아니다. 기록기·루프·장부·정산이 함께 도는지 보려고, 세력 판단 예약마다 시드 난수로 도시 빼앗기·반란(새 세력)·기술 오르내림을 일으킨다. 도시를 모두 잃은 유동 세력은 사라지고 자산은 이긴 쪽이 받는다. 고정 세력은 마지막 도시를 잃지 않는다(D-324).
- 대리 규칙으로 나온 D-391 결과는 아무것도 말하지 않는다. R4·R5가 이 파일을 대신한다.

## 이유
- 판정 함수 한 벌 + 가상 시계가 D-013을 지키는 가장 싼 길이다(기술 순서 ADR 이유). 시뮬용 규칙을 따로 두면 서버와 어긋나는지 늘 확인해야 한다.
- 차례를 키로 정하면 같은 상태에서 같은 차례가 나온다. 서버가 다시 켤 때와 실행 중 차례가 같아지고, 시뮬을 중간에 저장했다 이어 돌리는 일(실패한 세계를 다시 열어 보기)도 같은 차례를 지킨다.
- 장부 판단을 한 곳에 두면 R2(통화별 계정·에스크로)를 한 번만 고친다. 저장 방식(DB 묶음 커밋 / 메모리)만 고리로 갈린다.
- 팩 분류를 R2·R4로 미루는 것: 콘텐츠 ID는 다시 쓸 수 없고(PROTECTED), 모양은 규칙이 정한다. 토큰도 아낀다(사용자 선호 "간단하게").
- 실행 도구를 `packages/sim/cli/`에 둔 것: 빌드 없이 `node`로 바로 돌고(행성 bench와 같은 방식), 서버 모듈이 필요 없다. 서버 이미지 안에서 돌릴 일이 생기면 `cli.js`에 같은 `runSimulation`을 부르는 명령 하나를 더한다(서버는 원래 `@terra/sim`을 쓴다).

## 결과
- 좋은 점: R2~R5가 규칙 함수를 `packages/sim`에 더하고 대리 규칙 자리에 끼우면 바로 시뮬로 돈다. 서버와 같은 장부·정산·차례를 쓴다. 같은 시드는 같은 결과라 실패한 세계를 다시 연다.
- 감수할 점
  - 서버의 같은 시각 처리 차례가 바뀌었다(위 2절, 판정 결과 영향 없음).
  - 대리 규칙은 의미 없는 결과를 낸다. 요약의 통과 표시를 판단에 쓰지 않는다.
  - 시나리오 형식은 임시다. 팩 분류가 생기면 바뀐다(형식 판으로 구분).
- 다른 ADR에 생기는 일(확정할 때 표시)
  - 기술 순서 ADR R1 행: 팩 분류 형식과 서버 관리 명령은 이 ADR 4절·이유대로 미뤘다.
  - S3 ADR 1절 "예약 큐는 같은 시각이면 넣은 차례를 지키므로 큐는 고치지 않았다": 이제 큐가 차례 키를 받는다(이 ADR 2절).
- 다시 볼 조건: 진짜 규칙의 예약 하나가 무거워 조정 한 번이 몇 시간을 넘을 때(그때 ① 판단 주기 늘리기 ② 시드마다 프로세스 나누기 ③ 시험 세계 줄이기, 기술 순서 ADR 4절 차례), 관문 서버가 기록기를 붙일 때 줄 형식이 모자라면 형식 판을 올린다.
