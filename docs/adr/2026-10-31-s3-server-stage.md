## 배경
- PLAN 11장 S3 줄(Verified): "유닛 10만 개(유저 + NPC 세력 합계) 이벤트 예약 + 시야 전송 + NAS 밖 봇 1~2천 + 임시 전투 공식 + 오프라인 정산 + `kill -9` 복구". 통과 기준은 "이벤트 루프 지연 p99 < 50ms, 복구 < 60초 + 불변 조건 유지"다.
- 사용자 결정(2026-10-31, 원문): "동시 진행하라 10만테스트는 사실상 안해도 될거같긴하다 2차맵에서 1000개 유닛을 확인해서 충분하긴한듯"
  - S3는 행성 편집기 일과 동시에 한다.
  - 10만 유닛 규모 시험은 뺀다. S1에서 서버 경로 유닛 1,000개를 이미 봤다: 휴대폰 약 120fps, NAS 이벤트 루프 1분 p99 0.9~1.5ms, CPU 평균 1.54%(Verified: ADR 33 "S1 측정").
  - 기능은 남긴다: 이벤트 예약, 시야 전송, 오프라인 정산, `kill -9` 복구, 임시 전투 공식.
- 지금 코드(Verified: main `7bec7cb`)
  - 2차맵 월드는 메모리에만 있다(`apps/server/src/world/world.ts`). 유닛·건물·예약이 서버를 다시 켜면 사라진다.
  - 예약 큐(`packages/sim/src/events/eventQueue.ts`)는 (시각, 큐 안 예약 번호) 순서다. 번호는 큐마다 1부터 센다.
  - 볼 수 있는지 확인(`apps/server/src/world/visibility.ts`)은 늘 통과다. 모든 구독자가 모든 유닛의 경로 전체를 받는다.
  - DB에 월드·원장 표가 없다(`apps/server/src/db/schema.ts`: 계정·감사·설정·행성 초안뿐).
  - 복귀 요약(`apps/server/src/summary/summary.ts`)은 자리만 있고 사건 출처가 0개다. 확인 시각 표는 "첫 사건 출처(S3 오프라인 정산)와 함께 만든다"고 적혀 있다.
  - 시험 봇 상한은 20,000이다(`apps/server/src/config.ts` `MAX_TEST_BOTS`).
- NAS(Verified: `ops/nas-facts.md`, `ops/compose.yml`): R1600 2코어 4스레드, 앱 컨테이너 메모리 1GB, HDD라 동기 커밋 1번에 약 77ms(fdatasync), 컨테이너는 `restart: unless-stopped`.
- 기획이 정한 것(요약)
  - 오프라인: 모든 기기 연결이 끊긴 때부터 24시간(D-061·D-136). 그동안 반복 직무·피로 휴식·자동 방어만 한다(D-144). 습격받은 전투 안에서는 작전 성향대로 싸우고, 먼저 전투를 걸지 않는다(D-248). 24시간 뒤 대기에도 유지비 정산은 계속한다(D-162).
  - 유지비 = 유닛마다 필요한 생필품의 합(D-150). 유닛 수 상한은 주거 수용(D-153). 주거가 없으면 노숙: 피로 회복이 크게 줄고 만족도가 떨어지지만 떠나지 않는다(D-245·D-296).
  - 시야: NPC는 안개 없음, 안개와 탐사 기록은 유저만(D-143). 시야 밖 건물은 마지막 본 모습(D-152). 시야 반경은 유닛·건물마다 칸 수(D-107). 시야 = 기본 + WIS(주) + AGI(보조), 세력 단위로 공유(D-5037·D-6036). 같은 세력 = 같은 국가 전체(D-250).
  - 전투: 무관측 전투는 같은 규칙으로 빨리 계산하고 결과만 남긴다(D-189). 피해는 6축 곱(D-178). 지면 부상, 지우지 않음(D-099·D-145·D-173). 제한 시간이 다 되면 수비 승(D-210).
  - 복귀 요약: 생산·습격·부상·세계 소식(D-6014).

## 결정
요약
- 저장: DB가 원본이다. 예약은 그 주인 행의 "예정 시각" 열로 저장하고 부팅 때 다시 건다. 쓰기는 한 줄 대기열 + 0.25초 묶음 커밋이다(U2).
- 복구: 부팅 순서를 정하고, 밀린 예약을 시각 순서로 처리한 뒤 문을 연다. 불변 조건 8개를 부팅 뒤·시험·명령으로 검사한다.
- 시야: 시야 묶음(기술 기본안 = 최상위 세력, 없으면 본인)마다 1초 시야 틱으로 덮인 칸을 계산한다. 남의 경로는 덮인 칸 안 앞부분(최대 8초)만 보낸다.
- 정산: 소유 주체 단위로, 나눠 정산해도 결과가 같은 정수 함수 하나로 한다. 접속 상태가 바뀔 때·상호작용 전·60분마다 정산한다.
- 전투: S3에서 뺐다(U4). ADR 35는 제안 그대로 진짜 설계를 기다린다.
- 규모: 봇 수를 1천 → 10만까지 올리며 처음 무너지는 계단을 찾는다(U1). 그 값이 서버 유닛 상한(ADR 32)의 근거다.
- 새 런타임 의존성은 없다.

### 1. 저장: DB가 원본, 메모리는 캐시 (ADR 6을 구체화)
표(마이그레이션 하나, 모두 새 표라 직전 버전 앱이 그대로 돈다: ADR 22)
| 표 | 내용 |
|---|---|
| `factions` | id, 종류(npc·player), 위 세력(`parent_id`, 봉신용), 코드. S3는 시험 NPC 세력만 쓴다 |
| `faction_members` | 사용자 → 세력(사용자당 한 줄). 시험용 CLI로만 넣는다 |
| `world_owners` | 소유 주체 = 사용자 하나 또는 세력 하나(둘 중 하나만). `settled_at_ms`(마지막 정산 시각), 밀린 유지비 횟수 |
| `world_units` | 소유 주체, 종류·크기 등급·속도, 2차맵 키, 경로(꺾이는 점 정수 배열)·출발 시각, 활동·활동 끝 시각, 피로, HP, 부상 단계·회복 시각, 전투 ID, `ai_step`(판단 횟수) |
| `world_buildings` | 2차맵 키, 소유 주체, 칸 직사각형·회전 |
| `world_presence` | 사용자마다 "모든 연결이 끊긴 시각"(접속 중이면 비움, D-136) |
| `world_exploration` | (사용자, 2차맵) → 탐사한 시야 칸 비트 32×32 = 128바이트 |
| `world_heartbeat` | 한 줄: 부팅 ID, 마지막 생존 시각(10초마다) |
| `ledger_accounts`·`ledger_transactions`·`ledger_entries` | 원장(4절) |
| `summary_acks` | 복귀 요약 마지막 확인 시각(ADR 37 자리) |

- 예약은 따로 된 "이벤트 표"에 두지 않고 주인 행의 예정 시각 열로 둔다. 움직이는 유닛의 도착 = 경로의 도착 시각, 쉬기 끝·부상 회복 = 그 열, 전투 결과 = `battles.ends_at_ms`.
  - 부팅 때 모듈마다 "예정 시각 읽기"를 돌려 큐를 다시 채운다. 그래서 "예약은 있는데 주인이 없다"나 "주인은 있는데 예약이 없다"가 구조상 생기기 어렵다(불변 조건 I5는 그래도 검사한다).
  - 같은 시각의 순서 = (시각, 종류, 대상 ID). 다시 켤 때 이 차례로 정렬해 다시 넣는다. 예약 큐는 같은 시각이면 넣은 차례를 지키므로 큐는 고치지 않았다(Verified: `eventQueue.ts` 머리 주석이 이 방법을 적어 두었다).
  - 주인 없는 예약(예: 세계 사건)이 필요해지면 그때 예약 표를 더한다.
- 쓰기는 한 줄 대기열(`worldWriter`) 하나로 한다.
  - 같은 행의 바뀜은 마지막 것만 쓴다. 넣고 같은 묶음에서 지운 것은 둘 다 쓰지 않는다.
  - 0.25초마다(또는 2,000건이 쌓이면) 트랜잭션 하나로 커밋한다. 진행 중인 커밋은 늘 하나다(순서 보장).
  - "함께 적어야 하는 묶음"(정산 한 번, 전투 결과 적용 한 번)은 트랜잭션 사이에서 나뉘지 않는다.
  - 저장을 기다리는 명령(경제·소유)이 있으면 20ms 모은 뒤 바로 커밋한다. 응답은 커밋 뒤에 한다(U2).
  - 이동·경로 바뀜은 바로 응답하고 다음 묶음에 쓴다(U2 추천안). 죽으면 마지막 묶음 하나(약 0.25~0.35초)의 이동 바뀜이 사라질 수 있다. 다시 켜면 유닛은 그 전 경로를 따른다.
  - DB 쓰기가 30초 넘게 실패하면 프로세스를 끝낸다. 컨테이너가 다시 켜고 DB에서 복구한다(복구 길을 하나로 줄인다).
  - 묶음 커밋은 동기 커밋을 그대로 쓴다. 묶음 하나에 fdatasync 1번(약 77ms)이라 초당 4번이면 디스크가 버틴다(Assumed: Verified 77ms에서 산술). pg 드라이버는 비동기라 커밋을 기다리는 동안 메인 스레드는 다른 일을 한다(Assumed).
- 유닛·건물·전투 ID는 부팅 때 DB의 가장 큰 값 + 1에서 메모리로 센다(쓰는 프로세스가 하나다, ADR 3). 커밋되지 못한 ID는 다시 쓰여도 해가 없다. 유닛 ID는 프로토콜 상한(u32) 안에 있다.
- 잔고는 메모리에 캐시하고, 원장 항목과 잔고 열을 같은 묶음에 쓴다. 최신 값을 읽어야 하는 조회(복귀 요약 등)는 대기열이 비기를 기다린 뒤 DB를 읽는다.
- 종료 신호(SIGTERM): 새 명령을 막고, 대기열을 비우고, 생존 시각을 마지막으로 쓰고 끝낸다(ADR 6).
- Drizzle 1.0 RC의 `bytea`·정수 배열 열 지원은 계약 단계에서 패키지 코드로 확인한다(Unknown). 없으면 사용자 정의 열 타입을 쓴다.

### 2. 복구와 불변 조건
부팅 순서
1. 설정·콘텐츠 팩 → DB 연결.
2. `world_heartbeat`에서 지난 생존 시각을 읽는다.
3. 2차맵마다 임시 지형을 다시 만들고(칸 키로 결정적), 건물을 ID 순서로 놓아 배치 격자를 만든다. 경로 워커 사본도 만든다.
4. 소유 주체·유닛·잔고를 읽는다. 전투 중 유닛은 그 전투에 묶는다.
5. 접속 상태를 고친다: 접속 중으로 남은 사용자는 지난 생존 시각에 끊긴 것으로 친다(오차 10초 이내). `kill -9`는 끊김을 적을 틈이 없기 때문이다.
6. 모듈마다 예정 시각을 읽어 예약을 다시 건다.
7. 지난 예약(예정 시각 ≤ 지금)은 위 차례대로 곧바로 처리한다. 처리 시각은 지금이다. 정산은 예약에 기대지 않고 시각 구간으로 계산하므로(4절) 늦게 처리해도 결과가 같다.
8. 모자란 시험 봇을 만든다(`S1_TEST_BOTS`).
9. 불변 조건을 검사하고 로그에 남긴다. 위반 수는 `/health`의 `worldIssues`다.
10. 준비 완료. 서버는 이때 `listen`한다(Fastify `onReady`가 부팅 복구를 기다린다). 그 전 2차맵 요청은 `busy`다.

- 복구 시간 = `SIGKILL`부터 `/health`가 답할 때까지. 행성 타일 캐시가 이미 있으면 1차맵 준비는 1~3초다(Verified: AGENTS.md 7장 `PLANET_CACHE_DIR` 줄).

### 3. 시야 전송 (ADR 7·26을 구체화)
- 시야 묶음: 같은 것을 보는 사용자 모임이다. 기술 기본안은 최상위 세력(국가, D-250)이고 세력이 없으면 본인 혼자다(기획 질문 S3-Q1). 묶음을 정하는 함수 하나에 모은다.
  - NPC는 안개가 없다(D-143). NPC 판단은 시야를 거치지 않는다.
  - 관리자 전체 보기: 권한 표의 새 동작(admin·dev)이 있으면 묶음 = 전체다. 켤 때 감사 기록을 남긴다. 시험 2차맵을 보려면 필요하다.
- 시야 칸: 배치 칸 8×8 = 시야 칸 하나, 2차맵 하나에 32×32다(약 47m).
  - 반지름은 배치 칸 수다. 임시값: 유닛 24칸(약 140m), 건물 16칸. D-5037 식(기본 + ⌊(WIS × a + AGI × b) ÷ 1000⌋)은 스탯이 생기면 넣는다(수치는 Step 5).
  - 시야 칸 (dx, dy)가 반지름 R(시야 칸 수) 안이면 덮는다: dx² + dy² ≤ R² + R. 정수만 쓴다.
- 시야 틱 1초: 구독자나 유저 유닛이 있는 2차맵만 돈다. 유닛을 시야 칸 버킷에 넣고, 묶음마다 자기 유닛·건물이 덮는 칸을 모으고, 덮인 칸의 남의 유닛만 본다.
- 보내는 것
  - 자기 묶음 유닛: 경로 전체(S1 그대로).
  - 남의 유닛: 보이는 동안만, 경로 앞부분만. 지금 덮인 칸을 벗어나는 곳 또는 8초 뒤에서 자른다(250ms 간격으로 따라가 본다). 보낸 몫이 3초 아래로 남거나 경로가 바뀌면 다음 구간을 보낸다. 안 보이게 되면 `unit_hidden`(마지막 위치)을 보낸다. 서 있는 유닛은 바뀔 때만 보낸다. 전투 중 유닛은 보내지 않는다(ADR 35).
  - 남의 건물: 탐사한 곳의 건물을 보낸다. 마지막 본 모습(D-152, 시야 밖 건물의 바뀜을 숨기기)은 뒤로 미뤘다(작업 지시의 줄일 것 차례).
- 묶음마다 스트림 하나: 지금 `mapStream`을 (2차맵, 묶음)마다 하나씩 쓴다. rev도 묶음마다 따로다. 한 번 인코딩한 바이트를 그 묶음 구독자 모두에게 보낸다(ADR 35와 같은 방식).
- 탐사 기록: 사용자마다 128바이트다. 기술 기본안은 자기 유닛·건물의 시야로만 채운다(기획 질문 S3-Q2). 5초마다 더하고, 바뀐 기록만 1분마다 대기열로 쓴다.
- 지형 파일: 그 2차맵을 한 칸이라도 탐사했거나, 자기 묶음 유닛·건물이 그 2차맵에 있으면 파일 통째로 준다(U3 추천안). 기기는 탐사하지 않은 곳만 검게 칠한다(최소, 작업 지시). 조건이 안 되면 구독은 `not_visible`, 지형 파일은 404다.
- 프로토콜 3: `unit_paths` 항목에 자른 끝 시각(`until`, 남의 유닛만), 새 메시지 `unit_hidden`·`vision`(덮인 칸·탐사 칸 비트), 결과 코드 `not_visible`. 2차맵 메시지에 필요한 버전을 3으로 올린다. 인사는 2도 받지만(현재 + 직전, ADR 7) 2로 인사한 연결의 구독은 거절한다. 새 앱을 받으면 풀린다.
- 누출 시험: 무작위 장면에서 남의 유닛에 대해 보낸 꺾이는 점이 모두 그때 그 묶음의 덮인 칸 안(또는 자른 끝)에 있는지 본다.
- 비용(Verified: 저장소 밖 시험 스크립트, 개발 컨테이너 Xeon 2.1GHz 4 vCPU 공유, Node 24.22.1, 덮기 + 보이는 쌍 세기만, 자르기·인코딩 빼고. NAS 값이 아니다)
  - 2차맵 하나 유닛 1,000개: 묶음 16개 p50 0.52ms, 묶음 1,000개 0.77ms, 묶음 2,000개 0.79ms(p95 1.7ms).
  - 유닛 10,000개·묶음 100개 8.2ms, 유닛 20,000개·묶음 1,000개 61ms(보이는 쌍 960만 개. 쌍 하나 약 6ns). 비용은 보이는 쌍 수가 정한다. 한 2차맵에 2만 개가 서로 다 보이는 경우는 시험용 최악이다.
  - 모든 유닛을 묶음마다 훑으면 1,000 × 1,000에 5.4ms, 2만 × 1,000에 207ms였다. 그래서 칸 버킷을 쓴다.

### 4. 오프라인 정산과 최소 원장
- 접속 상태: 연결(인증된 WebSocket) 수를 사용자마다 센다. 0 → 1이면 그 사용자 소유 주체를 지금까지 정산하고 끊김 시각을 지운다. 1 → 0이면 지금까지 정산하고 끊김 시각을 적는다(D-136). 접속 상태가 바뀔 때마다 정산하므로 두 정산 사이에는 접속 상태가 하나다.
- 정산 단위 = 소유 주체(사용자 또는 세력). 그 주체의 모든 유닛·지갑을 한 번에 시각 순서로 정산한다. 지갑이 모자랄 때 어느 유닛 몫을 먼저 내는지가 정산 순서에 따라 바뀌지 않게 하려는 것이다.
- 정산 시점(ADR 5): 접속 상태가 바뀔 때, 상호작용 전(명령, 전투 시작, 그 주체의 잔고·유닛을 읽는 조회), 60분마다(1분에 오래된 순으로 몇 주체씩, Assumed). 관측만 할 때는 쓰지 않는다. 화면에 보이는 상태(일함·쉼)는 같은 함수를 그 시각에 계산해 보인다.
- 해결 함수 하나: `packages/sim/src/settle/`의 정수 함수가 (상태, 규칙, 접속 상태, 시작, 끝) → (새 상태, 원장 항목, 요약 수)를 낸다.
  - 나눠 정산해도 같다: (a → b) 다음 (b → c)가 (a → c)와 결과가 같아야 한다. 무작위로 자른 구간으로 시험한다. 그래서 접속 중(잘게)과 오프라인(한 번에)의 결과가 통계가 아니라 정확히 같다(ADR 5 "단계 사이 기대값 일치"를 더 강하게 지킨다).
  - 계산은 시간 길이에 비례하지 않는다(주기 수를 나눗셈으로 센다). 무작위가 필요한 규칙은 (유닛, 주기 번호)로 뽑는 난수를 쓴다(나눠도 같게).
- 시험 직무 [임시. 수치·모양은 기획 Step 5]
  - 제자리에서 일한다. 60초 주기마다 시험 자원 1개를 그 주체 창고에 넣는다.
  - 주기마다 피로 +1, 120이면 쉰다. 쉬면 회복한다. 주거가 아직 없어 모두 노숙 배율(D-296)로 회복한다. 다 회복하면 다시 일한다(D-144).
  - 오프라인이면 끊긴 시각 + 24시간에 대기로 바뀐다(그 주기의 산출은 없다, 기획 질문 S3-Q3). 다시 접속하면 직무를 잇는다.
  - 사냥처럼 오프라인에 하지 않는 직무는 끊긴 시각에 멈춘다(D-144). S3 시험 종류에 하나 둔다.
- 유지비 [임시]: 실제 1시간 경계(UTC 정시)마다 그 주체 유닛의 몫을 더해 한 거래로 낸다. 중복 방지 키 = (주체, 경계 시각). 모자라면 내지 않고 밀린 횟수를 1 올린다. 밀렸을 때의 결과(만족도·영토, D-162)는 기획 질문 S3-Q4다. 대기 상태(24시간 뒤)에도 낸다(D-162). 돈으로 내는 것은 생필품(D-150·D-148)을 대신한 임시다.
- 최소 원장(ADR 8을 먼저 만드는 몫)
  - 복식부기다. 거래 하나의 항목 합은 자산마다 0이다. 항목은 추가만 된다(감사 기록처럼 DB 트리거로 고치기·지우기를 막는다).
  - 화폐와 쌓이는 자원을 같은 원장에 자산 코드로 적는다. 창고 계정 = (주체, 자산). 시스템 계정: 발행, 소멸, 행성 매장량(총량 자원은 쓴 만큼 매장량으로 돌아간다, D-112·D-116). 그래서 자원 보존도 I1 하나로 본다. 장비처럼 하나씩 다른 아이템은 아이템 설계 때 따로 정한다.
  - 시험 자산 코드는 `s3_test_credit`·`s3_test_ore`다(임시임이 이름에 보이게).
- 정산 한 번의 원장 항목과 `settled_at_ms`는 같은 묶음 커밋에 들어간다. 커밋 전에 죽으면 다시 켠 뒤 같은 입력으로 다시 계산해 같은 결과를 쓴다. 그래서 두 번 내지 않는다(I6).
- 복귀 요약 첫 출처: 확인 시각 표(`summary_acks`)와 `summary.ack`를 만든다. "생산" 칸은 마지막 확인 뒤 그 주체의 산출 원장 항목 합이다. "부상"·"습격" 칸은 전투가 생길 때 더한다(U4로 S3에는 없다).

### 5. 임시 전투 — 뺐다 (사용자 결정 U4)
- 사용자 답(원문): "전투공식과 방식이 애매하므로 일단 넘어가는게 어떤지?"
- 판정 틀·임시 공식·빨리감기·`battles` 표·복귀 요약의 습격·부상 칸을 S3에서 모두 뺐다. ADR 35(전투맵 인스턴스)는 제안 그대로 두고, 진짜 전투 설계 때 함께 만든다.
- S3가 남기는 자리: 유닛 상태는 주인 행의 열로 늘릴 수 있다(전투 ID·HP는 그때 열 추가 마이그레이션). 정산은 상호작용 전에 먼저 하는 규칙이라(4절) 전투가 생기면 "전투 시작 전 정산"으로 붙는다.

### 6. 규모: 버티는 한계를 찾는 계단 시험 (사용자 결정 U1)
- 사용자 답(원문): "그냥 토큰 적게쓰는 방식 마음대로 간단하게" → 그 뒤 고침: "기존봇 1000개 20분 테스트는 필요없다 항상켜져있지 않았는가? 차라리 대량 테스트가 낫지 어디까지 버티는지".
- 봇 1,000개는 NAS 운영 컨테이너에서 늘 돈다(`ops/compose.yml`). 그래서 1천 단계는 배포 뒤 평소 `nas-metrics` 값을 적는 것으로 끝낸다.
- 계단 시험: 봇 수를 1천 → 2천 → 5천 → 1만 → 2만으로 올리고, 2만도 버티면 5만 → 10만까지 간다(이 시험만 상한을 올린다: `S1_TEST_BOTS` 상한 10만, 봇은 `S1_TEST_MAPS`개 시험 2차맵에 나눈다).
  - 계단마다 몇 분 돌리고 이벤트 루프 p99·최대, RSS, 힙, 쓰기 묶음(행 수·커밋 시간·밀림), 살아남았는지를 적는다.
  - 처음으로 p99 > 50ms, 메모리가 컨테이너 상한에 가까움, 프로세스가 죽음 중 하나가 생긴 계단에서 멈춘다. 그 계단이 답이다.
  - 살아남은 가장 큰 계단에서 `SIGKILL` 한 번으로 그만큼의 유닛 행에서 부팅 복구 시간을 잰다.
  - 운영 컨테이너를 건드리지 않는다: 수동 GitHub Actions 작업(NAS 실행기)이 같은 이미지로 짧게 사는 컨테이너를 따로 띄운다. DB는 시험 전용 PostgreSQL 컨테이너를 잠깐 띄운다(아래 WP-E "바뀜"). 운영 DB(`tic-db`)와 다른 프로젝트 DB(`sunplant-db`, ks-frontier)는 쓰지 않는다. 공개 포트가 없고 끝나면 지운다. 로그에 컨테이너 환경 변수·비밀값을 찍지 않는다.
  - 결과: 작은 표와 결론(한계, 먼저 닿는 것: CPU·이벤트 루프·메모리·DB 쓰기). 그 한계를 서버 유닛 상한(ADR 32)의 근거로 쓴다.
- NAS 값은 아래쪽 한계로 읽는다(작업 지시 2026-10-31). 사용자 메모(원문): "현재 서버는 저스펙 NAS서버이고 많은연산이 필요한 경우 본서버에서 더 사용높은 서버를 구축할수도 있다(초기 서버는 맥미니나 맥스튜디오 정도 고려중)"(PLAN 9.9). 그래서 계단마다 CPU 모델(R1600, 4스레드)과 1천 개당 비용(CPU ms/초, 늘어난 MB, DB 행/초)을 적어 다른 기계를 어림할 수 있게 한다. 한계가 NAS 탓(컨테이너 메모리 1GiB, CPU 상한 없음, 커널 4.4)이 분명하면 결론에 그렇게 적고, NAS에 맞춰 지나치게 다듬지 않는다.
- 남는 위험: 계단 시험의 봇은 걷기·쉬기만 한다. NPC 세력의 판단·직무 비용은 N1에서 처음 본다(ADR 27). 봇 하나의 비용이 실제 NPC보다 작으면 한계가 실제보다 높게 나온다(Assumed).

## 이유
- 예약을 주인 행에 붙이는 것: 예약 표를 따로 두면 예약과 주인 상태가 따로 놀 수 있다(그래서 "예약 누락"이 불변 조건으로 따로 있다, ADR 6). 예정 시각이 주인 행에 있으면 부팅 때 상태에서 예약이 다시 나온다. 이벤트 예약 모델에서는 "예약된 사실"만 지키면 나머지를 다시 만들 수 있다(ADR 6 이유).
- 묶음 커밋: NAS 동기 커밋 1번이 약 77ms다(Verified). 바뀜마다 커밋하면 초당 13번이 한계다. S1 봇 1,000개만으로도 경로가 초당 약 22번 바뀐다(Verified: ADR 33). 묶으면 커밋은 초당 4번으로 고정되고 행 수만 는다.
- 쓰기 실패 때 끝내기: 메모리와 DB가 어긋난 채 계속 도는 길을 없앤다. 복구 길은 `kill -9` 시험이 늘 확인한다.
- 소유 주체 단위 정산과 "나눠도 같음": 지갑을 같이 쓰는 유닛끼리의 순서 문제가 없다. 정확히 같은 결과라 로그아웃으로 이득을 보는 악용이 구조상 없다(ADR 5의 걱정).
- 원장에 자원도 적는 것: 총량 자원 보존(D-116)과 원장 균형(ADR 6 불변 조건)이 같은 검사 하나가 된다. 장비 같은 고유 아이템은 아이템 설계 때 정한다.
- 시야 묶음 = 최상위 세력(기본안): D-5037이 "시야는 세력 단위로 공유"라고 했고(Verified: 결정 로그), 묶음이 적을수록 계산·인코딩이 준다(3절 비용). 기획이 본인 단위로 정해도 묶음 함수 하나만 바뀐다.
- 남의 경로 앞부분만: 경로 전체는 목적지를 드러낸다(ADR 7). 덮인 칸 안에서 자르면 이미 보이는 곳만 보낸다. 8초·3초는 보내는 양과 끊김 사이의 출발값이다(Assumed: 보이는 남의 유닛 100개면 초당 약 20건, 약 0.8KB/초).
- 지형 파일 통째(U3 추천): 지금의 불변 캐시(`immutable`)를 그대로 쓴다. 1차맵과 같은 맞바꿈이다(ADR 26 사용자 결정 "1차맵 공개"). 건물·유닛·자원처럼 플레이에 중요한 것은 서버가 거른다.
- 계단 시험(U1 답): 봇 1,000개는 늘 돌아서 다시 잴 것이 없다. 무너지는 계단을 찾으면 서버 유닛 상한(ADR 32)을 잰 값으로 정할 수 있다. 지금 있는 손잡이(`S1_TEST_BOTS`)와 새 `S1_TEST_MAPS`만 쓰고 클라이언트 봇 무리는 쓰지 않는다.

## 결과
- 좋은 점: 서버를 다시 켜도 세계가 이어진다. 시야 밖 정보가 기기로 가지 않는다. 오프라인 정산이 접속 중과 같은 함수다. 원장·불변 조건 검사가 거래소보다 먼저 생긴다.
- 감수할 점
  - 이동 바뀜은 죽을 때 마지막 묶음만큼 사라질 수 있다(U2 답 A).
  - 시험 2차맵은 탐사한 곳도 유닛도 없는 사용자에게 열리지 않는다(`not_visible`). 시험 유닛 주기와 관리자 전체 보기로 확인한다.
  - 2로 인사한 기기는 2차맵을 열지 못한다(새 앱을 받으면 풀린다).
  - 기기를 고치면 탐사한 2차맵의 지형 전체를 볼 수 있다(U3 답 A).
  - 임시 직무·임시 유지비는 밸런스와 상관없다. 결과 수치를 기획 판단에 쓰지 않는다.
  - 부팅이 DB를 기다린다: DB가 약 60초(2초 × 30번) 안에 답하지 않으면 서버가 뜨지 않고 컨테이너가 다시 켠다. 전에는 DB 없이도 떠서 `/health`가 503이었다.
- 다른 ADR에 생기는 일(이 ADR을 확정할 때 표시한다)
  - ADR 22: 연결 풀 10개를 S3 측정(쓰기 대기열 1 + 조회)으로 다시 본다.
  - ADR 27·32: 10만 유닛 상시 시험 대신 한계를 찾는 계단 시험(사용자 결정). ADR 32 문턱은 그 한계에서 정하고 N1에서 다시 잰다.
  - ADR 33: "메모리에만(DB 저장·복구는 S3)"이 이 ADR로 풀린다.
  - ADR 35: 제안 그대로 둔다. 임시 전투를 뺐으므로(U4) S3는 전투 수치를 재지 않는다.
  - ADR 26: 탐사 기록 표와 지형 문 지키기가 생긴다.
  - ADR 37: 복귀 요약 확인 시각 표와 첫 출처가 생긴다.
- 다시 볼 조건: 계단 시험에서 쓰기 묶음이 먼저 밀리면 쓰기 구조(행 묶음 크기, 열 수)를 다시 본다. N1에서 NPC 몫이 정해지면 그 한계와 견준다.
