## 선택지
### 가중치 칸 덮어쓰기를 어디에
1. **D1과 같은 표·같은 판·같은 감사 기록, 칸 키 `<행 ID>.<칸>`**(칸 = `str`·`dex`·`agi`·`vit`·`int`·`wis`·`base`·`cap`·`half`). 칸 ID 검사를 넓히는 마이그레이션 하나.
2. 새 표 `stat_row_overrides` — 판·감사·켤 때 고르기·내보내기를 다시 만든다(같은 일을 두 벌).
3. 가중치를 팩 `tuning` 칸으로 옮김 — 18 × 9칸 = 162칸이 설정 칸 목록에 들어가고 팩 형식(`stat_rows`)과 겹친다.

### 계산 자리
- 가. 2차 스탯·+10 기여(가벼움, 표 두 벌 × 7번 `computeSecondary`): 서버 주 스레드.
- 나. 시드 대결(무거움): 주 스레드 / **워커 스레드(요청마다 띄움)** / 늘 떠 있는 워커.

### 편 쏠림
- ㄱ. 고치지 않고 화면이 편을 바꿔 두 번 돌려 평균만.
- ㄴ. **틱 안 행동 차례를 (시드, 틱)으로 섞기**.
- ㄷ. 두 단계 틱(모두 공격 → 모두 이동).

## 결정
덮어쓰기는 1, 계산은 가 + 워커(요청마다), 편 쏠림은 ㄴ(그리고 화면은 두 차례 평균도 한다).

### 1. 가중치 칸 = D1 덮어쓰기의 한 종류
- 칸 키: `<stat_rows 행 ID>.<칸>`. 가중치 칸 이름은 팩 `weights` 차례(STR·DEX·AGI·VIT·INT·WIS), 화면은 화면 차례(STR·VIT·INT·WIS·DEX·AGI)로 보인다. 양 모양은 `base`, 확률 모양은 `cap`·`half`(= `halfConstant`)만 있다. 공용 표·검사는 `@terra/shared/tuning`(`STAT_CELL_FIELDS`·`statCellKey`·`parseStatCellKey`·`statCellUnit`·`STAT_CELL_LIMITS`).
- 단위·범위(팩 스키마·sim 입력 범위와 같다): 가중치 `pm` ±100,000, `cap` `pm` 0~1,000, `half` `points` 1~10^7, `base` `points` ±10^7. 켜진 행(`enabled`)만 바꿀 수 있다.
- 저장: `tuning_overrides`에 같은 칸(값·저장 때 팩 값·단위·팩 판·메모·사람·시각)으로 넣는다. 마이그레이션은 칸 ID 검사를 `^[a-z][a-z0-9_]{1,47}(\.(str|dex|agi|vit|int|wis|base|cap|half))?$`로 넓히는 것 하나다. 직전 판 앱은 칸 키를 쓰지 않고, 켤 때 이 줄을 "팩에 없는 칸"으로 보고 지운다(`tuning.dropped` `unknown_entry`) — 되돌림 배포 = 팩이 더 나중(D-461 "가장 나중에 바꾼 것이 이긴다")과 같은 결과다.
- 쓰기·되돌리기·판·감사·속도 제한·서버 기록은 D1 그대로다: 밸런스 화면의 [적용]은 `tuning.save`(같은 묶음 검사·트랜잭션·스냅숏 바꿔 끼우기), [모두 되돌리기](`tuning.revertAll`)는 가중치 칸도 지운다. 묶음에 설정 칸과 가중치 칸을 섞어도 된다.
- 여러 칸 규칙(`tuningProblems`에 더함): `stat_primary_unused` — 켜진 모든 행에서 가중치가 0인 1차 스탯이 생기면 묶음을 받지 않는다("가치 없는 1차"를 세계에 넣지 않는다, D-458). 화면은 더 약한 신호(아래 3절)도 보이지만 막지 않는다(질문 227).
- 실효 표: 서버 접근자 `TuningState.statTable()`(스냅숏마다 한 번 만든다)·`statRows()`. 켤 때 고르기(D1 6절)도 같다: 지금 팩 칸 값 ≠ 저장 때 팩 값 → 팩이 이김(`tuning.pack_won`), 행이 빠짐·꺼짐·모양이 바뀌어 칸이 없음 → `unknown_entry`, 범위 밖 → `out_of_range`, 저장 차례로 얹다 `stat_primary_unused` → `rules_conflict`. 켤 때 던지지 않는다.
- 서버가 표를 읽는 곳: 유닛·사이보그 화면(`rosterCatalogOf`의 `combat`이 접근자 속성이 되어 읽을 때마다 실효 표, 표가 같으면 같은 객체). 범위 칩은 "서버 즉시"다. 세계에서 전투를 열 때(R5) 사양은 그 명령 순간의 `statTable()`로 만든다(아래 꼬임 점검).
- `/dev/tuning` 머리에 "가중치 표 바뀐 칸 N"을 보이고 밸런스 화면으로 잇는다(`tuning.list` `statOverrides`).

### 2. 내보내기 → 팩
- 차이 형식(`terra-tuning-diff` 판 1)에 선택 칸 `statRows: [{ row, field, from, to }]`를 더한다(가중치 덮어쓰기가 있을 때만 넣는다 → 없으면 옛 모양 그대로). 옛 도구는 이 칸이 있는 차이를 형식 오류로 거절한다(말없이 빠뜨리지 않는다).
- `pnpm tuning:apply`가 `stat_rows.json`의 그 칸도 바꾼다(칸마다 팩에 있는지·지금 팩 값 = `from`인지·범위 안인지, 건너뛴 칸은 종료 코드 1). 판은 한 번 올린다. 함수는 `@terra/content` `applyStatRowsDiff`·`overlayStatRowsDiff`(Node API 없음) 하나이고, 시뮬레이터 `--tuning`도 같은 차이로 스탯 표를 얹는다(서버 세계와 같은 실효 표).
- 지금 팩 표 = `TEST_STAT_TABLE`(sim 시험이 본다). 차이를 팩에 넣으면 그 시험이 실패한다 → 같은 커밋에서 `TEST_STAT_TABLE`도 고친다(D1 11절과 같은 TODO).

### 3. tRPC `balance.*`(dev·admin, 권한 문장 `tuning:read`, D1과 같은 두 겹 권한·속도 제한)
| 이름 | 하는 일 |
|---|---|
| `table` | 팩 판·세계 설정 판, 행마다 {ID·이름·모양·칸마다 팩 값·실효 값·덮어쓰기}, 무기 목록(맨손 + 팩 무기 아이템), 기본 유닛·상한 |
| `contribution` | 입력 {1차 6개, 담은 변경}. 지금 표(실효)와 고친 표(실효 + 담은 변경)마다 2차 스탯 값과 1차 하나 +10의 차이 6열. "가치 없는 1차"(+10이 어느 2차도 바꾸지 않음) 목록 |
| `duels` | 입력 {1차 6개, 무기, 인원 1~3, 판 수, 시드, 제한 시간, 담은 변경}. 1차마다 "기준 + 10 vs 기준"을 두 편 차례로 반씩 돌려 합친 승·무·패·시간 초과 판정·평균 시간, 지금 표와 고친 표(담은 변경이 있을 때만) |

- 고친 표 = 지금 실효 표 위에 담은 변경(`{key, value | null}`, null = 팩 값). `tuning.save`가 받을 묶음과 같은 검사(`plan`)를 미리 돌려, 받지 않을 묶음이면 그 까닭을 함께 돌려준다(화면이 [적용] 전에 보인다).
- 기본 유닛(기술 출발값): 1차 모두 10(새 사이보그 평균 = N9 합 60 ÷ 6, 서버 `BASELINE_PRIMARY`), 맨손, 1명, 10판(차례마다 5), 시드 1, 제한 120초. 판정 계수는 그 세계 설정 칸 실효 값(`combatCoefficientsFrom`, D1 전투 칸 덮어쓰기도 든다)에 제한 시간만 바꾼 것. 지도는 빈 32칸(`runStatDuels` 새 선택 `mapSize`, 기본은 64 그대로).
- 시간 초과 판정: 남은 (HP + 아머 + 쉴드) ÷ 최대의 ‰를 편마다 견줘 큰 쪽이 "판정승"(`DuelReport.aTimeoutLeads`·`bTimeoutLeads`, 새 칸). 승률 = (승 + 판정승 + 같음 ÷ 2) ÷ 판 수. 새 유닛은 10분 안에 거의 끝나지 않아(Verified: 1차 모두 10·맨손·시험 칼, 6판 모두 시간 초과) 판정이 없으면 승률이 늘 0이다.
- 남은 몫 차: 판마다 끝났을 때 (기준 + 10 남은 몫 − 기준 남은 몫)(‰)의 평균(`DuelReport.shareLeadPmSum`, 새 칸). 새 유닛의 +10은 1차가 두 배라 어느 1차든 늘 이긴다(승률 100%, Verified: 기본 설정 화면 시험) → 승률만으로는 1차 사이 차이가 보이지 않아 얼마나 앞서는지를 함께 보인다.
- "약한 1차" 표시(막지 않음): 고친 표에서 그 1차 +10 승률 ≤ 500‰(기준과 같은 유닛 50%를 넘지 못함). 기준은 화면 상수다(질문 227).
- 상한(NAS 부담): 판 수 2~40(짝수), 제한 30~300초, 판 수 × 제한 ≤ 2,400초, 인원 1~3. 대결은 사용자마다 따로 센다(순간 2·분당 4)와 서버 전체 한 번에 하나(바쁘면 `TOO_MANY_REQUESTS` `busy`). 기여 계산은 D1 조회 속도 제한을 같이 쓴다.

### 4. 대결은 워커 스레드에서(요청마다)
- `balance/duelWorker.ts`(빌드 `dist/balanceWorker.js`, 시작점 기준으로 찾는다 — 경로 워커와 같은 규칙). 요청마다 띄우고 결과를 받으면 끝낸다(평소 메모리 0, 죽어도 요청 하나만 실패). 받는 자료는 표 두 벌·계수·유닛·시드(요청 시작 때 값 한 벌, D1 "명령 하나는 값 한 벌")이고 워커는 DB·접근자를 모른다. 120초가 지나면 끝내고 `timeout`.
- 시험·DB 없는 개발은 같은 스레드("inline")로 돈다(지형 서비스와 같은 틀).
- 왜 주 스레드가 아닌가: 대결 한 판이 수십~수백 ms라(5절 잰 값) 주 스레드에서 돌리면 S3 관문 기준(루프 p99 ≤ 50ms)을 바로 넘는다.

### 5. 잰 값 (Verified: 개발 컨테이너 Xeon 2.1GHz 4 vCPU 공유, Node 24.22.1. NAS 값이 아니다)
- 고치기 전 대결 한 판(1차 모두 40·시험 칼·지도 64): 1명 260ms(평균 121초), 3명 492ms(225초). 지도 32면 68ms·123ms(틱당 약 55µs, 지도 64는 약 215µs — 흐름장·점유 배열이 칸 수에 비례). 새 유닛(1차 10)은 600초 시간 초과라 지도 64에서 한 판 약 1.2~1.4초.
- 대결 요청 하나(Verified: 같은 컨테이너, 빌드한 워커 `dist/balanceWorker.js`, 띄우기 포함 / 같은 스레드): 기본(1차 10·맨손·1명·10판·120초) 표 1벌 5.1초 / 4.5초, 표 2벌 7.3초 / 8.0초. 1차 40·시험 칼 표 2벌 6.8초. 상한(판 수 × 제한 = 2,400초, 표 2벌) 1명 20판 14.5초, 3명 20판 16.4초, 3명 8판·300초 17.2초. 워커 띄우기 자체는 수십 ms라 차이는 공유 CPU 흔들림 안이다. 주 스레드는 기다리기만 한다. 워커 제한 시간 120초는 상한의 약 일곱 배(NAS 여유, Unknown: NAS에서 재지 않음).

### 6. 편 쏠림 = 판정 코어 버그, 틱 안 행동 차례를 섞는다 (SIM_VERSION 4)
- 진단(Verified, 저장소 밖 짧은 스크립트, 시드 고정):
  - 같은 유닛 6 대 6(1차 40·시험 칼, 지도 32, 300판): 편 1 : 편 2 = 93 : 207.
  - 편 2 유닛의 ID를 편 1보다 작게 바꾸면 결과가 정확히 뒤집혔다(3 대 3, 30판: 10:20 → 20:10). 편 2를 한 칸 더 멀리(거리 9) 세우면 쏠림 방향이 바뀌었다(18:12), ID까지 바꾸면 다시 뒤집혔다(12:18). 좌우 자리를 맞바꿔도 같은 결과(자리·방향이 아니라 ID 차례).
  - 원인: 틱마다 유닛이 ID 차례로 행동하고, 걸음·피해가 곧바로 상태에 든다. 거리가 짝수면 앞 차례(편 1)가 걸어 맞닿은 그 틱에 뒤 차례(편 2)가 바로 친다(선공). 홀수면 둘 다 걸어 맞닿고 다음 틱에 ID가 작은 쪽이 먼저 친다. 같은 유닛끼리도 ID와 거리 홀짝이 선공·막타를 정했다. 세계 전투에서도 유닛 ID(만든 차례)가 승패에 끼어든다 → 판정 버그다.
- 고침: 틱마다 행동 차례를 (시드, 틱)에서 만든 흐름으로 섞는다(`actionOrder`, 피셔-예이츠, 공격 굴림과 다른 흐름). 상태에 들지 않고 시드·틱에서 다시 나와 스냅숏 재생이 바이트까지 같다(시험).

## 이유
- 덮어쓰기 1: 사용자가 고른 "바로 듦"(D-461)을 같은 길로 받는다. 판·감사·켤 때 고르기·내보내기가 한 벌이라 꼬임 점검도 한 벌이다. 칸 키에 점(.)이 있어 설정 칸 ID와 겹칠 수 없다.
- 계산을 서버에: 기기는 판정 코드를 받지 않는다(경계·서버 권위). 기여는 가벼워 주 스레드, 대결은 무거워 워커.
- 편 쏠림 ㄴ: 원인을 바로 없애고(같은 입력이면 같은 결과는 그대로), 상태 모양·스냅숏·굴림 수가 바뀌지 않는다.
