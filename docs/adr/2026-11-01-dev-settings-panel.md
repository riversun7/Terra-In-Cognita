- 요청(통합 담당, 2026-11-01): 개발자·관리자가 칸을 보고 바꾼다(예: N1 실제 시간 시험 조정). 바꾼 값이 재배포 없이 듣되, "설정 = 팩 값"과 서버 권위를 깨지 않는다. 바꾼 값을 팩 `tuning.json` 차이로 내보내 팩에 커밋할 수 있어야 한다.

## 선택지
### 바꾼 값이 듣는 법
1. **보기 + 내보내기만**: 패널은 값을 보이고 바꾼 값을 팩 차이로 내보낸다. 반영은 배포(지금 PLAN 그대로).
   - 좋은 점: 규칙이 하나다(팩 = 실행 값). 감사·저장 표가 없다.
   - 나쁜 점: 값 하나를 볼 때마다 커밋·배포(몇 분)다. NAS 세계에서 "바꿔 보고 돌려 보기"가 느리다.
2. **세계마다 덮어쓰기 층(DB)**: 실효 값 = 팩 값 위에 덮어쓰기. 덮어쓰기는 그 세계의 DB 표에 두고, dev·admin tRPC 쓰기 + 감사 기록 + 되돌리기. 서버의 모든 읽는 곳이 접근자 하나로 실효 값을 읽는다. 내보내기로 팩에 되돌린다.
   - 좋은 점: 바로 듣는다. 누가·언제·왜 바꿨는지 남는다.
   - 나쁜 점: 세계가 팩과 다른 값으로 돌 수 있다(보이게 해야 한다). 바로 바꾸면 진행 중인 일과 꼬일 수 있다(점검해야 한다). 표·코드가 는다.
3. **디스크 덮어쓰기 파일**(볼륨의 JSON, 켤 때 읽기) — 다시 켜야 듣고, 화면에서 못 바꾸고, 감사 기록이 없다.
4. **서버가 팩 파일을 직접 고친다** — 이미지 안 팩이 바뀌어 팩 해시·되돌림(이전 이미지 = 이전 팩)이 깨진다. 1단계 검사를 거치지 않는다.

### 단위·범위를 두는 곳
- 가. 팩 항목에 선택 칸(`unit`·`min`·`max`) — 1단계 검사가 범위를 본다(PLAN 7장 문장 그대로). 새 칸을 더하는 사람이 같은 파일에 적는다.
- 나. 코드 표(`TUNING_KEYS`)에 — 팩 검사(`packages/content`)가 sim 표를 볼 수 없어 1단계 검사가 범위를 보지 못한다.

### 여러 칸을 함께 보는 검사
- 칸마다 범위만으로는 막지 못하는 것이 있다(Verified: `@terra/sim` `rollStatSpread`는 N9 합이 칸 범위 × 6에 맞지 않으면 `RangeError`를 던진다 → 사이보그 굴리기가 모두 실패). 판정 코드 쪽 검사 함수가 필요하다.

## 결정
덮어쓰기는 선택지 2, 단위·범위는 가, 여러 칸 검사는 sim 함수. 사용자 답 204~206(아래 "사용자 결정")을 따른다.

### 1. 값의 층
- **실효 값 = 팩 값 위에 그 세계의 덮어쓰기.** 팩은 배포 기준 값이고, 덮어쓰기는 그 세계에서 바로 든다. 조정한 묶음은 내보내기 → 팩 커밋 → 배포로 팩에 넣을 수 있다.
- 세계 = DB 하나다. 단일 월드 설계라 DB 안에 세계 칸이 없다. NAS 세계, N1 관문 세계(따로 띄운 컨테이너 묶음), 시험 DB는 각자 덮어쓰기를 가진다.
- **모든 세계에서 바로 든다**(사용자 답 204: 앞으로의 공개·운영 세계 포함). 세계 종류로 잠그지 않는다. 덮어쓴 칸 수는 화면·`/health`가 보인다(10절).

### 2. 팩 형식 더함(`tuning` 분류)
- 선택 칸 셋을 더한다. 기존 팩이 그대로 통과하므로 `formatVersion`은 그대로다(ADR 24 규칙).
  - `unit`: `ms`(시간), `pm`(‰), `bp`(만분율), `pct`(%), `cells`(배치 칸), `count`(개·명·횟수), `minor`(화폐 최소 단위), `milli`(1/1000 점), `points`(점수), `level`(단계) 중 하나. 저장은 게임 규칙 단위(PLAN 7장). 화면은 `ms`를 "10분"처럼, `pm`·`bp`를 %로도 보인다.
  - `min`·`max`: 기술 범위(양 끝 포함). 1단계 검사가 `min ≤ max`, `min ≤ value ≤ max`를 본다. 서버 덮어쓰기도 같은 범위로 거절한다.
- `unit`이 없으면 화면은 영어 이름 끝 괄호(`(ms)`·`(‰)`·`(bp)`·`(%)`·`(cells)`·`(minor units)`)에서 읽는다(보이기만). 새 칸은 `unit`을 적는다.
- 지금 범위를 적는 칸(기술 출발값, 넓게): 서버가 지금 읽는 칸(7절) 전부와 C2(49 X11: 30분 상한, 1초 하한). 나머지는 스키마 한계(±10^12)만 본다. 칸을 읽는 코드를 쓰는 사람이 그 칸의 범위를 적는다.

### 3. 여러 칸 규칙 검사
- `@terra/sim` `tuningProblems(society)` → 문제 코드 목록. 지금 규칙: N9 합·칸 범위 맞음(`n9_fit`), N6 K 최소 ≤ 최대(`n6_order`), N36 칸 수·점수(4원소 1~4칸, 점수 ≤ 칸 × 10, `n36_fit`), N39 배율 최소 ≤ 최대(`n39_order`), 붐빔 보통 ≤ 붐빔(`crowd_order`), 민심 문턱 반란 ≤ 예고 ≤ 태업(`unrest_order`), T4 수명 최소 ≤ 최대(`lifespan_order`), N23 피로 구간 시작이 오르고 피로 상한 이하(`fatigue_order`), N27 단가 하한 ≤ 상한(`wage_order`), N28 조정 하한 ≤ 상한(`employer_order`), N33 포만감 0 문턱 ≤ 낮음 문턱(`food_order`).
- 팩 값은 문제가 없어야 한다(sim 시험이 본다). 덮어쓰기 묶음은 **바꾼 뒤의 전체 값**으로 검사해 새 문제를 만들면 거절한다(`rules_conflict`, 문제 코드는 오류 `data.details`). 그래서 서로 묶인 칸(N9 합과 칸 최대)은 한 묶음으로 함께 바꾼다.

### 4. DB 표
- `tuning_overrides`: `id`(칸 ID, PK, 콘텐츠 ID 규칙 검사), `value`(int8), `pack_value`(저장할 때의 팩 값), `unit`(저장할 때의 단위, 없을 수 있음), `content_version`(저장할 때의 팩 판 `core@N`), `note`(메모, 0~200자, 없을 수 있음), `updated_by`(→ `users`, 지우면 null), `updated_at`.
- `tuning_revision`: 줄 하나(`id` = 1), `revision`(int8, 세계의 설정 판), `updated_at`. 덮어쓰기를 바꾸는 트랜잭션마다 `revision = revision + 1 where revision = 기대 판`으로 올린다(판이 다르면 아무것도 바꾸지 않고 충돌). 줄은 켤 때 없으면 만든다.
- 마이그레이션 하나, 더하기만(직전 판 앱은 표를 모른 채 그대로 돈다).
- 판 기록 표는 두지 않는다. 누가·언제·무엇을(앞뒤 값)은 감사 기록에 남고, 화면의 "최근 바꿈"은 감사 기록을 읽는다.

### 5. 접근자 하나
- 서버 `TuningState`(`apps/server/src/tuning/state.ts`): `snapshot()`(판·실효 값·덮어쓰기를 든 바뀌지 않는 객체 하나), `values()`, `society()`(실효 값을 얹은 세력·사회 계수표, 판마다 한 번 만든다), `revision()`. 서버에서 설정 칸 값을 읽는 곳은 모두 이것을 **쓸 때마다** 부른다(켤 때 한 번 받아 두지 않는다).
- 바꾸기는 검사한 새 묶음으로 만든 새 스냅숏을 **한 번에 바꿔 끼운다**(대입 한 번, JS 한 스레드라 읽는 쪽은 앞 묶음 전체나 뒤 묶음 전체만 본다. 반쯤 바뀐 값은 없다).
- 쓰기: 한 프로세스 안에서 차례로 돈다(쓰는 프로세스는 하나, ADR 3). 판 확인 → 바꾼 뒤 전체 값 검사 → DB 트랜잭션(판 +1·덮어쓰기·감사 기록) 커밋 → 메모리 바꿔 끼움. 커밋 전에 실패하면 메모리는 그대로다. 커밋 뒤 죽으면 다시 켤 때 DB에서 싣는다. 감사 기록을 못 쓰면 요청이 실패한다(PLAN 4.8).
- 켤 때(`onReady`, 월드 부팅보다 먼저): DB에서 판과 덮어쓰기를 읽는다(월드 부팅과 같은 다시 시도: 2초 × 30번). 6절 규칙으로 고른 뒤 바꿔 끼운다. 지울 줄이 있으면 한 트랜잭션(판 +1, 감사 기록 `system`)으로 지운다. **이 정리가 실패해도 시작은 막지 않는다**(메모리에는 고른 덮어쓰기만 싣고 경고를 남긴다. 줄은 다음 시작에 다시 고른다).
- 시뮬레이터는 같은 내보내기 차이를 받는다(`pnpm --filter @terra/sim sim … --tuning <차이.json>`): 서버와 시뮬레이터가 같은 실효 값으로 돈다. 차이 형식·적용 함수는 `@terra/content`(`tuningDiff.ts`) 하나다.

### 6. 팩과 패널: 가장 나중에 바꾼 것이 이긴다(사용자 답 206)
- 덮어쓰기 줄은 저장할 때의 팩 값(`pack_value`)을 든다. 팩 값은 배포로만 바뀌므로, 켤 때
  - 지금 팩 값 = `pack_value` → 패널 저장이 더 나중이다 → **패널 값이 든다**.
  - 지금 팩 값 ≠ `pack_value` → 저장 뒤에 배포(또는 되돌림 배포)가 그 칸을 바꿨다 → **팩 값이 든다**. 덮어쓰기는 지우고 감사 `tuning.pack_won`(앞: 칸·덮어쓰기 값·저장 때 팩 값, 뒤: 지금 팩 값·팩 판)을 남긴다.
- 새 팩에서 칸이 빠졌거나 이름이 바뀌었으면(`unknown_entry`), 단위가 바뀌었으면(`unit_changed`), 새 범위 밖이면(`out_of_range`), 저장 차례대로 얹을 때 규칙 문제를 만들면(`rules_conflict`) 그 덮어쓰기는 지우고 감사 `tuning.dropped`(까닭)를 남긴다.
- 켤 때 실패하거나 막지 않는다. 무엇이 이겼는지는 서버 기록(`tuning overrides` 줄)과 패널 "최근 바꿈"에 보인다.
- 내보내기 차이의 `from`은 지금 팩 값이라, 적용 도구가 팩과 어긋난 차이를 알아본다.

- 규칙: **명령(요청) 하나는 시작할 때 값 한 벌(스냅숏)을 받아 끝까지 그것만 쓴다.** 명령은 커밋 전까지 기다림(await) 없이 한 번에 돈다(`cyborg/service.ts`). 그래서 "시작할 때 값" = "커밋할 때 값"이다. 지난 일(만든 사이보그의 처음 스탯·K, 낸 지원금, 지난 정산)은 바꾸지 않는다.
- **다시 켜야 듣는 값은 없다.** 서버가 읽는 칸은 모두 접근자로 쓸 때마다 읽는다.
- 워커·캐시: 경로·지형·행성 굽기 워커는 설정 칸을 읽지 않는다(Verified: 워커 진입 파일과 그 가져오기에 `@terra/sim` 계수표·설정 칸이 없음). 서버 안의 캐시는 접근자의 판별 계수표 하나이고 판이 바뀌면 새로 만든다. 사이보그 화면 자료(`rosterCatalog.society`)는 읽을 때마다 접근자를 부르는 접근자 속성이다. 기기 화면은 다음 조회 때 새 값을 받는다.
- 서버 전투는 팩 값을 아직 읽지 않는다(시험 계수표). 전투 시작 자료(`BattleInit`)에 계수를 넣어야 다시 계산(복구)이 같은 값을 쓴다. 그 뒤에 전투 칸을 "전투를 시작할 때 고정"으로 연다(이 ADR 밖, 작업 기록 TODO).
- 화면의 칸 줄마다 범위를 칩으로 보인다(서버 즉시 · 시뮬만 · 연결 없음). 서버가 읽는 칸 표는 `apps/server/src/tuning/scope.ts` 하나이고, 새로 읽는 곳을 더하면 거기에 줄을 더한다(시험이 표의 경로가 `TUNING_KEYS`에 있는지 본다).

### 8. tRPC `tuning.*`과 권한
| 이름 | 종류 | 권한 | 하는 일 |
|---|---|---|---|
| `list` | 조회 | `read` | 팩 판·해시·세계 설정 판, 칸마다 {ID·코드·이름·단위·범위·구조 값·팩 값·실효 값·범위 칩·덮어쓰기(값·저장 때 팩 값·메모·바꾼 사람·시각)} |
| `history` | 조회 | `read` | 최근 바꿈 30개(감사 기록: 시각·사람·동작·판·칸마다 앞뒤 값·메모·까닭) |
| `export` | 조회 | `read` | 내보내기 차이(11절) |
| `save` | 쓰기 | `write` | `{expectedRevision, changes: [{id, value | null}], note?, confirmStructural?}` — 칸 1~200개를 한 묶음으로. `null`·팩 값 = 되돌리기 |
| `revertAll` | 쓰기 | `write` | `{expectedRevision}` 모든 덮어쓰기를 지운다 |

- 권한 문장 `tuning: ["read", "write"]`를 dev·admin에게 준다(기본 거부). 두 겹으로 본다: 우리 권한 표(미들웨어) → Better Auth `userHasPermission`(세션 늘리지 않음, ADR 38 WP-B와 같다). 그다음 사용자별 속도 제한(조회 순간 30·분당 120, 쓰기 순간 20·분당 60). 셋 다 입력 검사보다 먼저 돈다.
- 동시 편집: 판 번호(`expectedRevision`)로 본다(행성 편집기의 판과 같은 결). 다른 사람이 먼저 바꿔 판이 오르면 `CONFLICT` `revision_conflict`이고 아무것도 바뀌지 않는다. 화면은 목록을 다시 받고 담은 변경은 남긴다.
- 받지 않음(`BAD_REQUEST`, `data.reason`): `unknown_entry`(팩에 없는 ID), `out_of_range`, `rules_conflict`(+ `data.details` 문제 코드), `structural_unconfirmed`(구조 값인데 `confirmStructural`이 참이 아님, D-5054), `invalid_note`(200자 넘음·DB가 못 담는 글자), `duplicate_entry`(한 묶음에 같은 칸 두 번). 하나라도 틀리면 묶음 전체를 받지 않는다. `TOO_MANY_REQUESTS` `rate_limited`. 나머지는 tRPC 전체 규칙(같은 출처, JSON 본문, `no-store`).
- 감사 기록: `tuning.apply`(앞: 판·칸마다 앞 값, 뒤: 판·칸마다 새 값·팩 값·팩 판·메모), `tuning.revert_all`, `tuning.pack_won`·`tuning.dropped`(켤 때, `system`). 행위자는 `admin`(세계 규칙을 바꾸는 운영 동작), 역할은 `meta.roles`. 조회는 감사 기록을 쓰지 않는다(비밀값이 없다).
- 오류 `data.details`: `reasonedError`에 선택 인자로 문자열 목록을 싣는다(지금은 `rules_conflict`만 쓴다). 기기는 코드를 메시지 키로 바꾼다.

### 11. 내보내기 → 팩
- 형식(`@terra/content` `tuningDiffSchema`): `{ format: "terra-tuning-diff", formatVersion: 1, exportedAt, packId, contentVersion, contentHash, changes: [{ id, code, from, to }] }`. `from` = 지금 팩 값, `to` = 덮어쓰기 값. 팩 값과 다른 덮어쓰기만 넣는다(ID 차례).
- 화면: [내보내기] → JSON 파일 받기 + 글 상자(복사).
- 팩에 넣기: `pnpm tuning:apply <차이.json> [--pack content/<팩 ID>] [--force] [--dry-run]`(`scripts/apply-tuning-diff.mjs`). 칸마다 팩에 있는지, 지금 팩 값 = `from`인지(아니면 건너뛰고 알린다, `--force`면 넣는다), 범위 안인지 본 뒤 `value`만 바꾸고 `manifest.json` 판을 올린다. 그다음 `pnpm check:content`·작업 기록·커밋은 사람·에이전트가 한다(PLAN 7장 v1 흐름). 그 팩이 배포되면 그 칸은 팩 값이 바뀌었으므로 6절대로 팩 값(= 같은 값)이 들고 덮어쓰기는 지워진다.

## 이유
- 선택지 2만 "재배포 없이 듣는다"와 "누가 바꿨나 남는다"를 함께 준다. 사용자가 모든 세계에서 바로 들기를 골랐다(204).
- 팩은 배포 기준 값으로 남는다: 덮어쓰기는 지우면 팩 값이고, 내보내기 → 팩 → 배포가 끝나면 켤 때 저절로 정리된다. "가장 나중에 바꾼 것이 이긴다"(206)는 저장 때의 팩 값 하나로 판정하므로 켤 때 오류가 날 길이 없다.
- 서버 권위: 값을 정하는 것은 dev·admin의 서버 요청이고, 서버가 범위·규칙 검사 뒤에만 받는다. 기기는 판정 코드를 받지 않는다(규칙 검사는 서버의 sim 함수).
- 범위를 팩 칸으로: PLAN 7장이 "1단계 검사가 거절"이라고 적었다. 팩 검사가 sim 표를 못 보니(경계 규칙 `@terra/content`는 `@terra/shared`만) 팩에 둔다. R5 등 다른 줄기가 칸을 더할 때 같은 파일에 범위를 적으면 된다(목록을 코드에 박지 않는다).
- 여러 칸 검사가 필요한 것은 Verified(N9 `RangeError`). 칸 하나 범위로는 합·순서를 못 막는다. 그래서 묶음 적용이 필요하다.
- 판 번호 충돌: 칸마다 기대 값보다 거칠지만(다른 칸을 바꿔도 충돌), 묶음 검사가 전체 값에 걸리므로 "남이 바꾼 값 위에서 검사한 묶음"만 받는 것이 안전하다. 행성 편집기와 같은 결이다.
- 디스크 파일(3)·팩 직접 고침(4)은 재시작·되돌림·검사 문제로 뺐다.

## 결과
- 좋은 점: 칸을 바꾸면 다음 요청부터 사이보그 만들기·지원금·환생 조건·세력 화면에 든다. 바꾼 사람·까닭이 감사 기록과 서버 기록에 남고, 지표 줄에 판이 붙는다. 조정한 묶음을 한 명령으로 팩에 넣는다. 시뮬레이터도 같은 차이로 돈다.
- 감수할 점: 세계가 팩과 다른 값으로 돌 수 있다(화면·`/health`가 보인다). 서버가 아직 읽지 않는 칸(전투·사회 규칙)은 바꿔도 서버에는 듣지 않는다(칩으로 보인다). 다른 칸을 바꿔도 판 충돌이 난다(목록을 다시 받고 담은 것은 남는다). 표 둘·tRPC 5개·화면 하나가 는다.
- 다시 볼 조건: 서버가 세력·사회 규칙(R5)·전투 계수를 실행할 때(7절 표와 `scope.ts`에 줄을 더하고, 명령마다 스냅숏 하나 규칙을 지킨다), 49 문서가 바뀔 때(`pnpm settings:cells`).
