## 선택지
### 바꾼 값이 듣는 법
1. **보기 + 내보내기만**: 패널은 값을 보이고 바꾼 값을 팩 차이로 내보낸다. 반영은 배포(지금 PLAN 그대로).
   - 좋은 점: 규칙이 하나다(팩 = 실행 값). 감사·저장 표가 없다.
   - 나쁜 점: 값 하나를 볼 때마다 커밋·배포(몇 분)다. NAS 개발 세계에서 "바꿔 보고 돌려 보기"가 느리다. 패널에서 바꾼 값을 서버가 모른다.
2. **세계마다 덮어쓰기 층(DB)**: 실효 값 = 팩 값 위에 덮어쓰기. 덮어쓰기는 그 세계의 DB 표에 두고, dev·admin tRPC 쓰기 + 감사 기록 + 되돌리기. 서버의 모든 읽는 곳이 접근자 하나로 실효 값을 읽는다. 내보내기로 팩에 되돌린다.
   - 좋은 점: 바로 듣는다. 누가·언제·왜 바꿨는지 남는다. 팩은 여전히 정본(덮어쓰기는 지우면 팩 값).
   - 나쁜 점: 세계가 팩과 다른 값으로 돌 수 있다(보이게 해야 한다). 표·코드가 는다.
3. **디스크 덮어쓰기 파일**(볼륨의 JSON, 켤 때 읽기)
   - 나쁜 점: 다시 켜야 듣는다. 화면에서 못 바꾼다(파일을 고칠 길이 없다). 감사 기록이 없다.
4. **서버가 팩 파일을 직접 고친다**
   - 나쁜 점: 이미지 안 팩이 바뀌어 팩 해시·되돌림(이전 이미지 = 이전 팩)이 깨진다. 1단계 검사를 거치지 않는다.

### 단위·범위를 두는 곳
- 가. 팩 항목에 선택 칸(`unit`·`min`·`max`) — 1단계 검사가 범위를 본다(PLAN 7장 문장 그대로). 새 칸을 더하는 사람이 같은 파일에 적는다.
- 나. 코드 표(`TUNING_KEYS`)에 — 팩 검사(`packages/content`)가 sim 표를 볼 수 없어 1단계 검사가 범위를 보지 못한다.

### 여러 칸을 함께 보는 검사
- 칸마다 범위만으로는 막지 못하는 것이 있다(Verified: `@terra/sim` `rollStatSpread`는 N9 합이 칸 범위 × 6에 맞지 않으면 `RangeError`를 던진다 → 사이보그 굴리기가 모두 500). 판정 코드 쪽 검사 함수가 필요하다.

## 결정
덮어쓰기는 선택지 2, 단위·범위는 가, 여러 칸 검사는 sim 함수.

### 1. 값의 층
- **실효 값 = 팩 값 위에 그 세계의 덮어쓰기.** 팩이 정본이다. 덮어쓰기는 세계(= DB 하나)에서 하는 조정 실험이고, 끝나면 내보내기 → 팩 커밋 → 배포로 팩에 들어간다.
- 세계 = DB 하나다. 단일 월드 설계라 DB 안에 세계 칸이 없다. NAS 개발 세계, N1 관문 세계(따로 띄운 컨테이너 묶음), 시험 DB는 각자 덮어쓰기를 가진다.
- 덮어쓰기가 있는 칸만 팩과 다르다. 화면·`/health`가 그 수를 보인다(아래 10절).
- 덮어쓰기를 어디까지 허용하나(공개 세계 포함?)는 사용자에게 묻는다 → 질문 200. 지금(가): 모든 세계에서 dev·admin이 쓴다(실유저 없음). L2 공개 테스트 점검표에서 다시 정한다.

### 2. 팩 형식 더함(`tuning` 분류)
- 선택 칸 셋을 더한다. 기존 팩이 그대로 통과하므로 `formatVersion`은 그대로다(ADR 24 규칙).
  - `unit`: `ms`(시간), `pm`(‰), `bp`(만분율), `pct`(%), `cells`(배치 칸), `count`(개·명·횟수), `minor`(화폐 최소 단위), `milli`(1/1000 점), `points`(점수), `level`(단계) 중 하나. 저장은 게임 규칙 단위(PLAN 7장). 화면은 `ms`를 "10분"처럼, `pm`·`bp`를 %로도 보인다.
  - `min`·`max`: 기술 범위(양 끝 포함). 1단계 검사가 `min ≤ max`, `min ≤ value ≤ max`를 본다. 서버 덮어쓰기도 같은 범위로 거절한다.
- `unit`이 없으면 화면은 영어 이름 끝 괄호(`(ms)`·`(‰)`·`(bp)`·`(%)`·`(cells)`·`(minor units)`)에서 읽는다(보이기만). 새 칸은 `unit`을 적는다.
- 지금 범위를 적는 칸(기술 출발값, 넓게): 서버가 지금 읽는 칸(7절) 전부와 C2(49 X11: 30분 상한, 1초 하한). 나머지는 스키마 한계(±10^12)만 본다. 칸을 읽는 코드를 쓰는 사람이 그 칸의 범위를 적는다.

### 3. 여러 칸 규칙 검사
- `@terra/sim` `tuningProblems(society)` → 문제 코드 목록. 지금 규칙: N9 합·칸 범위 맞음(`n9_fit`), N6 K 최소 ≤ 최대(`n6_order`), N36 칸 수·점수(4원소 1~4칸, 점수 ≤ 칸 × 10, `n36_fit`), N39 배율 최소 ≤ 최대(`n39_order`), 붐빔 보통 ≤ 붐빔(`crowd_order`), 민심 문턱 반란 ≤ 예고 ≤ 태업(`unrest_order`), T4 수명 최소 ≤ 최대(`lifespan_order`), N23 피로 구간 시작이 오르고 피로 상한 이하(`fatigue_order`), N27 단가 하한 ≤ 상한(`wage_order`), N28 조정 하한 ≤ 상한(`employer_order`), N33 포만감 0 문턱 ≤ 낮음 문턱(`food_order`).
- 팩 값은 문제가 없어야 한다(sim 시험이 팩을 읽어 본다). 덮어쓰기는 실효 값에 새 문제를 만들면 거절한다(`rules_conflict`, 문제 코드는 오류 `data.details`).

### 4. DB 표 `tuning_overrides`
- 열: `id`(칸 ID, PK, 콘텐츠 ID 규칙 검사), `value`(int8), `pack_value`(저장할 때의 팩 값), `content_version`(저장할 때의 팩 판 `core@N`), `note`(메모, 0~200자, 없을 수 있음), `updated_by`(→ `users`, 지우면 null), `updated_at`.
- 마이그레이션 하나, 더하기만(직전 판 앱은 표를 모른 채 그대로 돈다).
- 판 기록 표는 두지 않는다. 누가·언제·무엇을(앞뒤 값)은 감사 기록에 남고, 화면의 "최근 바꿈"은 감사 기록을 읽는다.

### 5. 접근자 하나
- 서버 `TuningState`(`apps/server/src/tuning/state.ts`): `values()`(실효 값 표), `society()`(실효 값을 얹은 세력·사회 계수표, 판마다 한 번 만들어 둔다), `revision()`. 서버에서 설정 칸 값을 읽는 곳은 모두 이것을 **쓸 때마다** 부른다(켤 때 한 번 받아 두지 않는다).
- 켤 때(`onReady`): DB에서 덮어쓰기를 읽는다(월드 부팅과 같은 다시 시도: 2초 × 30번). 이때
  - 팩에 없는 ID, 지금 팩 범위 밖, 규칙 문제를 만드는 덮어쓰기는 **적용하지 않는다**(행은 남긴다). 화면이 "적용 안 됨"과 까닭을 보이고 되돌리기만 준다.
  - 값이 지금 팩 값과 같은 덮어쓰기는 지운다(배포로 팩에 들어간 것. 감사 `tuning.absorbed`, 행위자 `system`).
- 쓰기는 한 프로세스 안에서 차례로 한다(쓰는 프로세스는 하나, ADR 3). DB 트랜잭션(덮어쓰기 + 감사 기록) 커밋 뒤에 메모리를 바꾼다. 감사 기록을 못 쓰면 요청이 실패한다(PLAN 4.8).
- 시뮬레이터는 같은 내보내기 차이를 받는다(`pnpm --filter @terra/sim sim … --tuning <차이.json>`): 서버와 시뮬레이터가 같은 실효 값으로 돈다. 차이 형식·적용 함수는 `@terra/content`(`tuningDiff.ts`) 하나다.

### 6. 팩이 바뀐 덮어쓰기
- 저장할 때의 팩 값(`pack_value`)과 지금 팩 값이 다르면 "팩 값이 바뀜(저장 때 X → 지금 Y)"을 보이고 덮어쓰기는 그대로 듣는다 → 질문 202(가). 내보내기 차이의 `from`은 지금 팩 값이라, 적용 도구가 팩과 어긋난 차이를 알아본다.

- **다시 켜야 듣는 값은 지금 없다**: 서버가 읽는 칸은 모두 접근자로 쓸 때마다 읽는다. 단 이미 일어난 일은 바꾸지 않는다(만든 사이보그의 처음 스탯·K, 이미 낸 지원금, 이미 지난 정산).

- 화면의 칸 줄마다 이 범위를 칩으로 보인다(서버 즉시 · 시뮬만 · 연결 없음). 서버가 읽는 칸 표는 `apps/server/src/tuning/scope.ts` 하나이고, 새로 읽는 곳을 더하면 거기에 줄을 더한다(시험이 표의 경로가 `TUNING_KEYS`에 있는지 본다).

### 8. tRPC `tuning.*`과 권한
| 이름 | 종류 | 권한 | 하는 일 |
|---|---|---|---|
| `list` | 조회 | `read` | 팩 판·해시·잠금, 칸마다 {ID·코드·이름·단위·범위·구조 값·팩 값·실효 값·범위 칩·덮어쓰기(값·저장 때 팩 값·판·메모·바꾼 사람·시각·적용 여부와 까닭)}, 팩에 없는 덮어쓰기 |
| `history` | 조회 | `read` | 최근 바꿈 30개(감사 기록: 시각·사람·동작·칸·앞뒤 값·메모) |
| `export` | 조회 | `read` | 내보내기 차이(11절) |
| `set` | 쓰기 | `write` | `{id, value, expected, note?, confirmStructural?}`. `expected` = 이 기기가 본 덮어쓰기 값(없으면 null) |
| `revert` | 쓰기 | `write` | `{id, expected}` 덮어쓰기를 지운다(팩 값으로) |
| `revertAll` | 쓰기 | `write` | 모든 덮어쓰기를 지운다(팩에 없는 것 포함) |

- 권한 문장 `tuning: ["read", "write"]`를 dev·admin에게 준다(기본 거부). 두 겹으로 본다: 우리 권한 표(미들웨어) → Better Auth `userHasPermission`(세션 늘리지 않음, ADR 38 WP-B와 같다). 그다음 사용자별 속도 제한(조회 순간 30·분당 120, 쓰기 순간 20·분당 60). 셋 다 입력 검사보다 먼저 돈다.
- 받지 않음(`BAD_REQUEST`, `data.reason`): `unknown_entry`(팩에 없는 ID에 `set`), `out_of_range`, `rules_conflict`(+ `data.details` 문제 코드), `structural_unconfirmed`(구조 값인데 `confirmStructural`이 참이 아님, D-5054), `invalid_note`(200자 넘음·DB가 못 담는 글자). `CONFLICT` `revision_conflict`(`expected`가 지금 덮어쓰기와 다름), `FORBIDDEN` `tuning_locked`(9절), `TOO_MANY_REQUESTS` `rate_limited`. 나머지는 tRPC 전체 규칙(같은 출처, JSON 본문, `no-store`).
- 감사 기록: `tuning.set`(앞: 덮어쓰기 값 또는 null, 뒤: 칸·값·팩 값·팩 판·메모), `tuning.revert`, `tuning.revert_all`(지운 칸·값 목록), `tuning.absorbed`(켤 때, `system`). 행위자는 `admin`(세계 규칙을 바꾸는 운영 동작), 역할은 `meta.roles`. 조회는 감사 기록을 쓰지 않는다(비밀값이 없다).
- 오류 `data.details`: `reasonedError`에 선택 인자로 문자열 목록을 싣는다(지금은 `rules_conflict`만 쓴다). 기기는 코드를 메시지 키로 바꾼다.

### 9. 잠금
- 환경 변수 `TUNING_EDIT`(기본 `on`). `off`면 보기·내보내기만 되고 쓰기는 `FORBIDDEN` `tuning_locked`, 화면은 "이 세계는 설정을 잠갔습니다"를 보인다.
- 쓰는 곳: N1 관문 세계(D-410 "규칙·타이머·설정값을 바꾸지 않고"). 관문 세계는 덮어쓰기 없이 시작한다(조정한 값은 팩에 넣고 시작) → 질문 201(가).

### 10. `/health`
- `tuningOverrides`(적용 중인 덮어쓰기 수)를 더한다. 0이면 그 세계는 팩 값 그대로 돈다. 배포 점검(`ops/smoke.mjs`)은 보지 않는다(알리기만).

### 11. 내보내기 → 팩
- 형식(`@terra/content` `tuningDiffSchema`): `{ format: "terra-tuning-diff", formatVersion: 1, exportedAt, packId, contentVersion, contentHash, changes: [{ id, code, from, to }] }`. `from` = 지금 팩 값, `to` = 덮어쓰기 값. 적용 중이고 팩 값과 다른 덮어쓰기만 넣는다(ID 차례).
- 화면: [내보내기] → JSON 파일 받기 + 글 상자(복사).
- 팩에 넣기: `pnpm tuning:apply <차이.json> [--pack content/<팩 ID>] [--force]`(`scripts/apply-tuning-diff.mjs`). 칸마다 팩에 있는지, 지금 팩 값 = `from`인지(아니면 건너뛰고 알린다, `--force`면 넣는다), 범위 안인지 본 뒤 `value`만 바꾸고 `manifest.json` 판을 올린다. 그다음 `pnpm check:content`·작업 기록·커밋은 사람·에이전트가 한다(PLAN 7장 v1 흐름). 그 팩이 배포되면 덮어쓰기는 켤 때 지워진다(5절).

### 12. 화면 `/dev/tuning`
- 주소 줄 `dev_tuning`(`/dev/tuning`, 부모 `dev`, 틀 있음, dev·admin). 개발자 홈 도구 줄 하나(ADR 38 WP-H 규칙).
- 촘촘(`data-density="compact"`), 모바일 먼저. 토큰만 쓴다(ADR `2026-11-01-ui-visibility.md`: 수·색 막대로 더 보이게).
- 머리: 팩 판, 칸 수, 바뀐 칸 수, 서버 즉시 칸 수, 잠금이면 알림. [내보내기]·[모두 되돌리기](확인 창).
- 찾기(코드·ID·이름 ko/en) + 거르기(바뀐 것만, 서버 즉시만) + 무리 고르기.
- 무리 = 49 코드 앞 글자, 49 차례: T 시간·유닛, M 맵·영토·건물, P 생산·물류, E 경제, C 전투, F 크리쳐·아이템·스킬, N 수치·공식, S 세력·사회, U 우주, B BM, 그 밖의 글자는 글자대로, 코드 없음(결정 ID 칸)은 끝. 무리 이름·차례는 `@terra/shared/tuning` 표 하나.
- 칸 줄: 코드 칩·이름(지금 언어)·구조 값 칩·범위 칩, ID(작게)·단위·범위, 지금 값(바뀌었으면 강조)·팩 값·차이(+6, +10%)와 범위 막대(범위가 있으면 팩 값·지금 값 눈금), 덮어쓰기 정보(사람·시각·메모·적용 여부·팩 값 바뀜). [바꾸기]는 줄 안에서 펼친다(값·메모, 단위 미리 보기). 구조 값은 확인 창(D-5054). [되돌리기].
- 팩에 없는 덮어쓰기 판(되돌리기만), "최근 바꿈" 펼침(감사 기록 30개).
- 조각: 진입 파일 `editor/tuning/TuningPanelScreen.tsx` → `TuningPanelScreen-*.js`·`.css`. 미리 캐시에서 뺀다: `DEV_ONLY_CHUNK`에 `[Tt]uningPanel`, `DEV_ONLY_SOURCE`에 `src/editor/tuning/`, `globIgnores`에 `assets/[Tt]uningPanel*.{js,css}`(ADR 38 1절 규칙).

### 13. 기획·사용자에게 물을 것(D-267, 추천 가를 지금 넣었다)
- 200 덮어쓰기 범위(모든 세계 / 개발·시험 세계만 / 쓰지 않음), 201 N1 관문 중 잠금, 202 팩이 바뀐 덮어쓰기(남김 / 팩이 이김), 203 팩에 없는 49 칸을 패널에 보일지. → `docs/questions/2026-11-01-d1.md`.

## 이유
- 선택지 2만 "재배포 없이 듣는다"와 "누가 바꿨나 남는다"를 함께 준다. 팩이 정본이라는 것은 그대로다: 덮어쓰기는 지우면 팩 값이고, 내보내기 → 팩 → 배포가 끝나면 켤 때 저절로 지워진다. 그래서 "설정 = 팩 값"은 "배포한 세계의 기준 값 = 팩 값"으로 남고, 덮어쓰기 수가 화면·`/health`에 보인다.
- 서버 권위: 값을 정하는 것은 dev·admin의 서버 요청이고, 서버가 범위·규칙 검사 뒤에만 받는다. 기기는 판정 코드를 받지 않는다(규칙 검사는 서버의 sim 함수).
- 범위를 팩 칸으로: PLAN 7장이 "1단계 검사가 거절"이라고 적었다. 팩 검사가 sim 표를 못 보니(경계 규칙 `@terra/content`는 `@terra/shared`만) 팩에 둔다. R5 등 다른 줄기가 칸을 더할 때 같은 파일에 범위를 적으면 된다(목록을 코드에 박지 않는다).
- 여러 칸 검사가 필요한 것은 Verified(N9 `RangeError`). 칸 하나 범위로는 합·순서를 못 막는다.
- 디스크 파일(3)·팩 직접 고침(4)은 재시작·되돌림·검사 문제로 뺐다.

## 결과
- 좋은 점: NAS 개발 세계에서 칸을 바꾸면 다음 요청부터 사이보그 만들기·지원금·환생 조건·세력 화면에 든다. 바꾼 사람·까닭이 감사 기록에 남는다. 조정한 묶음을 한 명령으로 팩에 넣는다. 시뮬레이터도 같은 차이로 돈다.
- 감수할 점: 세계가 팩과 다른 값으로 돌 수 있다(화면·`/health`가 보인다). 서버가 아직 읽지 않는 칸(전투·사회 규칙)은 바꿔도 서버에는 듣지 않는다(칩으로 보인다). 표 하나·tRPC 6개·화면 하나가 는다.
- 다시 볼 조건: L2 공개 테스트 전(질문 200), N1 관문 세계를 띄울 때(질문 201, `TUNING_EDIT=off`), 서버가 세력·사회 규칙(R5)·전투 계수를 실행할 때(7절 표와 `scope.ts`에 줄을 더한다), 49 칸이 팩에 더 들어올 때(질문 203).
