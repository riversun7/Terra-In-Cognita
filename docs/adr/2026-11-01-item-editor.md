# 아이템 편집기 개발자 화면(/dev/items): 팩 형식 넓힘(분류 자료·묶음), 덮어쓰기 층 보강(baseHash·은퇴 ID·잠든 줄), 서버가 셈하는 미리 보기

- 상태: 제안
- 날짜: 2026-11-01
- 관련: docs/PLAN.md 7장(설정값)·11장(개발자 페이지), 설계안 `docs/research/2026-11-01-item-editor-design.md`(이 ADR의 근거, 1~6장), ADR `2026-11-01-skill-editor.md`(덮어쓰기 층·감사·켤 때 고르기·내보내기 `entries` — 이 ADR 3절이 넓힌다), `2026-11-01-dev-settings-panel.md`(권한·속도 제한·`pnpm tuning:apply`), `2026-11-01-formula-editor.md`(실효 계산식), `2026-10-31-economy-core.md`(대분류·거래 방식), `2026-10-28-content-pack-format.md`(선택 칸 더함·ID 변경표), 질문 `docs/questions/2026-11-01-item-editor.md`(285~290, 사용자 답 D-496)·`docs/questions/2026-11-01-item-editor-2.md`(291), 기획 D-461·D-487·D-494·D-496·D-5001~D-5054

## 배경
- 아이템은 콘텐츠 팩 `items.json`이고 바꾸려면 팩 커밋·배포가 필요했다. 스킬 편집기(ADR `2026-11-01-skill-editor.md`)가 만든 항목 덮어쓰기 층은 `items`를 무기 소모 칸 때문에만 받았다.
- 사용자 답(D-496, 2026-11-01): 285 고친 값은 새로 생기는 것부터 + 필요할 때만 개발자 소급 명령, 286 같은 물약·요리는 같은 아이템이고 효과량은 쓰는 이의 수치(VIT→HP, WIS→MP)와 ±25%[임시], 287 전투 중에 물건을 쓴다(화살·탄약은 보조 칸, 원거리 1회 1개, 없으면 원거리 못 함), 288 신선도 0이면 아이템마다 고른 다른 아이템으로, 289 장비는 전투마다 닳고 지면 더 닳는다, 290 착용 요구치는 없고 1차 적정 스탯에 못 미치면 효율이 준다(2차 적정치는 그 1차 적정 스탯으로 셈). D-494 크리쳐 전용 장비 3칸.
- 설계안의 일 묶음: WP-1 덮어쓰기 층 보강, WP-2 팩 형식, WP-3 서버 API, WP-4 화면. 전투 연결(WP-5)·크리쳐(WP-C)·소모품 실행(WP-6)·대량 도구(WP-7)는 이 묶음 밖이고 자료 모양만 준비한다.

## 선택지
### 팩 형식
1. **선택 칸만 더한다(기존 항목은 그대로 통과)** — 새 분류 셋(`item_subcategories`·`item_tags`·`weapon_types`)과 아이템 묶음(`equip` 넓힘·`perish`·`use`).
2. 대분류마다 다른 스키마(판별 합집합) — 기존 팩·시뮬 자료를 한꺼번에 옮겨야 하고 시뮬 출력이 흔들린다.

### 적정 스탯(290)
- 가. **`equip.weapon.appropriate {str?,dex?,agi?,vit?,int?,wis?}` = 착용 제한 없는 1차 적정 스탯.** 2차 적정치는 그것으로 셈해 미리 보기에 보이고, 전투는 지금처럼 직접 적은 2차 적정치를 읽는다(전투 연결 WP-5).
- 나. 요구치(착용 막기) — 사용자 답 290이 막았다.

### 화면 담기
- 가. **고친 칸이 바로 담은 변경에 든다(실효 값과 같아지면 빠진다), [적용]이 한 묶음** — 여러 아이템·분류 자료를 고친 뒤 한 번에 검사·적용한다.
- 나. 항목마다 [담기] 단추 — 담지 않은 초안을 잃기 쉽다.

## 결정
### 1. 팩 형식(WP-2, 팩 `core@24`)
- 아이템 공통 선택 칸: `subcategory`(→ `item_subcategories`, 그 대분류 것), `tags`(→ `item_tags`, 16개, 겹침 없음), `weight`(g 정수), `stackMax`(장비는 1), `tradable`, `bound`(켜면 `tradable: true` 금지), `icon`.
- 묶음: `equip`(장비만, 장비는 필수), `perish {shelfLifeMs 1시간~365일, spoilsTo → items}`(자원·가공품·소모품만, 자기 자신·돌고 도는 바뀜 금지, 288), `use {effects 1~8}`(소모품만, 스킬 효과 줄과 같은 모양 D-425).
- `equip` 넓힘(모두 선택): `weaponType`(→ `weapon_types`, 칸이 맞아야), `maxDurability`, `combat {resistPm[12], defenseFlat, penetrationPm}`, `kinds`(입을 수 있는 유닛 종류), `creature {weight, stealPm}`(D-494 보유). `equip.weapon`에 `appropriate`(290 가), `twoHanded`, `ammo`(→ 보조 칸 무기 종류). 장비 칸 목록은 `@terra/shared/roster` `EQUIP_SLOTS` 하나(크리쳐 3칸은 WP-C).
- 새 분류: 중분류(`major`·`order`·`storage`·`food`·`foodFamily` — 식재료 계열은 식품만), 태그, 무기 종류(`slot` weapon|offhand). 처음 목록은 [임시]: 중분류 36, 무기 종류 14(무기 11 + 보조 3: 방패·화살통·탄창), 태그 0.
- 규칙 검사마다 코드(`params.rule` → `ContentIssue.code`)를 단다. 스키마 문제는 zod 코드와 한계 값을 싣는다. 화면은 코드로 메시지 키를 고른다(코드 없는 옛 문구는 `content_other`).

### 2. 덮어쓰기 층 보강(WP-1)
- 고칠 수 있는 분류 = `skills`·`items`·`unit_kinds`·`item_subcategories`·`item_tags`·`weapon_types`(DB 검사는 `effects`까지 넓혀 둠).
- 묶음의 바꿈마다 `baseHash`(고치기 시작할 때의 실효 항목 해시, 새 항목 null). 판이 달라도 모든 바꿈의 해시가 맞으면 받는다. 해시가 다르면 `entry_changed`(details = 키)로 묶음 전체를 거절한다. 해시 없는 바꿈(잠든 줄 버리기 등)이 끼면 예전처럼 `revision_conflict`.
- 만든 항목을 지우면 ID를 은퇴시킨다(표 `content_retired_ids`, 마이그레이션 `20261101161223_content_retired_ids` — 추가만, 갈래 셋의 끝을 `prevIds`에). 목록은 팩 `id-changes` + 그 세계 은퇴 ID를 보내고, 새 항목은 다시 쓰지 못한다.
- 켤 때 적용하지 않고 DB에 두는 잠든 줄: 더 새 팩에서 저장(`newer_pack`), 만든 항목과 같은 ID가 팩에 생김(`id_collision`), 모르는 분류(`unknown_category`). 화면은 띠로 보이고 `discard_sleeping`으로 지운다. 감사 `content.slept`.
- 실효 팩 = 팩 항목(파일 차례) + 만든 항목(ID 차례). 서버·`pnpm --filter @terra/sim sim --tuning`(`entries`)·`pnpm tuning:apply`가 같은 함수(`@terra/content` effective)를 쓴다. 내보내기는 `entries`와 `retiredIds`.
- 최근 바꿈은 감사 줄 요약(SQL에서 바꾼 항목 목록만), 항목 통째는 감사 줄 ID로 하나만(`items.historyEntry`).

### 3. 서버 API(WP-3, tRPC `items.*`, tuning:read·write + 사용자별 속도 제한)
- `list`(요약 줄·권고 수·코드 참조 표시·분류 자료·고르기 창 자료·은퇴 ID·잠든 줄), `get`(항목·팩 항목·덮어쓰기·쓰는 곳·권고), `check`(묶음을 얹은 실효 팩 검사의 코드가 붙은 문제 + 아이템마다 권고 + 끄면 멈추는 레시피·생필품), `preview`, `save`(baseHash 묶음), `history`, `historyEntry`.
- 미리 보기는 서버가 셈한다(게임 앱은 sim을 가져오지 않는다): 장비 = 유닛 화면과 같은 함수(`loadoutOf`·`itemAt`)로 범위 0·500·1000‰ 자리를 입힌 1차·2차 수치, 무기 = 그 세계의 실효 계산식(덮어쓴 식 표시)과 1차 적정 스탯으로 셈한 2차 적정치, 소모품 = 효과 줄, 값 = 레시피 원가(BigInt).
- 아이템을 읽는 서버 자리는 모두 실효 자료를 읽는다: 유닛·전투 자료(`roster/catalog.ts`)·전투 실험실·정원사 웨이브·전투 서비스(스킬 편집기 때부터), 경제 목록(`economyCatalogAccessor`, 거래 방식 `marketKindOf` 하나).
- 코드·시나리오가 ID로 쓰는 아이템 표(`SIM_ITEM_REFS`·`MAGIC_WEAPON`·다시보기 시범·전투 실험실 샘플·유닛/경제 시안)를 보내고, 화면은 그 아이템을 끄거나 칸·무기 공격 칸을 바꾸면 [적용] 전에 묻는다.

### 4. 화면(WP-4, `/dev/items`, `?item=<ID>`)
- 스킬 편집기에서 공용 부품을 꺼냈다: 입력 칸·효과 줄·최근 바꿈·모델(`editor/content/contentEditor*`). 스킬 편집기도 baseHash와 3방향 다시 얹기를 쓴다(`e2e/skills.spec.ts`는 고치지 않음).
- 왼쪽 목록(대분류 타일·찾기 300ms·거르기·정렬·200줄씩), 오른쪽 접히는 구역(기본·분류·값 → 장비·무기 → 사용 효과 → 신선도), 칸마다 쓰는 곳 칩(`ITEM_FIELD_USES`), 미리 보기·검사·쓰이는 곳 판, [아이템 분류] 칸(중분류·태그·무기 종류 고치기·새로 만들기).
- 담은 변경 막대: 수·칩·검사 상태(1초 멈춤 → `check`)·메모 200자·[적용]·되돌리기·다시하기(기기 안 50칸)·[비우기]. 새 아이템과 복제는 꺼진 채로(복제 이름 꼬리 "(복사)"·"(Copy)"는 두 언어 콘텐츠 값), 분류 자료는 켠 채로 만든다.
- entry_changed면 다시 받은 항목 위에 내 칸만 다시 얹고(`itemRebase.ts`), 양쪽이 같은 칸을 바꿨으면 칸마다 내 값·서버 값을 고른다.
- 조각 `ItemEditorScreen-*`·공용 `contentEditor…`는 미리 캐시 밖(`DEV_ONLY_CHUNK`·`globIgnores`·`DEV_ONLY_SOURCE`).

## 이유
- 선택 칸만 더하면 기존 팩·시뮬 자료가 그대로 통과한다. 시뮬 출력은 머리 줄(팩 판·해시)만 바뀌었다: war16 30일·stub16·econ16 180일, 시드 1, 두 번씩 — 본문 줄 같음, SIM_VERSION 6 유지(Verified, 작업 기록).
- baseHash가 있으면 다른 항목만 바뀐 판 충돌을 받아 주고(설계안 3.10), 행동별 소모의 무기 소모 칸 바꿈을 아이템 초안이 덮지 않는다.
- 은퇴 ID는 AGENTS 4장 "한 번 쓴 ID는 다시 쓰지 않는다"를 세계 안에서도 지킨다(내보내기 `retiredIds` → 팩 `id-changes`).
- 화면은 계산하지 않고 서버가 실효 자료·식으로 셈해야 판정과 같은 값을 보인다(서버 권위, 모듈 경계).

## 결과
- 하지 않은 것(이 묶음 밖이거나 미룸)
  - WP-5: 새 장비 칸(`appropriate`·`combat`·`kinds`·`twoHanded`·`elements`·`maxDurability`)을 전투에 잇기. 지금은 미리 보기와 쓰는 곳 칩("아직 없음")만.
  - WP-C 크리쳐 3칸, WP-6 소모품 실행(286 스탯 비례·±25%, 287 전투 중 물약·탄약 소모), 289 내구도 닳기, 285 소급 명령.
  - WP-7 대량 도구(여러 개 고르기 `patch_items`, JSON·CSV 가져오기). 감사 표 `content.%` 부분 색인은 줄이 쌓인 뒤 재 보고 더한다.
  - 잠든 줄 `id_collision`의 [새 ID로 옮기기]: 잠든 줄 항목을 화면에 보내지 않아 지금은 [버리기]만 있다.
  - 효과 고르기 창의 찾기·종류 거르기: 지금은 고르기 칸(이름·종류) + 줄마다 풀이 문장.
- 탄약 모양은 질문 291(가·나·다) 답 뒤에 정한다. 지금은 `weapon_types` 보조 칸 종류와 `equip.weapon.ammo` 연결만 있다.
- 처음 중분류·무기 종류 목록과 [임시] 표시 값은 기획 확인(D-487) 뒤 팩 커밋으로 바꾼다.

## 바뀜 (2026-11-02, 아이템 편집기 2차 — WP-5·WP-C·WP-6·WP-7, 팩 core@25)
- 까닭: 설계안 6장 WP-5·WP-C·WP-6·WP-7과 사용자 답 D-494·D-496(285~290)·D-497(291). 가지 `work/item-editor-2`, 작업 기록 `docs/worklog/2026/11/02-1100-item-editor-2.md`. 규칙 질문 292~295 `docs/questions/2026-11-01-item-editor-3.md`. 전투 판정 쪽 바뀜은 ADR `2026-10-31-combat-core.md` "바뀜 (2026-11-02)".

### 1. 장비 → 전투 (WP-5)
- "결과"의 "WP-5: 새 장비 칸을 전투에 잇기"를 했다. 장비 정의·입은 물건이 속성값(`elements`)·직접 값(`combat.resistPm`·`defenseFlat`·`penetrationPm`)·양손(`twoHanded`)·입을 종류(`kinds`)·1차 적정 스탯(`appropriate`)을 전투로 나른다(유닛 화면·사이보그·전투 실험실·시뮬 전투 `combatRun`이 같은 `loadoutOf`).
- 선택지 "적정 스탯(290) 가"의 "전투는 지금처럼 직접 적은 2차 적정치를 읽는다"를 바꾼다: `appropriate`가 있으면 전투도 그 세계의 실효 가중치 표로 셈한 2차 적정치(물리·속성 공격, 명중, 크리, 속도)를 쓴다. 직접 적은 2차 적정치는 `appropriate`가 없을 때만 쓴다(편집기 칸 아래에 "1차 적정 스탯이 있어 쓰지 않음"). 예(Verified, 시험): STR 25·DEX 15 → 물리 59·명중 18·크리 22·속도 54.
- 미리 보기 무기 판: 셈한 2차 적정치(식 몫), 기준 유닛 효율(D-420 틀, 예: 기준 유닛 1차 모두 10이면 물리 공격 26 ÷ 59 → 440‰, 시험 검 실제 공격 8. 직접 적정 40이면 650‰·13), 상한. 장비 판: 입지 못하는 종류·양손으로 빠진 물건.
- `test_heart` 속성값(불 2·냉기 3)을 팩으로 옮기고 유닛 화면 시안의 하드코딩을 지웠다(같은 값, `TEST_COMBAT_CATALOG`·`combatCatalog.test`).

### 2. 크리쳐 장비 칸 (WP-C, D-494)
- 팩 `unit_kinds` creature 칸 = 무기·방어구(body)·장신구. 칸 수·차례는 구조 값(D-5054)이라 편집기 화면에는 바꾸는 칸을 두지 않고 팩 커밋(사용자 결정 D-494 → core@25)으로만 바꾼다. 서버 덮어쓰기 층은 `unit_kinds`의 `slots` 바꿈을 따로 막지 않는다(화면이 보내지 않음, 쓰기 권한 계정만). 칸 차례에 기대던 곳(유닛 화면 시안, 전투 실험실 늑대·골렘 샘플의 장신구 칸 2, 시험 자료)을 같은 커밋에서 고쳤다.
- 크리쳐 전용 장비(`kinds: ["creature"]`)를 편집기에서 만들고, 미리 보기(유닛 종류 크리쳐)·전투 실험실(크리쳐 샘플)에 입힌다. 다른 종류에 입히면 빼고 셈하고 전투 실험실은 `dropped`(`unit_kind`)로 알린다(e2e). 조우 때 굴리기·훔치기는 크리쳐·전투 줄기(자료 `creature {weight, stealPm}`만).

### 3. 소모품·효과 사전 (WP-6)
- `use` 효과 줄 선택 칸 `scale {stat: 1차 6개, pmPerPoint 0~10,000}`·`variancePm 0~1,000`. 미리 보기 효과량 = 기준 × (1000 + 스탯 × ‰/점) ÷ 1000, ±오차(줄 값, 없으면 설정 칸 `d496_use_variance` 250‰ [임시]), BigInt 내림(식 모양은 질문 292). 예(Verified, e2e): 기준 40·VIT 10‰/점 → VIT 10이면 44(33~55), VIT 39면 55(41~68), 줄 오차 100‰면 49~60.
- [효과 사전] 탭: 효과 고치기·새로 만들기·끄기·되돌리기, 효과마다 쓰는 아이템·스킬(D-425). 2절의 고칠 수 있는 분류에 `effects`를 더한다(아이템과 같은 묶음·판·감사, 내보내기 `entries`, `pnpm tuning:apply`). 스킬 편집기의 효과 고르기도 실효 효과를 읽는다.
- 효과 사전 넓힘(팩 형식, 선택 칸): `stat`에 1차 6개, `exclusive`(배타 묶음 ID, D-472 "센 것이 이김"). 둘 다 **전투 판정은 아직 읽지 않는다**(1차 스탯 버프는 전투 자료에서 거르고, 배타 묶음의 세기 비교는 질문 293). 미리 보기는 배타 묶음을 표시한다.
- 먹기·전투 중 물약·썩기 실행은 보유 물건(인스턴스) 뒤다.

### 4. 대량 도구 (WP-7)
- [대량 도구] 탭: 내보내기(서버 실효 아이템 통째 `items.export` → JSON 팩 모양 또는 공통 칸 15개 CSV), 가져오기(틀린 머리·값을 줄 번호로, 새로 / 고침 / 같음 차이 뒤 담은 변경에만, 묶음 검사 한 번), 여러 개 고치기(바로 적용).
- 상한(`@terra/shared` `ITEM_BULK_LIMITS`, 서버가 다시 봄): 글 900 KiB, 300줄·300개, 항목 4 KiB, 고르기 300개, 기준 가치 바꿈 −900~+10,000‰.

- 옛 1차 자원 136개 변환본(`docs/research/2026-11-02-old-resources-draft.md`·`.json`)은 팩에 넣지 않았다(질문 295, 사용자 확인 뒤 팩 커밋).

## 바뀜 (2026-11-02, 아이템 편집기 3차 — 질문 292·293·294 답 D-501, 팩 core@26)
- 까닭: 사용자 답(질문 `docs/questions/2026-11-01-item-editor-3.md` 292~294, 기획 D-501 `docs/design/02_Decision_Log.md`). 가지 `work/item-editor-3`, 작업 기록 `docs/worklog/2026/11/02-1335-item-editor-3.md`.

### 1. 소모품 효과량 = 적정 스탯 대비 (292)
- "바뀜 (2026-11-02)" 3절의 `scale {stat, pmPerPoint}`(스탯 1점당 ‰)와 그 식을 바꾼다. 효과 줄 선택 칸 = `scale {stat: 1차 6개, appropriate: 1~10,000,000}`·`variancePm 250~500`.
- 효과량 = 기준 × min(상한, 쓰는 유닛의 그 1차 스탯 ÷ 적정 스탯) × (1 ± 오차). 정수 셈: 비율‰ = min(상한, ⌊스탯 × 1000 ÷ 적정⌋)(스탯이 음수면 0), 가운데 = ⌊기준 × 비율 ÷ 1000⌋, 범위 = ⌊가운데 × (1000 ∓ 오차) ÷ 1000⌋(BigInt, 음수 기준도 아래로). 굴림 = [최소, 최대] 안 균등한 정수 하나(시드 난수). 함수는 `@terra/sim` `useAmountRange`·`rollUseAmount`(`packages/sim/src/combat/useAmount.ts`) 하나이고, 비율은 무기 틀 `weaponScaled`와 같은 `appropriateRatioPm`(`formula.ts`로 꺼냄, 무기 값은 그대로)이다. 서버 미리 보기가 이 함수를 부른다. 먹고 쓰는 실행은 여전히 보유 물건 뒤다.
- 상한은 무기 효율과 같은 값이다: 설정 칸 N10 `n10_appropriate_cap`(구조 값, 팩 2000‰)의 실효 값 = 전투 계수표 `appropriateCapPm`(전투 `resolveAttack`과 편집기 무기 효율이 읽는 값). 새 수를 만들지 않았다.
- 오차: 설정 칸 `d496_use_variance` 250 → 500‰, 범위 0~1,000 → 250~500(줄 값도 같은 범위, 비우면 설정 칸). 옛 팩 값으로 저장한 설정 칸 덮어쓰기는 팩 값이 바뀌어 켤 때 팩이 이긴다(설정 칸 `packWon`).
- 예(Verified, 시험·e2e): 스탯 = 적정 스탯이면 기준 30·50·100 → 15~45·25~75·50~150. VIT 10 유닛에게 기준 30·적정 10은 30(15~45), 기준 50·적정 40은 250‰ → 12(6~18). VIT 39·기준 50·적정 10은 상한 2000‰ → 100(50~150), 줄 오차 250‰면 75~125.
- 편집기: 효과 줄마다 비례 스탯(1차 6개 중 아무것, 보통 HP는 VIT·MP는 WIS)·적정 스탯·±오차. 비례 스탯을 처음 고르면 적정 스탯 칸이 10으로 시작한다(입력 시작값: 기준 유닛 1차 10에서 1000‰, 아이템 값은 편집기에서 적는다). 미리 보기 줄 = "VIT 10 ÷ 적정 10 → 1000‰(상한 2000‰) → 30 (±500‰ → 15~45)".
- 옛 모양 DB 줄(core@25에서 저장한 `content_overrides`의 items): 켤 때 고르기와 싣기(저장 뒤 다시 싣기 포함) 전에 고쳐 읽는다(`apps/server/src/contentEdit/legacy.ts`). 옛 `scale`과 범위 밖 `variancePm`은 뺀다(= 기준 값 그대로·설정 칸 값). 새 모양으로 옮길 값이 없어서다(적정 스탯은 다시 적는다). DB 줄은 그대로 두고(그 항목을 다음에 저장할 때 새 모양으로 쓰인다), 고친 줄 키는 서버 기록 `content boot`의 `upgraded`에 남는다. 그러지 않으면 그 줄이 통째로 `invalid_entry`로 지워지고(다른 고친 칸도 잃음), 만든 항목이면 그것을 가리키는 줄까지 따라 지워진다. 옛 내보내기 파일(`pnpm tuning:apply`·`sim --tuning`의 `entries`)은 고쳐 읽지 않고 스키마 문제로 알린다.

### 2. 배타 묶음 교체 규칙 (293, 규칙 기록만)
- "바뀜 (2026-11-02)" 3절의 `exclusive`(D-472 "더 센 것이 이긴다")를 D-501로 정한다: 같은 묶음 안 같은 효과는 높은 값만 남긴다. 다른 효과는 확인 창("지금 버프가 사라집니다") 뒤 새 것으로 바꾼다. 자동 사용(자동 행동·NPC·전투 중 자동)은 그 상황에 더 좋은 쪽으로만 바꾸고, 같거나 더 좋은 것이 걸려 있으면 쓰지 않는다(낭비 막기).
- 판정·실행은 하지 않았다(보유 물건 뒤). "상황에 더 좋은 쪽"의 판단식은 보유 물건·자동 행동 줄기에서 정해 보인다(D-487). 이번에는 효과 사전 도움말 문구와 스키마·공용 타입 주석만 고쳤다.

### 3. 탄약은 보조 칸 장비 하나 (294)
- 탄약은 보조 칸 장비(대분류 4, 무기 종류 화살통·탄창, 내구도 = 남은 탄 수, 0이면 다른 탄약 장비로 바꿔 씀)로만 둔다. 소모품 중분류 `ammo`(대분류 5 "탄약")를 팩에서 지웠다: `id-changes.json` removed `{category: item_subcategories, id: ammo, since: 26, compensation: none}`(뒤에 추가). 처음 중분류 36 → 35.
- 끄기(`enabled: false`)가 아니라 지운 까닭: 답이 "두지 않는다(하나로 통일)"이고, 팩 ID는 지움 기록으로 은퇴해 다시 쓰지 못한다. 편집기의 끄기는 세계 안에서 팩 항목을 쉬게 하는 것이라 팩 커밋의 지움과 다르다.
- 그 중분류를 가리키던 DB 아이템 줄은 1절과 같은 곳에서 `subcategory`만 뺀다(팩 id-changes가 지웠고 지금 팩에 없는 중분류, 보관 창고는 대분류 기본). 그 중분류 항목 자체를 고친 줄은 켤 때 `unknown_entry`로 지운다(원래 길). 팩·코드·시험에서 `ammo` 중분류를 가리키는 곳은 없다(Verified, 찾기).

### 1. 기준 가치 → 시작 시세 (`baseValue` → `startPrice`)
- 1절 "아이템 공통 칸"과 경제 ADR 1절의 "기준 가치([임시] 처음 시세와 NPC 값 매기기의 출발점)"를 바꾼다: 칸 이름은 `startPrice`(시작 시세, 화폐 최소 단위 정수 ≥ 1)이고 뜻은 "그 세계에서 이 물건 시장이 처음 열릴 때의 첫 가격"뿐이다. 그 뒤 계산은 시장 시세다(D-505 "기준 가치는 없다").
- 바꾼 곳: 팩 스키마(`packages/content` `itemEntrySchema`), 공용 타입(`ItemJson`·`ItemRow`·미리 보기 `value.startPrice`·경제 목록 `CatalogItemView.startPrice`), 서버 편집기(목록·항목·권고 경로 `startPrice`·미리 보기 원가), 경제 시안(`previewStartPrice`, 시안 시장 `startPrice`), 시뮬 목록(`CatalogItem.startPrice`·`PreparedCatalog.startPrice`), 대량 도구(CSV 열 `startPrice`, 여러 개 고치기 `startPricePm`·`scaleStartPrice`), 화면 칸·정렬·요약·미리 보기 문구(ko·en). 유닛 묶음(`roster/catalog.ts`)의 `baseValue` 표는 읽는 곳이 없어 지웠다.
- 옛 이름 읽기: 켤 때 옛 덮어쓰기 줄(core@27까지 저장한 items)의 `baseValue`는 `apps/server/src/contentEdit/legacy.ts`가 `startPrice`로 옮겨 읽는다(같은 값, 둘 다 있으면 `startPrice`, DB 줄은 그대로·서버 기록 `content boot` `upgraded`). 감사 기록의 옛 판 항목(`items.historyEntry`, 다시 담기)도 같은 함수 `upgradeLegacyEntry`로 읽는다. 대량 도구 가져오기는 JSON 칸 `baseValue`와 CSV 열 `baseValue`를 `startPrice`로 읽는다(`ITEM_CSV_ALIASES`, 내보내기는 새 이름만). 옛 내보내기 차이(`pnpm tuning:apply`·`sim --tuning`의 `entries`)는 고쳐 읽지 않는다(스키마 문제, 앞 바뀜과 같은 방침).
- 옛 PWA 기기(새 서버, 옛 화면)는 아이템 편집기 항목 모양 검사(`isItemJson`)가 `baseValue`를 찾아 항목을 담지 못한다. 개발 화면이라 새로 고침(새 판)으로 푼다. 여러 개 고치기의 옛 칸 `baseValuePm`은 입력 검사에서 400이다.
- 편집기 값 구역: 시작 시세 칸 옆에 "지금 세계 시세"(읽기만). 서버 `items.get` 응답 `markets`(도시 시장마다 {도시, 화폐, 마지막 체결가, 사는 값·파는 값})이고, 서버가 물자 거래소를 아직 돌리지 않아(경제 ADR "결과", `economy.marketItems`도 `not_ready`) 지금은 늘 빈 목록 → "시세 없음 — 서버 거래소가 아직 열리지 않았습니다". 시안 시장(가짜 거래)은 쓰지 않는다(시험 자료를 시세로 보이지 않게). 서버가 거래소를 열면(R5·L1) 그 시장 표에서 이 칸을 채운다.
- 권고 `advice_value_below_cost`·`advice_value_above_cost`는 그대로(시작 시세 ↔ 입력 시작 시세 합으로 셈한 레시피 원가, 문구만 바꿈).

### 3. 보류: 철광석의 1g·티어 3 (사용자 선택 대기, D-487)
- `iron_ore`에는 중분류 광석만 얹었다. 티어 1 → 3과 무게 1g은 넣지 않았다: 켜진 시뮬 경제(econ16)가 쓰는 물건이라 둘 다 시뮬 규칙 출력·정수 시세를 바꾼다.
  - 1g 단위: 지금 철광석 1개 = 시작 시세 8, 레시피 캐기 10개·제련 10개 → 철 주괴 7개(옛 시드 1개 = 1,000g). 1개를 1g로 하면 1g당 0.008 최소 단위라 정수 값이 안 된다(물자 호가창 값 = 1개당 최소 단위 정수, 경제 ADR 4절). 가장 작은 값 1이면 1kg에 1,000(지금의 125배).
  - 티어 3: 레시피 티어 = 산출 최고 티어라 `mine_iron_ore`가 T3이 되고, econ16 광산(Lv1, 최고 T1)이 시작할 때 멈춘다("facility level too low"). 광산을 Lv2로 올리면 오염(레벨 × 6)이 두 배라 정원사·경제 출력이 바뀐다.
- 고를 안(작업 기록 "사용자 결정 대기"): 가. 시장·레시피는 1kg 묶음(로트)으로 사고팔고 보유는 g로 센다, 나. 화폐 최소 단위를 1/1000로 낮춰 모든 값 × 1000, 다. 보유 물건이 생길 때까지 철광석 1개 = 1kg(무게 1,000)으로 두고 g 셈은 그때. 티어는 econ16 광산 Lv2(출력 바뀜) / 철광석 T1 유지.
