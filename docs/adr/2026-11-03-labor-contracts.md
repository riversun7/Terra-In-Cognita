# 노동 계약: 임금형·임대형(보증금 에스크로, 일시 중지·자동 해고·유예)

- 상태: 제안
- 날짜: 2026-11-03
- 관련: 기획 D-479(분배형 없음, 임금형·임대형 2종)·D-507(옛 규칙 먼저)·49 N48·D-431·D-432·D-097, PLAN 14장, ADR `2026-10-31-economy-core.md`(원장·에스크로 계정)·`2026-10-31-s3-server-stage.md`(정산 단위 = 소유 주체, 쓰기 대기열, U2 커밋 뒤 답)·`2026-10-31-faction-society-core.md`(임금 식 N27·N28), 작업 기록 `docs/worklog/2026/11/03-1400-labor-contracts.md`

## 배경
- D-479: 생산 노동 계약은 임금형·임대형 둘이다. 임금형은 고용주(시설 주인)가 임금을 주고, 임대형은 자원이 필요한 쪽이 시설을 빌려 채취해 가며 오너는 시간당 고정 임대료(오너가 정함)를 바로 받는다. 사용자 원칙 "너무 복잡하지 않게, 꼬이지 않고 오류 없게".
- 49 N48은 옛 규칙을 출발값으로 적었다. D-507 "옛 규칙 먼저"에 따라 옛 코드(AntiGravt01, 얕은 복제 `FETCH_HEAD`)에서 다시 확인했다.
- 지금 코드(Verified, main 378852d): sim에 임금 식(`society/labor.ts` `wage`)은 있지만 아무도 임금을 내지 않는다(시뮬 휴먼 만족도의 임금 요소 = 0, 세력·사회 ADR "미룬 것: 급여 지급"). 서버에는 소유 주체·유닛·건물(주인 칸은 있지만 늘 null)·원장(시험 화폐)·소유 주체 정산(시험 직무 산출)이 있다.

## 선택지
| 무엇 | 선택지 | 고른 것 |
|---|---|---|
| 보증금·예산 | 1. 건물 임금 금고(옛 WAGE) / 2. 계약마다 보증금 에스크로(옛 salary_engine) / 3. 둘 다 | 2: 보증금이 그 계약의 고용주 예산이다(돈 길이 하나) |
| 모자랄 때 | 1. 자동 해고만 / 2. 일시 중지만 / 3. 둘을 나눔 | 3(해석, 아래 "확인 대기"): 보증금 0 = 자동 해고, 0 < 보증금 < 임금 = 일시 중지 |
| 지급 시각 | 1. 주기 끝(후불) / 2. 주기 시작(선불) | 2: 일한 주기는 모두 이미 낸 주기다(일시 중지 때 "일했는데 못 받음"이 없다) |
| 에스크로 | 1. 주체 계정 안 묶인 몫 / 2. 계약마다 시스템 계정 | 2(R2 ADR과 같은 까닭): `escrow:labor:<계약 ID>` |
| 산출 몫 | 1. 정산할 때의 상태로 / 2. 계약 상태 구간으로 나눔 | 2: 나눠 정산해도 같다(R2·S3 성질 유지) |
| 프로토콜 | 1. 판 올림 / 2. 같은 날 판 6에 더하기만 | 2: 올리면 원칙(현재 + 직전 1)상 5판 연결을 끊는다 |

## 결정
### 1. 규칙 한 벌(`packages/sim/src/economy/laborContract.ts`, 서버·시뮬 공용, 정수·BigInt)
- 계약 = {종류 wage | lease, 시설 주인 주체, 유닛 소유 주체, 유닛, 시설, 화폐, 단가(임금형 = 주기당 임금, 임대형 = 시간당 임대료), 보증금, 시작, 기간 끝(선택), 정산 시각, 다음 지급, 상태, 유예 끝, 끝난 시각·사유, 낸 합}.
- 상태: `active` 일함 → `paused` 일시 중지(임금형) → `grace` 해지 뒤 유예(임대형) → `ended`. 사유: owner·worker(손 해지), deposit_used_up(자동 해고), rent_unpaid, expired, unit_gone·building_gone.
- 임금형
  - 맺기: 고용주 지갑 → 에스크로 보증금 = 주기당 임금 × ⌈N48 날수 × 하루 ÷ 임금 주기⌉(출발값 30일·하루 주기 → × 30). 모자라면 맺지 않는다. 첫 주기 임금을 바로 낸다(선불).
  - 지급 시각마다: 보증금 ≥ 임금 → 에스크로 → 일꾼 지갑, 보증금 = 0 → 자동 해고, 그 밖 → 일시 중지(그 주기 산출 없음). 경고 = 남은 보증금 < 임금 × ⌈경고 날수 × 하루 ÷ 주기⌉(7일).
  - 채우기(고용주): 고용주 지갑 → 에스크로. 일시 중지였고 이제 한 번 임금이 되면 바로 내고 그 시각부터 새 주기.
  - 해지·만료·사라짐: 남은 보증금을 고용주에게 돌려준다(옛 자동 해고는 남은 몫을 지웠지만 원장은 돈을 없애지 않는다 → 돌려줌).
- 임대형
  - 맺기: 첫 시간 임대료를 낼 수 있어야 한다. 매시간 먼저 임차인(유닛 소유 주체) 지갑 → 오너 지갑(에스크로 없음, "오너는 화폐로 바로").
  - 못 내거나 기간 끝 → 해지 + 유예(N48 7일) → 유예 끝 = ended. 유예 동안 유닛은 계약에 묶이지 않는다. 유예의 뜻(옛 독점형) = 시설 창고에 남은 임차인 물건을 가져갈 기간 → **시설 창고가 아직 없어 지금은 상태만 있다**.
  - 오너가 임대료를 바꾸면 다음 시간부터. 손 해지는 유예 없이 끝(유예는 미납·만료만, N48).
- 원장: 거래 종류 `labor_deposit`(지갑 → 에스크로)·`labor_wage`(에스크로 → 일꾼)·`labor_refund`(에스크로 → 고용주)·`labor_rent`(임차인 → 오너). 지급 시각마다 거래 하나, 중복 방지 키 `labor:<계약>:<시각>`·`labor_refund:<계약>`. 시스템 계정 규칙(`simulator/economyRun.ts` `systemRule`): 에스크로 앞머리에 세 종류를 더했다 → 돈은 만들거나 없어지지 않는다(I1).
- 불변 조건 I14(`checkLaborEscrow`): 열린 임금형 계약의 에스크로 = 보증금, 끝났거나 유예·임대형이면 0. 서버는 같은 문구로 DB를 본다(+ 계약 없는 비지 않은 에스크로).
- 정산은 (정산 시각, toMs]의 지급·만료·유예 끝을 시각 차례대로 돌고(같은 시각이면 만료 먼저), 그동안 유닛이 한 일을 구간으로 돌려준다: work(계약대로), idle(일시 중지 = 산출 없음), free(유예·끝 = 계약 없는 유닛과 같음). 나눠 정산해도 같다(시험이 50일을 한 번·잘게 나눠 견준다).

### 2. 산출 나누기(`settle/owner.ts` `outputs`)
- 소유 주체 정산에 유닛마다 산출 구간(끝 시각, 창고 계정 | null)을 넘길 수 있게 했다. 직무 상태는 구간으로 나눠도 같고(settle.ts 성질), 산출 거래는 하나(매장량 → 기본 창고 + 계약 몫 창고). 구간이 없으면 예전과 같은 두 항목 거래다(시뮬 출력 그대로).
- 서버: work = 임금형이면 고용주 창고, 임대형이면 임차인(= 유닛 소유 주체) 창고. idle = 산출 없음(`discarded`로 셈). [임시] 산출은 S3 시험 광석이다.

### 3. 서버(`apps/server/src/labor/`)
- 표(`db/laborSchema.ts`, schema.ts가 다시 내보냄, 마이그레이션 `20261103043050_labor_contracts`, 새 표만이라 직전 판 앱은 모른 채 돈다): `labor_contracts`(계약, 끝난 줄은 기록으로 남김, 서버는 끝난 지 7일 안의 줄만 읽음), `labor_rents`(시설마다 시간당 임대료, 0 = 빌려주지 않음). 유닛·건물·주체에 외래 키 없음(유닛은 NPC 런타임이, 건물은 관리자가 지운다 → 정산 때 "사라짐"으로 끝냄). 쓰기는 월드 쓰기 대기열(원장 거래와 같은 커밋).
- 정산: 소유 주체 정산(`world/settlement.ts`)이 고리(`routeOutputs`)로 그 주체가 유닛 소유 주체인 계약을 같은 시각까지 정산하고 산출 구간을 받는다 → 계약 거래와 직무 산출이 같은 동기 처리 = 같은 커밋. 유닛 주인이 바뀌거나 유닛·시설이 사라지면 마지막 정산 시각에 끝낸다(남은 보증금 돌려줌).
- 명령(WebSocket, `labor/gateway.ts`): 바꾸기 전에 일하는 쪽 주체를 지금까지 정산하고(상호작용 전 정산), 커밋 뒤에 답한다(U2). 순간 10번·분당 30번.
  - 임금형 맺기 = 내 시설 + 내 유닛(옛 salary_engine처럼 내 유닛 고용), 고용주 조정 ‰가 N28 범위 안. 임금 = `wage(효율, N27 단가, 조정)` → 주기당. [임시] 효율 = 새 유닛 평균 1차 스탯 하나(유닛 스탯이 서버에 아직 없다, ⌊N9 초기 합 ÷ 6⌋ = 10 → 하루 20).
  - 임대형 맺기 = 남의 시설(임대료가 걸린) + 내 유닛. 내 시설은 빌리지 않는다.
  - 한 유닛에 열린 계약은 하나(unit_busy). 해지는 시설 주인·유닛 소유 주체 누구나. 채우기는 고용주만. 임대료는 시설 주인만.
- 시험 건물(관리자 `place_building`)은 놓은 사람의 소유 주체 것이 된다(전에는 늘 null) — 시설 주인이 있어야 계약이 된다.
- 조회 tRPC `labor.overview`: 내 계약(시설 주인·유닛 소유 주체로), 내 시설(임대료)·빌릴 수 있는 남의 시설, 내 유닛(열린 계약 여부), N48 규칙·임금 식 값, 내 잔고. 세계가 없으면 not_ready.
- [임시] 화폐 = 서버 시험 화폐(`s3_test_credit`). 임금을 받는 곳 = 유닛 소유 주체 지갑(서버에 휴먼 지갑 D-097이 아직 없다 — 내 유닛을 고용하면 돈이 내게 돌아온다).

### 4. 프로토콜(같은 날 판 6에 더하기만)

### 7. 시뮬레이터
- NPC 일꾼은 지금 임금을 받지 않는다(더 단순한 임금 모델도 없음: 시설 일꾼은 세력이 가진 머릿수, 휴먼 지갑 지출 D-148은 R4 미룸). 그래서 "단순 모델을 계약으로 옮기기"의 대상이 없다 → 시나리오에 계약을 넣지 않았다. 넣으면 돈이 국고에서 휴먼 지갑으로 가서 쓰이지 않고 쌓인다(경제 판단이 바뀌는 기획 결정, D-487) — 휴먼 지출을 넣을 때 함께 본다.
- 시뮬 출력: 그대로(`SIM_VERSION` 10 그대로). 작업 기록에 econ16 시드 1 앞뒤를 적었다.

## 이유
- 돈 길 하나: 보증금이 곧 예산이면 "예산 금고 + 보증금"의 두 잔고가 어긋날 일이 없다(사용자 원칙 "꼬이지 않고 오류 없게"). 에스크로 = 보증금 하나로 불변 조건을 본다.
- 선불: 일시 중지가 주기 경계에서만 생기므로 "일한 주기 = 낸 주기"가 늘 맞는다. 옛 salary_engine의 30일 = 30번 지급과 같은 결과다(맺기 0일부터 29일까지 30번, 30일에 자동 해고).
- 구간 산출: 계약 상태가 정산 사이에서 바뀌어도(일시 중지·유예) 접속·오프라인 정산을 어떻게 나눠도 같은 산출이다(S3 "로그아웃으로 이득을 볼 수 없다").
- 정산 고리: 계약을 따로 도는 타이머로 정산하면 주체 정산과 순서가 갈린다. 일하는 쪽 주체 정산 안에서 돌면 같은 커밋·같은 시각이다.

## 결과
- 좋은 점: D-479 두 종류가 서버에서 돈다(원장·불변 조건·복구). NPC가 계약을 쓰게 되면 같은 함수를 부른다.
- 감수할 점
  - 같은 정산 구간 안에서는 계약 거래(임대료)가 유지비보다 먼저다(경계 시각 사이 끼우기가 아님). 지갑이 바닥일 때만 차이가 난다(Assumed: 실제 영향 작음).
  - 남의 유닛을 임금형으로 고용하는 흐름(모집 조건·수락)이 없다 — 기획 UX가 없다(아래).
  - 임대형 유예는 시설 창고가 없어 보이기만 한다.
- 확인 대기(사용자, D-487 — 공식·규칙 해석)
  1. 모자랄 때: "보증금 0 = 자동 해고, 한 번 임금에 모자라게 남으면 일시 중지(채우면 바로 다시)"로 두 옛 규칙을 나눴다. 맞는가?
  2. 자동 해고 때 남은 몫(1번 임금보다 적은 돈): 옛 코드는 지웠다. 지금은 고용주에게 돌려준다.
  3. 선불(주기 시작에 냄), 중간 해지 때 이미 낸 주기·시간은 돌려주지 않음.
  4. 임대형 손 해지는 유예 없음, 유예 = 남은 물건을 가져갈 기간(옛 독점형).
  5. 임금을 받는 곳: 휴먼 지갑이 생길 때까지 유닛 소유 주체 지갑.
- UX 빈칸(기획 60_UX에 없음): 남의 유닛 고용(구인 게시·수락), 시설에 이름·종류가 없어 번호로 보임, 계약 화면의 자리(지금 경제 → 생산 칸 아래), 경고 알림(처리할 일 inbox 종류로 넣을지).
- 다시 볼 조건: 서버가 생산·시설 창고를 열 때(산출 = 진짜 레시피, 유예 물건 옮기기), 휴먼 지갑(D-097)·유닛 스탯·직무 가중치가 서버에 올 때(임금 = 진짜 효율), NPC가 계약을 쓸 때(시뮬 시나리오), 사용자가 확인 대기 1~5에 답할 때.
