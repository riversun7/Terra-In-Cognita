# 플레이어 위키: 기획서를 쉬운 말로 푸는 docs/wiki/ (항목 1개 = 파일 1개, 분류는 기획서 장을 그대로)

- 상태: 확정 (2026-11-09, 사용자 결정 — 아래 "사용자 답" 4개)
- 날짜: 2026-11-09
- 관련: `docs/design/README.md`(미러 규칙), `docs/design/03_Planning_Rules.md` §3 R3·R4·R5·R6·R11, `docs/PROTECTED.md`, ADR `2026-10-28-dev-workflow.md`(검사·훅), ADR `2026-10-29-app-shell.md`(메뉴 항목 ID·주소 표)

## 배경
- 기획서(`docs/design/`)는 제작 순서(Step 1~9)로 묶인 **작업용 문서**다. 소제목 462개마다 결정 ID(D-ID)와 "다음 단계로 넘기는 것"·"기술 세션 전달"이 붙어 있고, 결정 로그는 699개 항목 12,041줄이다 (Verified: 2026-11-09 `grep`·`wc -l`).
- 그래서 "만족도가 뭔가"를 알고 싶은 사람이 읽을 문서가 아니다. 지금 저장소에 플레이어용 도움말·위키·용어집은 하나도 없다 (Verified: `docs/`에서 "위키/도움말/용어집" 검색 0건, `packages/shared/src/routes.ts`에 `/help` 없음).
- 기획서는 **미러라서 이 저장소에서 고칠 수 없다** (`docs/PROTECTED.md`, 기획 규칙 R11 = 기획 결정 D-062). 그러니 고쳐 쓰는 것이 아니라 옆에 새 문서 묶음을 만든다.

## 선택지
1. 마크다운을 저장소에 두고 깃허브에서 읽는다 — 빌드가 없다. 모바일 가독성과 꾸미기는 깃허브에 달린다.
2. 게임 안 도움말 화면(`/help`)에 글을 넣는다 — 글이 앱 묶음에 들어가므로 **문서를 고칠 때마다 앱이 다시 빌드·배포된다**. 사용자 답 1이 반대한 것이다.
3. 서버가 문서 파일을 실행 중에 읽어 화면에 보낸다 — 게임 안에서 끊김 없이 읽는다. 문서가 서버 이미지 안에 있어 배포가 필요하고(볼륨으로 피할 수 있으나 NAS 설정을 바꿔야 한다), 마크다운 렌더러가 새 런타임 의존성이 된다.
4. 별도 위키 사이트(VitePress 등) — 사용자 답 1이 "번거롭다"고 제외했다.

## 결정
**1번으로 시작하고, 입구만 게임에 단다. 3번은 글이 쌓인 뒤 다시 본다.**

### 1. 자리와 빌드
- 위키는 `docs/wiki/`의 마크다운이다. 깃허브에서 바로 읽힌다.
- **문서만 고친 푸시는 이미지 빌드와 배포를 건너뛴다** (Verified: `.github/workflows/ci.yml` `changes` 단계가 `^(docs/|\.claude/|\.agent/)|\.md$`만 바뀌면 `deploy=false`). 사용자 답 1의 "계속 새로 빌드되는 것은 안 좋다"는 추가 작업 없이 지켜진다.
- 게임에서 들어가는 입구(메뉴·설정의 "도움말")는 **P1(핵심 항목 30개)이 쌓인 뒤 한 번만** 붙인다. 지금 붙이면 빈 위키로 보내게 되고 앱 배포가 한 번 돌아야 한다. 입구는 바깥 링크라 글을 고쳐도 앱은 그대로다.

### 2. 정본은 기획서, 위키는 풀이
- 규칙이 서로 다르면 **기획서가 맞다**(기획 규칙 R3·R4). 위키는 쉬운 말 풀이와 링크다.
- 위키를 쓰다 기획서의 모순·공백을 찾으면 위키에서 고치지 않고 `docs/questions/`로 기획 세션에 넘긴다.
- 수치는 쓰지 않거나 `[잠정]`을 붙인다(기획 규칙 R5, 기획 결정 D-515).

### 3. 쪼개는 단위 (사용자 답 2 "기존 기획서를 이용 … 체계적으로")
- **항목 1개 = 파일 1개**: `docs/wiki/pages/<slug>.md`. 파일명은 영문 ASCII(AGENTS.md 4장), 한 번 쓴 `id`는 다시 쓰지 않는다(콘텐츠 팩 ID 규칙과 같은 정신).
- **분류를 손으로 적지 않는다.** 항목의 `source`(기획서 경로)에서 뽑는다. 첫 출처의 기획서 장이 그 항목의 정본 장이고, 나머지는 관련 장이다. 그래서 위키의 분류 체계 = 기획서의 장 체계이고, 둘이 어긋날 수 없다.
- 색인·분류 지도·용어 대조표는 **자동 생성**한다(`pnpm wiki:index`). 손으로 고치지 않는다. 선례: `pnpm docs:index`(`docs/WORKLOG.md`), `pnpm settings:cells`.

### 4. 항목 하나의 모양 — 3단 깊이
머리 칸(front matter) + 고정 제목이다. 자세한 규격은 `docs/wiki/README.md`.

| 층 | 제목 | 누구에게 | 나중에 쓰일 곳 |
|---|---|---|---|
| 1 | `> **한 줄**:` | 사전처럼 찾는 사람 | 게임 안 툴팁·색인 |
| 2 | `## 쉽게 말하면` | 초보자 | 게임 안 도움말 화면 |
| 3 | `## 자세한 규칙` | 숙련자 | 기획서로 가는 링크 |

이렇게 나누면 나중에 게임 안 도움말을 만들 때 글을 다시 쓰지 않는다.

### 5. 상태 두 축 (사용자 답 3)
섞으면 "기능이 없는 것"과 "글이 모자란 것"을 가를 수 없어 따로 둔다.

| 칸 | 값 | 뜻 |
|---|---|---|
| `status` | `live` / `building` / `planned` | 기능: 지금 되는 것 / 만드는 중 / 기획만 있는 것 |
| `stage` | `stub` / `draft` / `done` | 글: 뼈대 / 초안 / 정리됨 |

`status`는 플레이어에게 거짓말을 하지 않기 위한 것이다. 항목 머리에 배지로 보인다.

### 6. 언어 (사용자 답 4)
본문은 한국어다. 머리 칸에 `titleEn`(영어 이름)을 적어 두고, 자동 생성되는 용어 대조표(`terms.md`)가 한국어·영어·다른 이름을 모은다. 영어 본문은 게임 안 도움말로 옮길 때 번역한다. 용어 대조표는 나중에 루트 `GLOSSARY.md`의 바탕이 된다.

### 7. 검사 (`pnpm check:wiki`, `pnpm wiki:index --check`)
손으로는 못 지키는 것만 기계가 본다. 둘 다 `lefthook` 푸시 전에 돈다(`check:docs`와 같은 자리. `pnpm check`에는 넣지 않는다 — 문서 검사는 푸시 전에 모아서 돈다는 기존 선례).
- 머리 칸 필수 칸·값, `id` = 파일명·중복 없음, `checked` 날짜 모양
- 본문 필수 제목(`한 줄`·`쉽게 말하면`·`출처`)
- 항목끼리의 링크와 기획서 링크가 **실제로 있는 파일**인가
- `decisions`의 D-ID가 `02_Decision_Log.md`에 정말 있는가 (없는 D-ID를 지어내는 것을 막는다)
- `source`에 적은 기획서 절 제목이 그 파일에 정말 있는가
- 색인·분류·용어 파일이 최신인가
- `--stale`: 인용한 결정에 "대체" 표시가 있는 항목을 알린다(실패는 아님. 미러를 새로 복사한 뒤 다시 볼 항목 찾기)

**앵커(`#...`)는 쓰지 않는다.** 깃허브가 한국어 제목에서 만드는 앵커 규칙을 이 환경에서 확인할 수 없어(Unknown), 링크는 파일까지만 걸고 절 번호는 글로 적는다. 그래서 검사가 통과한 링크는 깃허브에서도 깨지지 않는다.

## 이유
- 사용자 답 1의 세 조건(게임에서 들어감 · 깃허브에서 바로 읽힘 · 자주 빌드되지 않음)을 한꺼번에 만족하는 것은 "저장소의 마크다운 + 바깥 링크 입구"뿐이다. 글을 앱이나 서버 이미지에 넣으면 세 번째 조건이 깨진다 (Verified: CI `changes` 단계).
- 분류를 출처에서 뽑는 것은 사용자 답 2("기존 기획서를 이용 … 체계적으로")를 기계로 강제하는 방법이다. 분류를 따로 적으면 기획서가 바뀔 때 조용히 어긋난다.
- 미러는 통째로 다시 복사되므로(기획서 README 절차) 위키가 조용히 낡는 것이 가장 큰 위험이다. 그래서 항목마다 `decisions`·`checked`를 적고 `--stale`로 다시 볼 항목을 찾는다.

## 결과
- 좋은 점: 문서만 고치는 푸시는 배포가 없다. 기획서와 위키의 분류가 어긋날 수 없다. 깨진 링크와 없는 D-ID를 기계가 잡는다. 3단 깊이라 나중에 게임 안 도움말로 옮길 때 글을 다시 쓰지 않는다.
- 감수할 점: 항목 파일이 많아진다(전면 작업 시 약 150개 예상). 초보자가 지금은 깃허브에서 읽어야 한다. 영어 본문이 없다.
- 다시 볼 조건: ① P1이 끝나 게임 입구를 달 때 ② 글이 쌓여 게임 안 도움말 화면(선택지 3)을 만들 때 — 그때 마크다운 렌더러가 새 런타임 의존성이 되므로 ADR을 새로 쓴다 ③ 미러를 새로 복사해 `--stale` 목록이 길어질 때.
