# NPC 유닛 욕구·2차 지수·5상태: 1차 값(성향·욕구·만족도) → 2차 지수 → 판단, 개인 식사 몫이 만족도에 든다 (SIM_VERSION 69)

- 상태: 확정 (2026-11-21, 사용자 승인 — "A단계 시작")
- 날짜: 2026-11-21
- 관련: `docs/PLAN.md` 4.4장, ADR `2026-11-20-npc-autonomous-ai.md`(3절 유닛 8상태를 이 ADR이 바꾼다), `2026-10-31-economy-core.md` "바뀜 (npc-wage)"(휴먼 지갑·임금·생활비), `2026-10-31-faction-society-core.md`(만족도), 기획 `46_Faction_Society.md` §2.2·§2.4(D-219·D-253·D-433·D-438), D-097·D-431·D-555 1509·D-569 1782

## 배경

사용자 방향(2026-11-21): NPC AI의 1차 목적은 NPC 세력의 자원 채집·세력 확장이다. 유닛은 식사·경제활동·주거 같은 필수요소를 스스로 풀고, 가문장(사이보그·NPC 가문장·비접속 유저)이 가문원의 방향을 정하는 기본 단위다. 필수요소 만족도가 낮은 유닛은 명령을 잘 따르지 않는다. "기존의 것이 복잡하거나 불필요하면 고쳐도 좋다", "1차 스탯 → 2차 스탯처럼 영향을 주는 계층을 나눠도 좋다".

지금 코드에서 확인한 것(Verified: 코드 읽기, `39ed60ba`):

- 휴먼 지갑·임금·생활비는 이미 판정에 있다(`packages/sim/src/simulator/humanPurse.ts`). 하루 끝에 휴먼마다 그날 받은 생필품 몫을 세고(받는 차례 = 일꾼 먼저), 임금에 포만감 효율(N33)을 곱하고, 먹은 값을 지갑에서 낸다.
- 그런데 하루 끝 만족도(`society.ts`)의 포만감 요소는 **도시 평균** 생필품 충족을 모두에게 같이 넣었다. 받지 못한 휴먼과 다 받은 휴먼의 만족도가 같이 움직였다.
- 유닛 8상태 FSM(`unitBrain.ts`)은 2차맵의 보이는 움직임만 정한다(산출은 도시 경제가 센다). 피로 입력은 고정값(일하는 때 300·쉬는 때 650)이고, `consume`·`travel`·`gather`는 성향 점수만으로 고르는 상태였다. 식사·만족도는 입력에 없었다.
- 판단 함수마다 7축을 제각각 공식으로 읽었다(상태 8개 × 축 조합).

## 선택지

1. 새 욕구 값(포만·피로를 "마지막 값 + 시각"으로 저장)을 유닛마다 더한다. — 이미 있는 생필품 받기·피로 셈과 겹치는 두 번째 셈이 생긴다. DB 칸도 는다.
2. **이미 있는 값을 1차 값으로 쓰고, 그 위에 2차 지수 층을 둔다.** 그날 받은 생필품 몫(지갑 셈이 이미 센다)을 휴먼에 적어 만족도와 FSM이 읽는다. 저장은 더하지 않는다.
3. 지금대로 둔다(도시 평균, 8상태). — 필수요소가 유닛별로 드러나지 않아 가문장이 "챙겨 줄" 대상이 없다.

## 결정

선택지 2.

### 1. 층

| 층 | 값 | 어디서 |
|---|---|---|
| 1차(원본) | 7축 성향, 그날 받은 생필품 몫 `fedPm`(‰), 피로(‰), 만족도 | 성향 = `world_units.traits`, 식사 몫 = `SimUnit.fedPm`(하루 끝 `livingDay`), 만족도 = `SimUnit.satisfactionMilli` |
| 2차(지수, 0~1000) | 근로 의욕 `work`, 복종도 `obedience`, 위험 감수 `risk`, 소비 성향 `spend` | `packages/sim/src/npc/unitDrives.ts deriveUnitDrives` |
| 판단 | 유닛 5상태 FSM(다음 단계: 가문장 지시·도시 징발) | 2차 지수 + 욕구 + 상황만 읽는다 |

- 근로 의욕 = 성향 바탕(`discipline` 5 : `greed` 3 : `communalism` 2) × 만족도 배율(만족도 0 → 400‰, 100 → 1000‰) × 식사 배율(몫 0 → 500‰, 가득 → 1000‰). 만족도가 낮으면 덜 일한다(46 §2.4 태업).
- 복종도 = 1000 − 충성도 개입률(`loyaltyOverridePm` — 전투 작전에 쓰던 곡선을 그대로 쓴다. 만족도 = 충성도 D-253). 이번 단계는 지수만 내고, 지시 불복에 쓰는 것은 가문장 지시 단계다.
- 위험 감수 = `boldness` 6 : `belligerence` 2 : `autonomy` 2. 소비 성향 = `greed` 4 : `openness` 3 : `communalism` 3.
- 가중치는 [임시] 출발값이고 코드 상수다(`DRIVE_WEIGHTS`). 설정 칸은 `/dev/npc-ai` 정리 단계에서 연다.

### 2. 유닛 FSM 8상태 → 5상태

- 상태: 일 `work` · 욕구 해결 `need` · 휴식 `rest` · 순찰 `patrol` · 회피 `evade`.
- 일의 종류는 상태가 아니라 **일감**(`job`)이다: 운반 일정 `haul` → 배정된 일터 `post` → 일터 없는 시민의 둘레 채집 `forage`. 일감은 받은 배정이 정한다(다음 단계에서 가문장 지시·도시 징발이 여기로 든다).
- 옛 `work`·`gather`·`haul` → `work`(일감), `consume` → `need`, `travel` → 없앰(지도자 순회는 `leaderRoam.ts`가 집 자리를 옮긴다).
- 욕구 해결 점수 = 배고픔(1000 − 식사 몫) × 0.7 + 시장이 있으면 여가(소비 성향). 그날 몫을 못 받은 유닛은 일터 대신 시장·집으로 간다.
- 휴식 점수에 (1000 − 근로 의욕) ÷ 8을 더한다. 같은 피로에서 만족도가 낮은 유닛이 먼저 쉰다.
- 최소 체류·히스테리시스·기회당 1회 판단·탐색 온도는 그대로다(ADR `2026-11-20` 3절).

### 3. 개인 식사 몫 → 만족도 (판정 바뀜, SIM_VERSION 69)

- `livingDay`가 휴먼마다 `fedPm` = 그날 받은 경계 몫 ‰을 적는다. 받을 것이 없던 날·임금을 끈 판은 비운다.
- 하루 끝 만족도의 포만감 요소 = `unit.fedPm ?? 도시 평균`. 경제가 없는 시나리오는 옛 판과 같다.
- 저장하지 않는다. 서버를 다시 켜면 다음 하루 끝까지 도시 평균을 본다.

### 4. 서버 2차맵

- `BotHome`에 `fedPm`·`satisfactionMilli`(점 단위로 내림)를 넣는다(`aiBridge.ts needsOf` → `humanPlaces.ts`).
- 피로 입력 = 어림 피로 `shiftFatiguePm`: 일하는 때 동안 0 → 600‰로 오르고 쉬는 때 동안 0으로 내린다(피로 바퀴가 있으면 그 바퀴, 없으면 지역 낮·밤). 보이는 움직임용이다 — 판정의 피로·산출은 도시 경제의 쉼터 셈 그대로다.

## 이유

- 생필품 받기·지갑·임금은 이미 유닛별로 세고 있었다(Verified: `humanPurse.ts`). 그 값을 만족도에 잇는 것이 새 욕구 값을 만드는 것보다 작고, 판정이 두 벌이 되지 않는다.
- 만족도 목표값은 포만감에 선형이라 도시 평균 목표는 그대로다(Verified: `labor.ts satisfactionTarget`). 바뀌는 것은 분포다 — 못 받은 휴먼만 떨어진다.
- 전·후 비교(Verified: 실행, `econ16` 60일, 판 68 대 69):

| 시드 | 평균 만족도 | 반란(이김·진압·달램) | 굶어 멈춤 | 구인 | 불변 조건 위반 |
|---|---|---|---|---|---|
| 1 | 54 → 53 | 382·0·85 → 376·12·83 | 0 → 1 | 1,928 → 1,916 | 0 → 0 |
| 2 | 49 → 51 | 468·0·114 → 465·13·109 | 2 → 3 | 2,406 → 2,227 | 0 → 0 |
| 3 | 56 → 56 | 392·0·85 → 412·7·90 | 0 → 2 | 1,947 → 1,863 | 0 → 0 |

- 진압되는 반란이 새로 생긴다(0 → 7~13). 못 받은 휴먼만 반란 문턱 아래로 가서 반란군이 작아지기 때문으로 본다(Assumed: 줄을 따라가 확인하지 않았다).

## 결과

- 좋은 점: 필수요소가 유닛별로 드러난다(누가 못 먹었는지 → 그 유닛 만족도·근로 의욕·복종도). 다음 단계의 가문장 돌봄이 볼 값이 생겼다. 판단이 읽는 값이 지수 넷으로 줄었다.
- 감수할 점:
  - 굶어 멈춤(세력 국고 0 + 식량 부족이 이어짐)이 시드마다 1~2 늘었다(위 표). 판 68에서도 시드 2는 0이 아니었다. 가문장 돌봄·도시 징발 단계에서 다시 잰다.
  - 욕구 해결 상태는 아직 가서 서 있는 모습뿐이다. 도착해서 실제로 사 먹는 셈(가문 창고·지갑 구매)은 가문 창고 단계에서 붙인다. 그날 몫은 하루 끝에만 바뀌므로, 못 받은 유닛은 다음 하루 끝까지 욕구 상태에 머문다.
  - 받는 차례가 유닛 ID 차례라 모자란 도시에서는 늘 같은 휴먼이 못 받는다(기존 규칙 — "일꾼이 먼저 먹는다").
  - 2차 지수 가중치·어림 피로 꼭대기는 코드 상수다([임시]).
- 다시 볼 조건: 가문장 돌봄 단계 뒤에도 굶어 멈춤이 판 68보다 많으면 받는 차례(돌아가며 받기)나 포만감 요소 가중치를 손본다.
- 기획에 전할 것: 만족도 포만감 요소가 유닛별 값이 된 것(46 §2.2는 "생필품 충족"이라고만 적는다 — 해석 범위 안으로 본다, Assumed).

## 바뀜 (2026-11-21, 가문 일 지시 — 계획 B·C·D의 일손 몫)

사용자 방향(2026-11-21): "가문 판단주기는 너무 길고 상태체크를 돌려서 간단하게 체크하여 부하를 줄이고, 부족한 부분만 재판단", "도시는 도시 내 아예 명령 없이 놀고 있는 유닛을 강제로 불러 작업장이나 건설현장에 투여하고 임금을 준다".

확인한 것(Verified: 코드 읽기): 시뮬에는 가문이 없다(가문 = 서버 `npc/cityHouses.ts`의 소속 표, 판정에 쓰지 않음). 시설 일꾼 **수**는 도시가 정하고(`assignCityWorkers`), 일꾼 **신원**은 유닛 ID 차례였다(`cityWorkerUnits` — 임금·숙박비·물류, `humanPlaces.ts` — 보이는 일터). 돈 계정은 지배 가문 금고 하나뿐이다(`rulingVault.ts`). `houseAi.tick`은 부르는 곳이 없다.

정한 것:

- **가문 상태 점검**(`packages/sim/src/npc/houseOrders.ts`, 서버 `npc/laborOrders.ts`): 도시마다 5분([임시], 도시마다 시작을 흩음)에 한 번 그 도시 가문의 집계 값(가문원 수·못 먹은 수·평균 식사 몫·평균 만족도·불복 문턱 아래 수)을 세고 깃발(`food_short`·`morale_low`·`unruly`)을 세운다. 날·가문원 수·깃발·가문 없는 휴먼 수가 지난 점검과 같으면 다시 짜지 않는다.
- **일꾼 차례**: 가문마다 따르는 가문원을 근로 의욕 차례로 내고(가문끼리 한 사람씩 돌아가며), 가문 없는 휴먼은 도시가 그 뒤에 부른다(징발). 사기 낮음 깃발이 선 가문은 못 먹은 가문원을 뒤로 돌린다. 결과는 거울 세계 휴먼의 `laborRank`에 적고 `cityWorkerUnits`·`humanPlaces`가 읽는다(예전: 유닛 ID 차례).
- **불복**: 복종도 < 600‰([임시])인 가문원은 하루에 한 번 굴려(확률 = 600 − 복종도 ‰) 지시를 따르지 않는다(`onStrike`). 불복한 휴먼은 일꾼으로 세지 않고(도시 경제의 쓸 수 있는 일손 = 휴먼 − 경비대 − 불복) 도시도 부르지 않는다. 바뀐 도시만 일꾼 수를 다시 센다(`refreshCity`).
- 스위치는 `npc_ai_house_enabled`(끄면 적은 값을 지우고 옛 차례). 시뮬은 가문이 없어 값을 적지 않는다 — 시뮬 출력 그대로(`SIM_VERSION` 그대로 69). **서버만의 판정 고리**다(지배 가문 금고와 같은 꼴).
- 저장하지 않는다(켜면 첫 점검에 다시 짠다).

아직 안 한 것(사용자 결정이 필요):

- 돈이 드는 돌봄(가문 금고·배급)과 징발 임금의 **효과**. 지금 NPC 휴먼은 지갑이 비어도 주인이 현물로 부양하고(D-097, 질문 2292), 만족도의 임금 요소는 0이다(`society.ts` — `wage: 0`). 그래서 임금·배당을 줘도 유닛의 만족도·복종도가 바뀌지 않는다. 임금 요소를 잇는지(D-433 "임금, 상위 평균과의 임금 격차"), 가문 금고를 무엇으로 채우는지(가문원 임금의 가문세 — 플레이어 가문과 같은 꼴)를 정해야 한다.
- 건설 현장: 일 없는 휴먼은 지금도 짓는 시간을 줄인다(`npcBuild.ts withBuilders`). 임금은 주지 않는다 — 위 결정과 함께.
- 옛 가문 행동 점수(`houseBrain.ts decideHouseAction`·`npcHouseAi.ts`)는 그대로 두었다(부르는 곳 없음). 금고 처방이 정해지면 깃발 → 처방으로 바꾸며 없앤다.

## 바뀜 (2026-11-21, 임금·가문 금고 — 사용자 승인 "추천대로 진행", SIM_VERSION 70)

위 "아직 안 한 것"의 결정: 임금·배당이 만족도에 들게 하고, 모든 NPC 가문에 금고를 두어 가문세로 채운다.

### 1. 임금 → 만족도 (시뮬 판정, 판 70)
- `livingDay`가 휴먼마다 그날 받은 임금 `SimUnit.paidToday`를 적는다(일꾼·건설 도우미, 못 받으면 0, 경비대·임금 끈 판은 비움).
- 하루 끝 만족도의 임금 요소(D-433, 식은 그대로 `satisfactionTarget`): 그 도시에서 그날 받은 사람들의 상위 몫(N30 25%) 평균과 견준다. 임금 틀 안인데 못 받은 휴먼은 그 도시에 받은 사람이 있을 때 격차 불이익(`wageGap`, 입력 `unpaid`).
- 경비대·경제 없는 시나리오는 예전처럼 임금 요소가 없다.

### 2. 건설 도우미 임금 (시뮬 판정, 판 70)
- 그날 짓고 있던 도시(`Economy.today.building` — `buildPolicy`가 판단마다 적는다)의 일 없는 휴먼은 `npc_build_builders_max`명까지(짓는 시간을 줄이는 도우미 수와 같다, 일꾼 차례) 도시 주인 국고에서 일꾼과 같은 임금을 받는다. 국고가 모자라면 못 받는다.
- 사용자 방향 "놀고 있는 유닛을 … 건설현장에 투여하고 임금을 준다"의 몫이다. 작업장 몫은 일꾼 차례(가문 없는 휴먼 징발)가 이미 한다.

### 3. NPC 가문 금고와 돌봄 배당 (서버 고리, `apps/server/src/npc/houseCare.ts`)
- 하루 끝, 임금·생활비 다음·만족도 앞. 도시마다 원장 거래 하나(`npc_house_care`).

### 2. 들기 절차 (2502 다 — 2561)
- 두 길 모두: ① 대표가 초대(`invite`) → 그 가문장이 수락(`join`) ② 가문장이 신청(`join`) → 대표가 승인(`approve`). 받은 초대가 있으면 `join`이 바로 들고, 신청한 가문을 대표가 초대해도 바로 든다.
  거절·거두기 = `decline`(대표: 그 가문의 초대·신청 / 가문장: 자기 것). 표 `house_league_requests`(연맹 × 가문마다 하나, 기한 없음 [임시 — 질문 2641]). 옛 [임시] "가문장이 고르면 바로 든다"를 대신한다.
  `join`은 프로토콜 64부터 있던 행동이라 뜻만 바뀌었다(받은 초대가 없으면 신청 — 결과 `pending: true`).

  나가기 문턱 이상이면 받고 아래면 거절, 그다음 아무 연맹에도 들지 않은 NPC 가문 가운데 가장 가까운 하나를 초대 문턱(`house_npc_league_invite_score` 600)·나가기 문턱 이상이면 초대한다(플레이어 가문은 부르지 않는다 —
