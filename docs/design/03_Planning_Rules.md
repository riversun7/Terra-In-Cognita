# 03. 기획서 작업 규칙 (Planning Rules)

> **GDD v4를 읽거나 고치는 모든 사람과 AI 에이전트는 작업 전에 이 문서를 읽고 따른다.**
> - 이 문서는 진행 규칙의 정본이다. `00_README.md` §3은 이 문서를 가리킨다.
> - 결정 내용의 정본은 `02_Decision_Log.md`다.
> - 이 문서의 규칙은 사용자 승인으로만 바꾼다. 바꾸면 결정 로그에 기록한다 (D-072).
>
> 작성: 2026-10-28

---

## 0. 한눈에 보기: 가장 중요한 10가지

1. **물어보고, 사용자가 확정해야 넘어간다.** 답이 없으면 같은 질문을 다시 낸다.
2. **NPC만으로도 돌아가는 세계 시뮬레이션**이 목적이다 (P0). 모든 제안은 "유저가 0명이어도 작동하는가"에 답한다.
3. **아이디어를 많이, 다양하게 낸다.**
   - 확정된 것도 더 나은 안이 보이면 대체 제안으로 올린다.
   - 단, 사용자가 확정하기 전에는 본문을 바꾸지 않는다.
4. **얽힌 구조를 먼저 본다.** 결정 하나를 바꾸기 전에 §10 결합 지도에서 연결된 결정을 모두 확인한다.
5. **묻기 전에 찾는다.** 먼저 확인할 곳:
   - 기존 기획: `docs/GDD/**`, `docs/Projects/**`
   - 기술 세션: `terra-in-cognita`의 PLAN, ADR, DECISION_LOG
6. **근거를 표기한다.** Verified / Assumed / Unknown을 붙이고, 출처와 날짜를 적는다.
7. **결정 로그가 정본이다.** 지우지 않고 새 D-ID로 대체한다.
8. **한 개념은 한 문서에서만** 정의한다 (SSOT).
9. **쉬운 말로, 구체적으로** 쓴다. 원칙만 쓰지 말고 사례와 측정 방법을 붙인다.
10. **기록과 동기화를 빠뜨리지 않는다.** 순서는 다음과 같다.
    결정 로그 → README → 본문 → 결합 지도 → WORKLOG·changelog → 커밋·푸시 (미러는 기술 세션이 동기화, D-132)

## 1. 이 문서를 쓰는 법

- 기획 작업을 시작할 때 전체를 한 번 읽는다.
- 체크리스트는 그때그때 실제로 대조한다.

  | 시점 | 체크리스트 |
  |---|---|
  | 질문 보내기 전 | §8.1 |
  | 답을 받은 직후 | §8.2 |
  | 기록할 때 | §8.3, §8.4 |
  | 커밋·동기화 전 | §8.5 |

- 문서끼리 충돌하면 이 순서로 따른다.
  1. 사용자의 최신 지시 (결정 로그에 새 D-ID로 기록한다)
  2. 결정 로그 (내용)
  3. 이 문서 (작업 방식)
  4. 본문 문서
  5. 기존 기획 문서
- 이 문서에 없는 상황은 추측하지 말고 사용자에게 묻는다.

## 2. 사용자가 원하는 것 (원문)

> - 사용자가 직접 한 말이다. 원문은 고치지 않는다(오타 포함).
> - 오른쪽 열은 기획자가 작업 규칙으로 옮긴 것이다.
> - 새로 중요한 말이 나오면 여기에 추가한다.

### 2.3 사용자의 기획 성향 (기획자 해석, 정정 가능)

- 자유와 창발을 좋아한다. 정해진 트랙보다 자유형 구조를 고른다 (D-033).
- 시뮬레이션을 중심에 둔다. NPC가 유저와 같은 규칙으로 산다 (D-043, D-044).
- 독점을 싫어하고 역전 가능성을 원한다 (D-034).
- 다양성을 좋아한다: 아이디어, 경로 수, 크리쳐 변종 (D-048, D-071).
- 순환 경제를 중시한다 (D-007).
- 밝고 아기자기한 톤을 원한다 (D-063~D-066).
- 기존 기획과 기술 세션의 작업을 존중한다 (D-055, D-059).
- 복잡한 규칙보다 단순한 해법을 좋아한다. 문제는 생기면 고친다 (D-075).
- 친숙한 소재(국가 모티프, 신화)를 적극적으로 쓴다 (D-075, D-076).
- 익숙한 현실의 제도를 게임에 옮기는 것을 좋아한다. 예: 스포츠 선수 이적 시장 (D-097)
- 기술 부담보다 생생함을 고를 때가 있다. 예: 집계 인구 대신 모두 개별 유닛 (D-098). 이런 선택에는 기술 영향을 한 번 알리고 따른다.
- 추천안을 자주 고르지만, 다르게 답할 때도 많다.
  - 예: 레벨제(D-018), 백분위 등급(D-041), 과장 표현 불허(D-068)
  - 그러니 추천안을 당연한 결론처럼 쓰지 않는다.

## 3. 최상위 원칙 (어기면 안 되는 것)

| # | 원칙 | 내용 | 근거 |
|---|---|---|---|
| R1 | 확정 후 진행 | 사용자가 명시적으로 고르거나 답한 것만 확정이다. 다음은 확정이 아니다: 침묵, 질문 창 닫힘, "채팅에서 답장함", 다른 주제의 메시지 | W3, W4, D-001 |
| R2 | 시뮬레이션 우선 (P0) | 모든 시스템은 유저가 0명일 때도 작동해야 한다. NPC가 그 역할을 하는 방법을 함께 적는다 | G1, D-013, D-044 |
| R3 | 결정 로그가 정본 | 본문과 충돌하면 결정 로그를 따른다. 바꿀 때는 지우지 않고, 새 D-ID에 "D-0XX 대체"라고 적는다. 옛 항목의 요약에는 "→ D-0YY로 대체"를 표시한다 | D-001 |
| R4 | SSOT | 한 개념은 한 문서에서만 정의하고, 다른 문서는 링크만 건다. 요약을 두면 정본 위치를 적고, 정본을 바꿀 때 요약도 함께 고친다 | 기존 진행 규칙 3 |
| R5 | 숫자는 나중에 | 순서는 컨셉 → 루프 → 시스템 규칙 → 수치다. 시스템 규칙보다 먼저 나온 수치는 "예시" 또는 "잠정"으로 표시한다. 세부 수치는 데이터 시트로 분리한다 | 기존 진행 규칙 4 |
| R6 | 근거 표기 | 사실 주장에는 Verified(직접 읽음·실행·공식 문서) / Assumed(추론) / Unknown을 붙인다. 출처와 날짜를 적고, 2년이 넘은 출처는 표시한다. 실행하지 않은 것은 "미실행"이다. 없는 자료·작품·기능을 지어내지 않는다 | 사용자 공통 지침 |
| R7 | 기존 문서 보존 | `docs/GDD/**`, `docs/Projects/**`는 고치지 않는다 (PROTECTED). 기존 아이디어를 가져오면 출처를 적는다. 예: `(출처: 기존 CHR-1 §8.2)` | D-001, 기존 진행 규칙 6 |
| R8 | 재사용 표기 | 설계는 백지에서 한다. 기존 구현과 맞는 부분은 `♻️ 재사용 후보: <파일/시스템>`으로 표기한다 | D-002 |
| R9 | 안티-필러 | "이 게임은 ○○를 하지 않는다"를 기록해 범위를 지킨다. 현재 4개: 무한 발행 없음, 전용 미니게임 없음, 유저 의존 콘텐츠 없음, 실존 종교(교단)·국가·지명·인물을 직접 쓰지 않음(모티브 차용 허용, 신화·전설의 신과 존재는 그대로 사용 가능, 역사 인물은 D-087 범위 안에서 사용) | D-015, D-077, D-087 |
| R10 | 현실성 | 1인 + AI 에이전트가 만들 수 있어야 한다. 모바일 웹이 1순위다. 기술 계약(PLAN·ADR)을 어기지 않는다 | D-003, D-055, D-060 |
| R11 | 미러 직접 수정 금지 | terra-in-cognita의 `docs/design/`은 미러다. 그쪽에서 고치지 않는다 | D-062 |

| ② 조사 | 기존 기획에서 같은 주제를 검색한다(경로·행 번호 기록). 기술 세션의 PLAN·ADR·DECISION_LOG를 확인한다. 도구·법·시장처럼 바뀌는 사실은 웹으로 최신 상태를 확인한다 | 근거 목록 |
| ③ 분석 | §10 결합 지도로 영향 범위를 찾는다. 모순·공백·중복·누락을 찾는다 | 영향 메모 |
| ④ 질문 설계 | §5대로 질문 1~4개와 추가 아이디어를 만든다 | 질문안 |
| ⑤ 질의 | 질문 도구(예: Claude Code의 AskUserQuestion)나 채팅으로 묻는다 | — |
| ⑥ 답 확인 | 모든 질문에 실제 답이 있는지 확인하고, 없으면 다시 묻는다. 자유 답변은 "이렇게 이해했습니다"로 해석을 보여 준다 | 해석 |
| ⑦ 기록 | §9 순서대로 기록한다 | 결정 로그 등 |
| ⑧ 검증 | §8 체크리스트를 대조한다 | — |
| ⑨ 커밋·동기화 | 원본을 커밋·푸시한다. 미러는 기술 세션이 동기화한다 (§9.4, D-132) | 커밋 |
| ⑩ 다음 안내 | 남은 질문과 다음 하위 단계를 알린다. 확정 전에는 다음 단계를 시작하지 않는다 | — |

- 한 번에 다루는 범위는 작게 잡는다. 하위 단계 하나 = 질문 4개 이하 = 커밋 1개.
- 사용자가 중간에 다른 요청을 하면, 그 요청을 처리한 뒤 하던 질문으로 돌아와 다시 묻는다.
- **서브에이전트 분업** (D-132)
  - 질문과 확정은 사용자와의 대화에서만 한다. 서브에이전트는 결정하지 않는다.
  - 사용자가 답하는 동안 다음 질문에 필요한 조사(②: 기존 문서·에셋 확인, 웹 출처 확인)를 서브에이전트로 미리 한다.
  - 답을 받은 뒤의 기록(⑦)은 파일이 겹치지 않게 나눠 맡긴다. 결정 로그(정본)와 이 문서(보호 문서)는 메인 세션이 직접 고친다.
  - 서브에이전트의 결과는 메인 세션이 확인한 뒤 커밋한다. 확인 전의 수치·인용은 Assumed다 (§9.5).
  - 사용량 한도 경고가 나오면 동시에 돌리는 수를 줄인다.

## 5. 질문 만드는 법

### 5.1 형식

- 질문 하나에 결정 하나를 묻는다. 한 번에 최대 4개이고, 크면 나눈다.
- 질문 창만 보고도 이해되게 쓴다.
  - 질문 창이 앞의 설명을 가릴 수 있다.
  - 관련 수치, 결정 ID, 제약을 질문 문장 안에 넣는다.
- 선택지는 2~4개이고, 서로 겹치지 않게 한다. 추천안은 첫째에 두고 "(추천)"을 붙인다.
- 선택지마다 다음을 적는다.
  - 장점, 단점, 위험
  - 영향받는 결정 ID
  - 참고작 (실존 작품, 출시 연도)
- 쉬운 말로 쓴다. 전문 용어와 영어 약어는 풀어 쓴다 (W8).
- 기존 결정과 충돌하는 선택지는 충돌을 밝힌다. 예: "D-0XX와 충돌".
- 근거가 추정이면 "(추정)"을 붙인다.

### 5.2 추천하는 법

- 한 안이 분명히 나으면(대략 8:2 이상) 추천하고 이유를 한 줄로 쓴다. 그래도 기획 결정은 사용자 확정을 받는다.
- 안들이 비슷하면(7:3~6:4) 추천을 표시하되 장단점과 위험을 더 자세히 쓴다.
- 정보가 부족하면 먼저 조사하거나 묻는다. 추측으로 선택지를 만들지 않는다.
- 추천안을 당연한 결론처럼 쓰지 않는다 (§2.3).

### 5.3 답을 받은 뒤

- 자유 답변이 오면 그것이 답이다. 원문을 결정 로그에 그대로 옮기고, 해석은 따로 적는다.
- 답이 추천과 다르면 그대로 따른다. 다시 설득하지 않는다. 위험이 크면 한 번만 알리고 사용자가 고르게 한다.
- 답에 새 아이디어가 들어 있으면 별도 결정으로 기록하고, 영향받는 시스템을 표시한다. 예: D-071
- 사용자가 전제를 지적하면 그 전제를 바로 고치고, 같은 전제를 쓴 곳을 다시 본다 (G8).
- 해석이 둘 이상 가능하면 기록하기 전에 묻는다.

### 5.4 답이 없을 때 (W4)

- 질문 창이 답 없이 닫히거나 "채팅에서 답장함"으로 끝나면, 채팅 메시지가 그 질문의 답인지 본다.
  - 답이면 그 메시지를 답으로 쓴다.
  - 다른 요청이면 그 요청을 처리한 뒤 **같은 질문을 그대로 다시 낸다.**
- 질문 도구가 "다시 묻지 말라"고 안내해도 이 규칙이 우선이다. 사용자의 지시이기 때문이다.
- 답하지 않은 질문을 추천안으로 채우지 않는다.

## 6. 아이디어 제시 규칙 (W1, W5, W12)

### 6.1 무엇을 내나

- 질의할 때마다 **추가 아이디어를 1~3개** 함께 낸다.
- 관례적인 답만 내지 않는다. 아래 중 하나 이상을 넣는다.
  - 다른 장르의 방식
  - 실제 게임 사례
  - 역발상 안
- 좋은 아이디어의 조건
  1. 강화하는 기둥(P0~P5)이 분명하다.
  2. 다른 시스템과 시너지가 있다 (§10 결합 지도).
  3. NPC도 쓸 수 있다 (P0).
  4. 1인 + AI가 만들 수 있다.
  5. 위험과 비용을 함께 적었다.
- 사례
  - D-070 "같은 모델, 다른 조명": P5(거점과 전방의 톤 대비)를 조명만으로 구현해 제작비를 줄인다.
  - D-071 속성 아종: 12속성(D-056), 교배(D-005), 아트 색 체계(D-070)를 한 번에 엮는다.

### 6.2 확정된 것도 고정이 아니다 (W5)

- 확정된 결정도 더 나은 안이 보이면 **"대체 제안"**으로 올린다.
  - 무엇을 왜 바꾸는지, 어떤 결정이 영향을 받는지 함께 적는다.
  - 사용자가 확정하기 전에는 본문과 결정 로그를 바꾸지 않는다.
- 사용자가 "일단 오케이"처럼 잠정 승인한 항목(🟡)은 구체화 단계에서 다시 꺼낸다 (W11).

### 6.3 제안과 결정을 섞지 않는다

- 확정 전 아이디어는 본문에 쓰지 않는다. 질문이나 결정 로그의 "추가 제안 (미확정)"으로만 남긴다.
- 기각된 안도 지우지 않는다. 결정 로그의 "기각한 대안"에 남겨 다시 꺼낼 수 있게 한다.
- 채택한 아이디어를 출시 범위(MVP)에 넣을지는 Step 8에서 따로 정한다.

### 6.4 레퍼런스 쓰는 법

- 실존 작품만, 출시 연도와 함께 쓴다.
- 특정 작품의 핵심 설정이나 반전을 그대로 가져오지 않는다. 너무 비슷하면 경고한다.
  - 예: "오염된 숲이 사실은 세계를 정화하는 장치"라는 설정은 나우시카의 반전과 겹친다. Step 3-4(진실 설정)에서 주의한다.
- 다른 게임 고유의 이름과 디자인을 쓰지 않는다 (D-067).

## 7. 유기적 구조 파악 (영향 분석)

기획서는 서로 얽혀 있다. 결정 하나가 여러 시스템과 기술 계약을 바꾼다.

### 7.1 결정을 새로 하거나 바꿀 때

1. §10 결합 지도에서 해당 축을 찾는다.
2. 결정 로그와 본문에서 관련 D-ID와 핵심 낱말을 검색한다. 예: `grep -n "D-056\|속성" docs/GDD_v4/*.md`
3. 영향 표를 만든다.

   | 바뀌는 것 | 영향받는 결정·문서·기술 계약 | 조치 (지금 고침 / 해당 단계에서 / 사용자에게 질문) |
   |---|---|---|

4. 숫자가 여러 문서에 있으면 모든 곳을 함께 고친다. 예: 경로 27개, 공통 시스템 9개, 속성 12종.
5. 대체된 결정을 아직 인용하는 본문을 찾아 고친다.
6. 결합 지도를 갱신한다.
7. 기술 세션에 넘길 값이 바뀌면 `00_README.md` §3-1의 전달 현황을 갱신한다.

## 9. 기록·동기화 규칙

### 9.1 결정 로그 항목 형식

```markdown
## D-0XX
- **날짜**: YYYY-MM-DD
- **단계**: Step X-Y
- **결정 (사용자 원문)**: "…" (선택지를 골랐으면 선택지 이름)
- **해석**: (자유 답변일 때. 정정 가능)

- **기각한 대안**
- **영향**: (다른 결정, 다른 단계, 기술 전달)
- **미결**: (언제 다룰지)
```

### 9.2 상태 표기

| 표기 | 뜻 |
|---|---|
| ✅ | 확정 |
| 🔄 | 진행 중 |
| ⏳ | 대기 |
| 🟡 | 잠정. 구체화 단계에서 다시 본다 |
| ♻️ | 재사용 후보 |

### 9.3 문서를 만드는 시점

### 9.5 AI 에이전트가 방대한 문서를 다루는 요령

- 요약표(`00_README.md` §4)만 보고 판단하지 않는다. 관련 D-ID의 원문을 연다.
- 긴 문서는 목차(`grep -n '^## '`)로 위치를 찾은 뒤 필요한 부분을 읽는다.
- 서브에이전트가 요약한 수치·인용은 직접 확인하기 전까지 Assumed다.
- 대화가 길어져 앞부분이 요약되면 기억에 의존하지 않는다. 결정 로그와 `docs/WORKLOG.md`로 상태를 다시 맞춘다.
- 결정을 기록하면 바로 커밋한다. 여러 하위 단계를 모아 한꺼번에 기록하지 않는다.
- 진행 상황은 개수로 보고한다. 예: "Step 3: 하위 단계 3개 확정 / 1개 남음". 감으로 정한 퍼센트는 쓰지 않는다.

|---|---|---|
| 10-28 | 질문 창이 답 없이 닫혔는데, 다음 작업으로 넘어가려 했다 | 같은 질문을 다시 낸다 (§5.4) |
| 10-28 | 사냥꾼 지표 초안에 "개체 수가 적은 종을 잡으면 감점"을 넣었다. 사용자는 반대로 희귀종 보너스를 원했다 (D-049) | 사용자 의도와 반대로 작동하는 장치가 없는지 확인한다 |
| 10-28 | 백분위 등급이 신규에게 불리하다는 전제로 설명했다. 사용자가 "보상점수가 활동력에 달렸기에 신규라고 하위가 아니다"라고 바로잡았다 (D-041) | 전제를 검증한다 |

| 10-28 | 작업자 재시작으로 질문 창(Step 4-4 두 번째)이 답 없이 닫혔다. 재시작한 뒤 그 질문이 있었는지 모른 채 다른 조사와 다른 세션 알림을 먼저 처리했다. 사용자가 "답변안했는데 왜 마음대로 하냐? 질문 다시 해라", "이거 다시 질문하라고 뭐 이렇게 오래걸려"라고 했다 | 재시작 뒤에는 먼저 대화 기록에서 마지막 질문 창과 그 결과를 확인한다. 답 없이 닫힌 질문은 다른 일보다 먼저, 조사를 더 하지 않고 같은 내용으로 바로 다시 낸다 (§5.4) |
| 10-28 | 자원 회귀 모델을 물으면서 새 모델(정원의 원소 순환)을 추천했다. 기존 코드에는 이미 총량 자원 4종(`resource_supply_config`)과 관리자 감시 화면이 있었는데 확인하지 않았다. 사용자는 "기존 프로젝트를 참고하라"고 답했다 (D-112) | 시스템을 묻기 전에 기존 문서와 함께 기존 코드(테이블·시드·관리자 화면)도 찾아 본다. 이미 있는 구조를 선택지에 넣는다 |

## 12. 사용자의 공통 작업 지침 (요약)

Claude 세션의 사용자 설정을 기획 작업에 맞게 줄인 것이다. 다른 AI 도구도 따른다.

- **정직**
  - 확인한 사실만 단정한다. 주장마다 Verified / Assumed / Unknown을 붙인다.
  - 없는 기능·자료를 지어내지 않는다.
- **최신성**
  - 도구·라이브러리·법·시장 정보는 웹으로 현재 상태를 확인한다.
  - 출처 날짜를 적고, 2년이 넘은 출처는 표시한다.
- **결정**
  - 한 안이 8:2 이상으로 분명하면 이유를 한 줄로 적고 추천한다.
  - 비슷하면 멈추고 선택지를 낸다.
  - 요구가 모호하면 묻는다.
- **변경 절제**
  - 요청 범위만 바꾼다.
  - 구조 변경, 삭제, 범위 밖 수정은 먼저 묻는다.
  - `docs/PROTECTED.md`의 대상은 승인 없이 고치지 않는다.
- **보고**
  - 진행 보고는 요청받았을 때만 하고, 개수(분자/분모)로 한다.
  - 미검증·임시값·알려진 문제를 숨기지 않는다.
- **협업 기록**: 작업마다 `docs/WORKLOG.md`와 `docs/PROTECTED.md`를 갱신한다.
- **언어**: 사용자에게는 한국어로 답한다. 이름(파일·ID)은 영어, 설명은 한국어로 쓴다.
