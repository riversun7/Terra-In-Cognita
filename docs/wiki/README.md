# 위키 쓰는 규칙

이 폴더는 **기획서를 쉬운 말로 푼 문서**다. 위키백과처럼 찾아 읽고, 초보자 도움말 사전처럼 한 줄로 뜻을 알 수 있게 쓴다.
항목을 쓰거나 고치기 전에 이 문서를 읽는다. 왜 이렇게 정했는지는 ADR `../adr/2026-11-09-player-wiki.md`.

## 0. 가장 중요한 5가지

1. **정본은 기획서다.** 위키와 기획서가 다르면 기획서가 맞다. 위키는 풀이와 링크다.
2. **기획서를 고치지 않는다.** `docs/design/`은 미러다(`../PROTECTED.md`). 모순·공백을 찾으면 위키에서 고치지 말고 `../questions/`에 적어 기획 세션에 넘긴다.
3. **쉬운 말로 쓴다.** 전문 용어와 영어 약어를 풀어 쓴다. 한 문장은 짧게. 스킬 `korean-writing`을 쓴다.
4. **수치는 쓰지 않거나 `[잠정]`을 붙인다.** 세부 수치는 밸런싱으로 언제든 바뀐다(기획 결정 D-515).
5. **거짓말을 하지 않는다.** 아직 없는 기능은 `status`로 밝힌다. 확인하지 않은 것은 쓰지 않는다.

## 1. 파일 자리

| 자리 | 무엇 |
|---|---|
| `pages/<id>.md` | 항목 하나. 개념 하나당 파일 하나 |
| `guides/<id>.md` | 상황별 길잡이("첫 도시 세우기"처럼 여러 항목을 순서대로 엮은 글) |
| `start.md` | 처음 온 사람이 읽을 길잡이 |
| `index.md`·`categories.md`·`terms.md` | **자동 생성.** 직접 고치지 않는다 (`pnpm wiki:index`) |

파일명 = 머리 칸의 `id` = 영문 소문자·숫자·하이픈. 한 번 쓴 `id`는 다시 쓰지 않는다(링크가 남는다).

## 2. 머리 칸 (front matter)

파일 맨 위에 `---` 사이로 적는다. YAML이 아니라 이 저장소 전용 간단한 형식이다.
**목록은 `[ ]` 안에 `;`(세미콜론)으로 나눈다.** 쉼표는 값 안에 들어갈 수 있어 쓰지 않는다.

```
---
id: satisfaction
title: 만족도
titleEn: Satisfaction
aliases: [민심]
status: building
stage: draft
decisions: [D-219; D-253; D-433]
source: [40_Systems/46_Faction_Society.md §2.2 만족도; 40_Systems/48_Stats_Formulas.md §7.4 만족도]
checked: 2026-11-09
---
```

| 칸 | 필수 | 뜻 |
|---|:---:|---|
| `id` | ✅ | 파일명과 같아야 한다 |
| `title` | ✅ | 한국어 이름 |
| `titleEn` | ✅ | 영어 이름. 나중에 번역·용어집의 바탕 |
| `aliases` | | 다른 이름. 색인에서 "민심 → 만족도"로 보인다 |
| `status` | ✅ | `live` 지금 되는 것 / `building` 만드는 중 / `planned` 기획만 있는 것 |
| `stage` | ✅ | `stub` 뼈대 / `draft` 초안 / `done` 정리됨 |
| `decisions` | ✅ | 근거가 되는 기획 결정 ID. `02_Decision_Log.md`에 있어야 한다 |
| `source` | ✅ | 기획서 경로 + `§번호 제목`. `docs/design/` 아래 상대 경로 |
| `checked` | ✅ | 기획서와 맞춰 본 날(`YYYY-MM-DD`) |

- **분류는 적지 않는다.** `source`의 첫 줄에서 뽑는다(그 기획서 장이 이 항목의 정본 장). 그래서 위키 분류 = 기획서 장 체계다.
- `source`의 `§번호 제목`은 그 기획서 파일에 정말 있는 소제목이어야 한다(검사가 본다).

## 3. 본문 — 3단 깊이

제목은 아래 순서로, 이름 그대로 쓴다. `*`가 붙은 것은 없어도 된다.

```markdown
# 만족도

> **한 줄**: 도시에 사는 사람들이 지금 살기 좋다고 느끼는 정도.

**지금**: 만드는 중 — 서버가 하루가 끝날 때 계산한다. 화면에 보이는 자리는 아직 없다.

## 쉽게 말하면
## 어떻게 보고 쓰나      *
## 자세한 규칙            *
## 같이 보기              *
## 출처
```

| 층 | 어떻게 쓰나 |
|---|---|
| `한 줄` | **한 문장.** 사전 뜻처럼. 나중에 게임 안 툴팁에 그대로 쓴다 |
| `지금` | 머리 칸 `status`의 이름(`지금 되는 것`·`만드는 중`·`기획만 있는 것`)으로 시작하고, 한 마디를 붙인다. 검사가 머리 칸과 맞는지 본다 |
| `쉽게 말하면` | 초보자용. 3~6문장. 비유와 예시를 쓰고 숫자는 넣지 않는다 |
| `어떻게 보고 쓰나` | 어느 화면의 무엇을 누르면 보이나. 아직 화면이 없으면 쓰지 않는다 |
| `자세한 규칙` | 숙련자용. 조건·예외. 수치는 `[잠정]` |
| `같이 보기` | 관련 항목 링크 3~6개 |
| `출처` | 기획서 링크와 결정 ID. 머리 칸의 `source`·`decisions`를 사람이 읽을 형태로 |

## 4. 링크

- 항목끼리: `[만족도](satisfaction.md)` — 같은 폴더라 파일명만.
- 기획서로: `[46_Faction_Society.md §2.2](../../design/40_Systems/46_Faction_Society.md)`
- 결정으로: `[D-219](../../design/02_Decision_Log.md)` — 문서가 커서 찾아 들어가야 한다. 번호를 글로 적는다.
- **`#앵커`를 쓰지 않는다.** 깃허브가 한국어 제목에서 만드는 앵커 규칙을 확인할 수 없어(Unknown) 깨질 수 있다. 절 번호는 링크 글에 적는다.
- `[[위키 링크]]` 모양은 깃허브가 그리지 않는다. 쓰지 않는다.

## 5. 쓰는 차례

1. `pnpm wiki:index`로 색인을 보고, 그 개념이 이미 있는지 찾는다. 있으면 그 항목을 고친다(한 개념 = 한 항목).
2. 기획서에서 그 개념의 **정본 자리**를 찾는다(장·절). 결정 ID를 모은다.
3. 항목을 쓴다. 다른 항목에서 이미 설명한 것은 링크만 건다.
4. `pnpm check:wiki`와 `pnpm wiki:index`를 돌린다. 생성된 색인·분류·용어 파일을 함께 커밋한다.
5. 작업 기록(`../worklog/`)에 쓴 항목 수를 적는다.

## 6. 기획서가 바뀌면

미러는 통째로 다시 복사된다(`../design/README.md`). 그러면 위키가 조용히 낡는다.
- 미러를 새로 복사한 뒤 `pnpm check:wiki --stale`을 돌린다. 인용한 결정에 "대체" 표시가 붙은 항목이 나온다.
- 그 항목을 기획서와 맞춰 보고 `checked` 날짜를 새로 적는다.

## 7. 진행 세기

"거의 다 됐다"로 쓰지 않는다. `pnpm wiki:index`가 `categories.md` 아래에 장별 항목 수와 상태·단계 분포를 적는다. 그 숫자로 보고한다.
