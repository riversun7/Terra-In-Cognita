## 한 일
- 프로토콜 2(`packages/protocol`): 2차맵 구독·해제, 관리자 시험 명령(유닛 이동·건물 놓기·치우기), 스냅샷 조각·유닛 경로 묶음·건물 이벤트·요청 결과, 지형 이진 형식(TCTR 1판). `PROTOCOL_VERSION` 2, 최소 지원은 1 그대로.
- 서버 S1 월드(`apps/server/src/world/`, 메모리에만): 시험 2차맵 하나(`cellKey(0, 9, 256, 256)`), 임시 지형 배치 격자, 시험용 봇(`S1_TEST_BOTS`), 도착·쉬기 끝 예약 이벤트(sim 이벤트 큐 + 서버 타이머 하나), 관리자 명령, 건물 놓기 뒤 막힌 경로만 다시 찾기.
- 경로 워커 풀(`node:worker_threads`, `PATH_WORKERS` 기본 1): 워커마다 격자 사본, 편집을 같은 순서로 따라 함, 늦게 온 결과 다시 찾기, 죽으면 다시 띄우기. 개발(tsx)·시험(vitest)은 `src/world/pathWorker.ts`, 빌드는 `dist/pathWorker.js`.
- 전송: 구독 → `result` → 스냅샷 조각(64KiB 아래) → 약 100ms 묶음과 건물 이벤트. 느린 연결은 보내기를 멈추고 나중에 새 스냅샷.
- 권한: 보기는 로그인 사용자, 명령은 권한 표 `secondMap`(admin)만, 명령마다 확인. WebSocket은 Origin이 없거나 앱 출처일 때만 세션 쿠키를 믿는다. 사용자별 속도 제한, 명령 중복 방지(10분). ADR 26 시야 확인 자리 `canViewSecondMap`(모두 통과).
- 지형 파일 `GET /api/maps/<키>/terrain?v=<생성기 버전>`: 로그인 필요, `private, max-age=31536000, immutable`, gzip.
- 1분 지표 한 줄에 S1 값을 붙였다(아래 "지표 이름"). 같이 이벤트 루프 지연 지표의 기존 오류를 고쳤다: Node 히스토그램은 지연이 아니라 타이머 간격을 적어서 쉬어도 약 20ms로 나왔다(Verified) → 측정 간격을 뺀다.
- 측정 클라이언트 `ops/s1-probe.mjs`(새 의존성 없음): 들어가기 → 구독 → 스냅샷·갱신·명령 지연을 잰다. 받은 메시지는 `packages/protocol`로 모두 검사한다.
- 배포: `Dockerfile` 설치 단계에 `packages/sim`·`packages/planet` package.json(엔진 줄과 같은 이유로 명시, 없어도 설치는 된다 — 메인 세션 확인), `ops/compose.yml`에 `S1_TEST_BOTS: "1000"`.
- `SIM_VERSION`: 서버 `config.ts`가 `@terra/sim` 값을 그대로 내보낸다(두 곳에 두던 것을 하나로).
- 문서: ADR 33 "구현하며 정한 것 (서버 연결)", AGENTS 6장(Node 24 서버 확인 사항)·7장(봇·측정 명령), PLAN 4.2(경로탐색 워커 풀 한 줄).

## 정한 것 (ADR 33에 없던 것 — 확정 때 다시 본다)
| 항목 | 정한 값 | 이유 |
|---|---|---|
| 메시지 이름 | 기기 → 서버 `subscribe`·`unsubscribe`·`move_unit`·`place_building`·`remove_building`, 서버 → 기기 `result`·`map_snapshot`·`unit_paths`·`building_placed`·`building_removed` | 기존 `t` 값처럼 소문자, 두 낱말은 밑줄 |
| 요청 번호 | 모든 2차맵 요청에 `id`(u32). 결과는 `result`(같은 id) | ADR 7 "명령: id + 응답 확인 + 중복 방지 키" |
| 중복 방지 | (사용자, 2차맵, id)마다 10분, 2만 개까지. `busy`·`internal_error`는 기억하지 않는다 | 끊긴 뒤 다시 보낸 명령이 두 번 실행되지 않게. 다시 해 볼 수 있는 실패는 다시 하게 |
| 결과 코드 | 23개(`RESULT_CODES`: sign_in_required, forbidden, rate_limited, busy, unknown_map, not_visible, too_many_maps, unknown_unit, unknown_building, superseded, start_blocked, goal_blocked, no_path, budget_exceeded, path_too_complex, out_of_bounds, overlaps_building, overlaps_road, overlaps_unit, blocked_terrain, building_limit, invalid_request, internal_error) | 문장 대신 코드(기기가 번역). 지금 안 쓰는 not_visible도 미리 둔다(프로토콜을 다시 올리지 않게) |
| 위치·속도 범위 | 위치 0 ~ 262,143(배치 칸 1/1024 정수), 꺾이는 점 1~1,024개, 속도 1 ~ 2^20 | 판정 코드 상수와 같은 값(서버 시험이 확인) |
| 스냅샷 조각 | 64KiB 이하, 유닛 먼저 건물 나중, 순서 그대로. 조각마다 같은 머리(`snapshotId`, part, parts, rev, serverTime, 지형 주소·생성기 버전) | 메시지 상한(ADR 7). part 0부터 새로 모으는 규칙 하나로 끝난다 |
| rev 규칙 | 2차맵 변화마다 1씩. `unit_paths`는 (fromRev, rev], 건물 이벤트는 rev 하나 | 묶어도 빠짐을 알아챌 수 있다. 움직임은 통째 바꾸기라 겹쳐도 같다 |
| 묶기 | 2차맵마다, 첫 변화 뒤 100ms. 같은 유닛은 마지막 것만. 48KiB가 넘으면 바로. 한 번 인코딩해 모두에게 | 구독자 수만큼 인코딩하지 않는다 |
| 느린 연결 | 1MiB 넘으면 멈춤 → 64KiB 아래면 새 스냅샷(0.5초마다 확인) | 오래된 갱신을 쌓지 않는다(ADR 7). 연결마다 버퍼는 약 1MiB + 스냅샷 하나로 묶인다 |
| 경로 요청 규칙 | 움직이는 유닛은 멈춰 세우고 결과가 온 시각에 출발. routeSeq로 늦은 결과 버림 | 서버 움직임이 끊기지 않고, 지난 시각을 고치지 않는다. 묶기(100ms) 덕에 정지 움직임은 보통 전송되지 않는다 |
| 격자 버전 | 편집마다 1씩. 막는 편집(놓기)의 버전보다 옛 격자로 푼 결과만 다시 찾는다 | 치우기는 길을 막지 않는다 |
| 건물과 유닛 | 유닛 몸(s×s, 칸 사이면 한 칸 더)이 걸친 칸에는 놓지 않는다 | 갇히는 유닛이 생기지 않게(sim은 유닛 위 배치를 막지 않는다) |
| 탐색 예산 | 봇 32,768칸, 명령·다시 찾기 65,536칸 | 봇은 실패하면 다른 목적지. 명령은 끝까지 |
| 상한 | 건물 1,024개, 연결당 밀린 요청 16·구독 4, 명령 순간 30·초당 10, 구독 순간 10·초당 1 | 스냅샷 크기·메모리·CPU를 묶는다(Assumed 값) |
| 로그인 조회 | 연결마다 15초 기억 | 명령마다 DB를 부르지 않는다. 끊은 세션은 15초 안에 막힌다 |
| WebSocket 쿠키 | Origin이 없거나 `BETTER_AUTH_URL`과 같을 때만 | 다른 사이트가 사용자 쿠키로 연결을 여는 것(CSWSH) 막기. 브라우저는 늘 Origin을 붙인다 |
| 워커 풀 | 대기열은 메인 스레드(명령 먼저), 워커당 2개까지, 대기열 8,192, 1분 10번 넘게 죽으면 멈춤, 힙 128MB | 보내기 직전에 쓸모없는 작업을 버릴 수 있게 |
| 봇 | 크기 90·8·2%, 걷기 85%·차 15%, 유닛별 시드 난수(2차맵 시드 ^ 유닛 ID), 둘레 48칸, 쉼 2~6초, 첫 출발 5초 안 | 화면에서 고르게 움직이고 경로 요청이 벤치마크 가정(30초마다)에 가깝게(약 22개/초) |
| 지형 형식 | TCTR 1판, 머리 32바이트(형식 버전·머리 길이·생성기 버전·시드·크기·해시·키), 높이 i32 cm, 지표 u8 | 서버 값을 그대로(해시로 확인 가능). 머리 길이를 둬서 머리를 늘려도 옛 기기가 읽는다 |
| 지형 주소 | `/api/maps/<10진 키>/terrain?v=<생성기 버전>`, 다른 버전·없는 키·볼 수 없음은 똑같이 404 | 버전이 붙어 불변 → 1년 캐시. 있는지 없는지를 드러내지 않는다 |

- 해석(Assumed): 1,000개 봇은 NAS에서도 워커 하나로 충분할 것이다(계산 시간 합계 = 22개/초 × 0.1~0.3ms). 연결당 약 3KB/초라 4G에서 부담이 작다. 스냅샷 약 125KB는 4G에서 0.1~0.3초 정도(Assumed: 4G 5~10Mbps).
- 이벤트 루프 최대 40~68ms의 원인은 모른다(Unknown). GC(최대 5.8ms)도 CPU 부족도 아니다. p99는 3ms 아래라 S3 기준(p99 < 50ms)에는 여유가 있다. S3에서 CPU 프로파일로 본다.

## 지표 이름 (1분 지표 한 줄, `"metric":"server"`에 붙는다)

## 엔진 연결 메모 (메인 세션이 기기 쪽을 붙일 때)
- 구독: 인사(프로토콜 2) 뒤 `{ t: "subscribe", id, mapKey: S1_TEST_MAP_KEY }`. `result` ok 다음 `map_snapshot` 조각이 온다. part 0부터 모아 parts개가 차면 적용하고 내 rev = 스냅샷 rev. 그 뒤 `unit_paths`·건물 이벤트는 `secondMap.ts` 머리 주석의 rev 규칙대로. 빠지면 subscribe를 다시 보낸다.
- 지형: 스냅샷의 `terrain.url`을 로그인 쿠키와 함께 받아 `decodeTerrain`. 엔진 `TerrainInput`으로: `heights`(i32 cm) → `Int16Array`(값 ÷ 10, 0.1m), `baseHeightM` 0, `waterLevelM` 0(해수면), `surface` 그대로(같은 코드), `cellSizeM` 약 11.72(행성 격자 지형 칸 평균, ADR 34).
- 유닛: `UnitPath`의 `points` = `path` ÷ 1024(배치 칸), `departAtMs` 그대로(서버 시계, pong으로 맞춘 차이), `speedCellsPerSec` = `speed` ÷ 1024. `size`(1·2·3)는 엔진 `UnitLook` 고르기에 쓴다. 서 있는 유닛은 점 하나다.
- 건물: 엔진 `BuildingFootprint`의 `cellX`·`cellY` = `x`·`y`, `width` = `width`, `depth` = `height`, `rotation` = `rotation ÷ 90`(같은 규칙: 홀수면 가로·세로 바꿈, 기준 칸은 왼쪽 위).
- 명령: 고른 유닛을 누른 땅으로 → `move_unit`(목표 = 칸 × 1024 + 512). 결과 코드로 문구를 고른다(ko·en 메시지 키). 명령은 admin 계정만 된다.

## 함께 바꿔야 하는 파일
- 메시지 형식·의미를 바꾸면: `PROTOCOL_VERSION`과 ADR(PROTECTED). 1을 더는 받지 않게 되면 `MIN_SUPPORTED_PROTOCOL_VERSION`과 `session.ts`의 1 연결 거절 규칙.
- 지형 형식을 바꾸면: `TERRAIN_FORMAT_VERSION`과 기기 해석기. 생성기를 바꾸면 `TEMP_TERRAIN_GENERATOR_VERSION`(주소가 바뀐다).
- 판정 상수(`CELL_UNITS`, `PLACEMENT_SIZE`, `MAX_SPEED`, 지표 번호)를 바꾸면: `packages/protocol` 상수(시험 `secondMap.test.ts`가 다르면 실패).
- 권한을 player에게 넓히면(내 유닛 이동 등): `permissions.ts` 표 + 소유 확인(지금은 소유 개념이 없다).
- 워커가 import하는 코드(`pathWorker.ts` → `pathReplica.ts` → `@terra/sim`)는 지울 수 있는 TS 문법만(Node 타입 지우기로 바로 뜬다).

## 건드리지 말 것
- `main.ts`의 워커 주소 고르기: 시작점 파일이라 공용 조각(`dist/assets/`)으로 빠지지 않는다. 다른 모듈로 옮기면 빌드에서 주소가 어긋날 수 있다.
- 묶기 한도(48KiB)와 `MAX_PATH_POINTS`: 가장 큰 유닛 항목(약 14.4KB)이 남은 여유(16KiB)에 들어가야 메시지가 64KiB를 넘지 않는다.
- 워커로 가는 편집은 원본에 적용한 순서 그대로 보낸다(버전이 1씩 이어져야 사본이 맞다).

## 미검증·TODO·알려진 문제
- NAS(R1600)·휴대폰에서 재지 않았다. 배포 뒤 1분 지표와 측정 클라이언트로 다시 잰다(Unknown).
- 게임 앱은 아직 이 프로토콜을 쓰지 않는다(메인 세션이 엔진 시험 화면에 붙인다). 기기가 다시 연결할 때 이어 받기 버퍼는 없다(다시 구독 = 새 스냅샷).
- 저장: 메모리에만 있어 서버를 다시 켜면 봇·건물이 처음부터다. DB 저장·`kill -9` 복구는 S3.
- 시야: `canViewSecondMap`은 모두 통과. 남의 경로를 보이는 구간만 보내기(ADR 7)·탐사 기록 표는 S3.
- 2차맵 생성은 시작할 때 메인 스레드에서 한다(sim 벤치마크로 약 13ms, 서버에서는 재지 않음). PLAN 5.6의 "워커가 생성해 압축 저장"은 행성 생성기(S2) 때.
- 경로 지연 p50 약 75ms는 대부분 묶기(100ms)다. 차(약 4.7칸/초)는 받을 때 약 0.3~0.5칸 앞으로 건너뛴다. 휴대폰에서 거슬리면 묶기를 줄이거나 출발 시각을 앞당긴다.
- 이벤트 루프 최대 40~68ms의 원인은 Unknown(GC 아님). S3에서 CPU 프로파일.
- 도로 놓기 명령은 없다(임시 지형에 도로 없음). 봇은 순서가 같아도 워커 결과 시각이 매번 달라 전체 움직임이 똑같이 되풀이되지는 않는다.
- 관리자 명령의 감사 기록은 남기지 않는다(시험 명령, 메모리 상태). 실제 편집기 명령이 생기면 감사 기록(PLAN 4.8).
- `testViewer`(시험용 AppOptions)는 운영 코드에서 쓰지 않는다.
